# Gate 4 · A-30 执行提示词：把加速器提前装进去，再进 S3

> 目标：补上 A-29 漏掉的唯一一步 —— **加速器在场**，让 `m3dEnsurePresented()` 走通，
> 拿到 `open() RELEASED` + `first present accepted`，完成 S3 接管。
>
> **本关零代码改动、零重编、零 kext 安装。** 全程不重启（除非触发 §7）。
>
> **相对 20:09 那版的关键改动：加速器在进 S3 之前加载**，这样"装不上"时机器还在干净态，
> 不会像 A-29 那样 `open()` 被拒 + 屏幕直接彩噪。依据见 §0.4。

## 0. 为什么是这一步（每一条都有源码或日志）

### 0.1 A-29 的失败原文（`20-ops/A-29/stream.log`）

```
19:54:26.410  XEGFX_DISPLAY: M3d: present: accel not published XeGfxAccelPresent yet (attempt 1)
   ...  attempt 2 / 3 / 4（每 100 ms 一次）
19:54:27.118  M3d: open() denied (present-failed, checks 0x3f lastRc 0xe00002d8, denied=1)
19:54:27.118  M3d open/deny: ... presented=0 fails=8 accel=0 vbl src=0 count=0 ready=0
```

### 0.2 源码：这条失败只有一个入口

```c
// kexts/XeGfxDisplay/src/XeGfxDisplay.cpp  m3dEnsurePresented()
if (fPresented) return true;
if (!m3dGateEnabled() || !m3dApertureReady()) return false;

if (!fAccelObj && !m3dFindAccel(false)) {      /* ← A-29 死在这里 */
    fLastPresentRc = kIOReturnNotReady;        /*   0xe00002d8，与日志 lastRc 完全一致 */
    fPresentFails++;
    XLOG("M3d: present: accel not published XeGfxAccelPresent yet (attempt %u)", ...);
    return false;
}
```

`m3dFindAccel` → `xgAccelScanOnce`：
`serviceMatching("NMXAccel")` **且** `CFBundleIdentifier == "org.watchthelight.XeGfxAccel"`
**且** 属性 `XeGfxAccelPresent == true`。

A-29 里 `accel=0`、`ioreg` 里 `NMXAccel` 与 `XeGfxAccelPresent` 出现次数都是 **0** —— 加速器根本没加载。

### 0.3 同一天的反证（`~/xegfx-log/A-27/`）

A-27 那次 `open()` 是**通过**的，日志里有：

```
M3d: accel service NMXAccel found (XeGfxAccelPresent=true)
M3d: first present accepted (phys 0x2666d000 ggtt 0x80000000 pitch 12544 3120x2080 flip 1); head 4 now scans our buffer
```

**两次唯一的差别就是加速器在不在场。** 不是新机制，是流程漏了一项。

### 0.4 `XeGfxAccelPresent` 什么时候发布（决定本关的顺序）

```c
// kexts/NVRM/accel/nvrm-accel.cpp:522（framebuffer 到达时）
if (newService->metaCast("XeGfxFramebuffer")) {       /* ← 只有 KMS framebuffer 才算 */
    ...
    newService->retain();
    if (OSCompareAndSwapPtr(nullptr, newService, (void *volatile *)&me->fKmsFB)) {
        ...
        nvXePublishPresentAPI(newService, "adapter parked", me);   /* → setProperty("XeGfxAccelPresent", true) */
    }
}
// :787 在 head 4 被 pipe 起来时再发布一次（"head 4 piped"）
```

推论（三条，直接决定步骤）：

1. **干净态下加载 accel：`XeGfxAccelPresent` 不会出现**（那时的 framebuffer 是 `XeGfxIntelFramebuffer`，不是 `XeGfxFramebuffer`）。
   → 所以"加载后必须看到 Present"不能当门槛，**门槛是 `class NMXAccel` 有实例**。
2. accel 是**监听新 framebuffer** 的，S3 的 KMS framebuffer 出现时它会自己补上。
   A-27 就是"accel 先在场、S3 后起"并成功，**顺序有先例，不是猜想**。
3. 因此把 accel 提前加载，能把"装不上（`Code=28`）"这件事挡在**进 S3 之前** —— 这正是 A-29 彩噪的成因
   （`open()` 被拒，但 preflight 已经把 scanout 指到没人画过的 buffer）。

### 0.5 装载条件（别写错顺序）

```
XeGfxAccel.kext Info.plist：
  IOClass = NMXAccel、IOMatchCategory = IOAccelerator、IOProviderClass = IOPCIDevice
  IOPropertyMatch = { "nmxgpu-claimed" = true }      ← 由 core 在 stage 7 打在 IOPCIDevice 上
```

→ **core → stage 7 → accel**，否则匹配不上。

### 6.1 §2.3 返回 `Code=28`（accel 不能热加载）

→ 说明这个集合只允许开机加载。**按 A-29 的经验，`Code=28` 必然发生在新加入 KC 的 kext 上；

## 7. 停机条件（照做）

1. **屏幕彩噪 / 黑屏 / 冻结超过 10 秒** → 立即重启，别等 watchdog：

2. WS 活不到 60 s 且 crash-loop → 同上。
3. 门 2/3/4 任一不过 → 清 nvram 门 + `rm armed`，`pkill -f "log stream"`，停手报告。
4. `IGPUConsoleRange` 从 KC 消失 → 本关不重建 KC，理论上不会发生；若发生，停手别重启。
5. `starts` 涨到 `%02` 后，**下一次失败就是最后一次** —— 那时必须停下来分析，不要再试。

## 10. 铁律（今天用血换的）

1. `kmutil` 在 `/usr/bin`；装/改集合用 `kmutil create -z`；**绝不** kickstart `kernelmanagerd` / `syspolicyd`。
2. 新加入 AuxKC 的 kext **不能热加载**（`Code=28 requires a reboot`）—— A-29 实证。
3. `kmutil create` 的 `-B/-S` 必须绝对路径（`/System/Library/KernelCollections/BootKernelExtensions.kc`）。
4. `kmutil` 的 `rebuild done` 不可信；唯一判据是 `kmutil inspect` 逐条 id 都在。
5. 不在 boot 阶段推 `debug.xegfxaccelfb`（A-25b 证伪）。**本关不写任何 `debug.xegfxaccel*`**。
6. `armed` 之后 120 s 内不要重启。
7. macOS 没有 `timeout`；远端后台用 `( cmd > out 2>&1 & )`，收尾 `pkill -9 -f <标记>`。
8. **WS 活不到 60 s 时，`sample` 的绝对计数不算证据**；loginwindow 下的计数也不可与 1256 比较。
9. 一次一个变量：本关只加"提前加载 accel"。**不**改 `AGDC_FB_CLASS`、**不**改 vendor id、**不**改探针分。
