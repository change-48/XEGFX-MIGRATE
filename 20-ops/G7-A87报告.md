# G7 · A-87 报告：锁搬出去了（4.08 → 0.01 ms），帧一步没动——限速不在驱动里

> 日期：2026-11-03 20:17–20:40（一次装机重启；零 NVMTL 异常；accel/KC 未动）
> 目标：按 A-86 §4.4 把类锁里那 4 ms 搬出去，看能否把帧从 3 拍拉回 2 拍（60 fps）。
>
> **一行结论（三个数）：拖动 p50 = 25.30 → 25.00 / 25.12 ms（p90 42.04 → 41.89，≈40 fps，**60 仍然没拿到**）；
> 类锁等待 = **4.08 → 0.01 ms/帧**（dealloc / enqueue / submit / surface_in 四个入口全归零）；
> 提交计数自洽 = **16384 次提交，0 失败，peak in flight 3**，claimed == landed + failed + in-flight。**
>
> **锁不是限速项**——这是本关唯一确定的结论。搬走 4 ms 之后，等待原封不动地转移到了
> `DisplaySurface::AccessComplete`（0.88 → 3.01 ms），busy+wait 已经掉到 **15.39 ms < 16.67 ms（2 拍）**，
> 帧却还是 25 ms。而且 `defer=0` 时主线程 busy 只剩 **9.04 ms、idle 12.13 ms**，帧反而掉到 32 ms。
> ⇒ **主线程的工作量已经不是这条流水线的瓶颈了**，A-86 的"pass 边界越过那一拍"假设被证伪。

## 2. P0 · 锁边界表（读码产出，零改动）

| 入口 | 函数 | 锁内做了什么 | 读/写哪些共享状态 | 谁能与它并发 |
| --- | --- | --- | --- | --- |
| dealloc | `-[NVMTLCommandBuffer dealloc]` | `nvmtlReleaseReservation`（从 `queue->_reservations` 摘除）+ `nvmtl_pump_buffers`（可能 dispatch 执行 worker / ahead kick） | `_queue->_reservations`、`nvmtl_pending_buffers`、`nvmtl_pumping`、`nvmtl_pump_generation` | ahead pass / 执行 worker / enqueue / submit / completion 线程 |
| enqueue | `-[NVMTLCommandBuffer enqueue]` | `_nEnqueue++`、`nvmtlReserveQueue`（向 `_reservations` 追加）、`_cbstatus` | `_queue->_reservations`、`_cbstatus` | 同上 |
| submit | `nvmtlSubmitWithEvents` | `_committed/_commitMarking=YES`、`nvmtlReserveQueue`、封 part、`nvmtl_surface_register_writes`（写 `surface_writers`）、把 cb 塞进 `pending_buffers`、`nvmtl_pump_buffers`（`nvmtl_ws_mark_pending` 本来就在锁外） | `nvmtl_pending_buffers`、`nvmtl_surface_writers`、`_reservations`、`_parts`/`_nextPart` | ahead pass / worker / dealloc / completion |
| surface_in | `nvmtl_surface_in_for_cb` → `nvmtl_surface_pending_write` | 遍历 `surface_writers`（weak→strong 表）、读 `IOSurfaceGetSeed`，之后 `[t nvmtlSurfaceIn]`（surface 自己的锁） | `nvmtl_surface_writers`、texture 的 IOSurface | submit（register_writes）/ completion（finish_writes） |
| ahead | `nvmtl_gsub_ahead_pass` → `nvmtlSubmitAhead` | 遍历 `pending_buffers` + `queue->_reservations`；每个 part：evfold 表读写、`prepare_submission_copies`、`nvmtl_vk_inflight_new`、`nvmtl_buffer_sync_in`（主机拷贝）、`nvmtl_vk_submit_begin`（451 µs）、计数 | `_nextSubmit`、`_parts`、`part->{claimed,waitFolded,inflight,aheadFailed,aheadEmpty}`、`nvmtl_evfold_submitted`、`gsub_*` 原子量、`nvmtl_pending_buffers`、`queue->_reservations` | 上面四个 + completion 线程 |

**门 P0 判定：拆锁（给 ahead 一把独立的锁）不安全。**

ahead 与其余四个入口共享的**不只是** `_nextSubmit` / `part->inflight`，还有两张容器：
`nvmtl_pending_buffers`（commit 追加、pump/dealloc 删除）和 `queue->_reservations`（reserve 追加、release 删除），
外加 `nvmtl_evfold_submitted` 表。换成独立锁后，ahead 会**在枚举 NSMutableArray 的同时**被另一线程改写——
这是堆破坏/野指针级别的错误，不是"可能"，是必然（只差触发时机）。
⇒ 提示词 §3.1 的 P1（只换锁对象）在本代码里不能做，直接进 §4.4 的"按阶段拆"。

## 3. P1/P2 · 按阶段拆（锁内只 claim、锁外干活）——落地即 P2 的六步

`~/xegfx-log/A-87/tree-lock`（`patch_a87_lock.py`，10 处锚点全命中，构建 **0 error / 481 warning**，`97c8fc00…`）：

| A-86 §4.4 的要求 | 本关实现 |
| --- | --- |
| 1. 结构体加 `aheadBusy` | `NVMTLSubmissionPart.aheadBusy`（+ 每 cb 的原子计数 `_aheadBusy`） |
| 2. 锁内只 claim | `nvmtlA87Claim:inflight:`：选 part、`_nextSubmit++`、`aheadBusy=YES`、取好 `nvmtl_inflight` |
| 3. 锁外干活 | `nvmtlA87Run:inflight:`：`nvmtl_buffer_sync_in` + `nvmtlMarkScheduled` + `nvmtl_vk_submit_begin` |
| 4. 再进锁 land | `nvmtlA87Land:inflight:failed:`：`part->inflight=f`、计数、`aheadBusy=NO` |
| 5. `AdvancePart` 把 aheadBusy 当"不是我的" | 先等 `aheadBusy` 落地（≤20 ms），进锁再复查一次，仍在 submit 就 `return NO` |
| 6. 防 UAF | part 有栈上强引用；`nvmtlFinishExecution` 在 `_partsRetiring=YES` 之后、清空前，**无锁**等 `_aheadBusy` 归零（≤100 ms） |

额外两条本关自己加的保险：
- **一趟一锁**：`nvmtl_a87_passing` 用 CAS 保证同一时刻只有一个 ahead pass（它会中途放锁，两个 pass 会互相踩窗口）；
- **落锁补踢**：land 时若发现 worker 已经放弃（`!nvmtl_pumping`）而还有 part 没走完，主动 `nvmtl_pump_buffers()`，避免"最后一帧没人推"——
  这是拆锁后新增的窗口（submit 在锁外那 0.45 ms 里，worker 可能判定"无进展"退出），不补就会出现某个 cb 永不完成、`waitUntilScheduled` 挂死。

## 4. 新归因：那 4 ms 是被"显示完成"吃掉的，主线程已经不在关键路径上

| 观察 | 数字 | 含义 |
| --- | --- | --- |
| 类锁等待 → `AccessComplete` | 4.08 → 0.01 ms 同时，`DisplaySurface::AccessComplete` 从 0.88 → **3.01 ms** | 省下的时间原样转移到"等上一帧显示完成"，总量守恒 |
| busy + wait vs 2 拍 | 17.09 → **15.39 ms**（< 16.67） | 已经放进 2 拍的时间里，帧仍是 3 拍 ⇒ A-86 的"pass 边界越过那一拍"不成立 |
| `defer=0` | busy **9.04**、idle 12.13，p50 **32.17** | 主线程更闲，帧更慢 ⇒ 限速在 present/display 链路，不在主线程工作量 |
| `flip=0` | busy 8.74、wait 6.01，p50 **32.10** | 同上；两个显示开关都已是最好值，不能动 |

**结论**：这三拍的量化器在 **present → display 完成**这一环（`AccessComplete` 的 ~3 ms + 每帧等下一个 `CGXRunOneServicesPass` 的 9–12 ms 空闲），
Metal 驱动侧继续减 busy 或减锁都不会再换来一帧。**P3（描述符池）因此没有意义**：它减的是 busy（≈1.1 ms），
而 §4 已经给出"busy 减到 9.04 ms 反而更慢"的反证——**故 P3 本关主动不做**（不是没时间，是没靶子）。

## 8. 给下一关的三句话

1. **别再打驱动里的锁和 busy 了**：4.08 ms 的锁已经搬干净（0.01），p50 只挪了 0.2 ms；`defer=0` 把 busy 从 11.3 降到 9.0 反而更慢。
   这两条是"靶子已经打空"的硬证据。
2. **靶子换成 present/display 完成**：`AccessComplete` 3.0 ms + 每帧 9–12 ms 空等下一个 services pass。
   要看的是 NVAccel 的 flip 完成延迟、`IOPresentment`、`wait_idle=1` 的语义，以及"能不能不给上一帧等完成"。
3. **准入与测量纪律**：开机后必须等到 `XeGfxAccel` 已载入且 `flips` 在涨、`screen=1560×1040`，才准跑拖动；
   每轮至少两次重复（本关 p90 49 的假信号就是单轮噪声）；断线先查 panic 报告再归因。
