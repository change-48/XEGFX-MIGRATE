# Gate 3 · A-13 执行提示词（原生 1:1：不要关缩放器）

> 用法：把本文件全文作为一条消息发给执行会话。执行会话不需要任何前置上下文。
> **只做一件事：让缩放器跑 1:1（输入=输出=3120×2080），而不是关掉它。**

---

## 0. 一句话

A-12 的 S2 把 `PS_CTRL` 的 bit31 清 0（关缩放器），管道随即失锁、被 macOS 打回 1080p。
但主 agent 复核发现：**trans 时序本来就是原生的**，而 `TRANS_PIPESRC` 是**缩放器的输入尺寸**、`PS_WIN_SZ` 是**输出尺寸**。
所以正确做法不是"关掉缩放器"，而是**把输入也改成 3120×2080** —— 缩放比变成 1:1，输出就是原生像素。

---

## 1. 主 agent 刚复核的事实（比 A-12 报告更准，以此为准）

从 `XeDiag` 的 `w60` 窗口读 pipe A（开机快照）：

| 寄存器 | 值 | 含义 |
| --- | --- | --- |
| `TRANS_HTOTAL 0x60000` | `0x0D470C2F` | htotal **3400**、hdisplay **3120** → **原生宽度** |
| `TRANS_VTOTAL 0x6000C` | `0x089F081F` | vtotal **2208**、vdisplay **2080** → **原生高度** |
| `TRANS_PIPESRC 0x6001C` | `0x077F0437` | 缩放器**输入** 1920×1080 |
| `PS_WIN_SZ 0x68174` | `0x0C300820` | 缩放器**输出** 3120×2080 |
| `PS_CTRL 0x68180` | `0x80000200` | 缩放器使能 |
| `TRANS_DDI_FUNC_CTL 0x60400` | `0x00000000` | A 路 DDI 未使能（说明输出不走这条常规 DDI，别去改它） |

**结论 1：A-12 报告里"transcoder 时序仍是 1080p、需要完整 modeset"这个前提是错的。**
面板此刻就是以 3120×2080@~120Hz 在扫，只是缩放器把 1920 的源拉大了。`TRANS_HTOTAL/VTOTAL` 一个字节都不需要改。

**结论 2：`reg` 命令的索引映射没坏**（`0=SURF, 1=SIZE, 2=STRIDE, 3=PIPESRC, 4=PS_CTRL, 5=PLANE_CTL`，见 `xenative.cpp:741-749`）。
所以 S2 那些"被截断"的回读值不是工具写错地址造成的。

**结论 3：S2 最可能的致命动作是"清 PS_CTRL bit31"**，而不是尺寸本身。
缩放器从"3120 输出"变成"关闭"，pipe 的行缓冲立刻欠载 → 失锁 → `IGPUConsoleRange` 把整套状态打回 1080p。

---

## 2. 本关的判据调整（主 agent 定）

原计划 Gate 3 的第 4 条是「`PS_CTRL` bit31 = 0」。**本关改为：只要输出像素是 1:1 原生，就算达成**，
即使缩放器仍然"使能"（此时它的缩放比是 1:1，等于旁路）。

理由：目标是"面板拿到原生 3120×2080 的像素"，不是"某个使能位为 0"。
拿位当判据会让我们在真成功时判失败。

---

## 3. 铁律

- **本次绝对不写 `PS_CTRL`。** 让它保持 `0x80000200`。
- **不改 `TRANS_HTOTAL / VTOTAL / HBLANK / VBLANK / HSYNC / VSYNC / DDI_FUNC_CTL / PIPE_CONF`。**
- 只写三个平面寄存器：`PLANE_STRIDE`、`PLANE_SIZE`、`TRANS_PIPESRC`，外加 `PLANE_SURF`。
- 三个几何寄存器必须**背靠背写完再等**（`doReg` 每条之间 `IOSleep(20)`，等于让 pipe 在"半改"状态停留 60ms → 改成一个命令一次写完，只 sleep 20ms 一次）。
- 收尾必须 `restore`，屏幕回到 1080p 桌面。
- 不许改 boot-args / EFI / GPUBundles；不许装加速器；不许 `softwareupdate`。

---

## 4. 唯一的代码改动：加一条 `regset`（背靠背写多条）

```cpp
// sel = kXeRegSet；scalarInput = [n, which0, val0, which1, val1, ...]
// 全部写完再做一次 IOSleep(20)，中间不加延时
for (unsigned i = 0; i < n; i++) fReg[off(which[i]) / 4] = (UInt32)val[i];
IOSleep(20);
// 然后逐条回读、逐条 out64 返回
```
`which` 用和 `doReg` 完全相同的 0..5 映射，别新造一套。

`xenative-ctl regset 2 195 1 0x081F0C2F 3 0x0C2F081F` 这种形式（which/value 成对）。

## 5. 执行步骤

```bash
# 0) 现状
xenative-ctl status > ~/xegfx-log/A-13/before.txt

# 1) 把 3120 宽图案经孔径写进 <256MB 的可用区，并把 6338 条 PTE 指好
xenative-ctl mapfast 0x1000 6338 0x01000000      # 期望 bad 0
xenative-ctl apfill  0x1000 1                    # 1 = 3120 宽图案

# 2) 先把 SURF 切过去（此时几何还是 1080 → 会看到"紫色竖条纹"，这是正常的中间态）
xenative-ctl reg surf 0x01000000

# 3) 背靠背改三个几何寄存器（PS_CTRL 不动！）
xenative-ctl regset 3 2 195 1 0x081F0C2F 3 0x0C2F081F

# 4) 立刻读回 5 个寄存器 + SURFLIVE，并立刻看屏幕 / 拍照
xenative-ctl status
```

> macOS 侧一旦发现异常会**在 1 秒内**把寄存器打回 1080p（A-12 就是这么丢的）。
> 所以第 4 步要**抢在同一秒内**做完：先 `status`，再拍照，最后才分析。

## 6. 判读

| 现象 | 结论 | 下一步 |
| --- | --- | --- |
| **图案 1:1 铺满**（四角白块贴边、1px 棋盘能看出点阵、不再被拉伸） | ✅ **Gate 3 的技术核心达成** | 收尾 `restore`，报告成功；后续只需让 macOS 自己用 0x800000 那块 26MB 原生缓冲 |

## 8. 如果 A-13 成功，Gate 3 还差什么（写给下一步，不用现在做）

我们的图案能 1:1 上屏，说明"平面→缩放器→transcoder"这一段已经通了。
但屏幕上的内容还是我们写的测试图，不是桌面。

真正的收尾是：**让 macOS 自己往那块原生的 26MB 缓冲里画**。
固件已经在 `phys 0x800000` 处映射了 **6656 页 = 26 MiB** 的连续帧缓冲（`live_run_pages 6656`），
而 macOS 只用前 2025 页（1080p / stride 120）。把 `IGPUConsoleRange`（或 `NMIntelFB` 的 adopt 分支）
改成 3120×2080 / stride 12480，macOS 就会用满这 26MB —— 那时连 PTE 都不用碰。

这条路径同时绕开了本关发现的两个限制：缓冲天然 <256MB、天然连续、天然被引擎读过。

## 验收锚点（主 agent 独立跑）

1. `xenative-ctl status` 收尾回原值（`STRIDE 120 / SIZE 0x0437077F / PIPESRC 0x077F0437 / PS_CTRL 0x80000200 / SURF 0xFE600000`）。
2. `live_run_pages` 仍 6656、`live_phys` 仍 `0x800000`。
3. `PS_CTRL` 全程 `0x80000200`（本关没写过它 —— 这是关键对照）。
4. 屏幕 1920×1080、WindowServer 在、零新 panic、`IGPUConsoleRange` 在。
5. `~/xegfx-log/A-13/` 里有 `before.txt`、`status` 读回、照片。
