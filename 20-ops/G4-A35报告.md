## 0. 一行结论

占位 FB **在对象层面撤掉了**（`XeGfxIntelFramebuffer` 1 → 0，`Created FB` 从 `1 of 2` 变成 **`1 of 1`**），
但 IOP **仍然建不出 display pipe**：`Unable to create IOAccelDisplayPipe` 1 次、`Interface creation error: 0x2002` 1 次、
`System set to use IOP but no display pipes are present` 1 次、`Unable to find display pipe … regID 0x7c63 / 0x10000083f` **7 次
（全部指向我们这块 FB，不再有第二个 regID）**、`newDisplayPipe` / `initFramebufferResource` **0 次**。
WS 最长只活 **77 s**，屏幕变黑（`system_profiler` 里连 `Displays` 段都没了），已按 §7 止损清门重启，22:16 回到干净态
（`3120×2080@120` 在线、无新 panic）。
**判定：占位 FB 不是 IOP 建不出 pipe 的原因（§4 判读表第 2 行）。** 本关"成功条件 5+6+10"第 10 条不成立，整关不成立，
但拿到了明确的分岔结论，并新增两条 A-34 没有的现象（见 §6）。

## 6. 新增现象（A-34 没有的，供下一关判断用，本报告不改法）

1. **`NMXAccel: newUserClient(type 4/5/6) -> family returned 0x0`**
   A-34 里是 `type 0 -> family returned 0xe00002c9`（family 拒掉）。本关占位 FB 消失后，
   IOP 走的是 type 4（`IOAccelDisplayPipeUserClient2`）、5（`IOAccelDevice2`）、6（`IOAccelSharedUserClient2`），
   **三个全部 `0x0`（成功建出客户端）**，紧接着仍然 `Unable to create IOAccelDisplayPipe` + `0x2002`。
   即：客户端这一层已经通了，失败点在 pipe 自身的资源/接口初始化。
2. **`IOFBSetDisplayModeAndDepth: Setting mode 0x0 with depth 0x0 on displayID: 0x0` → `Failed to obtain mode info`**
   WS 从我们这块 FB 取 display mode 失败（displayID 为 0），紧接着 `Created FB 1 of 1` 后没有任何在线 display。
   1080p 那轮（占位 FB 在线）从来没有这条，说明我们这块 FB 的 mode 枚举对 CoreDisplay 不可见。
3. `kextunload` 被拒（rc=71）**仍然能终止它发布的 FB 对象** —— 说明占位 kext 的 retain 来自别处（不是它的 FB 实例本身），
   这一点对 A-36 判断"是否必须走 OC boot-arg"有直接影响。
