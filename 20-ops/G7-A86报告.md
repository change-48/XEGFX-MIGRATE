## 3. P1 · 每帧重编着色器：**推翻**

### 3.1 先加探针，再看事实

A-85 的结论来自 `sample`：线程 9 在 `create_fragment_shader → nvmtl_translate_with_fc_cached +1397 → nvmtl_translate_with_fc`
里 4354/4654 个采样点。本关第一步是给 `nvmtl_translate_with_fc_cached` 加**每次查表的 census**
（`patch_a86_diag.py`，写 `/private/tmp/nvmtl-fc.log`：tag / 函数名 / AIR 摘要 / 常量摘要 / AIR 长度 / 字符串对象指针 /
产物字节 / translate 耗时 / 键自身耗时）。

反汇编确认 `+1397` 正是**真 miss** 那条 `nvmtl_translate_with_fc` 调用点（`0x42910 callq`，返回地址 0x42915 = +1397），
所以 A-85 看到的确实是"每帧 miss"。

### 3.2 但换一次会话，它就不 miss 了

| 轮 | 场景 | fc 查表 | 结果 |
| --- | --- | --- | --- |
| A-85（19:20，pid 1330） | 拖动 12 s | 100+ hit 之后 **8 次 miss**，每次 **3.6–11.5 秒**（产物 699876/700136/701456/705836… 各不相同） | **冷缓存**：这 8 次是这台机器第一次见到这 8 个 spec 变体 |
| A-86（20:00，pid 1331，重启后） | 拖动 25 s | **37 次查表，37 次 FILEHIT，0 miss** | 变体已在盘上（`…/C/WindowServer/nvmtl/spvcache` 1088 个文件 / 290 MB，其中 467 个 `.fc1.`） |

**关键对照**：A-86 拖动时**着色器翻译一次都没发生**，p50 仍是 **25.24 ms**（与 A-85 的 25.15 一样）。
⇒ **"每帧重编"不是稳态，砍它换不来一帧。** A-85 的归因把"首次编译窗口"当成了"每帧成本"。

### 3.3 键的组成（§3.2 的三问，逐条答）

1. **键 = SHA256(AIR 全文 || stage/entry/constants 的规范 JSON)**，不是指针——`nvmtl_spvcache_path_air`，
   文件名还带 translator tag；内容哈希，本来就不会因为"指针变了"而 miss；
2. **拖动中组成不变**：同一函数 `air=d5ee8537`（AIR 长度 695912 字节，`NSString` 对象指针都没变），
   只有 `j` 变——即**常量组合**在变：`{"0":0,"3":0,"4":0,"5":1,"7":0|1,…,"15":0|1}`，是 CA 的**特性开关位**；
   不同位组合 → 不同 SPIR-V（699876 / 700136 / 715448…），**是有界的变体集合，不是每帧新值**；
3. 所以"命中率"取决于**这个变体见过没有**：第一次 miss（3.6–11.5 s），之后一直 hit。

### 3.4 那 A-85 的 23.6 ms/帧、"独占一核"是什么

是**冷缓存那一段**（pid 1330 的 8 次 miss，每次 3.6–11.5 s，串起来约 50 s）落进了 12 s 采样窗口，
于是"线程 9 99.5% busy"。它不是稳态成本，**是一个一次性代价**，而且这个一次性代价本身值得修（见 §6 建议 3）。

## 4. P2/P3 · 新归因 + 三条改法的 A/B（**都无效，但把范围收窄了**）

### 4.1 主线程（A-86 稳态，p50 24.59 / 25.24 的两次采样，数字互相印证）

| 类别 | ms/帧 | 内容 |
| --- | --- | --- |
| busy | **9.76**（另一次 10.90） | 极平：最大单项 `anv_descriptor_set_write_image_view` 0.35；**描述符簇合计 ≈1.1**（`anv_AllocateDescriptorSets` 0.32 + `nvmtl_snapshot_set_md` 0.22 + write 0.35 + …）；其余是 CA 渲染、malloc、memcpy 碎片 |
| wait | **5.73** | **`objc_sync_enter` 4.06**（同一把类锁）+ `AccessComplete` 0.68 + `MetalContext::Flush` 0.53 |
| idle | **8.61** | 其中 **86% 是 `CGXRunOneServicesPass` 的 mach_msg**——等下一次 services pass，不是工作 |

**类锁 4.06 ms/帧按入口拆**（`__ulock_wait2 ← objc_sync_enter`）：

| ms/帧 | 入口 |
| --- | --- |
| **2.06** | `-[NVMTLCommandBuffer dealloc]` ← `MetalContext::Flush` |
| **0.90** | `-[NVMTLCommandBuffer enqueue]` ← `MetalContext::RenderCommandBuffer` |
| **0.55** | `-[NVMTLCommandBuffer(EventSubmission) nvmtlSubmitWithEvents]` ← `commit` |
| **0.42** | `nvmtl_surface_in_for_cb` ← `setFragmentTexture:` / `renderCommandEncoderWithDescriptor:` |

持锁者是谁：`nvmtl_gsub_ahead_pass()` 在 `@synchronized` **里面**做 `nvmtl_buffer_sync_in`（主机拷贝）+
`nvmtl_vk_submit_begin`（451 µs/次），每帧 2.8 个 part 就是 2.8 次"锁内干活"。这就是 4 ms 等待的来源。

### 4.2 三条运行时可 A/B 的改法（本关新增 `/private/tmp/nvmtl-a86` 开关，一次重启试三种）

| 配置 | 做法 | p50 | 结论 |
| --- | --- | --- | --- |
| 基线（无开关文件） | A-80 行为 | **24.59 / 24.97** | 基准 |
| `nogsub` | 关掉 submit-ahead 通道，全交给执行 worker（锁内不再提交） | **32.48**（p90 42.1） | **反而掉一档**——ahead 通道是承重的，不能拆 |
| `cap=1` | 在飞上限 1 | 26.00 | 略差 |
| `cap=2` | 在飞上限 2 | 24.82 | 噪声 |
| `cap=4` | 在飞上限 4 | 24.89（p90 41.5） | 噪声 |

⇒ **① 关掉 ahead 不行；② 加深流水（P3 的原意）也不动档位。** 也就是说：**问题不是"提交串行"，是"提交在锁里"**。

### 4.3 为什么 15.5 ms 的工作量仍然给 3 拍

busy+wait = 15.5 ms < 2 vblank（16.67），但帧仍落 3 拍。两次采样都显示主线程在 pass 结束后
在 `CGXRunOneServicesPass` 里等 **8.6 ms** 才等到下一个 pass——即 pass 的**边界**刚好越过了那一拍，
于是被量化到 3 拍（`nogsub` 把工作加大后立刻变 32.5 = 4 拍，同一个量化器）。
**要跨档，需要给 2 vblank 留出余量，量级 2–4 ms；类锁正好是 4 ms。**

### 4.4 下一步该怎么做（本关没做，因为它是必须单独做的一次重构）

`nvmtlSubmitAhead` 的重构，**锁内只 claim，锁外干活**：

1. 结构体加 `BOOL aheadBusy;`；
2. `nvmtl_gsub_ahead_pass` 在锁内只做：选 part、`_nextSubmit++`、`aheadBusy = YES`，把 (part, f) 收进本地数组，**出锁**；
3. 出锁后做 `nvmtl_prepare_submission_copies` + `nvmtl_buffer_sync_in` + `nvmtl_vk_submit_begin`（451 µs × N 离开锁）；
4. 再进锁：`part->inflight = f; aheadBusy = NO;` 并更新计数；
5. **`nvmtlAdvancePart` 必须把 `aheadBusy` 当成"不是我的"**（`claimed=NO; return NO`），否则 ahead 与执行路径会**同时提交同一个 part**；
6. **必须防 UAF**：`nvmtlFinishExecution` 里的 `[_parts removeAllObjects]` 会把还在 submit 中的 part 释放掉
   → 出锁那一小段必须用本地 `NSMutableArray` **强引用住** part，并且 `_partsRetiring` 要在 claim 阶段就拦住后续 pass。

风险：第 5、6 条错任何一处，WindowServer 会卡死或 GPU 提交野指针（后果是黑屏/长按电源）。
**所以它不该在本关最后 20 分钟里做**——本关把它设计清楚了，留给下一关单独装、单独测、单独回滚。

**备选（更小的刀）**：`dealloc` 那 2.06 ms 是最大的一笔等待，但它只是**受害者**；真正的改动只有两种
（把 ahead 的提交搬出锁 / 把 dealloc 的记账挪到后台队列），两者都得动锁的语义，量级相当。

**第二把刀**：描述符簇 ≈1.1 ms busy（`nvmtl_snapshot_set_md` 每次 bind 都新建 descriptor set）。
把它改成按"绑定签名"复用池，**只动 busy、不碰锁**，是风险最低的一条；但 1.1 ms 不足以单独跨档，
需要与锁那条叠加。

## 6. 三件顺手发现的坑（下关别再踩）

1. **`nvlog` 按格式串指针去重**（前 8 次 + 每 4096 次）。A-85 用"日志里有几条 miss"判断频率**必然错**，
   本关一开始也被它骗了一轮，最后靠 `sample` 的返回地址反汇编才对上账。**要么加计数器，要么别数日志行。**
2. **开机后 2–3 分钟内 `NSScreen` 会报 0×0**（`screencapture` 也报 could not create image from display）。
   此时跑 `xa82load` 得到的是垃圾数据（p50 8.66 ms）。`caffeinate -u -t 2` + 等一次 bootArm 的
   "restarting WindowServer once" 之后才正常。**测量前先 `xa82load` 打印 screen 尺寸，不是 1560×1040 就别测。**
3. **冷缓存的一次性代价是真的**：第一次遇到一个新 spec 变体要 **3.6–11.5 s**（单次！）。用户"第一次拖某个窗口卡一下"
   是这个，跟稳态 40 fps 是两件事。要修它得看 `libnvmtl_translate` 侧（`emit_vulkan_spirv_inner` 占 1941/3389），
   与本关的帧预算无关。
