## 2. 已确认的寄存器事实（来自本机 i915 源码，别自己猜偏移）

源码在 `~/src/xe-src/linux/drivers/gpu/drm/i915/`，以下均已核对：

**pipe 基址**（`display/intel_display_device.c:76-79`）
```
PIPE_A 0x70000   PIPE_B 0x71000   PIPE_C 0x72000   PIPE_D 0x73000
```
`_MMIO_PIPE2` 等价于「基准寄存器 + 0x1000 × pipe」，所以 pipe X 的主平面寄存器 = 0x70000 + 0x1000·X + 下列偏移。

**主平面寄存器**（`display/i9xx_plane_regs.h`）
| 偏移 | 宏 | 行号 | 说明 |
| --- | --- | --- | --- |
| +0x180 | `_DSPACNTR` | :14 | PLANE_CTL。**bit31 = DISP_ENABLE**，**bits 29:26 = DISP_FORMAT**，**bit10 = DISP_TILED**（:16/:18/:43） |
| +0x188 | `_DSPASTRIDE` | :54 | stride，单位 64 字节 |
| +0x190 | `_DSPASIZE` | :64 | 低16 = w-1，高16 = h-1 |
| +0x19C | `_DSPASURF` | :71 | GGTT 偏移（我们要改的就是这个） |
| +0x1A4 | `_DSPATILEOFF` | :75 | tile 内偏移 |
| **+0x1AC** | **`_DSPASURFLIVE`** | :85 | **硬件当前真正在扫的 GGTT 偏移（只读，判断"是不是这一路"的唯一硬证据）** |

**其它**
| 地址 | 含义 |
| --- | --- |
| 0x60000 + 0x1000·p | TRANS_HTOTAL（pipe p） |
| 0x6001C + 0x1000·p | TRANS_PIPESRC（低16 = w-1，高16 = h-1） |
| 0x60040 + 0x1000·p | TRANS_FRMCOUNT |
| 0x68174 | PS_WIN_SZ |
| 0x68180 | PS_CTRL（**bit31 = scaler enable**） |
| 0x108040 | GGC（含 stolen 大小 GMS，位域去源码里查 `GMS_MASK`） |
| 0x1080C0 | DSMBASE |

**上一轮已经测到的值（基线，A-09 要复核）**
```
TRANS_HTOTAL  = 0x0D470C2F   → hblank_start 3120, htotal 3400
TRANS_VTOTAL  = 0x089F081F   → vblank 2080, vtotal 2208
PIPESRC       = 0x077F0437   → 源 1920×1080
PLANE_SIZE    = 0x0437077F   → 1920×1080
PLANE_STRIDE  = 120          → 7680 / 64
PS_WIN_SZ     = 0x0C300820   → 3120×2080
PS_CTRL bit31 = 1            → 缩放器开着
PLANE_SURF    = 0xFFE60000   → macOS 自己的表面
```
结论：**时序已经是原生的，只有"源"和"缩放器"要改。不需要碰 HTOTAL/VTOTAL，不需要 DSC。**

**上一轮的失败现场（必须解释清楚，别再重演）**
写了 `PIPESRC=0x0C2F081F`、`SIZE=0x081F0C2F`、`STRIDE=195`、`PS_CTRL &= ~bit31`、`SURF=0xFE800000`
（缓冲是内核里 IOBMD 分配的 26 MB，物理约 30.5 GB，建了 6338 条 PTE）。
结果：屏幕不是那块纯绿缓冲，而是**左上角漂移 + 底部黑**。
对照实验（只 map、不写任何寄存器）画面完全正常 → 说明**写入是生效的、落的是活的那一路**，
但**内容被解释错了**。

> 最可能的解释：`PLANE_CTL` 的 `DISP_TILED`(bit10)=1，硬件按 X-tile 解读，而我们写的是线性缓冲 →
> 表现为对角漂移 + 尾部黑。A-09 就是去把这一位读出来确认。

### 5.3 取数据并解码

```bash
sudo ioreg -l -w0 -r -c XeDiag > ~/xegfx-log/A-09/ioreg.txt
```
然后用下面这段 python 把 `w60/w61/w62/w63`、`w68`、`w70..w73`、`misc` 解成"地址→值"，
只打印你要的那几个地址（存成 `~/xegfx-log/A-09/decode.txt`）：

```python
import re, subprocess
txt = open('/Users/change48/xegfx-log/A-09/ioreg.txt').read()
blobs = {}
for name, hexs in re.findall(r'"(\w+)"\s*=\s*<([0-9a-fA-F\s]+)>', txt):
    hexs = re.sub(r'\s+', '', hexs)
    blobs[name] = bytes.fromhex(hexs)
BASE = {'w60':0x60000,'w61':0x61000,'w62':0x62000,'w63':0x63000,
        'w68':0x68000,'w69':0x69000,
        'w70':0x70000,'w71':0x71000,'w72':0x72000,'w73':0x73000,'misc':0x108000}
def rd(addr):
    for n,b in blobs.items():
        base = BASE.get(n)
        if base is None: continue
        if base <= addr < base+len(b):
            off = addr-base
            return int.from_bytes(b[off:off+4],'little'), n
    return None, None
want = []
for p in range(4):
    for nm,off in [('PLANE_CTL',0x180),('STRIDE',0x188),('SIZE',0x190),('SURF',0x19C),
                   ('TILEOFF',0x1A4),('SURFLIVE',0x1AC)]:
        want.append(('pipe%d %s'%(p,nm), 0x70000+0x1000*p+off))
    for nm,off in [('HTOTAL',0x000),('PIPESRC',0x01C),('FRMCOUNT',0x040)]:
        want.append(('pipe%d TRANS_%s'%(p,nm), 0x60000+0x1000*p+off))
for nm,a in [('PS_WIN_SZ',0x68174),('PS_CTRL',0x68180),('GGC',0x108040),('DSMBASE',0x1080C0)]:
    want.append((nm,a))
for nm,a in want:
    v,src = rd(a)
    print('%-22s 0x%05X = %s' % (nm, a, ('0x%08X'%v) if v is not None else 'N/A'))
```

### 5.4 A-09 要回答的四个问题（这是本关真正产出）

1. **哪一路在扫？** 四个 `SURFLIVE` 里哪些非 0。非 0 的那一路才是有显示的。
2. **SURFLIVE 跟 SURF 一致吗？** 一致 → macOS 已经锁存；不一致 → 有未完成的 flip。
3. **`PLANE_CTL` bit10（DISP_TILED）是 0 还是 1？** → 决定 A-10 的缓冲必须 X-tile 还是可以线性。
   同时把 bits29:26（DISP_FORMAT）和 bit31（ENABLE）解出来。
4. **stolen 够不够？** `GGC` 的 GMS 位域 + `DSMBASE`：算出 stolen 基址与大小，看 26 MB 放不放得进。

### 5.5 停机条件

- AuxKC 少任何一个保留 id → 停，不许重启。
- 重启后 180 s 不回来 → 护栏会在下次开机 attempts=2 时自动回滚；**不要自己去改机器**。
- 装 XeDiag 后屏幕异常（理论上不会，它只读）→ 停，留证，报告。

## 6. A-10：按 A-09 的结论分支（唯一变量 = 写入一组寄存器）

**只有 A-09 的四个问题都有答案才允许进 A-10。** 依据答案走对应分支：

### 分支 1：`DISP_TILED`(bit10) = 1（X-tiled，最可能）

优先走 **把平面改成线性** 这条（可验证、改动最小）：
1. 缓冲用线性布局（就是这个 kext 里自己填图案的那块）
2. 写 `PLANE_CTL` 时**清 bit10**，其余位（format/enable/pipe select）保持读到的值不动
3. 再写 SIZE/STRIDE/PIPESRC/SURF
4. 如果清 bit10 后硬件不接受（黑屏或花屏），下一轮（A-11）改成**按 X-tile 写缓冲**：
   X-tile 的 4KB tile = 8 行 × 128 列（每像素 4B），把线性图案按 tile 重排后再写。
   **tile 的具体排布不要凭记忆，从 `intel_plane`/`i915` 里 `X-tile` 相关注释或 `intel_fb` 的
   `intel_tile_width_bytes` 实现里读出来再写。**

### 分支 2：`SURFLIVE` 指向的 pipe 不是 A

那就说明之前所有偏移都写错了 pipe。把 A-10 的全部寄存器地址整体平移到那个 pipe（+0x1000 × 差值），
并且**先只写 SURF 一个寄存器**做最小验证（画面应变成你的图案），确认找对了再加其它寄存器。

### 分支 3：写了 SURF 后 `SURFLIVE` 不跟随（macOS 每帧抢回）

说明 macOS 的 IOFramebuffer 仍在驱动这个平面。此时不要硬抢，改走 A-11 的顺序化方案，
并且记录 `SURFLIVE` 在 3 秒内的变化序列作为证据（如果它反复回到 0xFFE60000，就是被抢回）。

### A-10 的写入内容（三种分支共用）

```
缓冲区：优先 stolen（若 GMS 够 26 MB），否则仍用 IOBMD + 自建 PTE
PIPESRC  = 0x0C2F081F        (w-1=3119=0x0C2F, h-1=2079=0x081F)
SIZE     = 0x081F0C2F
STRIDE   = 195               (12480/64)
PS_CTRL  &= ~bit31           (关缩放器)
PLANE_SURF = <缓冲的 GGTT 偏移>
```

**HA 校验（必做）**：写完后读回每一个寄存器并 `setProperty` 发布，同时读 `SURFLIVE` 与
`TRANS_FRMCOUNT` 两次（间隔 >20 ms）确认还在走。**画面验收 = 左红右蓝 + 左上白块 + 右下绿块。**

### A-10 的 xegfx 安全门

XeNative 的写入必须**只在 `/var/db/xegfx/armed` 存在时执行**，写完立刻 `unlink` 该文件
（一次性；hang 后重启不会重放）。A-09 的只读版不需要这个门。

## 7. A-11：若 A-10 仍黑（唯一变量 = 更新时序）

```
PLANE_CTL bit31 清零（关平面）
→ 写 PIPESRC / SIZE / STRIDE /（必要时 TILEOFF）
→ PS_CTRL 清 bit31
→ 读 TRANS_FRMCOUNT 两次，间隔 >20 ms，确认在走
→ 写 PLANE_SURF
→ PLANE_CTL bit31 置位（开平面）
```
理由：单写 SURF 依赖"下一个 vblank 锁存"，如果期间有别的写打乱了 double-buffer 更新，
就会出现"寄存器是新的、画面是旧的"。顺序化 + 帧计数确认可以排除这一项。
