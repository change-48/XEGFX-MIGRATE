### 副产物：SURF 被 accel 换成了自己的 GGTT 别名，屏幕依然干净

```
SURF           0xfd000000      ← accel init 之后
SURF_before    0xfe600000      ← 开机时固件/我们的 framebuffer 用的
PLANE_STRIDE   195
phys_base      0x71800000
```

即 accel 把扫描输出从固件的 `0xfe600000` 改指到它自己分配的 GGTT 窗口 `0xfd000000`（同一块 phys，
"already backed, nothing allocated"），**画面没有变化**。这就是"彩噪不复现"的直接原因：
这次的 `0xfd000000` 是 accel 自己算出来、自己映射的地址，不再是当年"pitch 靠猜"的产物。

## 3. 为什么 `vmmap nvmtl` 还是 0（**不是这关的锅**）

```
$ ls -A /Library/GPUBundles | wc -l
0
```

`/Library/GPUBundles` **整个目录是空的**（目录本身 16:24 建立，内容随
`/Library/XeGfx/rollback-backup-20261031-162412/` 一起被回滚）。但 accel 的 Info.plist 里写的是

```
MetalPluginName      = ../../../Library/GPUBundles/NVMTLDriver
MetalPluginClassName = NVMTLDevice
```

→ 路径不存在 → Metal.framework 没有可 dlopen 的插件 → WindowServer 拿不到 Metal 设备 →
不会产生任何 `nvmtl` 映射。旁证（`ioreg -c NMXAccel` 的 PerformanceStatistics）：

```
surfaceCount = 0          bufferSwapCount = 0      bufferFlipCount = 0
textureCount = 1          inUseVidMemoryBytes = 25958528   (就是那块 scan-out)
NVAccelEnableCount = 2
```

`inUseVidMemoryBytes` 正好等于 boot fb 的 25,958,528 B —— accel 只持有扫描输出那一块，
一个 surface 都没分出去。**这是"插件没装"，不是"accel 没生效"。**

所以提示词的判读表缺一行：`vmmap = 0` 但 `describeBootFramebuffer` **成功** → 先查 GPUBundles 是否存在。
本关的 `vmmap` 判据在"插件未安装"的前提下不可能为真，判它失败会误伤 A-23b 的方向。

## 4. 仍未解决的旧账（记录，不在本关处理）

1. **`results` 位置 5 = -28 未变**：`xg_i915_reserve_bootfb(0xFE600000, 25958400)` 仍然 ENOSPC
   （`0xFE600000 + 26 MB` 跨过 `GUC_GGTT_TOP = 0xFEE00000`）。A-18a 已定性为"GGTT 不知道这 26 MB 被占用"。
   本关 accel 恰好没往那片区域分配（只别名了 scan-out），所以没炸；**但一次性分配多个 surface 时它仍会咬人**。
2. **SURF 从 `0xfe600000` 变成 `0xfd000000`**：几何读数要与 A-18a/A-22 的口径对齐（`SURF_before` 才是开机原值）。
