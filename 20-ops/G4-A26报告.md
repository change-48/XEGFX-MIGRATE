## 5. 为什么还是软件合成（机制，已定位到具体门控）

`kexts/XeGfxDisplay/src/XeGfxDisplay.cpp:2626-2695` 的三段门控：

```
phase==2 && trial==1 && fail==0  →  startS3()          ← 真接管（可 expose，open() 才放行）
phase>=1 && fail                  →  什么都不注册（pull）
phase>=1                          →  IOFramebuffer::start()，但 fInert=true
                                     "open() denied, 0 connections, 0 modes, no aperture"   ← 我们在这
phase==0 + kapi                   →  进"become console device"分支（没有 S3 校验，风险更高）
```

- 当前 `phase=1` 的结果就是 **`0.5-s2` 哑 framebuffer**：注册了、CA 能看见它、但 `open()` 被拒、没有 aperture，
  → **WindowServer 不可能在它上面合成**，于是继续 `CA::OGL::SW` 软件光栅 + `CPU copy target` 拷出去。这与 A-25 的机制判断完全一致，只是现在有了实物证据。
- 要拿到"GPU 可直接写的 scanout surface"，必须 **`phase=2` + `trial=1`（必要时 `expose=1`）**，此时：
  `XeGfxFBClaim`(20100) 会真的压过 `XeGfxIntelFB`(20001) 接管 IOFramebuffer 类别，由 `XeGfxFramebuffer` 自己
  用 core 0011 的 M3d `xg_scanout_ggtt_map` 出 surface（`expose=1` 才 `open()` 放行）。
  **这是"接管面板"级别的动作**，本提示词通篇按"挂上就有零拷贝"写的，没有授权这一步，所以停手。

### 5.1 顺手发现的一个真问题（S3 之前必须先解决）

nub 报的测量时序是 **2560×1600@60**，而当前控制台/面板实跑是 **3120×2080@120Hz**（`fbgeom` 也是 3120×2080）。
S3 的 same-mode claim 三条自检里第 (b) 条正是"测量 raster 与引擎当前 KAPI 模式相等"——
**这两个数字对不上，S3 大概率会被自己的 preflight 拦下**（或者强行接管后出 3120×2080 的错位/黑屏）。
→ 下一步要么先修 `measured-panel-timing`（AGDC 给的记录），要么确认 3120×2080 是缩放后的活动区、2560×1600 是原生 raster，并让 claim 用正确的比较口径。
