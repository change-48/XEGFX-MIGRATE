# Gate 4 · A-31 执行提示词：先分清 `-19` 是哪一条，再决定要不要动代码

> 目标：把 A-30 挡住的 `stage 4 = -19` **定位到具体分支**，并通过清除双路径并发把它跑过去；
> 过了就顺势接上 A-30 没走完的 accel → S3 → AGDC → WS 全链。
>
> **本关默认零代码改动、零重编、零 kext 安装、不重启。** 只有 §5 的 Plan B 才动代码。

## 0. A-30 的结论需要修正一处（不是推翻，是补一条）

报告把 `-19` 归因到 `xg_drm_attached()` 假阴性。**但 `-19` 有两个来源**，报告只验了一个：

```c
/* xg_kext.cpp:1155-1162  stage 4 */
rc = xg_display_check();                       /* 只可能返回 1 / -6 / -70 / -71，不会 -19 */
if (rc == 1 && !xg_drm_attached())
        rc = -19;                              /* ← 来源 ①（报告认定的） */
if (rc == 1) {
        xg_i915_map_init();
        rc = xg_gt_check();                    /* ← 来源 ②：第一行就是 -19 */
}

/* xg_gt_check() */
int rc = xg_i915_state(&st) == 0 ? 1 : -19;    /* xg_i915_state 只在 -ENODEV 时失败 */
```

```c
/* xg_i915_exec.c  xg_i915_state() */
if ((i915 = xg_i915_find(&pdev)) == NULL) return (-ENODEV);
/* xg_i915_find(): 遍历 Intel PCI 设备，pdev_to_i915(pdev) != NULL 才算找到（LinuxKPI 的 drvdata）*/
```

### 两条分支可以用一个属性区分（**本关的核心手法，零代码**）

`xg_gt_check()` 无论成败都会 `setProperty("XeGfxGt", d)`（只要有 `gResident`）。而来源 ① 会在调用它之前就 `rc = -19` 直接跳出。

| 现象 | 含义 |
| --- | --- |
| `XeGfxResident` 上**没有** `XeGfxGt` 属性 | 来源 ①：`!xg_drm_attached()`（newbus 说 attached、函数说不） |
| 有 `XeGfxGt`，且 `result=-19`、`guc-fw-status=0`、`engines=0`、`gts=0` | 来源 ②：**`xg_i915_state()` 拿不到 drvdata**（i915 在 LinuxKPI 层没绑上） |

**A-30 没有抓这个属性，所以"两种情况"当时是分不开的。本关第一件事就是把它抓下来。**

### 0.2 双路径并发（报告 §1，我完全接受）

```
20:55:30.958  XeGfx: boot-armed by NVRAM xegfx-disp-bootarm: stages 1..7 scheduled on a kernel thread
20:55:31.173  XeGfx: ran 58 sysinit_set entries      ← 手工 debug.xegfx_stage=7 那条
20:55:32.961  XeGfx: ran 58 sysinit_set entries      ← boot 线程又跑一遍
20:55:33.063  XeGfx: boot stage 4 rc=-19 in 104 ms
```

`xegfx-disp-bootarm=%01` 从 A-27 起就在 nvram 里，我的提示词没用它当门 —— 这是流程缺陷。

**A-29 能起 S3，是因为它没有手工写 `stage`**（让 bootarm 单跑）。A-30 写了，于是双跑。

### 0.3 由此得到的假设（本关先验证它，不先改代码）

双跑 = `sysinit_set` 被执行两遍 = i915/LinuxKPI 的 probe 走两遍。
`pdev_to_i915()` 拿的是 `pci_get_drvdata(pdev)`；如果第二次 init 把 drvdata 清掉/重设，
就会出现**newbus 层 `state 30 driver drmn` 仍然成立、而 LinuxKPI 层 `pdev_to_i915()==NULL`** ——
这正好同时解释两个现象（报告说的"假阴性"其实就是这个）。

→ **所以第一招是"只留一条路径"，而不是给 `xg_drm_attached()` 打补丁。**

```bash

#   ↑ 期望「没有输出」。若仍出现 "boot-armed ... scheduled"，说明 nvram 没清掉，停手。
```

## 3. 门 1 通过后：把 A-30 没走完的链接上（同一开机，不需要重启）

> 这一节与 A-30 提示词 §2.3–§5 完全一致，只是现在是从"stage 全绿"这个正确起点开始。

### 3.1 accel（先装，验证它能起，再进 S3）

```bash
sudo /usr/bin/kmutil load -b org.watchthelight.XeGfxAccel; echo "rc=$?"
sleep 3
sudo /usr/bin/kmutil showloaded | grep XeGfxAccel | tee $L/accel.txt

```

**门 2：`class NMXAccel ≥ 1`。** 拿不到 → 停手（此刻仍在干净态，屏幕正常）。

### 3.2 进 S3

```bash
( sudo log stream --predicate 'process == "WindowServer" OR eventMessage CONTAINS "XEGFX_DISPLAY" OR eventMessage CONTAINS "AGDC" OR eventMessage CONTAINS "IOPresentment" OR eventMessage CONTAINS "M3d:"' > $L/stream.log 2>&1 & )

  ioreg -l -w0 -c XeGfxFramebuffer 2>/dev/null | grep -q '"XeGfxFbRegistered" = Yes' && { echo "FB registered @${i}s"; break; }
  sleep 1

```

**门 3：`XeGfxFbRegistered = Yes`。**（**不要**等"四条 Yes"，那是 `open()` 之后才发布的。）

### 3.3 等 accel 补上 Present

```bash
for i in $(seq 1 30); do
  n=$(sudo ioreg -l -w0 2>/dev/null | grep -c '"XeGfxAccelPresent" = Yes')
  echo "t=${i}s accelPresent=$n"; [ "$n" -ge 1 ] && break; sleep 1
done
```

**门 4：`XeGfxAccelPresent ≥ 1`。** 30 s 没有 → 见 §6.2 补救；仍不行 → §5 停机。

### 3.4 arm AGDC

```bash
for i in $(seq 1 10); do
  sudo sysctl -w debug.xegfx_agdc=1 >/dev/null 2>&1; sleep 1
  s=$(sudo sysctl -n debug.xegfx_agdc 2>/dev/null); echo "arm $i -> $s"; [ "$s" = "1" ] && break
done
sudo sysctl debug.xegfx_agdc_fbmap; sudo sysctl debug.xegfx_agdc_cmds
```

**门 5：`state=1`、`fbmap n=1`。**

### 3.5 重启 WS，60 秒判定

```bash
( sudo log stream --predicate 'process == "WindowServer" OR eventMessage CONTAINS "IOPresentment" OR eventMessage CONTAINS "M3d:"' > $L/stream-ws.log 2>&1 & )
sleep 2
sudo launchctl kickstart -k system/com.apple.WindowServer
sleep 60
ps -o etime=,pid= -p "$(pgrep -x WindowServer)"
sudo log show --last 3m --predicate 'process == "WindowServer"' 2>/dev/null | grep -c "SIGABRT\|__assert_rtn"

ioreg -l -w0 -c XeGfxFramebuffer 2>/dev/null | grep -oE '"(XeGfxFbOpened|XeGfxFbReady|XeGfxFbModeReady|XeGfxFbPresented|XeGfxFbOpenDenied|XeGfxM3dOpenDeniedReason)" = [^,}]+'
grep -E "first present accepted|open\(\) RELEASED|open\(\) denied|present rc|accel service .* found" $L/stream.log $L/stream-ws.log | tail -6

grep -c "transient surface .* not found" $L/stream-ws.log
```

判读：

| 现象 | 结论 |
| --- | --- |
| `open() RELEASED` + `first present accepted` + `accel 0x` 非 0 | **接管完成**，进 §7 判据 |
| `present rc 0x… (accel=yes)` | 加速器在但 present 被拒 —— 更深一层，**停手报 rc** |
| 仍 `accel not published` | accel 没被认到，按 §6.2 处理 |

## 4. 门 1 仍是 `-19`：先分清分支（**零代码**）

```bash
# 4.1 决定性判别：XeGfxGt 在不在
sudo ioreg -l -w0 -c XeGfxResident 2>/dev/null | tr "," "\n" | grep -A14 "XeGfxGt" | tee $L/gt.txt

sudo ioreg -l -w0 -c XeGfxResident 2>/dev/null | tr "," "\n" | grep -A12 "XeGfxPost" | tee $L/post.txt

# 4.3 i915 在 LinuxKPI 层到底绑没绑（旁证）
sudo ioreg -l -w0 2>/dev/null | grep -c "drmn"
sudo log show --last 5m --predicate 'eventMessage CONTAINS "drmn" OR eventMessage CONTAINS "i915"' 2>/dev/null | tail -12 | tee $L/i915.txt
```

判读表：

| 4.1 结果 | 4.2 / 4.3 旁证 | 结论 | 下一步 |
| --- | --- | --- | --- |
| **没有 `XeGfxGt`** | `XeGfxPost.result = 1`（display 通过） | 来源 ①：`xg_drm_attached()` 为 0 | 进 §5 Plan B-1（给该函数加一行诊断） |

> 若 `XeGfxPost` 也没有 → 说明 `gResident` 不存在或 display_check 没跑到，同样**停手报告**。

## 5. Plan B（只有 §4 定性后才做，**每次只做一条**）

### B-1：来源 ① —— 给 `xg_drm_attached()` 加诊断（log-only）

文件 `gpu/xegfx/shim/src/fbsd/xg_pci.c`，在 `xg_drm_attached()` 的循环里加一行：

```c
TAILQ_FOREACH(d, &xg_pci_devices, devlink) {
        printf("xegfx: drm_attached: %s state %d driver %s\n",
               d->nameunit ? d->nameunit : "?", d->state,
               d->driver ? d->driver->name : "-");        /* ← 新增，仅日志 */
        if (d->state == DS_ATTACHED && d->driver != NULL && ...)
```

重编 core → 用 `kmutil create -z` 换 AuxKC（**`-B/-S` 必须绝对路径**）→ **重启**（新入 KC 不能热加载）
→ 单路径推 stage → 看这行输出，确认是状态不符还是 `driver` 为空。

### B-2：来源 ② —— 给 `xg_i915_state()` 加诊断（log-only）

文件 `gpu/xkpi/src/i915/xg_i915_exec.c`，在 `xg_i915_find()` 的循环里加：

```c
while ((pdev = lkpi_pci_get_device(PCI_VENDOR_ID_INTEL, PCI_ANY_ID, pdev)) != NULL) {
        printf("xegfx: i915_find: pdev %p drvdata %p\n", pdev, pdev_to_i915(pdev));  /* ← 新增 */
        if (pdev_to_i915(pdev) != NULL) { ... }
}
```

作用：区分"根本没有 Intel pdev 被枚举到"与"pdev 有但 drvdata 被清空"。

**两条都不许顺手改判定逻辑。** 先拿日志，再决定改什么。

## 6. 补救与停机

### 6.1 §3.3 拿不到 `XeGfxAccelPresent`

```bash
sudo kextunload -b org.watchthelight.XeGfxAccel 2>&1; echo "unload rc=$?"
sleep 2
sudo /usr/bin/kmutil load -b org.watchthelight.XeGfxAccel 2>&1; echo "reload rc=$?"
sleep 5
sudo ioreg -l -w0 2>/dev/null | grep -c '"XeGfxAccelPresent" = Yes'
```

仍为 0 → 立即停机（§6.2）。

### 6.2 停机

1. **屏幕彩噪 / 黑屏 / 冻结 >10 s** → 立即重启，别等 watchdog：

```bash
sudo ioreg -l -w0 > $L/ioreg-final.txt
sudo log show --last 5m --predicate 'process == "WindowServer" OR eventMessage CONTAINS "XEGFX"' > $L/log-final.txt 2>/dev/null
sudo nvram xegfx-disp-phase=%00 xegfx-disp-trial=%00 xegfx-disp-expose=%00 xegfx-disp-fail=%01
sudo rm -f /var/db/xegfx/armed
sudo shutdown -r now
```

2. WS 活不到 60 s 且 crash-loop → 同上。
3. 门 1/2/3/4/5 任一不过 → 清 nvram 门 + `rm -f armed` + `pkill -f "log stream"`，停手报告。
4. `starts` 涨到 `%02` 后，**下一次失败就是最后一次**（`%03` 自动禁用）。

## 8. 铁律

1. `kmutil` 在 `/usr/bin`；`kmutil create` 的 `-B/-S` 必须绝对路径；**绝不** kickstart `kernelmanagerd`。
2. 新入 KC 的 kext 不能热加载（`Code=28`）→ 需要重启。
3. **`xegfx-disp-bootarm` 与手工 `debug.xegfx_stage` 只能二选一**，否则 stages 双跑（A-30 的教训）。
   本关统一用手工，且已 `nvram -d`。
4. `armed` 之后 120 s 内不重启。
5. macOS 没有 `timeout`；远端后台用 `( cmd > out 2>&1 & )`，收尾 `pkill -9 -f <标记>`。
6. WS 活不到 60 s 时 `sample` 计数不算证据；loginwindow 下的计数不可与 1256 比较。
7. 一次一个变量：本关先"清 bootarm"，过了门 1 才动 accel；**不要**同时设 `debug.xegfxaccelfb`、
   不改 `AGDC_FB_CLASS`、不改探针分。
