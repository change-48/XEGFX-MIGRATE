# Gate 7 · A-86 执行提示词：先重建插件源码树，再砍那 1–3ms（40fps → 60fps 的最后一步）

> 局势（A-85 实测）：一帧的全部工作 **16.91ms**（busy 11.22 + wait 5.69），
> 2 个 vblank = **16.67ms** —— **只超 0.24ms**，于是被判给 3 拍（25ms = 40fps）。
> **砍掉 1–3ms 就能掉到 2 拍 = 16.67ms = 60fps。** 这是全项目离 60 最近的一次。
>
> 三个靶子已量到可直接动手（A-85 §4.3）：
> ① 每帧重编着色器 **23.6ms/帧、独占一核**（空闲=0，纯拖动触发）；
> ② 类锁四入口 **3.87ms/帧**；③ 流水深度 peak=1，2.8 次串行 submit **5.3ms/帧**。
>
> **但 A-85 卡在一个工程问题上：A-80 插件的构建树没了**，源码只剩 A-79 态备份，
> 今天一行插件代码都改不了。**所以本关 P0 先修构建链，再谈性能。**
>
> 必读：`G7-A85报告.md`（§2 归因、§4.2 构建树现状、§4.3 三条改法）、`G7-A80报告.md`（P2b 的 15 处改动）。

## 3. P1 · 靶子①：每帧重编着色器（**只做这一条，先把 60 拿到**）

### 3.1 现象与调用链（A-85 §2.1 原文）

```
CA::OGL::MetalContext::dispatch_async_pipeline
 → MetalContext::create_pipeline_state → create_fragment_shader → load_shader_function
 → -[NVMTLLibrary newFunctionWithName:constantValues:error:]
 → nvmtl_translate_with_fc_cached → nvmtl_translate_fc → translate_one_as_written → emit_vulkan_spirv_inner
```
- 拖动中 **23.6ms/帧、独占一核**（线程 9，99.5% busy）；**空闲 0** ⇒ 纯拖动触发；
- 函数名带 `_cached` 却每帧 miss ⇒ **缓存键每帧都不同**。

### 3.2 要查的三件事（读码，不猜）

1. `nvmtl_translate_with_fc_cached` 的 key 由什么组成？（函数名 + constantValues 的哈希？
   还是把 `MTLFunctionConstantValues` 的**对象指针**当键？）
2. `constantValues` 里哪些值**每帧都在变**（层透明度？颜色空间？混合状态？）——
   逐帧打印一次 key 的组成，取两帧对比（这是最快的定位法）；
3. A-63 曾测"命中率 50%"（旧结论），现在拖动场景是否 **0% 命中**？
   加计数：`fc_cache_hit/miss` 每秒一行到 `/private/tmp/nvmtl-fc.log`。

### 3.3 修法（按查到的原因选，最小改动）

| 若原因是 | 修法 |
| --- | --- |
| 键里混进了指针/时间戳/序号 | 换成**内容哈希**（constantValues 的逐个值） |
| constantValues 有浮点抖动（如 0.9999 vs 1.0） | 按 `CT` 语义**量化**（颜色/alpha 量化到 1/256，或按 CA 的 layer 类型归一） |
| 确实是不同 spec 组合（每帧真不一样） | 只缓存**已翻译 IR 的中间表示**（`translate_one_as_written` 的产物），跳过 `emit_vulkan_spirv_inner`；
   或限制缓存条数（LRU 64）并预翻译常见组合 |

**门 P1（本关成功线）**：拖动 p50 **≤16.9ms（≥59fps）**；
`nvmtl-fc.log` 里 miss 率从每帧 1 次降到 **<1/10 帧**；
线程 9 的 busy 从 99.5% 降到 <20%；
画面正常（拖动/截屏/神奇效果）、30 分钟无 panic。

## 4. P2/P3 · 若 P1 拿到 60 就停；没拿到再依次做

**P2 · 类锁（3.87ms/帧）**：把 `nvmtlSubmitAhead` 里的 `nvmtl_vk_submit_begin`（451µs/次）
与 `nvmtl_buffer_sync_in` 移到 `@synchronized` 之外，锁内只做 claim 记账。门：p50 降 ≥2ms。

**P3 · 流水深度（5.3ms/帧）**：`peak in flight = 1` → 让 `nvmtlAdvancePart` 先按 cap 提交完、
再按序收 fence（别每个 part 都 `nvmtl_gsub_finish` 串行等）。门：`peak ≥2`、p50 降 ≥2ms。

**两条都很危险**（锁语义/提交顺序），**各自单独装、单独测、单独回滚**，不许打包。
