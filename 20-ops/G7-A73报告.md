## 3. Part 2 · H1 拷贝点定位（读码结论）

**这棵树里 H1 的"每帧 CPU 拷贝"已经被前人的 `<wtl>` 实现堵掉了**，提示词里"上游 e60f462 改成拷贝"的行为在本树只对**非 surface 的只读缓冲**生效：

| 位置 | 内容 |
| --- | --- |
| 拷贝函数 | `nvmtl_vk_image_write()`（surface-in 失败后）/ `nvmtl_vk_image_read()`（surface-out 失败后），内部 `memcpy` 逐行 |
| 调用点 | `NVMTLObjects.m` → `-nvmtlSurfaceIn`（第 1318 行）/ `-nvmtlSurfaceOutDirtied:`（第 1391 行） |
| 触发条件 | ① `nvmtl_vk_surface_host_import()` 返回失败：`nvmtl_range_writable()` 判定区间非全可写（`mach_vm_region` 的 `VM_PROT_WRITE` 缺失）、或指针/长度未按 `g_host_align` 对齐、或无 importable memory type、或 `vkCreateBuffer/vkAllocateMemory/vkBindBufferMemory` 拒绝；② 行距 `%32 != 0`；③ 多 plane；④ 图像大于 surface |
| 本树已有的正确路径 | `NVMTLDevice.m:1010` / `NVMTLObjects.m:1272` 的 `<wtl>` 分支：把 image **直接建成 surface 自己页面的别名**（`_hostImg=1`），此后 `nvmtlSurfaceIn` 直接返回、`nvmtlSurfaceOut` 只动 seed —— 既没有每帧拷贝，也没有每帧 GPU 搬运 |
| 实测 | `in_copy_n=0`、`out_copy_n=0`、`host_in=0`、`host_out=0`（host_in/out 为 0 说明连"GPU 从导入页搬"都没发生，全走别名）；`imp_ok=35–43/s`、`imp_bad=0` |

**怎么读：**
- **每次提交只等 4.5ms，但每秒提交 62 次、一帧只出 18 张** → 一帧里有 **3.4 次提交、串行等待**，加起来 15.4ms。
- `done_p50` 只有 1.9–2.5ms（GPU 端单次提交不长），但**均值 4.5ms ≫ p50**：等待分布有长尾（有些提交等 15–17ms），长尾才是 15.4ms 的主要来源。
- `sub_p50` 1.5ms × 3.4 次 = 5.1ms/帧，与 sample 里 libvulkan 提交 6.65ms/帧同量级 → **H2 的提交侧成本确认存在，但小于 H3。**

## 5. 裁决表（墙 B 落格）

| 裁决条件 | 实测 | 是否成立 |
| --- | --- | --- |
| `import_copy` 每帧 ≥ 数 MB 或 ≥ 5ms → H1 | **0 字节 / 0 ms** | ❌ **不成立** |
| `wait_us` 每帧 > 10ms → H3 | **15.3–15.5 ms/帧**（独立方法 sample 测得 17.7ms/帧） | ✅ **成立，最大单块** |
| 两者都小、CA/提交占 30ms+ → H2 | CA 4.9 + 提交 6.7 = **11.6 ms/帧**（未到 30ms） | ⚠️ 次要 |
| sample 里 GPU 相关但 CPU 全小 → H4 | `done_p50` 仅 1.9ms/次，但长尾到 17ms；**无 `xegfx_eb` oid，无法直读 execbuffer** | ⚠️ 无法裁决，长尾指向"偶发 GPU 忙" |

**结论（混合，每项有毫秒支撑）：**

| 项 | ms/帧 | 归属 |
| --- | --- | --- |
| accel 事务（等 vblank 4.9 + 拷贝 3.75 + 杂项） | 9.4 | 墙 A 的固有成本（A-69 拷贝路径） |
| **fence 等待（3.4 次提交 × 平均 4.5ms，长尾）** | **15.4** | **H3：WS 串行等 GPU** |
| libvulkan 提交/描述符 CPU | 6.7 | H2 |
| QuartzCore 图层绘制 | 4.9 | H2 |
| NVMTL 翻译层自身 | 2.0 | H2 |
| objc/malloc/CF/bzero/杂项 | ~5.6 | 背景 |
| runloop（无活可干等定时器） | 5.7 | 帧节奏 |
| 其它 | ~5 | — |
| **合计** | **≈55** | 与 55ms/帧（18.2fps）自洽 |

**读法：42.8ms 的"WS 两次事务之间"= 15.4ms 等 GPU + 23.5ms 自己的 CPU + 6ms 帧节奏空转。**
H3 与 H2 都是真身，H3 单独一块更大，且它是**唯一不需要猜的**——调用链已经指到 `commitAndWaitUntilSubmitted`。

## 7. 偏差与失败记录

1. **sample 用 15 秒而不是 25 秒**：`sample` 每毫秒抓栈本身会加重 WS 负担，15 秒已得 7506 样本（足够做 0.2% 粒度的判定），避免把被测系统推到失真工况。
2. **提示词的 H1 假设在本树已不适用**：本树 `NVMTLDevice.m` / `NVMTLObjects.m` 已含 `<wtl>` 的 surface host-import（即提示词要"下一阶段移植的 0006"内容）——**不是猜测，是读码 + 运行时计数双重确认**（`imp_ok` 有值、`imp_bad=0`、四个拷贝计数恒 0）。因此本关的 H1 判决是"已经被前人修掉了"，而不是"没测到"。
3. **`debug.xegfx_gt` / `debug.xegfx_eb` 不存在**：只有 `debug.xegfx_spin`。H4 因此没有直读证据，只能用插件侧 `done_p50` 与长尾间接判断；报告里不据此下 H4 结论。
4. **`ws-prof.log` 覆盖窗口比 25 秒长**（40/36/39 行）：日志在 fps-probe 启动前就被清空、在轮末 sleep 1 后才抓取，因此包含了几秒准备时间。所有每帧数字按 `合计/该轮帧数` 归一，三轮偏差 <5%，不影响判定。
5. **fps 略高于 A-72 基线（19/19/18 vs 18/18/17）**：加的是每秒一次 `atomic` 读取 + 每秒一次写文件，理论上无净效应；本次差值在工况波动范围内，不做"插桩变快"的断言。
6. **`imp_ok` 是累计量**（未做每秒交换），报告中用的是首末行差值；日志里同名字段为进程启动以来的累计值，读 log 时不要逐行相加。
7. **装机过程中的两次中断**：装插件后的 `kickstart -k` 使使用者被注销一次（已事先征得同意），`iop_ok` 自行恢复，无新 panic（最近一份仍是 `Kernel-2026-11-02-131730.panic`）。
