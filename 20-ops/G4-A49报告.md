## 4. 失败现场

### 4.1 三次开机，同一条曲线

```
19:02 boot  boot_steps=123 → 19:05:05 bootArm armed but no frames yet -- restarting WindowServer once → 整机失联（用户重启）
19:12 boot  boot_steps=123 → 19:14:22 同上 → 整机失联（用户重启）
19:16 boot  卡在 bootArm is driving（boot 序列没跑完）→ boot=3 失败 → 屏幕停在 CPU 渲染 3120x2080
```

前两次与改前的 18:28 开机形成干净对照：改前同一台机器 `boot_steps=123` → `sample 14: iop_ok 0 -> 8` → `OK: frames are reaching the panel`；改后 `boot_steps=123` → 无帧 → WS 重启 → 死。

箭头的方向是明确的：**闸门确实放开了（`boot_steps` 的 bit64 = flip 走到了 123，说明 arm 路径被执行），但 arm 之后引擎一帧都不出**，`iop_xe_flips` 仍为 0（不是 flip 失败，是没有帧来驱动 flip）。

### 4.2 19:16 那次是另一个原因（附带发现，值得单独立项）

第三次开机 `boot=3 / boot_steps=0`，内核查到：

```
kernel: (XeGfxIntelFB) XeGfxIntelFB: boot guard tripped (two starts without WindowServer): declining
kernel: (XeGfxAccel)  NMXAccel: boot-armed: FAILED -- no XeGfx framebuffer with an open start gate
                      after 30000 ms (published 0x0): the display stack never came up this boot
                      (steps 0x0, published 0x0, registered 0x0, piped 0x0, igpu 1, fb 0, iop 0, flip 0/defer 0)
kernel: (XeGfxDisplay) XEGFX_DISPLAY: provider has no fb-index
```

`XeGfxIntelFB` 的自带护栏（`intelfb.cpp:38`，NVRAM `xeintelfb-starts`，2 次"启动后 120 s 内没等到 WindowServer"就永久 decline）在前两次卡死断电后计数到 2，于是**拒绝 probe**；没有 framebuffer → `XeGfxDisplay` 无 fb-index → accel 的 bootArm 等 30 s 拿不到 head → 失败 → 只能退回 IntelFB/CPU 渲染（用户看到的 `3120x2080 CPU 渲染`）。

**解法（已验证）**：`sudo nvram xeintelfb-starts=%00`（一并清 `nmintelfb-starts=%00`）后重启，开机日志立刻变成

```
XeGfxIntelFB: boot guard: start 1 without WindowServer so far (off after 2)
… 120 s 后 …
XeGfxIntelFB: boot guard cleared: still up 120 s after start
boot_steps=123 → WindowServer back → sample 1: iop_ok 3 -> 10 → OK: frames are reaching the panel
```

⇒ **以后凡是"连续崩两次后开机变 CPU 渲染"的现象，先查 `nvram -p | grep intelfb`，不要去动 kext。**

## 7. 结论与下一步的判断依据（只给事实，不给改法）

事实清单：

1. `pitchArmable` 放宽后，arm 路径**确实被进入**（`boot_steps=123` 含 bit64 flip），所以 A-47 的 stride 代码这次是**活代码**。
2. 但 `iop_xe_flips` 仍然是 0，`iop_xe_arm_last_us` 也是 0 —— 说明**连 arm 内部那次计入都没跑到**，即帧根本没走到 arm 的调用点。
3. 同时 `iop_ok` 不再增长 → performTransaction 走了 defer 分支并 `return kIOReturnSuccess`（帧被"认领"），但后续既没有 flip 也没有拷贝，面板永远停在前一帧。
4. 于是 WindowServer 在"提交成功但画面不动"的状态下卡在等待里 → 整机失联。

⇒ 这一关的假设（"放开闸门就能让 A-47 的 stride 生效"）被证伪。真正缺的是 arm 到翻页之间那一环，而不是闸门。要往前走，得先在**不冻屏**的前提下观察 arm 到底走到哪一步（例如只放开闸门但不 `return`、或让 defer 在失败时退回拷贝），这属于改判据以外的工程，需另行设计并单独立项。
