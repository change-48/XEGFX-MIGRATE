# Gate 4 · A-47 执行报告：stride 已随 flip 一起写，但 flip 仍然一次都没被调用

## 1. 一行结论

**改动已按 §2 落位、构建、装机、跑通（`boot_steps=123`、`boot-armed: 6/6 READY`、画面正常 3120×2080），但 `iop_xe_flips = 0`、`iop_xe_defer_queued = 0`、`iop_xe_arm_last_us = 0` —— `nvAccelXeFlipArm` 一次都没有被进入过，所以新写的 stride 代码一次也没有执行；`copy_sum_us` 仍在长（+6 401 027 µs），3277→3858 帧全部仍走 CPU 拷贝（4.4 ms/帧）。**

判定：判据 **1–5、8、10 通过**，判据 **6、7、9 不通过** → 本关**未达成**。

未达成原因不是 stride 值写错，而是**位置鸡生蛋**：`q.pitch == P` 这道闸门挡在 `nvAccelXeFlipArm()` 之前，而 stride 的写又只发生在 arm 内部 —— 第一次比较时 `q.pitch` 仍是行距寄存器里的 12480（`stride=0xc3`），闸门不通过 → 不进 arm → 不写 stride → `q.pitch` 永远是 12480。本次改动在逻辑上**不可能被触发**，因此也对现场零风险（`iop_xe_arm_last_us=0` 即证据），**未回滚、未重启**。

## 4. 根因：闸门在 arm 之前，stride 写在 arm 之内

`performTransaction()`（`nvrm-accel.cpp:2491-2510`）：

```c
if (gIopXeDefer && gIopXeFlip && s && head == 4 && nvXePlaneWriteAllowed(fb)) {
    const unsigned W=…, H=…, P = (unsigned)s->getBytesPerRow();     /* 12544 */
    if (W && H && … && P >= 4*W …) {
        const IOReturn qr = a->askFramebufferForScanout(&q, fb);
        if (qr == kIOReturnSuccess && q.kva && q.pitch == P && q.height && …) {
            nvAccelXeFlipDeferQueue(this, s, W, H, P);   /* ← 只有到这里才会 arm */
```

- `q.pitch` 来自 `xgGetScanoutInfo` → `NMIntelFB::adoptFirmwareMode()`：
  `fRowBytes = stride * 64`（`kexts/NMIntelFB/intelfb.cpp:331`），当前 `stride=0xc3` ⇒ **q.pitch = 12480**。
- `P` = 合成器 IOSurface 行距 = **12544**（K6 行确认）。
- 两者不等 → `if` 不成立 → **不入队、不 arm** → stride 永不写 → `q.pitch` 永远是 12480。闭环自锁。

`nvAccelXeFlipArm()` 的三个调用点（`:1813` `:1819` `:1874`）全部位于 defer worker 内部，都在 `defer_queued` 之后；`nvAccelXeFlip()` 同步路径（`:2568`）也有同样形式的 `pitch == q.pitch` 前置条件。⇒ **arm 内部写 stride，在数学上不可能改变进入 arm 的条件。**

这也解释了判据 6/7 的全零：`iop_xe_arm_last_us = 0` 是"从未执行"，不是"执行了但不生效"。

> 事实层面（不含改动方案）：要让 `q.pitch` 变成 12544，stride 必须在**闸门被求值之前**就已经是 196；闸门之后写等于没写。
