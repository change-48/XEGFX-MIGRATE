# Gate 4 · A-34 执行提示词：补上 `IOAccelDisplayPipeCapabilities`（第二个 plist 键，零重编）

> 目标：让 IOP 认为这个加速器**支持 display pipe**，从而真的去调 `newDisplayPipe()`，
> 建起 `IOAccelDisplayPipe`，让 CA 走硬件合成，消掉 `transient surface not found` → SIGABRT。
>
> **不重编、不改源码。** 只加一个键（在 A-33 已加的 `IOCFPlugInTypes` 旁边）+ 重签 + 重建 KC + 一次重启。

---

## 0. 为什么是这一个键（证据在 A-33 自己的报告里，只是没连上）

### 0.1 A-33 已经证明"键写对了、也发布了"

```
NMXAccel 节点：
  "IOClass" = "NMXAccel"
  "IOAccelRevision" = 2
  "IOCFPlugInTypes" = {"ACCF0000-0000-0000-0000-000a2789904e"="IOAccelerator2D.plugin"}   ← 已在
```

**但结果一字未变**：`Unable to create IOAccelDisplayPipe` 9/9、`0x2002` 9/9、
`newDisplayPipe` **0 次**、`initFramebufferResource` **0 次**。

→ 说明 `IOCFPlugInTypes` 不是唯一缺口，而且 **`newDisplayPipe` 从没被调用** 这件事才是关键：
IOP 在"决定要不要建 pipe"这一步就已经否了，根本没走到插件工厂。

### 0.2 缺的键：Apple 原文里就紧挨着 `IOCFPlugInTypes`

A-33 §1 自己贴出的 Apple 原文（`AppleIntelICLGraphics.kext`）：

```xml
<key>IOAccelDisplayPipeCapabilities</key>
<dict>
    <key>DisplayPipeSupported</key><true/>
    <key>TransactionsSupported</key><true/>
</dict>
<key>IOCFPlugInTypes</key>
<dict>
    <key>ACCF0000-0000-0000-0000-000a2789904e</key>
    <string>IOAccelerator2D.plugin</string>
</dict>
```

**`IOAccelDisplayPipeCapabilities` 就在 `IOCFPlugInTypes` 正上方**，A-33 只抄了下面那个。

### 0.3 我们和 Apple 的 personality 差在哪（已逐键对比）

| 键 | Apple ICL / KBL | 我们 XeGfxAccel |
| --- | --- | --- |
| `IOAccelDisplayPipeCapabilities` | ✅ `{DisplayPipeSupported:true, TransactionsSupported:true}` | ❌ **缺** |
| `IOCFPlugInTypes` | ✅ | ✅（A-33 已加） |
| `IOClass` / `IOMatchCategory` / `IOProviderClass` / `IOPCIClassMatch` / `IOPCIPrimaryMatch` / `IOProbeScore` | ✅ | ✅ |
| `MetalPluginName` / `MetalPluginClassName` | ✅ | ✅ |
| `IOGLBundleName` / `IODVDBundleName` / `IOGVABGRAEnc` / `IOGVA*` | ✅ | ❌ 缺（**本关不管**，那是 Metal/GL/编解码，与 IOP 无关） |
| `GPURawCounter*` / `Debug` / `Development` / `IOSourceVersion` / `IOVARendererID` | ✅ | ❌ 缺（**本关不管**） |

→ **本关唯一变量：加 `IOAccelDisplayPipeCapabilities`。** 其余缺键一律不动（一次一个变量）。

### 0.4 为什么它能让 `newDisplayPipe` 被调用

IOP 的流程是「先问加速器：你支持 display pipe 吗？」→ 支持才建 `IOAccelDisplayPipeUserClient2`
（这一步**已经成功**，A-33 日志里有）→ 再取用户态接口（`IOCFPlugInTypes`）→ 再让家族调
`newDisplayPipe()` 生成 pipe 对象（**从未发生**）。

也就是说：**能力声明缺失 → IOP 认为不该建 → 提前 return，插件工厂与 `newDisplayPipe` 都不会被用到。**
这也解释了为什么 A-33 补了工厂键却毫无变化。


## 5. 判决点

```bash
sudo launchctl kickstart -k system/com.apple.WindowServer
sleep 20

echo "=== A) 失败链还在不在（0 = 修好）==="
grep -c "Unable to create IOAccelDisplayPipe" $L/stream.log
grep -c "Interface creation error" $L/stream.log

echo "=== B) 三个"进去了"的标志 ==="
grep -E "newDisplayPipe|initFramebufferResource|IOAccelerator2D" $L/stream.log | tail -8

echo "=== C) CoreDisplay 侧 ==="
grep -E "display pipe|IOFB service|System set to use IOP" $L/stream.log | tail -6

echo "=== D) 断言前那句 ==="
grep -c "transient surface .* not found" $L/stream.log

echo "=== E) WS ==="
ps -o etime=,pid= -p "$(pgrep -x WindowServer)"
sudo log show --last 3m --predicate 'process == "WindowServer"' 2>/dev/null | grep -c "SIGABRT"
```

判读：

| 现象 | 结论 | 动作 |
| --- | --- | --- |
| `A=0` 且出现 `newDisplayPipe` | **IOP 真的开始建 pipe 了** | 看 `initFramebufferResource` 与 WS 存活 |
| `A=0`、出现 `newDisplayPipe`、但 `initFramebufferResource` 里报 `scanout gate CLOSED` 或其他拒绝 | pipe 建了但资源初始化被拒 | 停手，贴那行原文（这是**新的一层**，比现在深） |
| `A` 仍非 0 | 能力键没生效或还有别的判定 | 停手，贴 `ioreg-caps.txt` 与 `0x2002` 原文 |
| `newDisplayPipe` 出现且 `initFramebufferResource` 成功、WS 活过 60 s | **成功** | 进 §6 |

## 8. 铁律

1. **S3 只走 bootarm**（`bootarm=%01` + `phase=%02` + `kmutil load core`），**绝不**写 `debug.xegfx_stage`
   （双跑 → `stage4 -19`）。
2. plist 键必须写在 **`IOKitPersonalities:XeGfxAccel` 内部**（A-33 已证：写 kext 顶层不会成为服务属性）。
3. 改 plist 必重签（adhoc）；`kmutil create` 的 `-B/-S` 必须绝对路径。
4. `armed` 后 120 s 内不重启；WS 出现第 2 实例立即停（别等 watchdog）。
5. 一次一个变量：**只加这一个键**。`IOGLBundleName`/`IODVDBundleName`/`IOGVA*`/`GPURawCounter*` 等
   一律不动（与 IOP 无关）。
6. `ReportCrash` 会因 `Log limit exceeded` 丢 `.ips` → 断言原文只能靠 `log stream` 现场抓。
