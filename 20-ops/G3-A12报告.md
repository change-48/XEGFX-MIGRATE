## 3. 三条推翻/新增的事实（会改后续 gate 的假设）

### 3.1 `fill` / `fillat` / `peek` 的映射根本没映射到那个物理页（A-11 §3.2 的真实原因）

单点判据：`fillat 0x01000000 1`（写 3120 图案）→ `peek 0x01000000` 读到 `0xffffffff`（我们的白角），
但同一时刻把 `SURF` 指到 `0x01000000`，屏幕**still 是原来那张 HONOR 开机图**。
→ `IOMemoryDescriptor::withPhysicalAddress()` + `createMappingInTask(kernel_task, …)` 这条路径**读写都不是请求的那个物理页**（自读自写一致，所以 A-11 看到"写不进 DRAM"）。
**A-11 的结论方向对，归因错**：不是"临时映射写不回"，是"这条映射压根不是那块内存"。

### 3.2 引擎可读物理区间 ≈ **< 256MB**

128MB 有内容、256MB 全黑；所有 ≥546MB 的缓冲全黑。与 BAR2 孔径 256MB 同值。
**推论：任何 ≥256MB 的缓冲都不可能上屏，无论写入路径多正确。**

### 3.3 唯一可用的像素写入路径：**BAR2 / GTT 孔径（MMIO）**

```
xenative-ctl mapfast <idx> <count> <phys>   # 先把 PTE 指好
xenative-ctl apfill  <idx> [0|1]            # 再经 BAR2 + idx*4096 直接写像素
```
`apfill` 写完后 MMIO 回读 `[0]=0xffffffff mid=0xff0000ff`，`reg surf` 立刻出图 —— 这是**本次唯一一次让图案真正出现在屏幕上**的路径。
（0.9–0.13 走的"内核缓冲 + VA 填充"即使 PTE 全对，因缓冲在 546MB 以上，引擎读不到，必然黑屏。）

## 4. S1 判定（成功）

```
xenative-ctl mapfast 0x1000 6338 0x01000000   # mapped 0x1000 .. 0x28c1  bad 0
xenative-ctl apfill  0x1000 0                 # 1080 宽图案，经孔径写入 16MB
xenative-ctl reg surf 0x01000000              # reg = 0x01000000  SURFLIVE = 0x01000000
```
几何一个都没动（`SIZE 0x0437077F / PIPESRC 0x077F0437 / STRIDE 120 / PS_CTRL 0x80000200 / PLANE_CTL 0x84000008`）。

**肉眼观察（用户描述，照片待补）**：左半红、右半蓝、蓝区内一条绿色短横杠、屏幕下方一条贯穿的灰带、四角白块被推到边缘 ——
即"我们的 1920×1080 图案被面板放大到 3120×2080"。1px 棋盘在放大后糊成均匀灰带，符合预期。

> 注：同一缓冲用 3120 宽图案（`apfill 0x1000 1`）时，1080 几何下呈**紫色竖向条纹**（红蓝两半被 7680B 行距切碎后交错），进一步证明像素确实来自我们写的那块内存。

## 5. S2 为什么失败（不是写入问题）

```
reg stride 195   -> 回读 0x00000040（两次都一样）
reg size 0x081F0C2F -> 回读 0x081F082C
reg pipesrc 0x0C2F081F -> 回读 0x0C2F081C
reg ps 0x00000200 -> 回读 0x00000000，同时 SURFLIVE 掉到 0
1s 后 status：全部回到 1080p 原值，SURF=0
```

判读：**transcoder 时序仍是 1080p**（`TRANS_HTOTAL_A` / `TRANS_HDISPLAY` / DDI 都没动，它们由 `IGPUConsoleRange` 在开机时按 1920×1080 设好）。
一个 3120 宽的平面往 1920 宽的 pipe 里送 → 行缓冲欠载/失锁 → 硬件进入异常态（回读出现被截断的 `0x40`/`0x082C`），
随后 `IGPUConsoleRange` 的 1080p 状态被重新落回，`SURF` 归零。

**所以 S2 的前提不是修写入，而是先做一次 3120×2080 的 modeset**（trans 时序 + DDI + 面板时序），这超出 A-12 "只动 4 个平面寄存器" 的边界。

## 8. 一行结论

`A-12：S1 成功 —— 经 BAR2 孔径写入的图案在 1080p 几何下真正上屏（被面板放大）；S2 未达成 —— 3120 宽平面送进 1080p pipe 必然失锁，需要完整 modeset；另发现引擎只能读 <256MB 物理内存（= 孔径大小），macOS 不提供该区间的分配。`

### 给 A-13 的三条建议

1. **像素写入固定走孔径**（`apfill`），彻底放弃 `withPhysicalAddress` 那一族（写、读都不可信）。
2. **缓冲必须落在 < 256MB**：现有三条分配 API 都办不到，需要显式方案（早期保留 / 用 `IGPUConsoleRange` 已占的 8–16MB 之后的固件空洞并纳入管理 / 或在 boot 阶段占位）。
3. **S2 改成 modeset**：先按 3120×2080 重算 `TRANS_HTOTAL_A / TRANS_HBLANK / TRANS_HSYNC / TRANS_VTOTAL / TRANS_VBLANK / TRANS_VSYNC / TRANS_DDI_FUNC_CTL` 与 `PIPE_CONF`，再写平面 4 寄存器；否则任何 3120 尝试都会把管道打回 1080p。
