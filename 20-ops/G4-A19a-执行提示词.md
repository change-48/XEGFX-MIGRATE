# Gate 4 · A-19a 执行提示词（零重编：把帧缓冲映射挪出"被抢窗口"）

> 用法：把本文件全文作为一条消息发给执行会话。执行会话不需要任何前置上下文。
> **一次重启、零新代码、零重编。** 它要么直接解决 Gate 4，要么明确告诉我们"只能重编"。

---

## 0. 为什么先试这个

A-18b 已证实：花屏 = **帧缓冲那 6656 条 PTE 被 i915 的 GGTT 分配器抢走**。
把 PTE 按原值写回，屏幕当场恢复；再跑一次探针，又被抢（断点 1783/1800，可重复）。

根因：`xg_i915_reserve_bootfb(0xFE600000, 25958400)` 返回 `-28 ENOSPC`
（因为 `0xFE600000 + 26MB = 0xFFEC1800` 跨过了 `GUC_GGTT_TOP = 0xFEE00000`），
**整段一条都没登记** → 分配器把那 8 MB（`0xFE600000..0xFEE00000`）当空闲，
且它是**从 GuC 栅栏往下分**，第一块就落在 `0xFECF7000` 附近 —— 正好压在我们的帧缓冲上。

**思路**：帧缓冲在 GGTT 里的位置是我们自己选的（`PLANE_SURF` 想指哪就指哪），
它指向的物理内存（`0x800000`）不变，macOS 也照旧写那块物理内存。
所以——**把 SURF 挪到分配器不去的低地址**，PTE 也建在那里，冲突就绕开了，core 一个字节都不用改。

**这一步同时是对根因的第二个独立验证**：如果挪位置后不再被抢，说明分配器确实只在那一段活动。

---

## 1. 铁律

- **不改任何文件**：不重编 core、不改 kext、不动 OpenCore / boot-args / 几何自愈脚本。
- 只允许改两个运行时状态：GGTT 的一段 PTE、`PLANE_SURF` 寄存器。**两者都在重启后自动失效**。
- 写 PTE **一律用 `mapfast`**（一次 ioctl、内核内循环、自带 `wbinvd` + `GFX_FLSH_CNTL` + 逐条回读校验）。
  `map` 是用户态循环，没有 `first/last/bad`，不要用。
- 每次重启前 `touch /var/db/xegfx/armed`；重启后核对 AuxKC 含 `IGPUConsoleRange`。
- **macOS 没有 `timeout`**：探针用 `( ~/xegfx-probes/mtlprobe > out 2>&1 & )`。
- 屏幕一旦异常，先把结论记下来就重启，不要停在花屏状态折腾。
- 不许开 `debug.xegfxaccelfb` / `debug.xegfxaccel_iop`。

---

## 2. 目标位置（先算清楚再动手）

当前帧缓冲：GGTT `0xFE600000` 起 **6656 页**，物理 `0x800000` 起，逐页 +0x1000，flags `0x3`。

被抢窗口：`0xFE600000 .. 0xFEE00000`（实测断点在 `0xFECF7000` 附近）。

**新位置选 `0xFD000000`**（索引 `0xFD000`）：
```
0xFD000000 + 6656*4096 = 0xFD000000 + 0x1A00000 = 0xFE A00000
```
即新范围 `0xFD000000 .. 0xFEA00000`，**上界 0xFEA00000 仍低于实测断点 0xFECF7000**（余约 3.0 MB：0xFECF7000 − 0xFEA00000 = 0x2F7000），
也完全在 `GUC_GGTT_TOP` 之下。

> 注意：`0xFD000000` 这段在表里现在是**跨开机残留垃圾**（全表 `nonzero=全部`、`present≈50%`），
> 我们用 `mapfast` 整段覆盖成正确映射即可，不需要先清零。

物理结尾自检（6656 页）：`0x800000 + 6655*0x1000 = 0x21FF000`，`|0x3` → **`0x21FF003`**。

## 3. 步骤

### 3.1 复现（确认起点状态）

```bash
mkdir -p ~/xegfx-log/A-19a
sudo kmutil load -b org.watchthelight.XeGfx
sudo sysctl -w debug.xegfx_wdog=60
sudo sysctl -w debug.xegfx_stage=7
sleep 25
sudo sysctl -b debug.xegfx_results | od -A n -t d4 | tee ~/xegfx-log/A-19a/results.txt   # 期望 0 1 1 1 -28 1 1 1
sudo /usr/local/bin/xenative-ctl scan 7000 | tee ~/xegfx-log/A-19a/scan-oldbase.txt
# 期望（按 A-18b 的结论）：live_run_pages 已经掉到 ~1800（此时探针还没跑）
```

### 3.2 把帧缓冲搬到 `0xFD000000`

```bash
sudo /usr/local/bin/xenative-ctl mapfast 0xFD000 6656 0x800000 | tee ~/xegfx-log/A-19a/mapfast.txt
# 期望：first 0x800003  last 0x21ff003  bad 0

sudo /usr/local/bin/xenative-ctl reg surf 0xFD000000 | tee -a ~/xegfx-log/A-19a/mapfast.txt
sleep 1
sudo /usr/local/bin/xenative-ctl latch | tee -a ~/xegfx-log/A-19a/mapfast.txt
```
**看屏幕：应仍是完整桌面**（同一块物理内存，只是换了 GGTT 入口）。
若此时黑屏 / 花屏 → 位置选错了 → 立刻 `sudo /usr/local/bin/xenative-ctl reg surf 0xFE600000` + `latch` 退回，报告。

### 3.3 关键验证：跑两次探针，看还会不会被抢

```bash
sudo /usr/local/bin/xenative-ctl scan 7000 | tee ~/xegfx-log/A-19a/scan-newbase-1.txt
# 记 live_run_pages（应是 6656，且 liveIdx 变了）

( ~/xegfx-probes/mtlprobe > ~/xegfx-log/A-19a/mtl1.txt 2>&1 & ) ; sleep 30
tail -3 ~/xegfx-log/A-19a/mtl1.txt
sudo /usr/local/bin/xenative-ctl scan 7000 | tee ~/xegfx-log/A-19a/scan-newbase-2.txt
# ★ 关键读数：live_run_pages 是否仍为 6656

( ~/xegfx-probes/mtlprobe > ~/xegfx-log/A-19a/mtl2.txt 2>&1 & ) ; sleep 30
sudo /usr/local/bin/xenative-ctl scan 7000 | tee ~/xegfx-log/A-19a/scan-newbase-3.txt
```
**同时抬头看屏幕**：两次探针跑完后，画面是否仍然完整。

### 3.4 若稳定，顺手把 Gate 4 的四条一次量完

```bash
sudo vmmap "$(pgrep -x WindowServer)" 2>/dev/null | grep -ci nvmtl | tee ~/xegfx-log/A-19a/vmmap.txt
sudo powermetrics --samplers tasks -n 1 2>/dev/null | grep -A3 -i windowserver | tee ~/xegfx-log/A-19a/power.txt
system_profiler SPDisplaysDataType | grep -iE "Metal|Resolution|UI Looks" | tee ~/xegfx-log/A-19a/sp.txt
```

### 3.5 收尾

```bash
sudo /usr/local/bin/xenative-ctl restore     # 寄存器回原值
sudo reboot                                   # GGTT 改动随重启消失
```
重启后复核：`scan 7000` 回到 `live_run_pages 6656` / `live_phys 0x800000`；屏幕 3120×2080；零新 panic。

## 4. 判读

| 结果 | 含义 | 下一步 |
| --- | --- | --- |
| 3.2 后桌面正常，**两次探针后 `live_run_pages` 仍 6656、屏幕不花** | ✅ **零重编解决**。分配器确实只在 GuC 栅栏下方那 8 MB 活动 | 把这个偏移固化进开机自愈脚本（SURF=`0xFD000000` + 建 PTE），再验一轮开机自动恢复 |
| 3.2 后桌面正常，但探针后又断（`live_run_pages` 变小） | 搬迁有效但分配器会往下长到 `0xFD…` | 换位置再试一次（如 `0xF8000000`），**最多两次** |
| 3.2 后直接黑屏/花屏 | `0xFD000000` 这段本身不可用（或落了别的东西） | 立刻退回 `0xFE600000`，报告；不要再猜位置 |
| 两次换位置都被抢 | 搬迁不管用，分配器会吃掉整片低地址 | 停手，转 **A-19b：重编 core**（拆分 reserve） |

## 验收锚点（主 agent 独立跑）

1. `~/xegfx-log/A-19a/scan-oldbase.txt` → `live_run_pages` 明显小于 6656（复现）。
2. `mapfast.txt` → `first 0x800003`、`last 0x21ff003`、`bad 0`（**不是 `0x1a00003`**）。
3. `scan-newbase-2/3.txt` → `live_run_pages` 是否保持 6656。
4. 重启后 `scan` → `live_run_pages 6656` / `live_phys 0x800000`（证明本轮改动未留痕）。
5. 屏幕 3120×2080、零新 panic、`fbgeom.log` 有本次开机记录。
