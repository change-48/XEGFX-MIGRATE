# Gate 3 · A-11 执行提示词（诊断型：PTE 写入为什么对显示无效）

> 用法：把本文件全文作为一条消息发给执行会话。执行会话不需要任何前置上下文。
> **本关不追求点亮屏幕。产出是"一句话结论 + 证据"。全部实验在运行期完成，不需要重启。**

## 0. 一句话

A-10 已经把五个显示寄存器全部写对并锁存（SURFLIVE 跟过去、画面跟着 SURF 平移），
但**写 GGTT 页表对画面零影响**。
本关只回答一个问题：**我们写进页表的字节，到底有没有到达显示引擎读到的那块内存？**

我的判断：**大概率没到 —— 被 CPU 缓存挡住了。** 用一个指令就能证伪或证实。

## 2. 为什么我判断是"写被缓存挡住"（推理链，你可以直接检验它）

A-10 的四个隔离实验合在一起只留下一路解释：

| 实验 | 观察 | 排除了什么 |
| --- | --- | --- |
| T4：`SURF 0xFE600000 → 0xFE700000` | 画面**平移**，内容仍是桌面 | 引擎**会**在 SURF 变化时重新走表；且表里 `0xFE700` 那条确实是 `0x900003` |
| T1：往**新索引** `0x1000` 写已知有效 PTE `0x800003`，`SURF=0x01000000` | **全黑** | 若写入到达内存，引擎重新走表必然读到 `0x800003` → 应显示桌面内容，不该黑 |
| T2：改 `PTE[liveIdx]` 指向我们的缓冲，SURF 不动 | 桌面**完全不变** | 引擎对未变 SURF 不再走表（缓存翻译）—— 这条本身不构成证据 |
| T5：改 `PTE[0xFE800]`，`SURF=0xFE800000` | 桌面**平移**但内容仍是桌面 | 同上：用到的仍是表里**原有**那条 `0xA00003` |

> **T4 证明了"引擎会在新地址走表"，T1 证明了"走表也读不到我们写的值"。**
> 两者同时成立，只剩一种解释：**我们写的那 8 字节没有真正落到那段物理内存里**，
> 而我们自己回读能读到 —— 因为我们读到的是自己 CPU 缓存里的副本。

同一个解释还能顺带说明 T6：`fillat 0x800000`（往活帧缓冲写 3120 图案）本该立刻毁掉桌面，
结果只是"黑/花屏" —— 如果填充没到 DRAM，画面就只会是"旧桌面按新 stride 重新解释"的样子。

**还有一条旁证**：`scan` 显示 `nonzero_entries = 1048576`（全表非零）、`present ≈ 50%`、
`[liveIdx-1] = 0x83431f047526a2cb`（明显是垃圾）。这符合"表所在内存是老数据、只有固件用过的那段被正确写过"。

## 3. 铁律

- **本关不改 3120 尺寸、不碰 PS_CTRL、不碰 PIPESRC/SIZE/STRIDE。** 这是纯诊断关，一次一个变量。
- 所有实验结束后必须 `xenative-ctl restore`，并确认 5 个寄存器回到第 1 节的原值。
- 任何会改变 `PTE[liveIdx..liveIdx+6655]` 的实验，**必须先备份原值**（至少备份你要动的那几条），结束后还原。
- 不许改 boot-args / EFI / GPUBundles；不许装加速器；不许 `softwareupdate`。
- 重建 AuxKC 只用 `kmutil install --volume-root / --allow-missing-kdk -v`（或既有可用的
  `kmutil load -z -p <kext>` 路径），**重启前逐条核对 id**，`IGPUConsoleRange` 必须在。
- 遇到计划外现象：停手、留证、报告。

## 4. 实验 E1：一个指令的判决（核心）

### 4.1 改法

在 `xenative.cpp` 里加一个缓存回写屏障，并在**任何写 PTE / 写物理内存之后、动显示寄存器之前**调用：

```cpp
static inline void xnFlushCaches()
{
    __asm__ __volatile__("wbinvd" ::: "memory");   // 回写并失效全部 cache
}
```

如果 `wbinvd` 在这个内核里不可用（很罕见），退化成逐行 `clflush`：

```cpp
static inline void xnClflushRange(void *p, size_t n) {
    for (size_t i = 0; i < n; i += 64)
        __asm__ __volatile__("clflush (%0)" :: "r"((char *)p + i) : "memory");
    __asm__ __volatile__("mfence" ::: "memory");
}
```

同时把 `pte` / `fill` / `fillat` / `switch` 这几条 user client 命令的写入路径都接上这个屏障，
并新增一条命令 `flush`（只做屏障，方便单独验证）。

> 顺带一个观察点：`IOMemoryDescriptor::withPhysicalAddress` + `createMappingInTask(..., kIOMapInhibitCache, ...)`
> 对**物理内存**描述符是否真的生效，本身就可疑（`kIOMapInhibitCache` 主要是给 `IODeviceMemory` 用的）。
> 如果 E1 证明是缓存问题，那么"改映射属性"也是一条可选修法；但先用 `wbinvd` 做判决，不要同时改两样。

### 4.2 判决实验（严格照这个顺序，全部运行期）

```bash
# 0) 记下现状，备份要动的 PTE
xenative-ctl status            > ~/xegfx-log/A-11/e1-before.txt
xenative-ctl scan              >> ~/xegfx-log/A-11/e1-before.txt

# 1) 把我们的缓冲填成可辨识图案（物理 0x71800000，stolen 里）
xenative-ctl fill              # 默认写 stolen 那块 3120x2080 图案
xenative-ctl flush             # 新命令

# 2) 复刻 T1：往一个从未被用过的索引写"已知有效"的桌面 PTE，再把 SURF 指过去
xenative-ctl pte 0x1000 0x800003
xenative-ctl flush
xenative-ctl reg surf 0x01000000
# 看屏幕（拍照），并记 SURFLIVE

# 3) 无论结果如何，立刻恢复
xenative-ctl restore
xenative-ctl pte 0x1000 0
```

### 4.3 判读（这一步决定后面所有事）

| 现象 | 结论 | 下一步 |
| --- | --- | --- |
| 屏幕显示**桌面内容**（不是黑） | **写入到达内存了，缓存假设成立→修法有效**。说明 A-10 之前所有 PTE 写入都被 CPU 缓存吃掉 | 进 A-12：重做 3120（带 flush），并预期 T6 的"花屏"也会变成正确图案 |
| 仍然**全黑** | 缓存假设**被证伪**。写入确实到了内存，但引擎看不到 | 进 E2 |
| 画面变成我们的图案（红蓝） | 缓冲区物理地址本身就被当作显示内容——说明 PTE 索引语义和我理解的不同 | 立刻停，报告，别继续 |

### 4.4 如果 E1 判为"全黑"（E2）

按这个顺序做，每条之间都要 `restore`：

1. **验证填充本身可见**：`fill` 之后，在**不改任何寄存器**的前提下，把 `PTE[liveIdx+1]`（桌面第 2 页，
   引擎一定走过）改成我们缓冲的物理地址 `0x71800003`，`flush`，然后看桌面**第二行附近**有没有变成我们的内容。
   - 变了 → 写入可见，但那说明 T1 的黑有别的解释 → 停，报告
   - 没变 → 写入确实被引擎忽略 → 进 2
2. **换个位置写**：把同一条 PTE 经 **BAR2 的 GGTT 写窗口**写（如果 `BAR2+0x800000` 段在 `xenative-ctl scan`
   里确认不是表，就先试 `BAR2 + idx*8`，即把 BAR2 前 256 MB 当作 PTE 镜像窗口）。
   - 关键：**先只读**确认该窗口写进去能被自己读回、且读到的是表内容；否则不要盲写。
3. **找第二份表**：反汇编 `/Library/Extensions/IGPUConsoleRange.kext`（约 64 KB），用
   `nm -m` / `otool -tV` 看它是否出现 `0x7019C`、`0x108100`、`0x1080C0` 这些常量，
   以及有没有写 GGTT 的代码。它是这台机器上唯一成功驱动过这块显示的东西。

> E2 的任何一步如果导致画面异常，`xenative-ctl restore` 一次就能回来（A-10 已验证过两次）。

## 5. 别做的事

- 不要为了"试试看"再改 `PLANE_CTL` 的位（A-10 已证明它没被动过，也不需要动）。
- 不要在同一次运行里同时改 flush 和缓冲地址 —— 那样无论结果如何都无法归因。
- 不要用 `TRANS_FRMCOUNT` 判断帧在走（它恒定）。
- 不要把 `results`（XeGfx 的 stage 数组）和 XeNative 的状态混在一起看，两者无关。

## 验收锚点（主 agent 独立跑）

1. `xenative-ctl status` 里 5 个寄存器回到原值（SURF `0xFE600000`、PS_CTRL `0x80000200`、PIPESRC `0x077F0437`、STRIDE `120`、PLANE_CTL `0x84000008`）。
2. `xenative-ctl scan` 的 `live_run_pages` 仍为 6656、`live_phys` 仍 `0x800000`（证明没有把活的那段弄坏）。
3. `PTE[0x1000]` 回到 0（或实验前原值）。
4. 屏幕 1920×1080、WindowServer 在、零新 panic、`/Library/Extensions` 里 IGPUConsoleRange 在。
5. E1 和 E1'（有/无 flush）**必须都有记录** —— 只做有 flush 的那一半，等于没有对照。
