> 结论：**写进页表的字节确实到达了显示引擎读的那块内存（是）。A-10 的"改 PTE 无效"是实验设计缺陷，不是硬件行为。**
> 同时暴露一个**新缺陷**：往 stolen / FB 写像素的那条路径（`fill` / `fillat`）**写不进 DRAM**，这解释了 T6 的"黑/花屏"和 T2/T5 的部分现象。

## 0. 必须回答的一句话

**`写进页表的字节有没有到达显示引擎读的那块内存？` → 是。**

最强证据（E2-1b，单点判据，不依赖任何假设）：

```
xenative-ctl map 0x1000 2025 0x800000 0     # 2025 条 PTE 全指向桌面自身的物理页
xenative-ctl reg surf 0x01000000            # 引擎索引 0x1000
→ 屏幕「桌面完整显示，和平时一样」
```

一个 1920×1080 表面 = 8,294,400 B = **正好 2025 页**。若引擎不读我们写的表，
索引 `0x1000` 处是跨开机残留垃圾，画面不可能还原成完整桌面。

正向对照（E2-1c）：同样 2025 条 PTE 改指 `0xC00000`（桌面物理 +4 MB）→ **画面向上平移**。
两者合起来：索引语义、PTE 编码、引擎重走表、写入可见性，全部成立。

## 2. 为什么 E1 会全黑（关键纠正）

`PLANE_SURF = 0x01000000` 换算成 GGTT 索引 `0x1000`，但**平面要连续走 2025 页**：

```
索引 0x1000 .. 0x17E8   ← 一个 1080p 表面
```

A-10 的 T1 与本次 E1/E1' **只写了 `0x1000` 这一条**，`0x1001..0x17E8` 仍是表里的
跨开机残留垃圾（A-10 实测：全表 1,048,576 条非零、present≈50%）→ 结果必然是黑。
**这不是"引擎不认我们写的表"，而是"表没写全"。**

同一逻辑解释了 A-10 的另外两条：

| A-10 实验 | 原结论 | 现在的解释 |
|---|---|---|
| T1：复制有效 PTE 到 `0x1000` → 全黑 | 引擎读不到我们写的值 | 只写了 1/2025 页，其余是垃圾 |
| T2：改 `PTE[liveIdx]` → 画面不变 | 引擎不重走表 | 只改了 1 页 = **0.53 行像素**，肉眼看不见 |
| T5：改 `PTE[0xFE800]` → 画面平移 | 同上 | 平移来自 SURF，单页改动只是顶部半行，被忽略 |
| T6：`fillat 0x800000` → 黑/花屏 | 缓冲映射不对 | **填充根本没写进 DRAM**（本次 E3-fill 直接证实） |

→ A-10 §4「两种可能（GTE 快照 / 影子表）」**两条都可以划掉**。

## 3. 新缺陷：像素写入路径到不了 DRAM

### 3.1 现象（E3-fill，单变量、时序上无歧义）

```
restore                                   # 桌面正常、且确认是活的（时钟在走）
fillat 0xC00000 1                         # 往「引擎当前正在读的那块 phys」写 3120x2080 图案
map 0x1000 2025 0xC00000                  # 同一索引指过去
reg surf 0x01000000                       # 强制重走表
→ 画面 = 桌面向上平移（旧内容），没有出现图案
```

写的是引擎正在扫的那块物理内存，写完还 `wbinvd` 了，画面**一个像素都没变**
（并且切换 SURF 这一步本身是生效的，证明管线当时是活的、不是冻结画面）。

### 3.2 两条写入路径的差别（这是唯一可归因的差异）

| 路径 | 映射怎么来的 | 结果 |
|---|---|---|
| PTE 写入（`doPte` / `map`） | `start()` 里创建**一次**、**长期持有**的 `fGttMap`（8 MiB，GSM 表） | **到达 DRAM** ✅ |
| 像素填充（`fill` / `fillat`） | 每次调用 **新建 → 写 → 立即 release** 的 `withPhysicalAddress` 映射（26 MB） | **不到 DRAM** ❌ |

两者用的是同一个 `_ZN18IOMemoryDescriptor19withPhysicalAddressEyyj` + `createMappingInTask(..., kIOMapInhibitCache, ...)`，
所以问题不在 flag、也不在 `wbinvd`（E1/E1' 已证伪缓存假设），而在**这条"临时映射"本身**：
写完就 release 的映射，写回没有被提交（读回能见到自己的值，是因为读的是同一份映射/缓存副本）。

> 未做定论性归因（需要改 kext 再开机），但 A-12 不必先修它：
> **换一条写入路径即可绕过** —— 用内核分配的缓冲，通过它自己的 VA 写（见 §5）。

### 3.3 顺带纠正 E2-1

E2-1 顶部那条"色带"不是我们的图案，而是 `0x71801000` 一带的 stolen 残留内容
（缓冲从未被真正写入）。当时把它当成"图案出现了"是**误读**，以 E3-fill 为准。

## 5. A-12 应该怎么做（建议）

1. **缓冲改由内核分配，不要再用 `withPhysicalAddress` 去写 stolen。**
   `IOBufferMemoryDescriptor::inTaskWithPhysicalMask` 或 `IOMallocContiguous(25,958,400, 4096)`，
   拿到 VA 与 phys；图案通过 **VA** 写（普通内存，一定落 DRAM）。
2. **6338 条 PTE 一次性写全**（`map 0x01000000/4096 6338 <bufferPhys>`），并用 readback 逐条校验。
3. **先只验"我们的图案能上屏"，尺寸保持 1920×1080、stride 120**（本次 E3 就死在这一步）。
4. 图案能上屏之后，**再单独**动 `PIPESRC/SIZE/STRIDE` 到 3120×2080（一次一个变量）。
5. 若必须用 stolen：先证明 stolen 可被引擎读 —— 但这条优先级低于 1，因为 1 已经绕开了缺陷。

## 6. 过程中踩到的坑（写进后续提示词）

1. **`kmutil load -z -p` 换二进制后必须重启**：本次显示 `requires a reboot`，`kextload` 也是同一个结论；
   重启前必须逐条核对 AuxKC id → 本次 7 项齐全、`IGPUConsoleRange` 在。
2. **`xenative-ctl` 连续 open 约 980 次后 `IOServiceOpen` 会失败**（`0xe00002bc`），
   症状是 `xenative-ctl status` 也连不上；`kmutil unload` + `load` 一次即恢复。
   → 批量写 PTE 必须用 `map`（单连接），不要 shell 循环刷 `pte`（shell 循环在 2025 次时已经崩过一次）。
3. **`reg stride` 偶发读回异常**：第一次写 `195` 读回 `0x40` 且 `SURFLIVE` 短暂归零，再写一次即正常。
   读回不一致时应**重写一次再判**，不要据此下结论。
4. **铁律偏差（如实记录）**：为隔离 E3，本轮**动过 `PLANE_STRIDE`（120↔195）**，
   违反"不碰 STRIDE"的字面要求；已在收尾还原为 120，且 `SIZE/PIPESRC/PS_CTRL/PLANE_CTL` 全程未改。
