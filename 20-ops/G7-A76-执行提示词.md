## 0. 调研结论（前人实现，A-75 偏离点已标出）

1. **锁纪律（panic 头号嫌疑）**：0024 里 `nvSurfWaitReady` 的全部调用点都**不持锁**：
   - 翻转路径：worker 从队列 pop 之后已 `IOLockUnlock(gXeFlipLock)`，等待时无任何锁；
   - page-off 路径（`nvXePoPageoff`）：**先 `IOLockUnlock(gXePoLock)` → 等待 → 重锁 → 用
     `e->id == id && e->cache == cache` 重验条目**（防等待期间被替换）。函数头注释写明
     "the caller holds nothing"。
   - 我们 A-75 的移植里 marks 活着时出现 **4 处**有界等待，报告自述「分别在 page-off、翻转、
     拷贝路径上，且可能持有加速器 family lock」——**这是偏离。A-74 里这些路径是空转的，panic
     与「marks 活着」的窗口重合，机制上对得上：持锁等待 100ms 上限 → 其它 CPU 在锁上自旋 →
     watchdogd NMI → `mp_kdp_enter` 超时。**
2. **「未标记 = 就绪」是前人故意设计**（"a surface with no pending mark is done"）：
   他们的栈里 WS 每个 command buffer 的 surface 都会在 commit 时标 pending，所以零等待
   = 合成已完成的正常快路径。我们 199 帧里 3/14 帧零等待却伴随残帧——**不能照抄修，
   先取证**：要么 sid 对不上（插件标记的 IOSurface ID ≠ 事务里的 surface ID），要么 mark 迟到
   （事务先于 pending 到达）。
3. **early 释放（mark 段 13–15ms 的直接原因）**：我们插件的 `nvmtl_vk_accel_surface_wait()`
   能力探测匹配 `NVAccel`（NVIDIA 的 `NVAccelSurfaceWait` page-off 能力），Intel 加速器叫
   `NMXAccel`，于是 `holds->early` 恒 NO → holds 只能等整个 command buffer 结束才释放。
   0026 的 `nvmtl_vk_set_accelerator` 里有现成的两分支写法：
   `IOObjectConformsTo(accel, "NMXAccel")` → vendor 0x1002/0x8086（marks 走 XGDR）；
   `IOObjectConformsTo(accel, "NVAccel")` → 0x10de（走 NVK escape）。
   **对 Intel，能力探测应判「accel 的 XGDR 客户端支持 selector 1 marks + page-off 等待」，
   而不是匹配 NVAccel 字符串。**
4. 0024 的 mark 等待决策（我们已移植，列出供核对）：
   `markonly` 生效 = `gIopXeMarkOnly && 最近 1 秒内有 mark`；
   `marked==false`（100ms 超时）只计 `mark_timeouts` 不改变路径；
   超时照样 arm（`idle_forced`）。

## 3. Part 1 · 锁纪律对齐（改 accel，先于任何 marks 重开）

按 §0.1 把 4 处等待全部改成 0024 的形态：

- 翻转 worker：等待发生在 pop 之后、无锁段（核对现有实现是否如此，不是就改）；
- 其它路径（page-off/拷贝）：**先解锁 → `nvSurfWaitReady` → 重锁 → 重验**
  （重验字段按各路径的条目语义，照 `nvXePoPageoff` 的 `e->id/e->cache` 模式）；
- 每处加计数：`mark_wait_enter/exit/timeout`（按调用点分列），让下次 panic 时能立刻看出
  谁在等。**等待绝不发生在持 family lock / queue lock 的区间。**

**门 1**：源码审读 + `grep` 自检（4 处调用点向上 20 行内无 `IOLockLock`/family lock 获取）；
编译装机后安全模式（marks 关）无回归。

## 4. Part 2 · 残帧取证（改 accel 观测 + 插件重开 marks）

1. accel：`nvSurfMark` 的 set/release、`nvSurfWaitReady` 的查询、arm 时的 sid，全部进
   `iop_tl` 或独立环形缓冲（**sid + 时刻 + 事件类型**，200 帧容量，照 A-72 模式）；
2. 重装 A-75 版插件（`~/xegfx-log/A-75/NVMTLDriver.a75new`）+ `surface_gpu_on=1`，
   markonly=1，跑 3 轮拖动；
3. 对齐分析：残帧出现时段里，零等待 arm 的那些帧——
   - 其 sid 在 mark 缓冲里**从未出现** → sid 对不上（插件标记的 ID ≠ 事务的 ID）→ 记录两个 ID 各来自哪段代码；
   - 其 sid 的 pending **晚于事务入队**才出现 → mark 迟到（竞态）→ 记录两条时间线；
   - 其 sid 先 pending 后 ready 且 arm 在 ready 之后 → 零等待是合法快路径，残帧另有原因（如实记录，别硬凑）。
4. 用户目视确认残帧是否复现（markonly=1）。

**门 2**：残帧的机制有数据支撑（三种情形判其一；判不出也是结论，如实写）。
**若判出是 sid 不匹配/竞态**：允许做最小修正——worker 对「无条目且 marks 活跃」的
surface 先给 **2ms 宽限**等条目出现再判（这是对本栈竞态的局部补丁，报告里要标注
「偏离前人设计，原因：…」）；sid 不匹配则修插件的 ID 采集。

## 5. Part 3 · early 释放（改插件）

按 §0.3：`nvmtl_vk_accel_surface_wait()` 的能力判定改为——加速器是 `NMXAccel`（vendor 0x8086）
时，探测 **XGDR selector 1 marks 是否可用**（探针成功 = accel 会等 pending surface，即
NVAccelSurfaceWait 的 Intel 等价物）。0026 的两分支写法在 §0.3 引了原文。

装新插件 + marks 开 + markonly=1，3 轮拖动 A/B（对照 markonly=0 与 early 修复前）。

**门 3**：
- WS 日志出现 early 形态（`marked newest ... at commit` 一类，对照 A-75 §2 的日志行变化）；
- mark 段 p50 从 13–15ms 降到 **≤ 8ms**（early 释放后只需等本 surface 的合成，而非整个 cb）；
- 拖动 3 轮中位 **≥ 30** 且无残帧（用户目视）。

## 6. 判死活（本关的最后一步，写给下一关的路标）

全部门过后综合判断：

| 情形 | 决定 |
| --- | --- |
| 门 0–3 全过，fps ≥ 30 且稳 | marks 默认开（`surface_gpu_on=1` 开机默认），写进 bringup；下一关 = 阶段 2 |

它的 page-off 机制复用本关修好的锁纪律与等待，所以 Part 0/1 的成果无论如何不白做。
