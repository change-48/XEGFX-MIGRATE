# Gate 7 · A-72 执行提示词：120fps 之前的「测量三件套」（纯测量，零行为改动）

> 目标：**为把桌面帧率从 19fps 推向 120fps 做测量准备**。
> 在动任何性能代码之前，先拿到三样东西：① 逐秒帧率探针；② accel 逐帧时间线；
> ③ WindowServer 里 pipeline 每秒创建量与去重量（判定「着色器编译墙」的真实大小）。
>
> **本关只许加测量，不许做任何性能改动**——哪怕看起来无害。
> 研究背景见 `20-ops/G7-120fps-研究.md`（必读）。
> 动手前先读 `20-ops/AI-远程连接说明.md` 和 `20-ops/AI-远程调试作业说明.md`。

---

## 0. 背景（一分钟版）

- 机器：HONOR MagicBook Art 14 2025，Core Ultra 7 255H（Xe-LPG+ `8086:7D51`），面板 3120×2080 **@120Hz**，macOS 26.5.2。
- 图形栈：Metal → NVMTL 插件 → Mesa ANV → XeGfx(i915) → XeGfxAccel → XeGfxIntelFB → eDP。
- 当前桌面拖动帧率中位 **19fps**（一帧 ~52ms），而 120Hz 预算是 8.33ms。
- 已知成本构成：WS CPU（ANV 编译 26.5% + CA::OGL 15% + NVMTL 12–13%）≈ 65%；同步拷贝事务 3.85ms；等待仅 1.2%。
- 前人成果 Mountainatic/ArrowWhatever（`github.com/Mountainatic/ArrowWhatever`）已把同类栈推到 ~70fps，
  他们公开了测量工具（`scripts/tools/`：fps-probe、anim-probe、anim-summary、flip-sampler）和
  逐帧时间线设计（`debug.nvaccel_iop_xe_tl`，200 帧环形缓冲，见其 patches/0024）。
- **本关要回答的三个问题**：
  1. 拖动场景逐秒帧率的稳定基线是多少（复现总账的 18–21）？
  2. 一帧 52ms 里，拷贝/vblank/排队各占多少（accel 侧分解）？
  3. WS 每秒创建多少 VkPipeline、其中去重后有多少个**不同**的？（决定墙 B 的修法）

## 2. Part 1 · 帧率探针（零风险，先做）

### 2.1 取工具

```bash
mkdir -p ~/src/ArrowWhatever && cd ~/src/ArrowWhatever
git clone --depth 1 https://github.com/Mountainatic/ArrowWhatever .
ls scripts/tools/    # fps-probe、anim-probe、anim-summary、flip-sampler、mark-timeout-watch…
```

**先读源码再跑**（他们读的是自己 accel 的 sysctl 名 `debug.nvaccel_*`，我们的是 `debug.xegfxaccel_*`）。

### 2.2 适配帧计数源

我们的帧计数器是 **`debug.xegfxaccel_iop_ok`**（每帧上屏 +1，拷贝路径下就是实际帧率）。
把 fps-probe（或一个等价的 ~60 行脚本）改成每秒采样它一次、连续 25 秒、输出逐秒序列 + 中位/均值/最大。

存到 `~/xegfx-log/A-72/fps-probe.sh`（自研，注明改自 ArrowWhatever）。

### 2.3 基线测量（需要用户配合拖动）

请用户**拖动一个窗口 25 秒**（和总账 2.1 相同工况），连跑 3 轮，每轮间隔 30 秒。
另跑 1 轮**空闲**（不碰机器）作对照。

```bash
sudo sysctl -n debug.xegfxaccel_iop_ok > 起点
./fps-probe.sh 25 | tee ~/xegfx-log/A-72/drag-run1.txt
```

**门 1**：3 轮拖动中位数都在 16–22 区间（复现总账基线）；空闲轮明显高于拖动轮或为零翻转计数（记录数字即可）。
若中位 >25 或 <10：工况可能不具可比性（动画内容不同），如实记录，不强行解释。

## 3. Part 2 · accel 逐帧时间线（改 accel，只加观测）

文件：`~/src/NvGfx-xe-2.6.2/kexts/NVRM/accel/nvrm-accel.cpp`（装机树，与 `/Library/Extensions` 对齐的那棵）。
参考实现：ArrowWhatever `patches/0024-accel-deferred-flip-tile4-pageoff.patch` 里的 `debug.nvaccel_iop_xe_tl`
——**只许搬它的「时间线环形缓冲 + sysctl 导出」部分，它混在同一个补丁里的 flip/marks 逻辑一行都不许带**。

### 3.1 顺手修一个已知问题

本会话实测（20:28）：装机 accel 里 **`iop_copy_*` 计时 sysctl 读不到**（`sysctl -a | grep iop_copy` 为空），
但 `iop_ok`/`iop_xe_*` 都在。原因大概率是那批 SYSCTL_* 没手动 `sysctl_register_oid`（11-02 已知：kext 里
静态 SYSCTL_* 不自动注册）。把 A-69 的拷贝计时找回（注册或并入时间线输出）。

### 3.2 时间线设计（适配我们的拷贝路径）

环形缓冲 200 帧，每帧记录相邻步骤的微秒差：

```
enter(performTransaction 进来) → src_mapped(拿到 kva/surface) → copy_done → vblank_done → ret(返回 WS)
```

外加每帧的 pitch/宽高（一行），导出成一个 sysctl：`debug.xegfxaccel_iop_tl`（读一次 dump 最近 200 帧）。
计时用现成的 nanoseconds/mach_absolute_time 工具（树里 A-46/A-47 加过的那些计时宏照抄）。

**纪律**：
- 不新增任何锁竞争敏感路径上的 I/O（只在内存里填 ring，sysctl 读时才格式化）。
- 不改变 `performTransaction` 的返回值、拷贝方式、vblank 等待逻辑。
- 构建按老规矩：`SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk`，adhoc 签名，
  六 id 校验，装机前 diff 确认只有观测代码。

### 3.3 验证与测量

装好后（KC 重建 + 重启，先问用户），等桌面起来、`iop_ok` 恢复增长，再请用户拖动 25 秒：

```bash
sudo sysctl -n debug.xegfxaccel_iop_tl > ~/xegfx-log/A-72/tl-drag.txt
sudo sysctl -a | grep -E 'iop_copy|iop_vblank|iop_ok' > ~/xegfx-log/A-72/counters-drag.txt
```

**门 2**：时间线可读、200 帧覆盖拖动期；给出 p50/p90 表：copy / vblank / enter→ret 全程；
A-69 拷贝计时恢复可读且与时间线自洽（copy_done-enter ≈ iop_copy_last）。
预期：copy p50 ≈ 3–4ms，事务全程 ≈ 3.8–4.8ms（对齐总账 2.3）。若 vblank 项异常大（>3ms p90）如实记录——这是新发现。

## 4. Part 3 · pipeline 创建计数（改插件，判墙 B）

文件：插件源码树 `~/src/NvGfx-xe-2.6.2/plugin/`（`nvmtl_vk.c` / `NVMTLObjects.*` 那套；A-67 的 host-pages 补丁就落在那里）。
装机插件：`/Library/GPUBundles/nvmtl/`（NVMTLDriver `fcaf4fa0`，2.6.2 + host-pages + 函数对象缓存）。

### 4.1 加什么

在插件里统计 **`vkCreateGraphicsPipelines`（以及 compute，如有）**：

- 总创建次数（每帧/每秒）；
- **去重后数量**：用轻量 key——各 stage shader 模块的 SPIR-V 哈希（A-63 的着色器缓存已有哈希，复用它）
  + render pass 附件格式组合 + 顶点布局/混合状态是否参与（先做前两项，够用）；
- 每秒把一行汇总写 `/private/tmp/nvmtl-ps.log`（插件在 WS 沙盒里，`/private/tmp` 可写；A-54b 的哨兵文件同路）。

**注意开销**：哈希只在创建时算一次（创建本身是 ms 级，多一次哈希无感）；**不许**在渲染热路径上加任何东西。

### 4.2 验证与测量

构建插件（照 A-67 的构建流程），装到 `/Library/GPUBundles/nvmtl/`，kickstart WS（提醒用户重新登录），
等 `iop_ok` 恢复，然后请用户拖动 25 秒：

```bash
tail -40 /private/tmp/nvmtl-ps.log > ~/xegfx-log/A-72/ps-churn-drag.txt
```

**门 3（本关最重要的一张表）**：拖动期间——

| 每秒创建数 | 去重后不同 pipeline 数 | 结论方向 |
| --- | --- | --- |
| 大（>20/s）且去重后仍大 | 每秒多个**不同** | CA 每帧真的在要新状态 → 修「为什么状态变了」或异步编译兜底 |
| 大但去重后小（<5/s 新增） | 缓存未命中问题 | 修缓存键 |
| 小（<5/s） | 编译不是每帧的 | 墙 B 在 CA 绘制本身（GPU/CPU 像素量），走减像素/减带宽路线 |

**这一格数字直接决定 G7 后续几天的方向，务必测准**（连测 3 轮，中间清一次 log）。
