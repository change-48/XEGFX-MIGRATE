# Gate 7 · A-83b 执行提示词：L1 重试 —— 单变量修 accel 命名，看另两个是不是连锁

> A-83 Phase 0/1 已完成（27 枚补丁 0 reject、六件出件），L1 装机三项不过并已回滚。
> 复核后发现：**三个根因里有两个很可能是同一个**，所以这次**只改一个变量**再试。
>
> 已核实的关键事实（本次 SSH 现场查证）：
>
> ```
> ① accel 命名：xegfx_accel_names.h 整个 rename 块包在 #ifdef NMX_XEGFX 里，
>    而 build/accel_build.sh 只传 -DNM_TAHOE，从不传 NMX_XEGFX / NMX_ACCEL
>    ⇒ 产物类名是 NVAccel、sysctl 是 debug.nvaccel_*，与装机 plist 的 NMXAccel 不匹配（199 处）
>    （A-79 当时就踩过这个坑：-DNMX_XEGFX -DNMX_ACCEL 缺一不可）
> ② AGDC 的类名扫描不是主因：gAgdcFBClass[] = { IONDRVFramebuffer, "XeGfxFramebuffer" }，
>    我们的 FB 是 XeGfxIntelFramebuffer : IONDRVFramebuffer，主类名就能匹配
> ③ 真正的 AGDC 失败是 "left out: noidx 1" —— 该 FB 节点没有 IOFBDependentIndex；
>    这个属性由 XeGfxDisplay 发布（XeGfxDisplay.cpp:3529 / 3831）
>    ⇒ 若 Display 没正常跑起来（很可能因为 accel 没 attach），AGDC 就拿不到 index
> ④ HiDPI 不是"框架丢了"：A-83 的 FB 里有 -xeintelfbhidpi（默认 1）、
>    "getDisplayModes: base %u + scaled mode %#x"、fHidpi 默认 true
>    ⇒ L1 显示 3120×2080 只是那条路没走通（需看 FB 日志判原因）
> ```
>
> 目标：**L1 过关**（accel attach、AGDC fbmap ≠ 0、UI 仍是 1560×1040、flips 增长）。
> 必读：`G7-A83报告.md` §7（L1 失败三项与回滚）、§2.2（三处必需适配）、`G7-A79报告.md`（构建宏的坑）。

## 3. P2 · 若 accel 仍不 attach（只在这一情形下做）

按顺序取证，**每步只读**：

1. `kextstat | grep -i watchthelight` + `kmutil showloaded | grep XeGfxAccel` 是否在列；
2. `log show --last 3m --predicate 'eventMessage CONTAINS "XeGfxAccel" OR CONTAINS "NMXAccel"'`；
3. `ioreg -l -w0 -p IOService | grep -A3 -i "NMXAccel"` 看 personality 是否匹配；
4. 对照 A-79 的装机件（`d180c6bf`）用同样命令的输出，逐项比。

**门 P2**：给出"personality 没匹配 / 匹配了但 start 失败 / 依赖未满足"三者之一的结论。

## 4. P3 · 若 AGDC 仍 noidx（accel 已 attach 的前提下）

1. `ioreg -l -w0 -c XeGfxDisplay | grep -E "IOFBDependentIndex|IOClass"`（有值吗）；
2. `debug.xegfx_agdc_fbmap` 完整字符串（看 `noidx/range/dup/gpu/hole/repeat/alt` 各计数）；
3. 对照 A-83 §7.2 的日志：`AGDC scan: class …: no iterator` 那段，确认扫到的是哪个类；
4. **最小改动**：在 FB 的 `start()` 里补 `setProperty("IOFBDependentIndex", 4)`（head 4，与 bootArm 的
   "head 4 has a display pipe" 一致），只改这一处、带 sysctl 开关，再试一次。

**门 P3**：`fbmap n ≥ 1`；`debug.xegfx_agdc_state` 不再停在 timeout。

## 5. P4 · HiDPI（只在 P1 通过、但 UI 变成 3120×2080 时做）

先判原因，别直接改代码：

```bash
log show --last 3m --predicate 'eventMessage CONTAINS "XeGfxIntelFB"' | grep -iE "hidpi|L0 options|scaled mode|getDisplayModes|mode discovery"
ioreg -l -w0 -c IOFramebuffer | grep -E "IOFBModes|IOFBUIScale" | head -5
```

| 日志形态 | 原因 | 处置 |
| --- | --- | --- |
| `L0 options: hidpi off` | 没开 | 显式加 boot-arg `-xeintelfbhidpi=1`（**注意：EFI 改动要先问使用者**） |
| `mode discovery: base getDisplayModes failed` | 基类的模式列表为空 | 查 FB 是否在 publish 前就报错（`published IOFBDetailedTimings` 有没有出现） |
| 有 `+ scaled mode` 但 `system_profiler` 仍原生 | 是 adapter/Display 选了原生 | 查 `XeGfxDisplay` 的模式列表（KAPI `getTiming(XG_KMS_FIXED_MODE_BASE+n)`） |
| 完全没有 scaled mode 日志 | `fTimingValid` 为假（量不出时序） | 看 `panel timing measured:` 那行在不在；不在就是 BAR0/帧计数窗口问题 |

**门 P4**：`UI Looks like: 1560 x 1040`。
