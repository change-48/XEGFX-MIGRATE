## 2. 判定实验本身

```
$ sudo /usr/local/bin/xenative-ctl mapfast 0xFE600 6656 0x800000
mapped   0xfe600 .. 0xfffff  first 0x0000000000800003 last 0x00000000021ff003  bad 0
```

- `bad 0` —— 6656 条全部写入并逐条回读校验通过
- `first 0x800003` / `last 0x21ff003` —— 物理 `0x800000 + 6655*0x1000 = 0x21ff000`，与基线连续映射完全一致
- 写完抬头看屏幕：**条纹立即消失，画面完整**
- `scan` 的 `live_run_pages` 同步回到 **6656**

→ 只能是"PTE 被改写"，不可能是"物理页被写脏"：若是内容/物理层被覆盖，重写页表不会改变显示。

## 3. 三处与提示词不符的现场事实（重要，需主 agent 采纳）

### 3.1 `map` 换成 `mapfast`（`map` 打印不出 first/last/bad）

`xenative-ctl map` 是**用户态循环**调 `SEL_PTE`，一条连接写 N 次，成功只打印
`mapped 0xfe600 .. 0xfffff -> phys 0x800000  failures 0`，**没有 first/last/bad**；
提示词 §3.2 期望的那行输出实际是 `mapfast`（`SEL_MAPFAST`）的格式：

```c
// xenative.cpp:1244 doMapFast —— 一次 ioctl、内核里循环、自带 wbinvd + GFX_FLSH_CNTL + 逐条回读
for (i...) fGtt[idx+i] = ((phys + i*4096) & PHYS_MASK) | fPteFlags;
... return first/last/bad
```

后续凡是要"写一段 PTE 并验证"的场合，**一律用 `mapfast`**，比 `map` 快几个数量级且自带校验。

### 3.2 期望值 `last = 0x1a00003` 算错了，实际是 `0x21ff003`

`0x800000 + (6656-1)*0x1000 = 0x800000 + 0x19FF000 = 0x21FF000`，`|0x3` = **`0x21ff003`**。
`0x1a00003` 对应物理 `0x1A00000`，那只是 **4608 页**（6656 页的 69%）。
脚本若按 `0x1a00003` 断言，会误判失败。**以 `0x21ff003` 为准。**

### 3.3 花屏不是探针造成的 —— **XeGfx 一加载就被抢了**

提示词 §3.1 的期望是"跑完探针后 `live_run_pages` 明显变小"。
实测：`kmutil load` + `stage=7` + `sleep 25` 之后、**mtlprobe 还没启动**，`live_run_pages` 已经是 **1800**。
时间线（dmesg）也对得上：`NMXAccel: getStampMemory -> descriptor (4096 stamps, 16 KB)` / `createUserGPUTask init=1`
都发生在这之前 —— **触发点是加速器第一次分配显存，不是应用提交**。

这条对 S2 有利：修好保留区后，"加载即花屏"应该同步消失，不必依赖跑探针才验证。

## 4. 新增的一条硬证据：被抢的窗口正好是"该保留却没保住"的那一段

两次复现的断点：`live_run_pages` = **1800 / 1783**（几乎相同，差 17 页 = 分配尺寸差异）。
断点意味着 PTE 索引 `0xFE600 + 1783` 处的物理地址不再是 `0x800000 + 1783*0x1000`：

```
物理断点 = 0x800000 + 1783*0x1000 = 0xEF7000
被抢窗口起点（GGTT）= 0xFE600000 + 1783*0x1000 ≈ 0xFECF7000
GUC_GGTT_TOP         = 0xFEE00000
```

**被抢窗口起点比 `GUC_GGTT_TOP` 低约 1.03 MB**。这说明：

- i915 的分配器把 `[0xFE600000, 0xFEE00000)` 这 8 MB **当成空闲**在用（因为 `xg_i915_reserve_bootfb` 整体 insert 失败、一条都没登记）；
- 而且它是**从 GuC 栅栏往下**分配（first-fit 顶端 / top-down），所以第一块缓冲正好落在栅栏下面一点；
- `0xFEE00000` 以上（`0xFEE00000..0x100000000`，4608 页）本轮**看不到被抢**（连续段在 1783 就断了，看不到上面），与注释里"at or above GUC_GGTT_TOP keeps it free"的前提部分相符。

→ **对 S2 的直接指导：真正必须补上的保留区间是 `0xFE600000 .. 0xFEE00000`，共 `0x800000` 字节 = 2048 页**，
而不是全部 25,958,400 字节。这也正是"拆两段 insert"里 **lo = GUC_GGTT_TOP - gBootSurf = 0x800000** 的由来。

> 算术复核（原判断成立）：`0xFE600000 + 25,958,400 = 0xFFEC1800 > 0xFEE00000`，
> 一段 insert 必然跨过 GuC 保留区 → `-28 ENOSPC` → 整段没登记 → 加速器往里分 → 帧缓冲 PTE 被改 → 扫描读出别处的内存。
> **这条链现在从端到端都被证实了（寄存器没动 + 屏幕随页表恢复而恢复）。**

## 7. 下一步（等主 agent 发 S2 提示词，本轮不动源码）

S2 的修法已经可以定死到具体边界值：

```c
uint64_t end   = (uint64_t)gBootSurf + xg_boot_fb_size;   // 0xFFEC1800
#define GUC_GGTT_TOP 0xFEE00000u
if (end <= GUC_GGTT_TOP) {
    err = xg_i915_reserve_bootfb(gBootSurf, xg_boot_fb_size);
} else {
    uint64_t lo = GUC_GGTT_TOP - gBootSurf;               // = 0x800000（2048 页），本轮实测被抢的就是这一段
    err = xg_i915_reserve_bootfb(gBootSurf, lo);
}
```

S2 必须单独一轮：core 重编 + 6 处二进制补丁重新定位（3×`pci_dev_put`、1×stage-loop、2×`idr_preload`）。
S2 之后的第一条验收判据建议改为：**加载 XeGfx + accel 初始化后 `live_run_pages` 仍为 6656**（不跑探针就能判）。
