# G7 · A-82b 报告：占用率与时钟 —— 「不发热」的真实原因是**单核 CPU 打满**，不是 GPU 低频

> 日期：2026-11-03 17:27 – 18:20（**零行为改动**：没改一个 kext、没设一个开关、没重启）
> 目标：回答三个问题（GPU 频率 / 帧时间是否被 vblank 量化 / 那 12ms 在等什么），每个都要数字。
>
> **一行结论：三个数 —— GPU 活跃度负载下 17–21%（不是饱和）、GPU 频率「拿不到」（powermetrics 在本机
> 没有该字段，这是结论不是失败）、帧间隔 34.52ms = 4.14 个 vblank 拍（47.2% 紧贴整数倍）。**
> **但真正决定一切的是第四个数字：每帧 CPU 35.9ms ≈ 34.52ms 帧间隔的 1.04 倍 —— 流水线完全串行、
> 单核 99% 打满。GPU 有 3 倍余量，CPU 一寸余量都没有。**
>
> **⚠️ 本关推翻了提示词的两个前提**（§4）：①「12ms 纯等待」**不存在** —— vblank 等待实测 **0.001ms**，

> 都是干净的反证，加负载只会更慢。

## 2. 测量（按序）

### 2.1 GPU 频率与占用：频率拿不到，占用拿到了

**来源①（powermetrics）—— 频率不支持，活跃度支持：**

```bash
sudo powermetrics --samplers gpu_power -i 1000 -n 2     # 只有表头，无 GPU 段 → 本机 Intel iGPU 不支持
sudo powermetrics -A -i 500 -n 4 | grep "^GPU Active"   # 只有活跃度
```

| 场景 | GPU Active | 证据 |
| --- | --- | --- |
| 空闲 | 0.00 / 0.00 / 0.00 / **0.49%** | `gpu-idle.txt` |
| 玻璃负载 1100×760 | **17.08 / 21.27 / 17.96 / 20.11%** | `gpu-load.txt` |
| 三负载（+800×600 +700×500） | **13.85 / 18.70 / 16.85%** | `gpu-triple.txt` |
| 卸载后 | 0.37 / 0.00% | 同上 |

**这条数据本身就否掉了「低频锁死」假说**：GPU Active 是**占空比**（GT 醒着的时间比例）。如果 GPU 被
SLPC 压在低频、合成因此变慢，占空比会**顶到接近 100%**（活干不完，GT 一直醒着）。实测只有 20%，
说明 GT 有大量时间在睡 —— 它是**没事干**，不是**干得慢**。

**来源②（他们的 `debug.xegfx_gt_act`）—— 我们树没有：**

```bash
grep -n "xegfx_gt" ~/src/ArrowWhatever/patches/*.patch
# 0023-core-kms-boot-commit-joiner-cursor.patch:  xg_i915_gt_act_mhz() + SYSCTL_PROC(_debug, OID_AUTO, xegfx_gt_act)
# 0027-tools-frame-rate-and-pageoff-measurement.patch:  s->gtMhz = sc("debug.xegfx_gt_act")
```

他们的实现是 `intel_rps_read_actual_frequency(&to_gt(i915)->rps)`。我们 core **导出了这个符号**
（`nm -gU /Library/Extensions/XeGfx.kext/...` → `_intel_rps_read_actual_frequency` 存在，35 个 `intel_rps` 符号），
但**没有 sysctl 包它**，也拿不到 `drm_i915_private *`。

**来源③（自己加只读 sysctl）—— 本关判定「不做」，理由：**

寄存器地址是有的：MTL 用 `GEN12_RPSTAT1 = 0x1381b4`，`MTL_CAGF_MASK = GENMASK(8,0)`
（`~/src/xe-src/drm-kmod/.../intel_gt_regs.h:1563`、`:26`；换算见 `intel_rps.c:2074-2085`）。
**但 accel 现有的 BAR0 映射只到 `0x71000`**（`nvrm-accel.cpp:1234` 的 `map->getLength() >= 0x71000` 门），
`0x1381b4` 在窗口外；且 Gen12+ 读 RPSTAT 需要 forcewake。

⇒ 要拿这个数，得**扩 BAR0 映射 + 重新编译 accel + 重启机器**。而 GPU Active 已经回答了同一个问题
（20% 占空比 = 不饱和），两个加负载实验（§3）又是干净反证。**为一个已知答案的次要指标重启使用者的机器，不划算。**
配方记在这里，A-83 若要频率可以照做。

### 2.2 帧间隔：半量化，不是硬锁

`frame-times` 抓 24s（652 帧），`quant.py` 判读（`intervals-base.txt`）：

```
n=652  p50=34.52ms  p90=48.59ms  max=137.49ms  mean=36.77ms
紧贴 vblank 整数倍（±1.0ms 内）: 308/652 = 47.2%

  4 拍 ≈ 33.33ms :  245 帧  ( 37.6%)
  5 拍 ≈ 41.67ms :  174 帧  ( 26.7%)
  3 拍 ≈ 25.00ms :  120 帧  ( 18.4%)
  6 拍 ≈ 50.00ms :   56 帧  (  8.6%)
  2 拍 ≈ 16.67ms :   27 帧  (  4.1%)
```

**判读（和提示词设想的两种结局都不一样）**：不是「绝大多数紧贴 33.3 或 41.7」的硬量化，也不是「完全连续」的
纯 CPU 时间。它是 **47.2% 紧贴、主峰在 4 拍但 3/5 拍各占 18%/27% 的软量化** —— 帧被 vblank 吸过去，
但吸力不足以钉死在一档。物理含义：CPU 每帧要 35.9ms，跨过 4 拍（33.33ms）一点点，所以大部分帧
落到 4 拍、一部分溢出到 5 拍、一部分（负载轻的瞬间）掉回 3 拍。

**这一条给出了本关最有行动价值的换算**（`§2.2 附`）：

| 目标 | 拍数 | 帧间隔 | 等效 fps | 相对现在（34.52ms）要砍 |
| --- | --- | --- | --- | --- |
| 现在 | 4.14 | 34.52ms | 29.0 | — |
| **40 fps** | 3 | 25.02ms | 40.0 | **9.50ms** |
| **60 fps** | 2 | 16.68ms | 59.9 | **17.84ms** |

> **关键洞察**：从 3 拍跳到 2 拍只差 **8.34ms**，但收益是 **+20 fps**（40→60）。所以「最后 8.3ms 最值钱」——
> 这也是为什么 A-82 那些 1–2ms 的小优化全都没能跳档：**它们不够跨过一个整拍**。

### 2.3 那 12ms 在等什么 —— 前提被推翻，等待换了位置

**先说清楚：提示词说的「38.5ms 里有 12ms 纯等待」在本关没有复现。**

`iop_tl` 逐帧路径（`tl-base.txt`，199 帧，全走拷贝通路 `ok=1`）：

| 段 | p10 | **p50** | p90 | max | 含义 |
| --- | --- | --- | --- | --- | --- |
| `enter->src` | 4008 | **5927** | 7771 | 14112 | 校验 surface + `prepare`/`map` 26MB |
| `src->vb` | 1 | **1** | 1 | 1 | **等 vblank = 0.001ms，几乎不存在** |
| `vb->copy` | 1230 | **4679** | 7646 | 9004 | 26.1MB 非临时写进 WC aperture |
| `copy->ret` | 2645 | **3213** | 7191 | 10644 | 收尾（stride 恢复 + 采样校验） |
| `enter->ret` | 10500 | **14788** | 19099 | 25315 | performTransaction 总计 |

**⇒ vblank 等待实测 0.001ms。** 拷贝通路里 `nvAccelIopWaitVblank()` 的 `IOSleep(1)` 轮询根本没在等 ——
因为拷贝本身 4.7ms 已经跨过了 vblank 边界，下一帧来时面板早就在扫了。

**⇒ 真正的等待在这三处（`wait.py` 的叶子帧，12s 采样）：**

| 线程 | 等待位置 | 占该线程墙钟 | 在等什么 |
| --- | --- | --- | --- |
| `ws_main_thread` | `__ulock_wait2 ← objc_sync_enter ← -[NVMTLCommandBuffer dealloc]` | **8.2%** | **NVMTL 插件的命令缓冲锁** |
| `ws_main_thread` | `__ulock_wait2 ← objc_sync_enter ← -[NVMTLCommandBuffer enqueue]` | 4.1% | 同一把锁，入队侧 |
| `ws_main_thread` | `__ulock_wait2 ← objc_sync_enter ← nvmtlSubmitWithEvent` | 2.9% | 同一把锁，提交侧 |
| `ws_main_thread` | `__psynch_cvwait ← -[NVMTLCommandBuffer waitUntilScheduled] ← commitAndWaitUntilSubmitted` | 4.4% | **等 GPU 调度（Metal 语义）** |
| `coreanimation.render-server` | `__psynch_cvwait ← CA::Render::Fence::resolve_batches` | **45.3%** | **等 CA fence（GPU 完成信号）** |
| `Thread_13340` | `io_connect_method ← IOConnectCallScalarMethod ← nvmtl_po_service` | **100%（3720/3720 样本）** | 见 §3.2，page-off 服务线程 |

**⇒ 答案：不是等 displaylink、不是等 surface 空闲、不是等定时器。是等两把锁和一个 fence —— 全部在 NVMTL 插件和 CoreAnimation 的交界处。**

## 3. 两个实验（都是干净的反证）

### 3.0 先说方法学：第一次跑错了，必须写出来

第一版实验 1 用 `fps-probe2.sh` 的全局上屏计数做判据，得到「p50 31→35，+13%」，看起来像「提频命中」。
**这个 +13% 是假的** —— 我加的**两个背景窗口自己也在上屏**，`iop_ok` 是全系统计数，涨的是它们的帧，不是正主的。

**修正口径**：判据换成 **WindowServer 自己的 CPU 时间**（`ps -o cputime` 前后差）+ 正主负载的 p50。
重跑后结论反转。

### 3.1 实验 1 · GPU 提频测试（加 GPU 负载，看是否被拉上去）

```
基线（单负载 1100×760 玻璃 25s）  WS cpu 5:21.50 → 5:49.92 = 28.42s   p50 = 31.0  p90 37  max 38
提频（+800×600 +700×500 同时）    WS cpu 5:50.68 → 6:20.90 = 30.22s   p50 = 30.0  p90 36  max 42
```

**判读：CPU +6.3%，fps −1。** 按提示词的判据「若 fps 不降反升、或 mark 段变短 → 提频是最大一笔」——
**没命中，而且方向相反**。GPU 加负载只会让本来就紧的 CPU 更紧（多两个窗口要合成）。

### 3.2 实验 2 · CPU 加热测试（回答「CPU 还有多少余量」）

```
基线（单负载）        WS cpu 6:22.03 → 6:51.83 = 29.80s   p50 = 31.0  p90 36  max 38
加热（15 核 yes 打满） WS cpu 6:53.46 → 7:25.40 = 31.94s   p50 = 31.0  p90 33  max 35
```

**判读：fps 一点没掉（31→31），CPU 只涨 7%。** 按判据「掉 <10% ⇒ CPU 不是瓶颈（印证单线程串行判断）」——
**命中**。打满 15 个核、只留 1 核给 WS，帧率纹丝不动 ⇒ **WS 就是一个单核问题，别的核闲着帮不上忙。**

> 核数已核实：`hw.ncpu=16`、`perflevel0.physicalcpu=16`、**没有 perflevel1/2** —— 255H 的 6P+8E+2LPE
> 被 macOS 报成 16 个同质核，XNU 不区分大小核。所以加热打 15 核是对的（不是 8）。

### 3.3 每帧 CPU 成本（本关最硬的一个数）

同 30s 窗口内 `ps cputime` 增量 ÷ 上屏帧增量：

```
WS cputime  7:38.07 → 8:07.70  = 29.63 s / 30 s 窗口  →  99% 个核
上屏帧      9387 → 10212        = 825 帧 / 30 s      →  27.5 fps
每帧 CPU    = 29.63/825*1000 = 35.9 ms
帧间隔 p50  = 34.52 ms          →  35.9/34.52 = 1.04
```

**两个独立测法（`ps`/`top` 仲裁 vs `sample` 结构）交叉验证了同一件事：**

| 仲裁手段 | 读数 |
| --- | --- |
| `ps -o %cpu -p WS`（负载下） | **107.7%** |
| `top -l 2 -pid WS`（负载下） | **95.7%**，13 线程 |
| `ps cputime` 30s 窗口 | **99% 个核** |
| `sample` 结构（修正归属后） | CPU 工作占 16.6% 墙钟 ≈ 2.1 核当量，**但其中约 1.2 核是「阻塞在 ioctl 内部」被误计**，扣掉后 ≈ 0.9 核 —— 与 `ps` 一致 |

> **诚实说明**：`sample` 无法区分「在内核里干活」和「在内核里等」，所以它的百分比只能读**结构**（哪个线程、
> 哪个调用点占用墙钟），不能读 **CPU%**。CPU 真值一律取 `ps`/`top` 的 0.91–1.08 核。

**⇒ 每帧 35.9ms CPU，帧间隔 34.52ms，比值 1.04 ⇒ 流水线完全串行、CPU 时间几乎 100% 暴露在帧间隔里。
要 60fps（16.68ms）必须把每帧 CPU 砍到 46% —— 砍 17.84ms。**

**35.9ms 花在哪（两个测法拼起来）：**

| 位置 | 成本 | 出处 |
| --- | --- | --- |
| `performTransaction` 全程 | **14.79ms** | `iop_tl` p50 `enter->ret` |
| └ 其中 `prepare`/`map` 26MB | 5.93ms | `enter->src` |
| └ 其中 26.1MB 非临时写 | 4.68ms | `vb->copy`（≈5.6 GB/s 到 WC aperture） |
| └ 其中收尾 | 3.21ms | `copy->ret` |
| └ 其中**等 vblank** | **0.001ms** | `src->vb` |
| `performTransaction` 之外（Metal/Vulkan 提交 + 合成） | **≈21.1ms** | 35.9 − 14.79 |

**⇒ A-83 的靶子非常明确：这 21.1ms 是最大的单块，而它里面最重的是 §2.3 那两把锁。**

### 3.4 顺带发现：page-off 服务线程 100% 空转，命中率 0.27%

`attribute.py` 追父链，挖出一条**此前没人看过的事实**：

```
CPU 工作的 mach_msg2_trap 合计 5849 样本 = 1.57 核当量
    3720 = 1.00 核  (63.6%)   io_connect_method ← IOConnectCallScalarMethod ← nvmtl_po_service ← _pthread_start
    1088 = 0.29 核  (18.6%)   ... ← drmSyncobjWait ← vk_drm_syncobj_wait_many ← vk_common_WaitForFences
     767 = 0.21 核  (13.1%)   ... ← drmXeGfxRawIoctl ← drmIoctl ← anv_gem_execbuffer_impl ← i915_queue_exec_locked
```

`Thread_13340` 的栈**整条只有四行**，3720/3720 样本全部在同一个 ioctl 里：

```
Thread_13340
  thread_start → _pthread_start → nvmtl_po_service (NVMTLDriver) → IOConnectCallScalarMethod
    → io_connect_method → mach_msg2_trap
```

配合 A-82 的账本（本关重读，**数字变了，方向没变**）：

| 计数 | A-82 报告 | **A-82b 实测（17:29）** | 含义 |
| --- | --- | --- | --- |
| `before-scan` 调用 | 1759 | **10627** | 上屏前要页面 |
| └ `sent`（命中） | 28（1.6%） | **29（0.27%）** | **命中率又掉了一个数量级** |
| └ `no entry` | 1731 | **10598** | 查不到「插件标过 current」的那条 |
| `page-offs` 实际完成 | 34（均值 5.5ms） | **31（均值 5.968ms）** | 真拷的次数没涨 |
| `sel6 gave / empty` | 189 轮询 | **gave 32 / empty 2832** | 轮询 2864 次，只有 32 次有活 |

**读法**：`nvmtl_po_service` 这个线程**把 100% 的墙钟花在「问有没有活」的 ioctl 上**，2864 次轮询只换来
32 次真活；同时上屏侧 10627 次请求只有 29 次命中（0.27%）。**它是一个纯空转的服务线程。**

> **它烧不烧 CPU？** 算术上不烧：若它真在 100% 自旋，仅这一线程就 ≥1.0 核，加上 `ws_main` 的 0.43 核
> 就已经超过 `ps` 实测的 0.91 核。所以它是**阻塞在内核里等活**（每次 ioctl 约 4ms 超时返回）。
> 结论：**它不抢 CPU，但它是一个永远占着、永远没活的线程，而且 page-off 那条路本身是死的。**

## 4. 本关推翻/修正了什么（写给 A-83 用）

| # | 提示词或前序报告的说法 | 本关实测 | 影响 |
| --- | --- | --- | --- |
| 1 | 「38.5ms 里有 **12ms 纯等待**」 | **不存在**。`src->vb` 等 vblank **0.001ms**；`performTransaction` 总共 14.79ms，其中 13.7ms 是**真活**（映射 5.9 + 拷贝 4.7 + 收尾 3.2） | 「等」不是问题，「干」才是。别再去优化 vblank 同步 |
| 2 | 「GPU 利用率低 → SLPC 压频 → 合成慢 → 帧率低 → 利用率仍低，**自我锁死**」 | **不成立**。GPU Active 是占空比，真锁频会顶到 ~100%，实测 20%；两个加负载实验都是负结果 | **「提频」这一刀没有靶子，别做**（§5 建议里明确写） |
| 3 | 「不是算力不够，是流水线串行 + 等待」 | **前半句对，后半句错**：是流水线串行，但**不是等待**，是**单核 CPU 打满**（35.9ms/帧、99% 核、比值 1.04） | 优化方向从「减等待」改成「减 CPU 工作」 |
| 4 | A-82 §3.2「page-off 命中率 1.6%」 | **实际 0.27%**（29/10627），更糟；且 `nvmtl_po_service` 线程 100% 空转 | 修 1.6% 那个靶子之前，先修「线程根本没在服务」 |
| 5 | 「38.5ms ≈ 4.6 个 8.33ms」 | 实测 **34.52ms = 4.14 拍**（本机 119.891Hz，拍长 8.341ms，不是 8.33） | 差 1.5 拍，正好是 4 拍与 6 拍的区别 |
| 6 | 帧率「30–32」 | 本关四轮独立复测：**31 / 30 / 31 / 31**（p50），`ps` 口径 27.5–31 | 基线稳定，可作 A-83 的对照锚点 |

## 5. 给 A-83 的一句话建议

> **GPU 一点没使劲（20%），CPU 已经使满（99% 单核）——所以「提频 + 流水线」这一刀只有后半截有靶子，
> 整树换血值得做但预期是 40 帧不是 60：换血能砍掉 `performTransaction` 里的映射 5.9ms + 拷贝 4.7ms ≈ 10.6ms
> （35.9 → 25.3ms/帧 ≈ 40fps，正好跨过 3 拍那一档），剩下的 8.7ms 缺口在 `performTransaction` 之外的
> 21.1ms 里，靶子是 `NVMTLCommandBuffer` 那三把锁（占 ws_main 墙钟 15.2%）和 `CA::Render::Fence::resolve_batches`
> （占 render-server 45.3%）——这是第二刀，换血换不到。**

**展开成三条可执行判断：**

1. **别做提频**（`i915_enable_rc6=0` 等）。没有证据支持低频，且加负载实验方向相反。省下那一轮重启。
2. **换血值得做，但目标定 40 不是 60。** 它同时能把 page-off 从「0.27% 命中 + 100% 空转」变成真命中 ——
   这是换血除帧率外的第二个收益。
3. **要 60 必须动合成提交路径**（锁 + fence 解析 + `anv_gem_execbuffer` 的 ioctl 次数），
   这不是换驱动能解决的，需要在 `NVMTLDriver` 侧改。A-83 若只换血，做到 40 帧就该收手写报告。
