# G7 · A-90 报告：开机直通三种修法全部被证伪；「App 首次启动慢」的真因是每次启动都带不起 GPU

> 日期：2026-11-03 21:28 – 22:30（**11 次整机冷启动**、1 次 panic、1 次自伤事故并已完全恢复）
> 目标：A = bootArm 之后不重启 WindowServer 也能出帧；B = 把 App 的"首次启动代价"降下来或说清它是什么。
>
> **一行结论（三个数）**
> ① 今晚 11 次冷启动，除 1 次提前中止，**每一次都仍然需要重启一次 WindowServer**——A1/A2/A3 三种修法全部无效；
> ② App 热启动中位 **5.19 s**（文本编辑 4.93 / 5.19 / 6.35）、**4.97 s**（计算器 3.93 / 4.97 / 6.23）；
> ③ 把 1919 个文件的共享着色器缓存整体搬走后，这两个 App 的启动**一个新文件都没写**（冷 4.95 / 4.38 s，与热同档）。
> ⇒「首次慢」不是着色器缓存，而是**每次启动都花 2.08 s 带起 ANV 然后失败**（`vkEnumeratePhysicalDevices -> 0`）。

## 1. 问题 A · 机制证据（先把"为什么"钉死）

### 1.1 时间线：WS 枚举比 pipe 存在早约 55 秒

```
21:18:03  syspolicyd/kernelmanagerd：XeGfxIntelFB 开始加载（开机第 5 秒）
21:18:05  XeGfxIntelFB: EDID 256 B ... refresh measured 120.00 Hz
21:18:06  XeGfxIntelFB: published IOFBDetailedTimings（面板模式已发布）
21:18:12  XeGfxIntelFB: scanout described: mode 0x64 3120x2080
21:18:18  WindowServer[204] [com.apple.CoreDisplay] [ERROR]
          Unable to find display pipe for IOFB service / regID: 0xb613 / 0x1000004f4   ← 就在这里放弃
21:19:02  bringup: core loaded（登录 + 25 s 沉降之后才允许加载 i915）
21:19:09  bootArm: boot_steps=123（bit32 iop）
21:19:31  bringup: bootArm armed but no frames yet -- restarting WindowServer once
21:19:50  iop_xe_flips 12 -> 18，出帧
```

`NMXAccel` 侧同步证据（同一次开机前后）：

```
21:47:15.813 NMXAccel: sysctl debug.xegfxaccelfb=3: scanout-backed display pipe ENABLED, re-delivering the mode change
21:47:15.813 NMXAccel: boot-armed: 4/6 ... -> head 4 has a display pipe (piped 0x10) after 0 ms
```

**判据成立**：WS 在 ~20 s 完成 display 枚举（此时 `piped=0`），display pipe 在 ~70 s 才出现；
CoreDisplay 记录"这块 IOFB 没有 pipe"之后**再也不问第二次**。重启 WS 之所以有用，是因为那是一次全新的枚举。

### 1.2 为什么不能把 pipe 提前：25 s 沉降是硬约束

`xegfx-bringup.sh` 第 3 步之前有 `sleep 25`（A-25b：在 loginwindow 期推 stage 7 会让 WS 在 `push_surface` 断言）。
core 要到登录后 25 s 才加载，accel 的 bootArm 又要等 core → **pipe 永远晚于 WS 的枚举**。这不是脚本写得不好，
是"必须等真人桌面"和"WS 一定在开机 20 s 内枚举"两条约束的交叉结果。

## 2. 问题 A · 三种修法，逐条结果

### 2.1 A3（先做，最便宜）：显示器 DPMS 关/开，代替重启 WS —— **证伪**

对照组（健康桌面、21:29，未重启）：

```
21:29:27 displayWillSleepWithImages
21:29:32 displayDidWake
21:29:32 IOFBSetDisplayModeAndDepth: Setting mode 0x64 ... displayID 0x23d05e40 fbRegID 0x1000004f4   ← 唤醒会重新设模式
```

冷启动实测（boot #1，21:46）：

```
21:47:43 A-90: no frames -- display sleep/wake first
21:47:48 A-90: display wake asserted
21:47:46.880 WindowServer[204] displayDidWake          ← 唤醒事件到了
（此后 15 秒内没有任何 IOFBSetDisplayModeAndDepth）      ← 但没有模式要设
21:48:04 bootArm armed but no frames yet -- restarting WindowServer once
```

**结论**：唤醒只对"已经拿到 pipe 的显示"有意义；开机时那块显示从未有过 pipe，唤醒走不到设模式那一步。

### 2.2 A2：让加速器重送一次模式变更（`debug.xegfxaccelfb=3`）—— **证伪**

boot #2（21:51）：`21:53:27 A-90[accel]: re-delivering the mode change ... waiting up to 120 s`，
**到 21:55:15 我进入下一轮时 `iop_xe_flips` 仍是 0**（110 秒零帧）。同一路径在 bootArm 内部也走过一次（21:47:15），同样无效。
（A-44 记录的"重送会卡住事务计数 1–2 分钟"在这里表现为：计数器全程 0，看不出被卡，但就是没有帧。）

### 2.3 A1：让 FB 重放 display 通知 —— **能发出去，但没用**

三次迭代（源码 `kexts/XeGfxIntelFB/intelfb.cpp`，全部走 `bin/nvgfx/build_xegfxintelfb.sh` 重编 + AuxKC 重建）：

| 迭代 | 做法 | 结果 |
| --- | --- | --- |
| v1 | 静态 `SYSCTL_PROC(_debug, …, xegfxfb_notify, …)` | `sysctl: unknown oid 'debug.xegfxfb_notify'`——没注册上。**同一写法在 A-60 版源码里是有效的**（现装的元件 `sysctl debug.xegfxintelfb_scale1x` 读回 1），差异未查明；v1 那次是从 A-56 老树构建的，怀疑与树的差异有关 |
| v2 | `thread_call_enter1_delayed` 在 +70 s / +95 s 各打一次 | 只有 "armed" 日志，**投递从未发生**（同 kext 的 guard 用 `thread_call_enter_delayed` 就能跑，差别就在 enter1） |
| v3 | 全局 mask + `thread_call_enter_delayed`（照 guard 的写法） | **投递发生了**：`22:07:31.961 / 22:07:56.961 A-90 notify: delivering mask 0x3 (mode 0) to the clients`；`iop_xe_flips` 仍为 0；22:08:36 仍靠重启 WS 出帧 |

v3 的 `mask 0x3` = `kIOFBNotifyOnlineChange` + `kIOFBNotifyDisplayModeDidChange`，`mode 0` 是因为 WS 从未对这块 FB
调用过 `setDisplayMode`。**通知到了客户端层，但 CoreDisplay 没有因此重建显示。**

### 2.4 门 A 判定与结论

| 判据 | 要求 | 实测 | 判定 |
| --- | --- | --- | --- |
| `frames are reaching the panel` 出现 | 3/3 次 | 11/11 次都出现了——**但除 1 次提前中止外，每一次都是重启 WS 之后** | ❌ |
| bringup 日志里没有 `restarting WindowServer` | 3/3 | 10/10 都有 | ❌ |
| 登录后不需要重新登录 | — | 每次都要 | ❌ |
| 拖动 p50 与现在同档（±1 ms） | 25 ms 档 | **未采样**：恢复后 load 16.5，A-89 脚本按设计拒绝（`REFUSED: load >= 3`） | — |

**按 §2.3 收口：这不是"缺一个通知"，是 CoreDisplay 的枚举时序——display 在 pipe 存在之前被登记，
之后没有任何一个 FB 子类可用的通知能让它重新枚举。本栈无解，不动系统服务（A4）。**
代价如实写进 README：每次开机多约 40 秒 + 一次重新登录。

## 3. 问题 B · 先量，结论是「靶子错了」

### 3.1 方法

- 启动耗时 = `open -a` 的 monotonic 起点 → 该 **pid** 的 layer-0 窗口出现在 `CGWindowListCopyWindowInfo` 上
  （自写 `winwatch2`，20 ms 轮询；pid 匹配，绕开 owner name 被本地化的问题——`文本编辑` / `计算器`）；
- 归因 = 启动期间 `log stream --info --debug` 抓该进程，统计 `spvcache: caching in` / `translated` / `cache hit` / NVMTL 设备带起；
- 冷 = 把 App 用到的那份缓存目录整体移走（本关实际执行：`~/Library/Caches/nvmtl/spvcache`，1919 文件）。

### 3.2 冷/热耗时表

| App | 热 ×3（ms） | 中位 | 冷（缓存整体移走） | 冷启动后缓存增量 |
| --- | --- | --- | --- | --- |
| 文本编辑 | 5188 / 6348 / 4926 | **5.19 s** | **4.95 s** | **0 个文件（目录都没被创建）** |
| 计算器 | 6226 / 4971 / 3932 | **4.97 s** | **4.38 s** | **0 个文件** |
| 预览 | 无 layer-0 窗口（不打开文档时） | — | — | 测量方法不适用 |

> 说明：这批数字是在 load 2–16 的机器上取的（重启后登录项在跑），绝对值偏大；关键是**冷热同档**，
> 这与"它们不在自己进程里翻译"完全一致。

### 3.3 归因：慢的不是着色器，是每次都要带一次 GPU 然后失败

`22:20` 一次计算器启动的原始日志（同一进程）：

```
22:20:01.161 NVMTL: initWithAcceleratorPort:34819 ... GPU vendor 8086 (Intel, ANV) ... allow-listed: Calculator
22:20:03.243 NVMTL: vk: driver opened directly: /Library/GPUBundles/nvmtl/libvulkan_intel.dylib
22:20:03.244 NVMTL: vk: zero physical devices through this ICD — vkEnumeratePhysicalDevices -> 0, count 0
22:20:03.244 NVMTL:   NVK did not come up in this process - refusing to be the Metal device for Calculator
```

- **2.083 s**（01.161 → 03.244）花在把 ANV 带起来、枚举到 **0 个物理设备**、然后放弃；
- 之后 App 回落（CPU 渲染），窗口在 ~4.4 s 上屏——**2.08 s 占了一半**；
- 这不是"首次"代价：**每次启动都付**（热启动同样有这两行）。

**结论：在这台机器上，除 WindowServer 之外的用户态进程根本拿不到 GPU。**
"App 首次启动慢"这个用户感受是真的，但它的成因不是 A-86 §6.3 那条冷缓存（那条是 WindowServer 自己的、
一次性 3.6–11.5 s），而是**每个 App 每次启动一次的 2 s 设备带起失败 + 全程 CPU 渲染**。

### 3.4 B1 共享缓存池：可行性评估（结论：**不做**，理由变了）

| 项 | 结论 |
| --- | --- |
| 改动点 | `plugin/NVMTLLibraryLoad.m:402 nvmtl_spvcache_dir()`：`beside`（aircache 同级）→ `own`（`confstr(_CS_DARWIN_USER_CACHE_DIR)/getprogname()`）→ `tmp`。把 `own` 里那个 `getprogname()` 去掉即可让同一用户的 root/沙盒进程共用一个池 |
| 对普通 App 的收益 | **0**。它们不翻译（§3.2 缓存增量为 0），缓存池再共享也没有命中可言 |
| 对沙盒 App 的收益 | 有，但沙盒进程只能写自己容器；要让它们共享，需要 **(a) root XPC helper 代写** 或 **(b) 带 application-groups entitlement 的 group container**——两者都动签名/权限，超出"改个 key" |
| 对 WindowServer 的收益 | 已经是一份热缓存（1088 文件/290 MB），共用不会更快 |
| 风险 | 中（`<wtl>` 那段注释写明：WindowServer 沙盒只允许写 `…/C/WindowServer`，改错就是"每个 App 每次都从零翻译"的最坏情况） |
| 建议 | **不做 B1**。真正值得做的是 B0：让 App 进程拿得到 GPU（改 Accel 的 user client / ANV 设备枚举，使 `vkEnumeratePhysicalDevices` 不再返回 0）。收益是每次启动 −2 s 以上，且 App 真的用 GPU；风险中高，属下一关独立课题 |

## 4. 异常记录与可回滚点

### 4.1 本关自伤（已完全恢复，必须记下来）

**拿错了源树。** 仓库里 `kexts/XeGfxIntelFB/intelfb.cpp` 只有 22.5 KB（**A-56 时代，`scale1x` 计数 0**），
而**装机的 FB 是 A-60 版**（44 KB，`scale1x` 计数 7，源码就是仓库根的 `tmp_intelfb_60.cpp`）。
A1 v1 用错的那棵树构建并安装 → **boot #3–#5（21:57–22:10）跑的是旧 FB**。
发现方式：boot #3 的 `system_profiler` 里 `scale1x` 日志消失、二进制 72912 B ≠ 元件 77920 B。
恢复方式：用 `tmp_intelfb_60.cpp` 重编 → **sha256 与元件逐字节一致**：

```
d4c74c03ac475e94df76ff3715abad6608446682150f4e5b879c46db575c8a62   /Library/Extensions/XeGfxIntelFB.kext/Contents/MacOS/XeGfxIntelFB
```

装配 → `kmutil create` → `kmutil inspect` 6 个 `watchthelight` id + `IGPUConsoleRange` 齐全 → 重启后
`Resolution 3120 x 2080 / UI Looks like 1560 x 1040 @ 120.00Hz / Online: Yes`，帧流正常。

**教训（写给下一关）**：装机二进制要在**第一次**改动前就从 `/Library/Extensions` 备份，并且**备份只备份一次**
（本关的 `install-fb-a90.sh` 每次安装都覆盖 `.before`，导致 restore 时拿到的是 v1 补丁件，才不得不从源码重建）。
另外：`build/nvgfx/build_xegfxintelfb.sh` 对同一份源码**可复现**（两次构建 sha 相同），这是能救回来的原因。

## 5. 下一步（如果要继续）

1. **别再做 A**：CoreDisplay 枚举时序，本栈无解（§2.4）。真要省这 40 秒，只有 A4（延后 WS 启动）一条路，
   属于动系统服务，风险与收益都不划算。
2. **B 换成 B0**：查清 `vkEnumeratePhysicalDevices` 为什么在非 WindowServer 进程里返回 0
   （大概率是 Accel 的 user client 只允许一个持有者 / ANV 的 DRM 节点只给 WS 开）。
   这条一旦通，用户感受是"每次开 App 都少卡 2 s 以上 + App 真的用 GPU"，比共享缓存池划算得多。
3. **顺手修**：`drm_syncobj_create_ioctl` 里的 `malloc`（§4.2），它是这台机器今天 4 次 panic 的共同签名。
