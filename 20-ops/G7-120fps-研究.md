# G7 · 120fps 研究报告（2026-11-02）

> 委托：把桌面实际帧率从当前 18–21 fps 提升到 120 fps。
> 方法：读本仓全部记录 + 上游/第三方 GitHub 前人成果，不做无依据猜测。
> 结论先行：**面板模式本身已经是 120Hz；缺的是每帧 8.33 ms 预算内的交付能力。
> 最相关的前人成果是 Mountainatic/ArrowWhatever（27 个可重放补丁 + 完整性能文档），
> 他们已把同类栈推到 ~70 fps（3840×2400 后备光栅 @240Hz）。要逼近 120，需要移植
> 他们的性能链 + 解决我们自己独有的「WS CPU 着色器编译」大头。**

---

## 1. 问题定义

| 项 | 值 | 来源 |
| --- | --- | --- |
| 面板模式 | 3120×2080 @ **120Hz**（HiDPI 2×，UI 1560×1040） | 总账 / README |
| 实际桌面帧率（拖动 25 秒逐秒） | 中位 **19**，均值 18.1，最大 21 | 总账 2.1 |
| 每帧预算 @120Hz | **8333 µs** | 总账 |
| 当前一帧实际耗时 | ~52 ms | 由 19fps 反推 |
| 显示路径 | CPU 拷贝（A-69 非临时存储）3.0–3.9 ms，事务 3.85 ms，同步阻塞 WS | 总账 2.3 |
| WS CPU 构成 | ANV 编译 26.5% + CA::OGL 15% + NVMTL 12–13% + Render::Updater 5.7% + naga 3.7% ≈ **65%**；等待仅 1.2% | 总账 2.2 |

**结论：这不是「显示模式没开 120」的问题，是「每帧成本 52 ms ≫ 8.3 ms」的问题。**
两块成本：① 同步事务 3.85 ms（拷贝路径固有）；② WS CPU 渲染+翻译+编译 ≈ 36 ms（大头）。

## 2. 前人成果（GitHub 调研，2026-11-02）

### 2.1 Mountainatic/ArrowWhatever —— 最直接的前人

仓库：https://github.com/Mountainatic/ArrowWhatever
（Core Ultra 9 275HX / Xe-LPG，macOS Tahoe；基于 XeGfx 0.0.44 基点 `5a19a73f` + 插件基点 `497d521e`）

他们已实现且**全部有数据**的优化链：

| 技术 | 效果 | 出处 |
| --- | --- | --- |
| **K9 延迟翻转**：WS 提交不等 GPU，内核 worker 等 GPU 空闲后在 vblank 写 `PLANE_SURF` | 2560×1600@60 下面板路径从 **~15 fps → ~60 fps** | XeGfx README / k9-deferred-flip.md |
| **按帧排序（per-frame marks）**：插件在 commit 时把本帧 surface 标 pending，GPU 做完标 ready；worker 只等**本帧自己的标记**，不再等整个 GT 空闲 | 解决「任何进程的长 batch 拖住翻页」；这正是我们 A-53/A-54 flip 变慢的原因（我们的 K9b 等整个 GT 空闲） | frame-pipeline.md |
| **WS no-wait**（`xemtl-ws-nowait` 哨兵，开机 LaunchDaemon 重建）+ 排序交给 accel | 配合 marks 才有效（我们 A-54b 单独开 no-wait 更慢——因为没有内核侧排序配对） | frame-pipeline.md |
| **HIGH 优先级**：WS 的 Vulkan 队列用 `VK_KHR_global_priority` HIGH，GuC 先调度合成 | 减少其他 GPU 任务干扰 | frame-pipeline.md |
| **Tile4 扫描 + IOSurface Device Cache + page-off + CCS_E 压缩** | 相同负载下翻转吞吐 **76 → 97–99 次/秒**；窗口动画多层合成显著改善 | page-off-and-compression.md |
| **超时照样 arm**（`idle_forced` 逃生口） | defer 不再被连续失败永久关掉 | frame-pipeline.md |
| 原生显示 KMS + 双管拼接 + DSC + 240Hz HiDPI | 1920×1200 HiDPI @ 240Hz，3840×2400 后备光栅 | kms-boot-mode.md |

**他们当前状态：桌面实际 ~70 fps**（275HX，3840×2400 后备光栅）。他们自己的帧流水线分析给出的一般规律：

> 一帧占 ⌈(合成+arm)/vblank⌉ 个 vblank。**想稳定 120Hz，合成+arm 必须压进一个 vblank 预算**（他们的 240Hz 面板上是 4.17 ms；**我们的 120Hz 面板上是 8.33 ms**）。他们的实测：合成 8.5 ms → 3 个 vblank（80fps）；2–4 ms → 2 个（120fps）。

他们公开的全部工具与日志在 `scripts/tools/`（fps-probe、anim-probe、flip-sampler、`debug.nvaccel_iop_xe_tl` 逐帧时间线）——**这套测量工具本身就是我们缺的仪器**。

### 2.2 上游 watchthelight-labs/XeGfx / NvGfx (xe)

- 上游**没有采纳** ArrowWhatever 的性能补丁（"We have not taken a patch yet"）。
- 上游自己的面板是 2560×1600@165Hz——`2560×4=10240=256×40`，CA 行距与扫描行距**天然相等**，所以 pitch 闸门从未咬过他们。
- 我们已提 **issue #14**（3120 宽面板上 `q.pitch==P` 永假 → defer flip 永不运行），并给出三个解法，其中最小改动是方案 1（放宽闸门 + 在 arm 时写 `PLANE_STRIDE`）。
- NvGfx xe 分支 2.6.3+ 含 host-pages 缓存等更新（A-67 已按 hunk 移植，无害但对合成器无收益——该路径服务 app）。

### 2.3 steelbrain/metal2vulkan

- 无性能相关 issue（仅许可证讨论）。**WS 着色器编译/每帧 pipeline 重建问题没有现成前人答案，需要我们自证**（总账遗留的「量化 CA 每帧创建多少 pipeline」仍是必要一步）。

### 2.4 我们已试过且被证伪的路（总账第四节，不再重复）

零拷贝 flip 按本地 K9b 原样跑（等 GT 全空闲）更慢；单独 no-wait 更慢；缩 backing CoreDisplay 拒绝；VkPipelineCache / 函数对象缓存 / 2.6.6 整换 / 双缓冲 / 关 vblank 等待 / 异步上传——全部无益或有害。
**注意：A-53/A-54 的失败 ≠ ArrowWhatever 路线的失败。他们的 marks 按帧排序正是针对我们失败的根因。**

## 3. 差距分析（数字对齐）

| | ArrowWhatever 当前 | 我们当前 | 要 120fps 需要 |
| --- | --- | --- | --- |
| 机器 | 275HX（8 P 核 + 更多 Xe 核） | 255H | — |
| 后备光栅 | 3840×2400（9.2 MP） | 3120×2080（6.49 MP） | 6.49 MP |
| 显示路径 | GGTT 零拷贝 + marks 延迟翻转 | CPU 拷贝 3.85 ms 同步 | <1 ms（异步翻转，WS 不阻塞） |
| 合成 | ~5.4 ms（2 MP 探针窗，Tile4 开） | ~36 ms CPU（编译为主，未测 GPU 分解） | ≤8.33 ms 合计 |
| 实际帧率 | ~70 fps | 19 fps | 120 fps |

两个独立的墙：
- **墙 A（显示路径）**：3.85 ms 同步事务 + 撕裂/双缓冲问题 → ArrowWhatever 的 0008/0009/0012/0024 + 0026 整链可解，且有他们逐帧时间线数据背书。
- **墙 B（WS CPU 编译）**：~36 ms/帧的 CA 渲染+翻译+编译，**ArrowWhatever 文档没有正面讨论**（他们 275HX 的 CPU 更快 + 或许其插件 port 已含缓解）。我们不确定按帧 marks 之后这堵墙剩多少——**必须先量化再动工**。

## 4. 建议路线（分阶段、每步有验收判据、可回滚）

### 阶段 0 · 测量先行（不动任何驱动，≈ 半天）

1. 移植 ArrowWhatever `scripts/tools/` 的 fps-probe / anim-probe / flip-sampler（纯用户态 Python，直接可用）。
2. 在 accel 加 `debug.nvaccel_iop_xe_tl` 逐帧时间线（0024 的测量部分单独按 hunk 移植）——把 52 ms 分解到「排队→取出→合成→arm→latch→通知→下一帧」。
3. 执行总账遗留的 **A-72：pipeline 创建计数**（每秒创建次数 + 去重后数量），判定墙 B 真实大小。
   - 验收：得到拖动场景的逐帧时间分解 + pipeline churn 数字。

### 阶段 1 · 零拷贝翻转链（墙 A，预计 1–2 天）

按依赖顺序把 ArrowWhatever 的 accel/插件性能链按 hunk 移植进 2.6.2 树（沿用 A-67 的移植方法，不整目录替换——A-65 教训）：

- `0008` GGTT flip slots（core 侧）
- `0009` accel 零拷贝翻转（含我们 issue #14 的 pitch 解法：3120 宽需要放宽闸门 + arm 时写 `PLANE_STRIDE`——A-47/A-49 已探明地形，A-49 缺的「arm→翻页」一环按 0009/0024 的完整实现补齐）
- `0012` present/boot-arm 衔接
- `0026` 插件 marks（pending/ready 标记 + no-wait 哨兵 + `VK_KHR_global_priority` HIGH）
- `0024` 延迟翻转按帧排序 + 超时照样 arm 逃生口
- 验收：`iop_xe_flips` 与 `markonly_flips` 增长、WS 事务返回 <1 ms、拖动帧率 ≥ 30 fps（ArrowWhatever 同类改动 15→60 的按比例预期下限）。

### 阶段 2 · Tile4 / page-off / CCS（墙 A 余量 + GPU 带宽，预计 2–3 天）

- `0024`/`0026` 的 Tile4 扫描、IOSurface Device Cache、page-off、CCS_E 压缩部分。
- 验收：同负载翻转吞吐对齐他们的 76→97–99 曲线方向；拖动 ≥ 45 fps。

### 阶段 3 · 墙 B（视阶段 0 数据决定）

- 若 pipeline churn 高：弄清 CA 为什么每帧要新 pipeline（spec constants？render pass 变化？），或把编译改异步（兜底 pipeline 过渡帧）。
- 若 CA 绘制本身重：减少图层/效果（Liquid Glass 的 5–14 层整窗读写是带宽杀手，他们的文档点名过）。
- 验收：合成+arm ≤ 8.33 ms，稳态 120 fps。

### 备选方案 A'（如果按 hunk 移植太痛苦）

在 `~/src` 里按 ArrowWhatever 的重放说明**整树构建他们的 0.0.44 基点栈**（他们验证过 27 补丁可完整重放），再把手面板时序换成 3120×2080@120。工作量大、要整机切换（需用户在场+可断电回滚），但每一步有前人验证。**仅当阶段 1 的移植冲突过多时才走这条。**

## 5. 现实预期（不粉饰）

- ArrowWhatever 自己当前也只有 ~70 fps，且他们 CPU/GPU 都更强、面板带宽条件更好（DSC 双管）。
- 我们 6.49 MP @120Hz 要 8.33 ms/帧全链路，**是激进目标**。合理预期：阶段 1 后 30–40 fps，阶段 2 后 45–60 fps，阶段 3 视墙 B 大小决定能否接近 100–120。
- 「模式 120Hz + 实际 60–90」已经是非常好的结果；「稳定 120」需要墙 B 被实质性解决。

## 6. 风险与护栏（来自本仓教训）

- A-49：arm→翻页缺一环会让 WS 卡死到断电——阶段 1 每一步装机前先做完整 A-49 式验证（`boot_steps`、六 id、`iop_ok` 增长）。
- A-65：绝不整目录换版本；只按 hunk 移植。
- boot guard：每次失败后 `sudo nvram xeintelfb-starts=%00` 再重启；连续两次崩溃后 FB 拒绝 probe。
- 既有 panic（`thread_invoke: preemption_level 1`）随时可能再来一次，表现为「iop_ok 恒 0」，先清 NVRAM 重启再归因。
- 改动前照例：AuxKC + 原 kext 备份到 `~/xegfx-log/<日期>/`，`kmutil inspect` 核对 `IGPUConsoleRange`。
