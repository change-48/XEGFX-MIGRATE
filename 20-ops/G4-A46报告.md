# Gate 4 · A-46 执行报告：bootArm 第 6 步已打开，但零拷贝 flip 未进帧路径

## 1. 一行结论

**`boot_steps = 123`（0x7B，含 `64`），`6/6` 日志出现 `iop_xe_flip=1 + iop_xe_defer=1` —— bootArm 六步全部跑通；但 `iop_xe_defer_queued = 0`、`iop_flip = 0`，3277 帧全部仍走 CPU 拷贝（`iop_copy_sum_us = 14 869 019 µs`，约 4.5 ms/帧），零拷贝 flip 被 `pitch == q.pitch` 挡住：合成器的 IOSurface 行距是 **12544**，scanout 的行距是 **4×3120 = 12480**。**

判定：判据 **4、5 通过**，判据 **6、7 不通过** —— 本关按判据表**未达成**（按 §4 表属于"flip 分支被别的条件挡住 → 停手贴原文"，未做任何补救性改动）。

## 5. 为什么 flip 没进帧路径（源码原文，不写改法）

### 5.1 bootArm 第 6 步的置位是活着的

`gIopXeFlip` / `gIopXeDefer` 读回都是 `1`，且全文件只有三处会写：初始化（:1545）、flip 失败清零（:1781/:1834/:1882，本关均未触发，否则读回会是 0）、bootArm（:3017）。所以武装没问题，问题在**分支判据**。

### 5.2 帧确实到达 performTransaction 的 defer 判据前


| 条件 | 实测 | 依据 |
| --- | --- | --- |
| `gIopXeDefer` | 1 | `debug.xegfxaccel_iop_xe_defer: 1` |

### 5.3 旧 flip 也不适用于这块面板

```
// nvrm-accel.cpp:3772 nvAccelIopFlip()
if (!gIopFlip || !fb || !s || head >= kNvMaxFB) return false;
// zero-copy scan-out is an NVIDIA display-engine flip; another vendor's panel (NMIntelFB) always takes the copy
if (!fb->metaCast("NVRMNVDAFramebuffer")) return false;
```

`fb` 是 `XeGfxIntelFramebuffer`，不是 `NVRMNVDAFramebuffer` → 旧 flip（`iop_flip`）在这块屏上**结构性地为 0**，所以 `iop_flip` 增长这一条判据在 XeGfx 面板上本来就不可能靠它满足；新路径（`iop_xe_flips` / `iop_xe_defer_queued`）是唯一可能，而它卡在 pitch。

> 说明：`q.pitch` 没有 sysctl 暴露，上表最后一行是"排除法"结论（同一组 `qr/q.kva/q.width/q.height` 在拷贝路径被测通且未计数失败，defer 块中唯一未被证实的剩余项就是 `q.pitch == P`），不是直接读到的值。

## 8. 一句话给下一关

bootArm 的六步已经是**唯一正确的武装方式**，问题不在武装、而在 `q.pitch == P` 这条等号：合成器给的是 12544（64 字节填充），scanout 是 12480。在动任何代码之前，先把 scanout 的实际 pitch 读出来坐实（当前 kext 没有暴露它的 sysctl），否则下一关仍然会在同一个等号上原地打转。
