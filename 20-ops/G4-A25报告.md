## 1. A-25a：是否还在软件合成（不重启，已量准）

### 1.1 方法

之前两次 sample 都采在静止桌面，两边都是 0、没有判别力。这次自建了一个**动画面发生器**（`/tmp/anim.swift`，已编译为 `/tmp/xegfx-anim`）：
一个 1100×700 的窗口里放 120 个彩色图层，每个图层同时跑 position / rotation / scale 三条 `CABasicAnimation`，`repeatCount = ∞`。
CA 动画由 render server（也就是 WindowServer）合成，**正好压的就是"合成"这件事**，比 `open -a TextEdit` 更能区分"GPU 合成 vs 软件合成"。

启动姿势（ssh 会话直接跑会被 audit session 挡住，必须先注入用户会话）：

```bash
sudo launchctl asuser 501 sudo -u change48 /tmp/xegfx-anim &
# 直接跑会报：Could not switch to audit session 0x186a0: Operation not permitted
```

### 1.3 未加载基线（A/B 的另一半）：**拿不到，已说明**

按提示词 §3.2 先试了卸载：

```
kmutil unload -b org.watchthelight.XeGfxAccel → kext is in use or retained (cannot unload)
kmutil unload -b org.watchthelight.XeGfx      → 同上
```

WS 已经持有这个驱动，卸载被内核拒绝。原计划的替代路径是"重启后趁未加载先采一次"，但 A-25b 的自启正好在开机早期就把 accel 拉起来了，两条路都断了，**故 A-25a-5 记为 N/A**。

替代论证（比基线更强）：`PerformanceStatistics` 全 0 是**绝对证据** —— 只要 WS 有任何一个合成帧走 GPU，`bufferSwapCount`/`context2DCount` 不可能为 0。基线值是多少都不影响"这次是软件合成"这个结论。

### 1.4 为什么插件装好了还在软件合成（机制判断）

- 17:36:48 WS 日志确认它**拿到了** Metal 设备：`NVMTL: vk: UP in this Metal process — "Intel(R) Graphics (ARL)" api 1.4.363`。
- 但合成走 `CA::OGL::SW`。合理解释：`debug.xegfxaccelfb=3` 是 **CPU copy 呈现**，framebuffer 没有可被 GPU 直接写的 scanout surface，CoreAnimation 判定该 display 不可 GPU 合成 → 回落到软件光栅再拷出去。
- 也就是说：**这不是插件层的 bug，是呈现路径（scanout）的问题**。继续在 GPUBundles / 平台位 / Metal 能力上报上折腾不会让它变。

## 2. A-25b：自启（失败，已回退）

### 2.1 做了什么

- `/usr/local/bin/xegfx-boot.sh`：等 fbgeom（带"本次开机"时间戳判定）→ `kmutil load core` → `wdog=60`、`stage=7` → 睡 20 s → `kmutil load accel` → `accelfb=3` → 记录 `results` / NMXAccel 数 / `vmmap nvmtl`；带 attempts 计数，连续 3 次不成功自禁用。
- `/Library/LaunchDaemons/org.xegfx.boot.plist`：`RunAtLoad=true`、无 `KeepAlive`、`ProcessType=Background`、stdout/err → `/var/db/xegfx/boot.{out,err}`。
- **桌面态干跑两次全绿**：

```
[17:47:34] core loaded, stage sysctl present
[17:47:54] stage=7 已推进
[17:47:56] NMXAccel 实例出现（第 1 次尝试）
[17:47:59] accelfb=3 已设置
[17:47:59] results: 0 1 1 1 1 1 1 1
[17:48:05] vmmap nvmtl = 18 ✅
```

### 2.2 冷启动现场（失败）

17:54:37 开机自启实跑：

```
[17:54:37] === boot-arm start (attempt 1) ===
[17:54:38] core loaded, stage sysctl present
[17:55:00] stage=7 已推进
[17:55:00] NMXAccel 实例出现（第 1 次尝试）
[17:55:03] accelfb=3 已设置
[17:55:03] results: 0 1 1 1 -28 1 1 1      ← 第 5 项 = -28（桌面态干跑是 1）
[17:55:05] NMXAccel MetalPluginName 行数: 3
[17:55:12] vmmap nvmtl = 21 ✅
```

随后 WindowServer **连续两次 abort**，登录被踢回登录界面：

| 报告 | 进程 | 时间 | 异常 |
| --- | --- | --- | --- |
| `WindowServer-2026-10-31-175500.ips` | WS pid 5xx | 17:55:00 | SIGABRT |
| `WindowServer-2026-10-31-175521.ips` | WS pid **544**（17:54:57 起） | 17:55:18 捕获 | `EXC_CRASH / SIGABRT / Abort trap: 6`，`consecutiveCrashCount=1` |

崩在**主合成线程**（`com.apple.root.default-qos`）的断言上：

```
abort ← __assert_rtn
  ← QuartzCore  CA::OGL::Context::push_surface(CA::OGL::Surface*, bool, unsigned, unsigned)
  ← CA::OGL::FlattenNode::retain_surface(float&, unsigned)
  ← CA::OGL::ImagingNode::render / CA::OGL::render_layers / LayerNode::apply   （多层递归）
  ← CA::OGL::Renderer::render
```

**根因**：`accelfb=3` 是在 WS 已经起来、正在渲染登录界面的过程中改的呈现后端，surface 尺寸/后端在 `push_surface` 时对不上 → QuartzCore 断言失败 → WS abort → 登录回环；同时 framebuffer 几何与新后端不一致，出现**黑底彩噪条纹**（A-16 那个现象的同源版本）。`results` 第 5 项 `-28` 也是同一件事的失败返回。

A-24 手动三步之所以安全，是因为它在**桌面已经稳定、WS 空闲**时操作；而 LaunchDaemon 在 `RunAtLoad` 阶段、loginwindow 刚起时就动手，时机完全不同。**"同样的命令、不同的时机" = 完全不同的结果。**

### 2.3 回退与恢复（已完成）

```bash
sudo touch /var/db/xegfx-boot/disabled          # 脚本第一行就 exit 0
sudo launchctl bootout system/org.xegfx.boot
sudo shutdown -r now
```

17:57:49 开机，`boot.log` 记 `self-disabled, skip`；恢复后状态：

| 分辨率 | `3120 x 2080`、`Main Display: Yes`、`Online: Yes` |

| 新 panic | 无 |

`org.xegfx.boot.plist` 与脚本**留在盘上但被 `disabled` 熔断**，随时可改时机后重试；要彻底撤掉见 §4。

```bash
sudo sysctl -w debug.xegfx_stage=7
```

## 5. 下一步（顺序建议）

1. **别再在 boot 阶段推 stage 7**。如果一定要自启，改成 **LaunchAgent（用户级、登录后）**，并且先轮询"`pgrep -x WindowServer` + `stat /dev/console` 是目标用户 + WS 空闲 10 s"，再动手；或者干脆写成一个显式的桌面小工具，由人点一下。boot 早期这条路已经被证伪。
2. **软件合成这件事要换战场**：方向是给 `XeGfxIntelFB` 提供 GPU 可写的 scanout surface（零拷贝直出），让 CA 认为这个 display 可硬件合成；`accelfb=3` 的 CPU copy 路径决定了 CA 只能走 SW。这条不解决，Metal 3 再"支持"也不会进合成器。
3. 稳态结论回收：Gate 4 目前只能标注为「本次开机、手动加载后 `vmmap=18`」，**不能**当冷启动稳态指标。
