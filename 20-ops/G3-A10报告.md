## 1. 最重要的发现：GGTT 页表不在 BAR2+8 MiB，在 stolen 的 GSMBASE

提示词的骨架（以及 v0.1 的源码注释）认为页表在 `BAR2 + 0x800000`。**实测那里全是 0**
（`xnCandAPte = 0`，BAR2 268 MB、索引 `0xFE600` 读出 0）。

真正的位置来自 i915 源码（本机 `~/src/xe-src/linux/drivers/gpu/drm/i915/`）：

- `i915_utils.c:89 i915_direct_stolen_access()`：MTL 上走"直达 stolen"路径；
- `gt/intel_ggtt.c:1152 ggtt_probe_common()`：
  `phys_addr = intel_uncore_read64(uncore, GEN6_GSMBASE) & GEN11_BDSM_MASK`；
- `i915_reg.h:4202 GEN6_GSMBASE = _MMIO(0x108100)`（**不是** 0x108040 的 GGC）；
- `intel_ggtt.c:1141 gen8_get_total_gtt_size()`：GGMS=3 → 表 8 MiB → `vm.total = 8MiB/8*4K = 4 GiB`。

实测：

| 项 | 值 |
|---|---|
| GGC(0x108040) | `0x000004C0` → GGMS=3、GMS=4 |
| GSMBASE(0x108100) | **`0x70000000`**（低于 DSMBASE，**不在** stolen 窗口内） |
| 表大小 | 8 MiB → **1,048,576 条 PTE → 4 GiB GGTT** |
| 这解释了 | `PLANE_SURF` 是 32 位、macOS 把表面放在 `0xFE600000`（4 GiB 顶端） |

索引公式与源码一致（`display/intel_plane_initial.c:55`：`gte += base / I915_GTT_PAGE_SIZE`）。

## 2. 活的那一路映射长什么样（关键实测）

`xenative-ctl scan` 读 GSM 表：

```
liveIdx = 0xFE600 (=1041920)
[liveIdx+0]  0x0000000000800003     <- present|RW, phys 0x00800000
[liveIdx+1]  0x0000000000801003
...                                 <- 连续递增，共 6656 页
xnLiveRun   = 6656 页 = 27,262,976 B = 26 MiB
```

即：**固件在 phys `0x800000` 处映射了一整块 26 MiB 的帧缓冲，正好是 3120×2080×4**
（25,958,400 B 向上取整到 26 MiB）。macOS 只用其中前 8.29 MB（1920×1080×4）。

> 这一条本身是重要情报：**面板确实是 3120×2080**，固件已经按原生尺寸分配了缓冲，
> 只是 macOS 驱动（IGPUConsoleRange）按 1080p 在用。

表里除了这 6656 条，其余位置是**跨开机残留的垃圾**（`nonzero_entries = 全部 1M`、
`present = 528279 ≈ 50%` ≈ 随机）。所以"空闲槽位"不能用 `== 0` 判断，已改为
"**结构上不像有效 PTE**"（present 位为 0 / 高 12 位非零 / 物理地址不在 4 GiB 内）。

## 4. 隔离实验（每次都是运行时改，不占开机）

| 试验 | 动作 | 现象 | 推论 |
|---|---|---|---|
| **T1** | `PTE[0x1000] = 0x800003`（**已知有效的桌面 PTE**）→ `SURF=0x01000000`，尺寸仍 1920×1080 | 全黑 | 设备没从"我们写的那张表"读到 0xFE600 那条有效项 |
| **T2** | `PTE[0xFE600]` 改成 `0x71800003`（指向我们的缓冲）→ `SURF` 保持 `0xFE600000` | 桌面**完全正常** | 改 PTE 对扫描**零影响** |
| **T3** | 同 T1，但把 `PLANE_CTL` 关掉再打开强制重取 | 仍全黑 | 不是"平面没重新取帧" |
| **T4** | `SURF = 0xFE600000 → 0xFE700000`（同一段连续映射内平移 1 MB） | **画面位置变了** | SURF 有效，且显示引擎确实在按某个 4 KiB 页表在走 |
| **T5** | `PTE[0xFE800] = 0x71800003`，`SURF=0xFE800000` | 桌面**左上平移**（内容仍是桌面） | 再次证明：**PTE 改写被忽略** |
| **T6** | 把 3120×2080 图案直接写进固件那块 **26 MiB 已映射**的帧缓冲（`fillat 0x800000`），再设 `STRIDE=195 / SIZE=3120×2080 / PIPESRC 3120×2080 / PS_CTRL bit31=0` | **黑/花屏** | 连"已映射、物理连续、正好 26 MiB"的缓冲都不出图 |
| **T6'** | 马上把尺寸退回 1920×1080 | 桌面**立刻回来** | 寄存器路径健康，问题只在 3120 模式/地址解析 |

### 由 T2/T4/T5 得到的一句话

> **改 SURF 有效（画面跟着平移），改 PTE 无效（画面纹丝不动）。**
> 也就是说：显示引擎用的 GTE 值，**不是**我们从 `GSMBASE` 映射的那块内存里现读的。

两种可能（本次未能区分）：

1. **显示引擎持有开机时的 GTE 快照/缓存**，需要一个我们还没找到的失效动作。
   已试过 `GFX_FLSH_CNTL(0x101008) = 1 → 0`（i915 `gen8_ggtt_invalidate` 的做法），无效。
   注意 i915 在 MTL 上**默认根本不做**这个 flush（`needs_wc_ggtt_mapping()` 为 false），
   说明它认为这块内存是直连的 —— 那问题就更可能在显示侧。
2. `GSMBASE` 指向的是**影子副本**，权威那份在别处（固件/驱动另存）。

T1 的"复制有效 PTE 也黑"偏向第 1 种：那个索引从未被取过 → 表里那条对我们可见、
但显示侧看到的是空。

## 5. 其他实测事实（会改后续 gate 的假设）

1. **`TRANS_FRMCOUNT(0x60040)` 恒为 `0x001AB138`**：跨 6 次开机、跨 1920/3120 两种模式都不变。
   A-09 报告写"在走"是误判（只读了一次）。后续不能用它当"帧在走"的判据。
2. **`kmutil load -z -p <kext>` 会即时重建 AuxKC**（cdHash 变了就重编），`kmutil install` 仍是静默 no-op。
   本次共重建 5 次，每次都逐条核对 id，`IGPUConsoleRange` 一次没丢。
3. **`com.apple.kcgen.instructions.plist` 里的 `bundlePathMainOS` 会被沿用**：
   第一次从 `~/xenative` 加载，表里就写成用户目录路径；改成 `/Library/Extensions` 后重编即修正。
4. `IOMemoryDescriptor::withPhysicalAddress` 在本机 SDK 下**符号 ABI 对不上**
   （头文件按 32 位地址编出 `...Ejjj`，内核导出 `...Eyyj`），必须显式声明导出符号。
5. 本机 SDK **没有 KDK、没有 bsd/ 头**：`vnode_unlink`/`vnode_remove` 也未导出，
   所以"写完立刻 unlink armed"在核内做不到。本次改为**运行时可调用**（见下），
   armed 只作为 `switch` 的前置条件，用完由用户态删。

## 8. 给主 agent 的三个决策点

1. **A-11 应该改方向**：不是"再换个地址"，而是**查清显示引擎从哪儿取 GTE**。
   最省力的下一步：反汇编 `/Library/Extensions/IGPUConsoleRange.kext`（64 KB），
   看它有没有写 `0x7019C` / 有没有用 BAR2 的 GTT 写端口 —— 它是这台机器上唯一成功驱动过这块显示的东西。
2. **试试"通过 BAR2 写 PTE"**：某些平台要求 GTE 经 MMIO 窗口写，硬件才会失效自己的 GTE 缓存。
   当前 `xnCandAPte=0` 说明 `BAR2+8MiB` 不是表，但 `BAR2+0` 那段 256 MB **可能是 GGTT 0..256 MB 的窗口**，
   可以在 `SURF=0x00xxxxxx` 的低地址段做实验（把 PTE 经窗口写、再看画面）。
3. **3120 模式本身可能还有第二个坎**：T6 用"已映射、物理连续、正好 26 MiB"的缓冲仍不出图，
   所以即便 PTE 问题解决，也要单独验证 `PIPESRC=3120×2080 + PS_CTRL 关` 能不能点亮。
   建议下一步先在**不开原生尺寸**的前提下（1920×1080 源）把"改 PTE 能让画面变"这件事打通，
   再动尺寸 —— 一次一个变量。

一行结论：`A-10 FAIL: 显示引擎不采用我们写入的 GGTT 页表（改 PTE 无效果，改 SURF 有效）`
