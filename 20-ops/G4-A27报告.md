## 3. pitch 错位：12544 → 12480（本次真正修掉的一个硬 bug）

**现象**：接管后屏幕花屏，但"能看出是壁纸的颜色"，刷新时闪黑。

**证据链**：

| 来源 | 数值 |
| --- | --- |
| S3 分配的扫描缓冲 | `M3d: scanout handle 0x101 ... len 0x18e2000 pitch 12544 3120x2080` |
| 固件/开机 fb 的平面 stride（A-23a 实测） | `boot framebuffer .Display_boot: 3120 x 2080 pitch 12480` |
| 源码 | `gpu/xkpi/src/i915/xg_display_hook.c:616` `pitch = (row + 255ULL) & ~255ULL;` |

`3120×4 = 12480` 本身已是 64 B 对齐，但按 **256 B** 进位变成 `12544`；而显示平面从头到尾没有被重编程
（日志 `plane untouched` / `0 register writes`），仍按 `12480` 读——每行错 64 B，累积成斜向撕裂，
颜色统计仍接近原图，正好对应"看得出壁纸但整体花屏"。

**改法**（Intel 线性平面只需 64 B 步幅对齐）：

```c
/* A-27b: 256B rounding made 3120*4=12480 -> 12544, while the firmware-programmed
 * display plane still scans with stride 12480 -> sheared image.  Linear planes only
 * need 64B stride alignment, so keep 12480 and match the live plane. */
pitch = (row + 63ULL) & ~63ULL;
```

**验证**（重编 core → 重落 AuxKC → 重启 → 载 core → 重启 WS）：

```
M3d: scanout handle 0x101 phys 0x34653000 len 0x18c2000 pitch 12480 3120x2080 ggtt 0x80000000
enableController READY -- scanout 0x34653000 3120x2080 pitch 12480 ...
open() RELEASED (opens=2) -- aperture 0x34653000/25958400 live, head 4 scans our buffer
```

`0x18c2000 = 25 958 400 = 12480×2080`，与开机 fb 的字节数**逐字节相同**。
用户肉眼确认：花屏消失，画面内容正确（壁纸/桌面正常显示）——**pitch 这条修对了**。

## 4. 新墙：`CA::OGL::Context::push_surface` 断言（真因，已定位到函数）

pitch 修好后屏幕变成"正常(冻结) / 黑屏"来回切换。查下去发现不是画面问题，是 **WindowServer 在崩溃循环**：

```
launchd: [system/com.apple.WindowServer [1240]:] exited due to SIGABRT | sent by WindowServer[1240], ran for 8777ms
launchd: [system:] service inactive: com.apple.WindowServer
launchd: [system/com.apple.WindowServer [1311]:] Successfully spawned WindowServer[1311] because ipc (mach)
```

每 8.7 s 一轮。崩溃报告（`20-ops/A-27/WS-183951.ips`）触发线程：

```
libsystem_c  __assert_rtn
QuartzCore   CA::OGL::Context::push_surface(CA::OGL::Surface*, bool, unsigned int, unsigned int)
QuartzCore   CA::OGL::FlattenNode::retain_surface(float&, unsigned int)
QuartzCore   CA::OGL::ImagingNode::render(...) → CA::OGL::render_layers → LayerNode::apply (…递归 3 层)
QuartzCore   CA::OGL::Renderer::render(...)
termination: SIGNAL / Abort trap: 6 / code 6
```

**与 A-25b 那次冷启动崩溃是同一个断言签名**，说明它不是"S3 时序"造成的，而是
**我们的 framebuffer 作为 CA 渲染目标时，`push_surface` 的前置条件不满足**。
"正常画面冻结" = 每个新 WS 只画了第一帧就被 abort，下一帧永远不再来。

已核对 `/Library/Logs/DiagnosticReports` 里没有 `WindowServer-18:49/18:50` 的报告落盘（系统延迟合并），
但 18:50 的 launchd 日志给出了 8.7 s 的存活周期，与肉眼"画面卡死 + 黑屏交替"节奏一致。

**为什么"冻结"还能看见正确画面**：面板确实在扫我们的 buffer（`head 4 scans our buffer`），
但 buffer 里的内容是 WS 崩溃前那最后一帧，之后没人再往里画。

**结论**：这不是 pitch/flip 的算术问题，是**"CA 不接受这块 framebuffer 当作 OGL surface"** 的能力缺口
（对应上游 M4/expose 那条路，而 `accelfb=3` 的 CPU copy 路径不提供 CA 需要的 surface 语义）。

## 7. 下一步（A-28 建议，按代价排序）

1. **先读 `push_surface` 断言的真实条件**：在 `XeGfxDisplay.cpp` 的 `getPixelInformation`/`getFramebufferInfo`/
   `setAttributeForConnection` 上对齐 CA 的期望（`kIOFBSurfaceInfo` 的 `bytesPerRow/bytesPerPixel/pixelFormat`、
   `kIOFBSetAttribute(kIOFBFlush)`、`kIOFBGetAttributeForCGS(kIOFBCLutMode/kIOFBSurfaceMode)`）。
   注意 §4 已经排除了 pitch 不一致（`getPixelInformation` 给 12480、真 buffer 也是 12480）。
2. **确认 `accel=1` 是不是"假配对"**：`M3d ... accel=1` 但 `ioreg -c IOAccelerator` 在接管态下仍然取不到
   `PerformanceStatistics`（本轮 grep 为空）。若加速器没真正提供 surface，CA 只能走 OGL/SW，`push_surface` 必然对不上。
3. **崩溃隔离**：`sudo launchctl bootout system/com.apple.WindowServer` 不行（WS 是必需），
   但可以在实验前 `sudo sysctl` 关掉 watchdog 对 panic 的触发（若可控），或**每次实验后 60 s 内必回滚**，
   避免又被看门狗打断构建（本轮 18:43 那次重编就是被 panic 吃掉，日志 0 字节）。
4. **别再指望"boot 阶段自动接管"**：core 不自动加载这条已经两次咬人（A-24/A-27），
   要彻底解决必须先让 core 在 WS 之前加载，否则每次都要"载 core → 重启 WS → 立刻验"。
