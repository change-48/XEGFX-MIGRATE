# G7 · A-88 报告：把"工作量 → 帧时间"量化成阶梯表了；E2 提前信号判死

> 日期：2026-11-03 20:40–21:10（两次装机重启；零 panic、零 NVMTL 异常）
> 目标：不再靠推算，先测出"往工作里加 X µs → 帧时间怎么跳"，再按曲线决定砍什么。
>
> **一行结论（三个数）**：
> **① 阶梯表：每帧多加 4.5 ms 主线程工作，p50 一步不动（24.75 → 24.99），再加到 13.5 ms 才跳 25.0 → 33.3**
> ⇒ 这套栈有 **≥4.5 ms 的"免费"余量**，说明 **帧不是被工作量顶住的**；
> **② E2 提前信号：p50 24.82/24.81（关）→ 24.74/24.75（开），差 0.07 ms = 噪声**；
> 早信号确实每帧发一次（796 / 826 次），但 `AccessComplete` 的等待 **2.95 → 3.01 ms 一点没少** ⇒ 打错了对象；
> **③ 最终档：p50 24.8 ms、p90 33.9 ms（≈40 fps）。60 不在驱动侧——要换 WS/CA/CoreDisplay 那条呈现链（A-83 整树）。**

## 2. P1 · 量化阶梯表（本关的主交付）

插件侧加了一个**可调自旋**（`/private/tmp/nvmtl-spin`，内容 `"<µs>[m|w]"`，200 ms 生效，默认无文件 = 全关），
`work/a88/patch_a88_spin.py`（3 处锚点，0 error / 481 warning，装机件 `7f8cc6e1`）：

| 位置 | 线程 | 语义 |
| --- | --- | --- |
| `m` | 提交（WindowServer 主）线程，`nvmtlSubmitWithEvents` 出锁段 | 与 CA 自己的工作同一条路 |
| `w` | submit-ahead worker（`nvmtlA87Run` 入口） | **对照**：不在主线程上的工作该不该影响帧 |

每轮：25 s 拖动（1100×760 玻璃）+ 16 s 逐帧间隔（frame-times 300 µs 轮询）+ 12 s 后 6 s WindowServer sample；
**每点两轮**。X = 0 / 1000 / 2000 / 3000 / 5000 / 8000 µs。

### 2.1 阶梯表

| X（µs/次提交） | 每帧多加的工作 | p50 第 1 轮 | p50 第 2 轮 | p90 | 落在几拍 |
| --- | --- | --- | --- | --- | --- |
| 0（基线） | 0 | **24.83** | **24.67** | 41.26 / 34.09 | 3 拍 |
| 1000 | ≈ +4.5 ms | **25.13** | **24.85** | 41.33 / 41.55 | 3 拍（**没动**） |
| 2000 | ≈ +9.0 ms | 26.31 | 31.94 | 41.79 / 41.99 | 3↔4 拍过渡（分布变宽） |
| 3000 | ≈ +13.5 ms | **33.40** | **33.28** | 49.81 / 42.69 | 4 拍 |
| 5000 | ≈ +22.5 ms | **41.61** | **41.45** | 57.84 / 50.60 | 5 拍 |
| 8000 | ≈ +36 ms | **50.37** | **50.27** | 66.52 / 65.61 | 6 拍 |
| **3000w（对照，worker 侧）** | ≈ +13.5 ms | **32.96** | **33.12** | 41.66 / 41.77 | **4 拍 —— 和主线程一模一样** |

"每帧多加的工作"的换算：`sample` 里主线程 busy 从 **8.22 ms**（X=0，按各轮自己的帧长折算）涨到 **21.78 ms**（X=3000），
Δ = 13.56 ms ÷ 3.0 ms/次 = **≈4.5 次 commit/帧**。X=1000 的 +4.5 ms 就是它。

### 2.2 表告诉我们的两件事

**① 台阶确实在整拍上，而且现在离"上一级"还有 ≥4.5 ms。**
0 → 1000 µs，p50 一步不动（24.75 → 24.99，噪声内）。也就是说：**每帧再多 4.5 ms 的工作，系统毫不费劲地吃下去了**
（主线程 idle 从 10.3 ms 缩到 5.9 ms 让位）。到 +13.5 ms 才跳 4 拍。
⇒ 反过来说：**砍掉 4 ms 工作也不可能掉档** —— A-87 把类锁 4.08 ms 搬干净帧不动（时间转进 `AccessComplete`），
本关的阶梯从**正面**解释了那次失败，两条独立证据对上了。

**② 对照点（worker 侧）和主线程**同档**：33.0 vs 33.3。**
往 submit-ahead worker 里塞 13.5 ms，帧时间一样跳 4 拍。⇒ 这条链是**串行**的：主线程、提交 worker、GPU、present
首尾相接，**任何一段加 4.5 ms 都直接记到帧上**。这也解释了"把工作搬出锁"为什么没用——搬走了，还在链上。

**③ 分布是双峰的，不是整齐的 3 拍**：基线轮里 **23–29% 的帧落在 9.5–17.5 ms（= 2 拍，60 fps）**，
32–38% 落在 17.5–26.2 ms（3 拍）。**60 fps 不是不可能，是现在"半半"** —— 见 §5 给下一关的第一条。

## 3. P2 · E2 提前信号：判死（这一次是测出来的，不是算出来的）

### 3.1 实现（`work/a88/patch_a88_early.py`，9 处锚点，0 error / 34 warning，accel `014103de` → 装机 `985ee9df`）

| 文件 | 改动 |
| --- | --- |
| `accel/nvrm-accel.cpp` | 新开关 `gIopXeEarly`（`debug.xegfxaccel_iop_xe_early`，默认 0）+ 计数 `..._early_signals` |
| `nvAccelXeFlipArm` | 在 `PLANE_SURF_1_A` 的写入之后（**attempt 0，仅一次**）：清 `gXeFlipBusy`（队列空时）→ `signalTransactionInterrupt(pipe)` |
| defer worker | 把 `p.pipe` 通过 `gXeEarlyPipe` 交给 arm；**早发过的帧不再发第二次**（避免一帧两次完成） |
| `xegfx_accel_names.h` | 两个新名字的 `nvaccel_* → xegfxaccel_*` 别名（A-76 §2.3 的注册规则照做，注册块里补了两行） |

判据按提示词放宽：**不设"连续 32 帧第三面"的门槛，直接受开关控制**（A-84 已证那条判据在本栈永不满足：两表面轮换）。

### 3.2 A/B（每档两轮，同一台机、同一负载、同一 25 s 拖动）

| 配置 | 早信号次数/轮 | p50 | p90 | 主线程 busy / wait / idle |
| --- | --- | --- | --- | --- |
| `early=0`（锁内路径，默认） | 0 | **24.82 / 24.81** | 41.44 / 34.12 | 9.06 / 6.32 / 9.44 |
| `early=1` | **799 / 821** | **24.74 / 24.75** | 40.94 / 33.84 | 9.12 / 6.35 / 9.27 |
| `oollock + early=0`（A-87 锁外路径，让 latch 等待露出来） | 0 | **24.62 / 24.47** | 34.33 / 33.79 | 10.14 / 4.12 / 10.34 |
| `oollock + early=1` | **796 / 826** | **24.55 / 24.49** | 33.93 / 34.13 | 10.42 / 4.22 / 9.96 |

**四轮八组，p50 差 0.07–0.08 ms。E2 对帧时间没有任何作用。** 计数自洽：`flip_fail=0`、`latch_timeouts=0`、无 panic。

### 3.3 为什么没用（这次有物证，两条）

**① 我们发的早信号，`AccessComplete` 一点没少吃。**
锁外路径下（latch 等待真正露在关键路径上）专项对比：

| | `oollock + early=0` | `oollock + early=1` |
| --- | --- | --- |
| `CoreDisplay::DisplaySurface::AccessComplete` 等待 | **2.95 ms/帧** | **3.01 ms/帧** |

早信号已经按帧发到 pipe 上了，WS 的 `AccessComplete` 却**分毫未动** ⇒ 它等的**不是我们这个 pipe 的完成**，
而是 `CoreDisplay::DisplaySurface` 自己那把信号量（由扫描输出/display link 侧给），跟 accel 的
`signalTransactionInterrupt` 不是同一个对象。**E2 打错了门。**

**② WS 确实在看我们的完成，但那是轮询，不是阻塞点。**
5 s 拖动前后：`debug.xegfxaccel_pipe_perform +211`，`debug.xegfxaccel_pipe_complete +422`（**每帧问两次**）
⇒ `isTransactionComplete` 是被问的；真正让主线程停 3 ms 的是 `AccessComplete` 的 `__psynch_cvwait`。
所以"把完成提前 4.5 ms"改变不了任何相位 —— 这正是提示词里"若 E2 只降到 20 ms 左右说明只减了 latch"的**更坏版本**：
连 latch 都没减下来，因为它不在那条等待链上。

## 4. P3 · 砍 busy：**主动不做**（不是没时间，是阶梯表已经否定它）

| 证据 | 数字 | 含义 |
| --- | --- | --- |
| P1 阶梯（本关） | +4.5 ms/帧 工作 → p50 不变 | 余量 ≥4.5 ms，砍 1–3 ms 的工作量换不来一帧 |
| A-87（上一关） | 类锁 4.08 → 0.01 ms，p50 25.30 → 25.00 | 砍 4 ms 实测无效，时间转进 `AccessComplete` |
| A-87 / 本关 | `defer=0`：busy 9.04、p50 **32.17**（更慢） | 少干活反而更慢 |
| 本关 E2 | 提前 3–6 ms 的完成，p50 −0.07 | 减法在同一处做了第四遍，还是零 |

描述符池（≈1.1 ms busy）、malloc/objc 碎片（≈1 ms）都在"砍了也不会动"的量级里。**继续砍 busy 是拿 90 分钟换一个已知为零。**
⇒ P3 判"无靶子"，与 A-87 的结论一致，但这次有**正面**的阶梯数据支撑。

## 5. 给下一关（A-89）的三句话

1. **60 fps 的入口在"半半"里**：基线轮有 **23–29% 的帧已经做到 2 拍（9.5–17.5 ms）**。同一套驱动、同一负载，
   有些帧能，有些不能 ⇒ 差的是**相位/节拍**，不是能力。下一关该做的是**逐帧对齐**：把 2 拍的帧和 3 拍的帧
   各自的 `performTransaction` 时间戳、`AccessComplete` 等待、`iop_tl` 的那几列**并排比**，找出"能"与"不能"的分界
   （现在的工具只给 p50/p90，把分布拍平了，这正是 A-86 §6 三个坑之外的第四个坑）。
2. **不要再动 Metal/accel 侧的"减法"**。四轮证据（锁、busy、latch、worker 侧）都指向同一件事：
   这条链是**串行**的，任何一段的时延都原样记到帧上，而帧的落点是 **WS/CA/CoreDisplay 的呈现节拍**。
   要做 60，必须让"下一帧的 CPU 工作"和"上一帧的扫描输出"**重叠**，那是 A-83 那条整树换血的路
   （同一负载 82 翻/秒）。本栈的天花板就是 40 fps 上下，**这关的数据已经把这句话钉死了**。
3. **测量纪律（本关新增两条，已写进脚本）**：
   ① 开机后 **2 分半**内 `NSScreen` 仍可能 0×0（本关 base1 那轮 4 个样本全废，就是踩了这个）；
   ② **开机后 Software Update / iconservicesagent 会把 load 顶到 10+**（本关 e0a/e0b 两轮废掉），
   准入要加 `load < 3`，否则测的是 macOS 在给自己擦地。
   另外：`frame-times` 只打原始间隔，没有 p50 汇总行 —— 汇总用 `work/a88/stats.py`（本关新写，带 8.33 ms 分桶）。
