## 2. A-22a 撞上的坑：**mode ID 不能用 NMIntelFB 的 `1`**

提示词里从 `NMIntelFB` 原样搬来的 `getCurrentDisplayMode → { *mode = 1; *depth = 0; }` **直接把 WindowServer 打死**：

```
CoreDisplay  CoreDisplay::AssertTracer
CoreDisplay  build_mode_list_if_needed(MPPriv*)
CoreDisplay  index_to_mode(MPPriv*, int, int*, int*, float*, MPDisplayModeInfo const**)
CoreDisplay  current_mode_index
CoreDisplay  CoreDisplay::Framebuffer::Framebuffer(...)
SkyLight     WS::Displays::CoreDisplayManager::initialize()
```

原因：`NMIntelFB` 自己 `override` 了 `getDisplayModeCount()/getDisplayModes()`（模式表 = `{1}`），
而 `XeGfxIntelFramebuffer` **沿用 `IONDRVFramebuffer` 的 IOFBConfig 模式表**，里面唯一的模式是

```
"IOFBConfig" = {"IOFBModes"=({"ID"=100,...   ← 0x64
```

CoreDisplay 拿 `getCurrentDisplayMode` 的返回值当**模式表下标**用，`1` 不在表里 → 断言 abort（pid 443，开机 16 s）。
开机后 `IOConsoleUsers = ()`、无 WindowServer、`system_profiler` 只剩 GPU 段。

### 修法（A-22b，仍只改这一个类）

```cpp
IOReturn getCurrentDisplayMode(IODisplayModeID *mode, IOIndex *depth) override
{
    if (!mode || !depth) return kIOReturnBadArgument;
    if (kIOReturnSuccess == IONDRVFramebuffer::getCurrentDisplayMode(mode, depth)) return kIOReturnSuccess;
    IODisplayModeID m = 0;   // 没有 NDRV 实例：我们自己发布的第一条模式就是固件那条
    if (getDisplayModeCount() && kIOReturnSuccess == getDisplayModes(&m)) { *mode = m; *depth = 0; return kIOReturnSuccess; }
    return kIOReturnUnsupported;
}
```

`getPixelInformation` 同时**不再写死 `mode != 1` 就拒绝**，改成拿基类的 `getInformationForDisplayMode` 验一次模式存在性；
行距/尺寸仍用 `PLANE_SIZE`/`PLANE_STRIDE` 的真实值（`fW/fH/fRowBytes`）。

改完这一版开机：`scanout described: mode 0x64 depth 0 3120x2080 rowBytes 12480`（4 次，来自 WindowServer），
显示 Online，**无崩溃**。→ 这三行是 A-22 真正的成果。

## 4. ★ 新证据：`0xe00002c7` 已经不是「头不会描述」

调用链（`kexts/NVRM/accel/nvrm-accel.cpp`，两个树都核对过）：

```cpp
// NVDisplayPipe::initFramebufferResource   (:1028)
IOReturn ret = a->askFramebufferForScanout(&r, fb);
if (ret == kIOReturnSuccess && r.kva && !r.phys) { ...CPU-only scanout...; return nullptr; }   // 有 kva 无 phys：友好退出
if (ret != kIOReturnSuccess || !r.phys || !r.actualSize) {
    ALOG("...framebuffer would not describe its scanout (0x%x)", ret);    // ← 我们打到的就是这条
```

```cpp
// askFramebufferForScanout   (:903 / 5a19 树 :900)
if (nvXeIsKmsFB(fb)) return nvXeKmsScanoutInfo(fb, r);                    // ← 我们不在这条路上
IOReturn ret = fb->callPlatformFunction(fSymScanout /*NVRM_VRAM_FN_SCANOUT*/, ...);   // 返回 0xe00002c7
if (ret != kIOReturnSuccess)
    if (IOFramebuffer *ifb = OSDynamicCast(IOFramebuffer, fb)) ret = describeBootFramebuffer(ifb, r);  // 兜底
```

而**已安装的 `XeGfxAccel`（来自 `~/src/NvGfx-5a19a73...` 树）把这个兜底函数第一行就 return 了**：

```cpp
IOReturn describeBootFramebuffer(IOFramebuffer *ifb, struct NVRMVramRequest *r) {
    /* EXPERIMENT: refuse to describe the boot raster.  With the accelerator loaded the panel
       shows a band of colour noise at the bottom ...  if it disappears without this, the
       write-combined map of the aperture below is what corrupts the scanout.  Remove to restore
       the copy target. */
    if (1) { ALOG("describeBootFramebuffer: DISABLED by experiment -- no copy target"); return kIOReturnUnsupported; }
```

日志实证（17:05:49）：`describeBootFramebuffer: DISABLED by experiment -- no copy target`
紧接着 `initFramebufferResource: framebuffer would not describe its scanout (0xe00002c7)`。
**这一轮 accel 一次都没调我们的 `getCurrentDisplayMode/getPixelInformation`**（`scanout described` 只出现在
17:03:33 WindowServer 那一批，17:05:49 一条都没有）——所以 0xe00002c7 与我们的改动**不再有因果关系**。

还有一条更关键的：accel 有**专门的 KMS 适配器通道**，完全不碰 IONDRV/平台函数：

```cpp
static bool nvXeIsKmsFB(IOService *s) { return s && s->metaCast("XeGfxFramebuffer"); }
// → nvXeKmsScanoutInfo(): 对 fb 调平台函数 "xgGetScanoutInfo"，要 80 字节的 XeGfxScanoutInfo
//   （version/size/flags NVXE_SCANOUT_READY/phys/kva/width/height/pitch），拿到就建真正的 display-pipe resource
```

`metaCast("XeGfxFramebuffer")` 按类名继承匹配 → 我们的 `XeGfxIntelFramebuffer` **不匹配** → 只能走 placeholder 路
（`0018` 补丁的原话：*"Not XeGfxIntelFramebuffer: that name belongs to the XeGfxIntelFB placeholder"*
—— **我们这两轮在改的东西，在上游设计里明确叫 placeholder**）。

### 4.1 ★ 上游参考实现是完整的，而且已经解掉了我们正在撞的每一堵墙

`~/src/aw/patches/` 有一整套 **0011–0022**（未应用到本机任何树，也没有构建产物，`/Library/Extensions` 里没有
`XeGfxDisplay.kext`）。它的做法不是改 placeholder，而是**新做一个 KMS 适配器 kext `XeGfxDisplay`**：

| 补丁 | 内容 | 与今天的发现的关系 |
| --- | --- | --- |
| `0011` core-native-display | 发布 `XeGfxDisplayNub`（KMS KAPI 地址 + VBT/child 捕获） | 适配器的匹配对象 |
| `0015` adapter-xegfxdisplay-kms | **5142 行**，新文件 `kexts/XeGfxDisplay/{Info.plist,src/XeGfxDisplay.h,src/XeGfxDisplay.cpp,xegfx_kms_kapi.h}`，含 `class XeGfxFramebuffer : public IOFramebuffer` | `xgGetScanoutInfo` 的**生产者实现就在这里**（v2/80 字节，`static_assert` 对齐检查） |
| `0012` accel-m3d | M3d：加速器通过 `xgGetScanoutInfo` 导入 display-pipe resource，**首帧就是零拷贝 flip**；回调 `xgFlipPresent/xgVblankCount/xgCursorImage` | 已安装的 `XeGfxAccel` 里就有这些字符串 |
| `0018` adapter-intel-class-name | **类名换成 `XeGfxIntelKMSFramebuffer`**（空子类，名字含 "Intel"），行为仍在 `XeGfxFramebuffer` | **正好是 A-21 与 A-22 互相拉扯的那个点**：名字要含 Intel 才让 CoreDisplay 开 IOPresentment，而 `metaCast("XeGfxFramebuffer")` 仍能匹配 → accel 走 KMS 路 |
| `0019`–`0022` | 守卫/keep-armed、EDID/DPCD、K1 staged eDP takeover | 我们还没碰的部分 |

`0018` 的动机写得很清楚：类名不含 Intel → `GetGPUVendorForFramebufferService()` 判成厂商 0 →
`UseIOPresentment()` 静默关掉 useIOP → 每个 WindowServer 都撞 `CA::OGL::Context::push_surface` 断言
（"transient surface ... not found"）。**这就是「类名」与「metaCast」必须同时成立的解法：空子类，名字带 Intel。**

→ **A-23 不应继续在 `XeGfxIntelFB` 上加方法**，而应评估把 `0011 + 0015 + 0016 + 0018`（必要时 + 0019–0022）
应用到 `NvGfx-xe-2.6.2` 并构建 `XeGfxDisplay`。这是工作量更大但方向唯一的一条。

## 7. 给 A-23 的三条

1. **A-22 的改动值得保留**：它把「`getPixelInformation` 未实现 → Unsupported」这条根因彻底消掉了，
   WindowServer 现在真的在用这份描述（`scanout described: mode 0x64 ... rowBytes 12480`，显示正常、零崩溃）。
   **不要回退它**，否则 CoreDisplay 又回到转发 `IONDRV` 的老路。
2. **下一道闸门在 accel 侧，不在 framebuffer 侧。** 三条路，按推荐顺序：
   - **A-23b（首选，正道）**：把上游 `~/src/aw/patches/` 的 **`0011 + 0015 + 0016 (+0018)`** 应用到
     `NvGfx-xe-2.6.2`，构建并安装新的 **`XeGfxDisplay`** kext（`class XeGfxFramebuffer : public IOFramebuffer`
     的 KMS 适配器，`0018` 把 IOClass 换成 `XeGfxIntelKMSFramebuffer`）。它会：
     ✅ 提供 `xgGetScanoutInfo`（v2/80 字节）→ accel 走 M3d 零拷贝 display-pipe resource；
     ✅ 同时满足「类名含 Intel」和「`metaCast("XeGfxFramebuffer")` 成立」这两个互相拉扯的约束；
     ✅ 不碰 `describeBootFramebuffer` 那个实验开关，绕开彩噪问题。
     代价：5142 行新 kext + 依赖 core 的 KMS KAPI（0011）+ 构建脚本（0016），要先确认 `xe-src` 的 KAPI
     scanout 扩展在本机可用。**这是唯一能真正走到 `vmmap nvmtl > 0` 的路。**
   - **A-23a（最省事、但只是续命）**：`NvGfx-5a19` 树里把 `if (1)` 改成 `if (0)` 恢复 `describeBootFramebuffer`，
     重编 **`XeGfxAccel`**，走「有 phys 的 copy target」路径。注释里那条「面板底部一条彩噪」是当时
     `getPixelInformation` 还没实现、几何靠猜时看到的，现在 pitch=12480 是真的，值得重测——但它拿到的仍是
     **CPU 拷贝**，不是零拷贝，且 phys 用的是 aperture 地址（`0x71800000`），和 SURF 的 GGTT 地址
     （`0xfd000000`）不是一回事，属于在旧架构上打补丁。
   - **A-23c（不建议）**：继续在 `XeGfxIntelFB` 里实现 `callPlatformFunction(NVRM_VRAM_FN_SCANOUT)`，
     手工复刻 `NVRMVramRequest` 布局。等于自己重造 0015 的轮子，且要跨 kext 对齐私有 ABI。
3. **铁律照旧**：`-z` 绕审批门、不要 `kickstart` 守护进程、探针分不动。
   另外补两条今天新踩的：
   - **`getCurrentDisplayMode` 返回的模式 ID 必须来自自己的模式表**，照抄别的 framebuffer 类的硬编码值
     会直接让 WindowServer 在 `build_mode_list_if_needed` 断言（§2）。
   - **`~/src/aw/patches/` 是上游的完整设计，动手改 placeholder 之前先读它**：0012 的 M3d 段和 0018 的注释
     已经把我们 A-21/A-22 的全部困扰写清楚了。
