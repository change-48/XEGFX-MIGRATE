## 2. 与 1031 计划的偏差（主 agent 已定，按本文执行）

**Metal 不在本关判据内。**

计划把「`mtlprobe` → `MTLCopyAllDevices count = 1` 且 16/16」放在 Gate 2。
但 Metal 的设备枚举来自 `IOAccelerator` 服务声明的 `MetalPluginName`，而加速器 kext
（`XeGfxAccel`，IOClass=`NMXAccel`）是 Gate 4 的组件，且有 panic 风险（需要 2 处 `idr_preload` 补丁）。
把它塞进 Gate 2 = 一个 gate 两个变量。

所以本关：

- **判据只有 Vulkan**（它只依赖 `XeGfx` 内核 + ANV + libdrm + DRM 节点，与加速器无关，是一条干净的全链路）
- `mtlprobe` **照跑**，但结果**只记录、不判定** —— 它顺便回答一个有价值的问题：
  "没有加速器时 Metal 到底能不能枚举到设备"。这个答案决定 Gate 4 怎么写。
- 计划里 Gate 2 的「系统认 Metal」同样归 Gate 4（现在 `system_profiler` 根本没有 Metal 这一行）。

## 3. 铁律

- **只拷贝。** 不编译、不 `install_name_tool`、不 `codesign -f`（除非某个 dylib `codesign -v` 明确报错）。
- 不装 kext、不改 AuxKC、**不重启**。本关不碰内核任何东西。
- 不动 `/Library/Extensions`。
- 路径必须**精确**：`/Library/GPUBundles/nvmtl/libvulkan_intel.dylib`
  （`vkprobe2` 把这个绝对路径写死在源码第 17 行，少一层目录就 dlopen 失败）。
- `nvmtl-allow.txt` 原样拷贝，**不要**为了"试试看"改成别的（那是 Gate 4 的变量）。
- 遇到计划外现象：停手、留证、报告。

## 4. 步骤

### 4.1 记录 before

```bash
mkdir -p ~/xegfx-log/A-03
{ ls -laR /Library/GPUBundles/ 2>&1; echo "---"; sudo sysctl -b debug.xegfx_results | od -A n -t d4; } \
  | tee ~/xegfx-log/A-03/before.txt
```

### 4.2 拷贝（六条命令，别用通配）

```bash
S=~/_xegfx-old-20261030/GPUBundles
sudo mkdir -p /Library/GPUBundles
sudo cp -R  "$S/nvmtl"                 /Library/GPUBundles/nvmtl
sudo cp -R  "$S/NVMTLDriver.bundle"    /Library/GPUBundles/NVMTLDriver.bundle
sudo ln -sfn NVMTLDriver.bundle        /Library/GPUBundles/NVMTLDriver
sudo cp -p  "$S/nvmtl-allow.txt"       /Library/GPUBundles/nvmtl-allow.txt
```

### 4.3 权限

```bash
sudo chown -R root:wheel /Library/GPUBundles
sudo find /Library/GPUBundles -type d -exec chmod 755 {} \;
sudo find /Library/GPUBundles -type f -name "*.dylib" -exec chmod 755 {} \;
sudo chmod 644 /Library/GPUBundles/nvmtl/intel_icd.x86_64.json /Library/GPUBundles/nvmtl-allow.txt
sudo xattr -cr /Library/GPUBundles
```

### 4.4 拷完先校验（不通过就别往下跑）

```bash
ls -l /Library/GPUBundles/nvmtl/            # 必须 11 个文件
test -L /Library/GPUBundles/NVMTLDriver && echo SYMLINK-OK
for f in /Library/GPUBundles/nvmtl/*.dylib; do codesign -v "$f" || echo "BAD-SIG $f"; done; echo SIG-DONE
otool -l /Library/GPUBundles/nvmtl/libvulkan_intel.dylib | grep -A2 LC_RPATH | grep path
otool -L  /Library/GPUBundles/nvmtl/libvulkan_intel.dylib | grep -E "libdrm|SPIRV"
cat /Library/GPUBundles/nvmtl/intel_icd.x86_64.json
codesign -v /Library/GPUBundles/NVMTLDriver.bundle && echo BUNDLE-SIG-OK
```

期望：11 个文件、软链 OK、无 `BAD-SIG`、rpath 是 `@loader_path`、
依赖是 `@loader_path/libdrm.2.dylib` 和 `@loader_path/libSPIRV-Tools.dylib`、
json 里 `library_path` = `/Library/GPUBundles/nvmtl/libvulkan_intel.dylib`。

### 4.5 跑 Vulkan（本关判据）

```bash
~/xegfx-probes/vkprobe2 2>&1 | tee ~/xegfx-log/A-03/vk.txt
```

期望（全部要满足）：

```

  [0] Intel(R) Graphics (ARL)  ...vendor=0x8086 device=0x7d51
vkCreateDevice -> 0
vkCreateCommandPool -> 0
vkAllocateCommandBuffers -> 0
vkQueueSubmit -> 0
vkWaitForFences(5s) -> 0        ← 这条最重要：GPU 真的执行完了
```

### 4.6 跑 Metal（只记录，不判定）


**返回 0 不算失败**，但要在交付里明确写"有/没有设备"，并附日志里有没有插件加载记录。

## 5. 停机条件

| 现象 | 处置 |
| --- | --- |
| `dlopen FAIL` + `no code signature` / `no cdhash` | 某个 dylib 没签名 → 对该文件 `codesign -f -s -` 后重试**一次**；仍失败则停 |
| `dlopen FAIL` + `symbol not found _drmXeGfxOpen` | libdrm 不对（两个补丁没都打）→ 停，报告，别自己重编 |
| `dlopen FAIL` + `errno=13` / sandbox | rpath 又变成绝对路径了 → 停，报告 |
| `vkCreateDevice` 非 0 | 停，取 `sudo dmesg | tail -50` 和 `~/xegfx-log/A-03/vk.txt`，可能是 XeGfx 侧 DRM 问题 |
| `vkWaitForFences` 超时非 0 | 停，报告（说明提交了但 GPU 没完成，是内核侧语义问题） |
| 屏幕闪/黑、WindowServer 退出 | 立刻停，报告（理论上不会发生，本关不碰内核） |
