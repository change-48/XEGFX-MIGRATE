# Gate 4 · A-37 执行提示词：回到上游验证过的那条路（放弃 IOP）

> 结论先行：**停止追 `IOAccelDisplayPipe` / IOP。** 上游（XeGfx 作者本人，Issue #9，2026-10-28）
> 的可用配置是 `XeGfxIntelFB`（IONDRV 子类）持有面板 + 加速器 + Metal 合成 + **帧拷贝**，
> 全程不经过 IOP。本关回到那条路，并**把"是否真的 GPU 合成"量准**。
>
> **零代码改动。** 只加载、设一个 sysctl、采样。

---

## 0. 上游依据（本关的全部理由）

### 0.1 XeGfx Issue #9，作者 2026-10-28 的状态更新（原文）

> "Status: the panel runs on **XeGfxIntelFB** now (NvGfx `xe-2.6.2`, `kexts/XeGfxIntelFB`), not NMIntelFB.
> It keeps the firmware's mode, **WindowServer composites into it on the Intel GPU through Metal**,
> and since 0.7 it reads the panel's EDID and offers HiDPI 1280x800.
> It is **not flip-only yet: frames are still copied rather than flipped**."

### 0.2 同一 issue 里对其他项目的调研（作者自己整理的）

- **VedCloud（Meteor Lake）**：i915 **跳过 display discovery**，一个小 framebuffer kext 扫描固件缓冲
  → 拿到"第一个 GPU 合成的桌面"。
- **nmx-intel（Raptor Lake）**：i915 点亮面板，但**合成在软件里**，靠把别处合成的帧拷过来。

→ 三个项目、三种结局，**没有一个用 IOP / `IOAccelDisplayPipe`**。
`IOAccelDisplayPipe` 属于 Apple `IOAcceleratorFamily2` 内部机制，第三方加速器建不出来是常态（`0x2002`）。

### 0.3 我们其实到过那条路（本项目的旧账）

| 关口 | 当时的现象 |
| --- | --- |
| A-21 | `NMXAccel: .Display_boot: XeGfxIntelFramebuffer accepted as head 4`、`heads published 0x10, registered 0x10, piped 0x10` |
| A-23a | `boot framebuffer .Display_boot: 3120 x 2080 pitch 12480 … (CPU copy target)`、`NVDisplayPipe::initFramebufferResource(head 4, index 0) -> vidmem over the LIVE SCANOUT` |
| A-24 | `vmmap WindowServer | grep -c nvmtl` = **18**、`Metal Support: Metal 3` |

**这就是上游描述的形态**：display pipe 由加速器自己的 `NVDisplayPipe` 建，不经过 IOP。
A-26 之后我们转去 `XeGfxDisplay` + S3 + IOP，离开了这条路。

### 0.4 那 A-25 为什么测到软件合成（本关要重测的原因）

A-25 的采样给的是 `CA::OGL::SW` = 1256 / Metal = 1，与上游"GPU 合成"的说法相反。
**但那一轮的状态没有被逐项固定**（`debug.xegfxaccelfb` 当时是多少、`XeGfxAccelPresent` 是否在、
插件是否已装、WS 是否登录态，都没有同时确认）。本关要**在同一时刻把这四项全部落实**，再采样。

## 2. 执行（全部运行期，不重启）

```bash
L=~/xegfx-log/A-37; mkdir -p $L

# 2.1 干净态确认（必须 phase=%00，且只有 XeGfxIntelFB 在供屏）
sudo nvram -p | grep xegfx | tee $L/base.txt
ioreg -l -w0 2>/dev/null | grep -ac "class XeGfxIntelKMSFramebuffer"      # 期望 0
system_profiler SPDisplaysDataType | grep -E "Resolution|Online"          # 期望 3120x2080 / Yes
ls /Library/GPUBundles | head; ls -A /Library/GPUBundles | wc -l          # 期望 11+，不为 0

# 2.2 core → stage 7（单路径，不写 bootarm 冲突项）
sudo /usr/bin/kmutil load -b org.watchthelight.XeGfx
sudo sysctl -w debug.xegfx_wdog=60 >/dev/null
sudo sysctl -w debug.xegfx_stage=7 >/dev/null
sleep 22
sudo sysctl -b debug.xegfx_results | od -A n -t d4 | tee $L/results.txt  # 期望 0 1 1 1 1 1 1 1

# 2.3 accel + 帧拷贝模式
sudo /usr/bin/kmutil load -b org.watchthelight.XeGfxAccel; echo "accel rc=$?"
sleep 3
sudo sysctl -w debug.xegfxaccelfb=3      # 上游描述的"帧拷贝"形态（A-23a 用过）
sleep 3
```

**门 1：`results` 七项全 1、`class NMXAccel ≥1`。**

```bash
# 2.4 四项必须同时成立的"上游形态"证据
echo "=== a) accel 认了这块 framebuffer 当 head 4 ==="
sudo log show --last 5m --predicate 'eventMessage CONTAINS "NMXAccel"' 2>/dev/null | grep -E "accepted as head 4|parked as the alternative|heads published|head 4 piped" | tail -5
echo "=== b) 帧拷贝目标 ==="
sudo log show --last 5m --predicate 'eventMessage CONTAINS "NMXAccel"' 2>/dev/null | grep -E "CPU copy target|initFramebufferResource|XeGfxAccelPresent|API armed" | tail -6
echo "=== c) 插件映射进 WindowServer ==="
sudo vmmap $(pgrep -x WindowServer) 2>/dev/null | grep -ci nvmtl
echo "=== d) 系统认 Metal ==="
system_profiler SPDisplaysDataType | grep -iE "Metal|Resolution"
```

**门 2（本关的核心前提）：a) 出现 `accepted as head 4` 或 `head 4 piped`；b) 出现 `CPU copy target`
或 `initFramebufferResource`；c) `nvmtl` 计数 > 0；d) `Metal` 行为 `Metal 3`（或至少出现 Metal 行）。**

任一条不成立 → **停手报告**（把四条各自的实际输出贴出来），不要进 §3 —— 因为采样没有意义。

```bash
# 2.5 arm AGDC（上游用 AGDC 让 WindowServer 认出显示；A-29 已验证一次成功）
for i in $(seq 1 10); do
  sudo sysctl -w debug.xegfx_agdc=1 >/dev/null 2>&1; sleep 1
  s=$(sudo sysctl -n debug.xegfx_agdc 2>/dev/null); echo "agdc $i -> $s"; [ "$s" = "1" ] && break
done
sudo sysctl debug.xegfx_agdc_fbmap
```

## 3. 量准"到底谁在合成"（本关唯一要产出的数字）

> 必须**登录状态、桌面有动态内容**。静止桌面两边都是 0，没有判别力（本轮已踩过三次）。

### 3.1 起动画面 + 采样（若平时用 A-25 那个发生器脚本，直接用它）

```bash
# 基线：加载前那一刻的软合成计数（如果 WS 已经稳稳在跑，直接用现在的）
sudo sample $(pgrep -x WindowServer) 2 -file $L/ws-after.txt >/dev/null 2>&1
echo "SW  = $(grep -cE 'CA::OGL::SW|scanline|draw_polygon' $L/ws-after.txt)"
echo "MTL = $(grep -cE 'CA::MTL|MTLCommandBuffer|IOGPU|NVMTL|MetalContext' $L/ws-after.txt)"
```

**判据（与 A-25 同机同法的基准对照）**：

| 采样结果 | 含义 |
| --- | --- |
| `MTL` 显著 > 0 且 `SW` 从 1256 大幅下降 | **GPU 合成成立** ← 上游说的形态，Gate 4 第 3 条达成 |
| `SW` 仍 ~1256、`MTL` ≈ 0 | 仍软件合成：上游的"Metal 合成"在我们机上没成立，需要继续查（不是 IOP 方向） |

### 3.2 三个独立旁证（不要只靠 sample）

```bash
# b) 加速器自己的统计：有合成就该有 surface/swap 计数
sudo ioreg -l -w0 -r -c NMXAccel 2>/dev/null | grep -A12 "PerformanceStatistics" | head -16 | tee $L/perfstats.txt

# c) WindowServer 的 CPU（ms/s 不是百分比）
sudo powermetrics --samplers tasks -n 1 2>/dev/null | grep -A1 "Name " | grep -E "WindowServer|CPU ms/s" | head -3 | tee $L/power.txt

# d) 插件在进程里干什么
sudo lsof -p $(pgrep -x WindowServer) 2>/dev/null | grep -c nvmtl
```

## 6. 停机

1. 屏幕彩噪/黑屏/冻结 >10 s → 立即重启，并清 `armed`：

```bash
sudo ioreg -l -w0 > $L/ioreg-final.txt
sudo log show --last 5m --predicate 'eventMessage CONTAINS "XEGFX" OR eventMessage CONTAINS "NMXAccel" OR process == "WindowServer"' > $L/log-final.txt 2>/dev/null
sudo nvram xegfx-disp-phase=%00 xegfx-disp-trial=%00 xegfx-disp-expose=%00 xegfx-disp-fail=%01
sudo rm -f /var/db/xegfx/armed
sudo shutdown -r now
```

2. 门 1 / 门 2 不过 → 清门、卸 accel（`kextunload -b org.watchthelight.XeGfxAccel` 可能被拒，被拒就重启），报原文。
3. **不要**在本关里碰 `XeGfxDisplay` / S3 / IOP 的任何东西。

## 7. 铁律

1. 本关**不加载 `XeGfxDisplay`**、不设 `phase=%02` —— 走 IONDRV 那条路。
2. `debug.xegfxaccelfb=3` 是上游"帧拷贝"形态；不要试其它值（一次一个变量）。
3. 采样必须登录态 + 动态画面；静止桌面无可比性。
4. `powermetrics` 的列是 `CPU ms/s`，不是百分比。
5. `armed` 后 120 s 内不重启；WS 出现第 2 实例立即停。
