# Gate 7 · A-75 执行提示词：补完 marks（XGDR selector 1，把 flip 的等待从「GT 空闲」换成「本帧完成」）

> 目标：A-74 的 Phase 2 卡在 `dlsym("nvmtl_nvk_surface_dirty")` 缺失。**调研已确认这不是缺符号，
> 而是我们插件里该函数的旧版少了回落分支**：ArrowWhatever 0026 的 Intel 路径根本不走 ANV——
> 插件直接开加速器的 IOKit user client `'XGDR'`，用 **selector 1** 传 `(surfaceID, pending)`；
> `dlsym` 是 NVIDIA 遗留路径，失败时本应回落。accel 侧的 selector 1 入口我们树里已有（A-74 实测
> `nvSurfGpuEscape` 存在但从未被调用——**内核一直在等一个不会来的调用者**）。
> 本关把这两端接上：**plugin 提交时标 pending、GPU 完成标 ready；accel worker 只等本帧的 mark**。
>
> 预期收益：arm 等待从「整个 GT 空闲」变成「本帧合成完成」（ArrowWhatever 数据：同段 5.4ms @2MP，
> 我们的 arm p50 4.6ms 应降到 ≤2.5ms）；帧率稳定性提升（37/27/26 的抖动部分来自 GT 空闲等待被
> 无关负载拖住）；其它 app 的 GPU 工作不再拖桌面翻页。
>
> 必读：`20-ops/G7-A74报告.md`、`G7-120fps-研究.md`、`AI-远程连接说明.md`、`AI-远程调试作业说明.md`。

## 0. 调研结论（前人代码，照此移植，不要自己发明）

### 0.1 插件侧（ArrowWhatever `patches/0026-plugin-marks-tile4-pageoff.patch` 的 marks 部分）

**只取 marks 半边；Tile4 / page-off / selector 2 / selector 5–8 一律不取**（阶段 2 的活）。

```c
// 1) 连接：一次性打开 accel 的 'XGDR' user client
static io_connect_t g_mark_conn;
static io_connect_t nvmtl_mark_conn(void)
{
    static int opened;
    if (!opened) {
        opened = 1;
        if (!g_nmx_accel || IOServiceOpen(g_nmx_accel, mach_task_self(), 0x58474452u /* 'XGDR' */, &g_mark_conn) != KERN_SUCCESS)
            g_mark_conn = 0;
    }
    return g_mark_conn;
}
// 2) selector 1：(surfaceID, pending)
static uint32_t nvmtl_nmx_surface_mark(uint32_t surfaceID, int pending)
{
    if (!nvmtl_mark_conn()) return 0x80000002u;
    const uint64_t in[2] = { surfaceID, pending ? 1u : 0u };
    return (uint32_t)IOConnectCallScalarMethod(g_mark_conn, 1, in, 2, NULL, NULL);
}
// 3) 分发：NVIDIA 路径优先，缺失回落 XGDR（我们永远走回落）
uint32_t nvmtl_vk_surface_gpu_mark(uint32_t surfaceID, int pending)
{
    if (!pnvk_surface_dirty || !g_dev) return nvmtl_nmx_surface_mark(surfaceID, pending);
    return pnvk_surface_dirty(g_dev, surfaceID, 0x80000000u | (pending ? 1u : 0u));
}
```

- `g_nmx_accel` 的发现也在 0026 前部：枚举 accel 服务，`IOObjectConformsTo(accel, "NMXAccel")` 类的
  判定按我们树实际类名对齐（我们的是 XeGfxAccel 体系——**读我们 accel 的 user client 类名与
  `externalMethod` 的 selector 表，按实际值对齐，不要照抄 NMXAccel**），vendor 校验 `0x8086`，retain 保存。
- **EventSync（marks 的另一半，在 `NVMTLEventSync.m`）**：
  - 提交路径调 `nvmtl_ws_mark_pending(cb)`：遍历 command buffer `_parts` 里每个 surface 的 texture，
    收集 IOSurface ID，逐个发 pending（登记 hold）；
  - **GPU 完成（hold 释放）时发 ready**：同一 surface 的 hold 全部释放 →
    `nvmtl_ws_mark(sid, NO, NO)`（即 `nvmtl_vk_surface_gpu_mark(sid, 0)`）；
    等待 mark 的 deferred 列表 `nvmtl_ws_deferred` 同步唤醒（照 0026 原样）；
  - 探测 `nvmtl_ws_kernel_waits()`：用 `nvmtl_vk_surface_gpu_mark(0, 0)`（surface 0 是内核应答并忽略的
    探针）判定内核支持，每秒重查一次（A-57 的既有模式）。
- 我们插件里 `nvmtl_ws_kernel_waits` / `nvmtl_ws_mark_pending` 的骨架可能已存在（A-74 门 2 显示
  探针在跑、只是恒假）——**先读码盘点缺哪几块，按 0026 对齐，不重写已存在的部分**。

### 0.2 accel 侧（ArrowWhatever `patches/0024` 的 mark 等待部分）

0024 里 selector 1 的语义与等待链（对照我们树逐一核对，缺的补）：

```cpp
// selector 1：只收 WindowServer 的 marks（proc_selfname 校验），surface 0 是探针
// pending 表：32 槽 LRU（id/seq），gSurfPendLock 保护；最近一次 mark 记在 gSurfMarkLastAbs
// nvSurfWaitReady(id)：轮询该 surface 的表项，超时 ~100ms（kSurfGpuWaitMs："100ms 没画完就是挂了，照样翻"）
```

worker（`nvAccelXeFlipArm`）的等待顺序改成三级：

```
1. mark-only（默认开，gIopXeMarkOnly=1，且最近 1 秒内有 mark）→ 只等本帧 surface 的 mark
2. fence snapshot（nvAccelXeSnapTake/SnapWait，若我们树有 xgFlipSnapshot）→ 等入队时活跃 timeline 的 fence
3. 整个 GT idle 轮询（我们现状）→ 兜底
超时（iop_xe_idle_ms，默认 120ms）照样 arm + idle_forced（A-74 已装好这条）
```

对应 sysctl（核对存在性，缺的补）：`iop_xe_markonly`、`iop_xe_mark_last_us/_max_us`、
`iop_xe_mark_timeouts`（部分名字 A-74 已注册）、`iop_xe_snap`、`iop_xe_wait_idle/_idle_ms`。
时间线 `iop_tl` 里加 mark 段（照 0024 的 `nvXeTlNote(&NVXeTl::mark)`，让我们能看见
「取出→mark→arm→latch」各段）。

**注意**：`nvSurfGpuEscape()` 我们树已有（A-74 实测）——先读它的现状（selector 表、pending 表、
`nvSurfGpuEnabled()` 闸门），差什么补什么；名字对不上时以 0024 语义为准做功能对照。

## 2. 分两步（先内后外，每步有门）

### 步骤 A · 两端各就位（编译 + 装机 + 安全模式验证）

1. 插件：按 §0.1 补 XGDR 连接、回落分支、EventSync 的 pending/ready；
2. accel：按 §0.2 核对/补齐 selector 1 语义、三级等待、计数器、`iop_tl` 的 mark 段。

**门 A**：安全模式全关时行为 = A-74 末态；随后开 marks：
- `debug.xegfxaccel_surface_gpu_marks > 0` 且随拖动增长（**marks 通道第一次活起来**）；
- 探针与 pending/ready 无内核错误（`iop_fail=0`、无 panic）；
- 画面正常（用户目视，重点：无残帧——marks 时序错的最典型症状是"上一帧内容残留半秒"）。

### 步骤 B · A/B 与门 B

# A/B：markonly 1 vs 0（同一会话交替，各 3 轮拖动 25s）
sudo sysctl -w debug.xegfxaccel_iop_xe_markonly=1
~/xegfx-log/A-74/fps-probe2.sh 25 ; sudo sysctl -n debug.xegfxaccel_iop_tl | tail -200
sudo sysctl -a | grep -E 'xegfxaccel_iop_xe|surface_gpu_marks'

**门 B（本关成功线）**：

| # | 检查 | 期望 |
| --- | --- | --- |
| 1 | marks 占比 | `markonly_flips` 占翻转的 **>80%**；`mark_timeouts` 每分钟 < 10 |
| 2 | 等待坍缩 | `iop_tl` 的 mark 段 p50 **≤ 2.5ms**（A-74 的 arm 里 GT 空闲段是 4.6ms） |
| 3 | 帧率 | 拖动 3 轮中位 **全部 ≥ 30**（A-74 是 37/27/26——marks 应消掉后两轮的塌陷） |

## 3. 可选加分项（做完门 B 且时间允许再试，单独 A/B）

- **fence snapshot**（0024 的 §32.14）：`iop_xe_snap=1`，作为 mark 缺失时的中间级（不等整个 GT，
  只等入队时活跃 timeline 的 fence）。A/B 各 3 轮，好于 idle 就默认开。
- **HIGH 优先级**：WS 的 Vulkan 队列 `VK_KHR_global_priority=HIGH`（若本 ANV 构建支持）。
  判据：拖动时后台跑一个重 GPU 负载（如 `fps-probe` 带动画），开 HIGH 前后桌面 fps 对比。
