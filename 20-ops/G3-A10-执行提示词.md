## 0. 一句话

A-09 已经确认：显示器挂在 **PIPE_A 的 primary plane**，格式 **XRGB8888**，**线性（TILING=0）**，stolen 有 **128 MB**。
所以 A-10 只有一个动作：**把一块内容正确的 3120×2080 线性缓冲放进 GGTT 的空闲位置，把平面的 SURF/SIZE/STRIDE/PIPESRC 指过去，关掉缩放器**。
`PLANE_CTL` 的 format/tiling/alpha 位**一个都不许动**（读到的 `0x84000008` 就是对的）。

## 3. ⚠️ 主 agent 复核出的新发现：上一轮失败的原因很可能不是 tiling，而是**地址撞车**

```
macOS 当前活的表面：SURF = 0xFE600000
  尺寸 1920 × 1080 × 4 = 8,294,400 B = 0x7E9000
  占据 GGTT 区间：0xFE600000 .. 0xFEDE9000     ← 这就是桌面正在用的 7.9 MB

上一轮把缓冲放在：0xFE800000                    ← 落在这个区间里面（+2 MB 处）
```

**也就是说：上一轮的缓冲压在 macOS 桌面表面自己的 GGTT 区间上。** 两个后果同时成立：
1. 我们写的 6338 条 PTE 覆盖掉了 macOS 桌面表面的一部分页表 → 桌面自身内容被破坏；
2. 平面从 `0xFE800000` 起读、却按 `STRIDE=195`(12480) 解释一块本来是 120(7680) 步长的内存 →
   斜向错行，读到 26 MB 之外就是黑的。

这比"tiling 猜错"更能解释"**左上漂移 + 底部黑**"，而且和 A-09 实测（TILING=0）完全自洽。

**因此 A-10 的第一条硬约束：新缓冲的 GGTT 偏移必须完全避开 `0xFE600000 .. 0xFEDE9000`，并留足余量。**

- **一次开机只改一个变量。** 本次只做 A-10，不做 A-11、不动 NMIntelFB、不装加速器。

  `org.watchthelight.IGPUConsoleRange`、`XeGfx`、`XeDiag`、`HighPointRR`、`HighPointIOP`。

## 5. A-10 步骤

### 5.1 改 `D:/XEGFX-MIGRATE/11-native/xenative.cpp`

保留现有骨架（IOResources 挂载、自己遍历 IOPCIDevice 找 8086:030000、BAR0/BAR2 映射、GGTT 在 BAR2+0x800000）。
改动只有三块：

**(a) 缓冲改到 stolen，物理地址连续**
```
PHYS_BASE = DSMBASE + 0x01000000     // 从 stolen 里 16 MB 处开始（boot framebuffer 占 0..8 MB，留余量）
BYTES     = 3120*2080*4 = 25,958,400
GGTT_OFF  = 0x01000000               // 与 PHYS_BASE 的偏移一致，便于人眼核对
```
**先读、后写**：`DSMBASE(0x1080C0)`、`GGC(0x108040)` 读出来发布成属性；
算出 stolen 大小后**校验 `PHYS_BASE + BYTES ≤ DSMBASE + stolen_size`**，不满足就 `xnState = "stolen-too-small"` 并停手（不写任何寄存器）。

用 `IOMemoryDescriptor::withPhysicalAddress(PHYS_BASE, BYTES, kIODirectionOutIn)` + `createMappingInTask`
拿到 CPU 可写指针来填图案。**不要再用 IOBufferMemoryDescriptor**（那会拿到非连续的物理页）。

**(b) 显式建 PTE，不假设 stolen 已线性映射**
```
index = GGTT_OFF / 4096 = 0x1000
for i in 0..6337:  GGTT[index+i] = (PHYS_BASE + i*4096) | 0x3
然后 GFX_FLSH_CNTL(0x101008) = 1; = 0; IOSleep(50)
回读 GGTT[index] 与 GGTT[index+6337]，必须等于期望值 → 否则 xnState="pte-verify-failed"，停手不写显示寄存器
```
物理地址连续 → 不存在"PTE 顺序错、跨页错行"那一类问题。

**(c) 写显示寄存器（唯一变量）**
```
PIPESRC(0x6001C)  = 0x0C2F081F     // w-1=3119=0x0C2F 在高 16 位，h-1=2079=0x081F 在低 16 位
PLANE_SIZE(0x70190) = 0x081F0C2F   // w-1 在低 16 位，h-1 在高 16 位
PLANE_STRIDE(0x70188) = 195        // 12480 / 64
PS_CTRL(0x68180)    &= ~(1u<<31)   // 关 pipe scaler。当前 0x80000200 → 0x00000200
PLANE_SURF(0x7019C) = 0x01000000
```
**不写 `PLANE_CTL`。** `PLANE_TILEOFF` 保持 0（现值已是 0）。

顺序按上面这个次序写，每个寄存器之间 `IOSleep(5)`；写完再 `IOSleep(1000)`。
然后**读回全部 5 个寄存器** + `SURFLIVE(0x701AC)` + `TRANS_FRMCOUNT(0x60040)` 两次（间隔 >20 ms）。

### 5.2 测试图案（这次要能自动判定"原生 vs 放大"）

A-09 已经证明缩放器在做 1.625×1.926 非等比放大。所以图案要能**直接暴露是否还在缩放**：

1. **全幅 1 像素棋盘带**：在 `y ∈ [1000,1080)` 区间画 1px 黑白交替（`(x+y)&1 ? 0xFFFFFFFF : 0xFF000000`）。
   - 如果 1:1 原生 → 肉眼看到的是很细的密纹（可能接近灰，但**放大拍照能看到点阵**）
   - 如果仍在缩放 → 非等比放大把 1px 棋盘抹成**纯灰**
2. **四角标记**：在 `(0,0)`、`(3112,0)`、`(0,2072)`、`(3112,2072)` 各画 8×8 纯白方块。
   - 原生 → 四个角**贴边**、方块是正方形
   - 放大 → 标记会往里缩、且横向被拉长（1.625 vs 1.926）
3. **左右半屏底色**：左半 `0xFFFF0000`（红）、右半 `0xFF0000FF`（蓝），用于一眼确认是我们写的缓冲。
4. 在 `(1560,1040)` 附近（画面正中偏下）画一条 2px 高、400px 宽的纯亮绿横线，作为"这条线是否变形"的参照。

> 记住 `PLANE_CTL` format = XRGB8888，字节序 B,G,R,X —— 写 32-bit 值时按 `0xAARRGGBB` 排，红色是 `0xFFFF0000`。

写完立即 `unlink("/var/db/xegfx/armed")`。这样即使这次 hang，重启也不会自动重放一遍。

## 6. 停机条件

| 现象 | 处置 |
| --- | --- |
| stolen 不够 / PTE 回读不一致 | 停手，**不写显示寄存器**，报告（这属于"发现信息"，不算失败） |
| `PLANE_CTL` 读回来跟 `0x84000008` 不一样 | 说明有人动了它 → 停手，报告现值 |
| 屏幕全黑但 SSH 还在 | 立即把 SURF 写回 `0xFE600000`、PS_CTRL 恢复 `0x80000200`、PIPESRC 写回 `0x077F0437`、SIZE 写回 `0x0437077F`、STRIDE 写回 120，然后重启 |
| 屏幕全黑且 SSH 断 | 等 60 s；不通则断电重启一次；重启后应恢复 1080p（XeNative 写入被 armed 门限住，不会重放） |
| 出现新 panic | 停，把 panic 与 `~/xegfx-log/A-10/` 一起交上来 |
| 画面是我们写的图案但仍在缩放（棋盘变灰、四角内缩） | **这其实是半成功**：SURF 生效了，只是缩放器没关掉。留证，报告 PS_CTRL 读回值，不要在同一次开机里再改别的 |

## 验收锚点（主 agent 独立跑）

1. 从目标机拉回 `~/xegfx-log/A-10/` 全部文件，核对 PTE 首尾两条与 `PHYS_BASE` 自洽。
2. `sudo sysctl -b debug.xegfx_results | od -A n -t d4` —— XeGfx 侧不应因本次改动变化（仍 `0 1 1 1 -28 1 1 1`，若当次开机推过 stage）。
3. 读 `xenative` 的 ioreg 属性：`PS_CTRL` bit31 = 0、`SURFLIVE` = 写入值、帧计数在动。
4. 看 `screen.jpg`：`0xFE600000` 附近的桌面是否还有残留错乱（若 A-10 的缓冲没撞车，桌面应该完全正常）。
5. 无新增 panic；`/Library/Extensions` 里 IGPUConsoleRange 始终在；`armed` 已被清。
6. 若失败：确认 `SURF` 已回到 `0xFE600000`、`PS_CTRL` 回到 `0x80000200`（或者说明"靠重启恢复"）。
