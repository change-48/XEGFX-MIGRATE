# Gate 4 · A-35 执行提示词：让面板只剩一个 framebuffer

> 目标：S3 期间同时存在 **两个 IOFramebuffer**（我们的 `XeGfxIntelKMSFramebuffer` 3120×2080 +
> 占位的 `XeGfxIntelFramebuffer` 1080p）。把占位那个撤掉，让 WS 只面对一个显示，
> 看 IOP 能不能为它找到 display pipe。
>
> **零代码改动、零重编。** 一次进 S3，一次可能的 `kextunload`。

---

## 0. 为什么是这一步（用户目视 + 三处日志同时指向它）

### 0.1 用户目视（本关的起点）

> 「正常画面和黑屏反复出现的时候，**正常画面是 1080P 的大界面**」

### 0.2 三个独立证据都指向"两个 FB 并存"

| 证据 | 原文 |
| --- | --- |
| CoreDisplay 建 FB 的计数 | `Created FB 1 of 2`（A-34 §4.C） |
| IOP 找不到 pipe 的服务 | `Unable to find display pipe for IOFB service / regID: 0x…7f0` **和** `0x…525`（两个 regID） |
| S3 期间全量 ioreg（`20-ops/A-33/ioreg-s3.txt`） | `class XeGfxIntelKMSFramebuffer` = **1**、`class XeGfxIntelFramebuffer` = **1** |

### 0.3 这解释了"正常画面 / 黑屏交替"

```
WS 起来 → open() 我们那块 3120×2080 → CA 在 surface 记账上断言 → ~10 s 自杀
WS 一死 → 面板回落到占位 framebuffer 的 1080p 控制台画面   ← 用户看到的"1080P 大界面"
launchd 又拉起 WS → 又切过去 → 又黑
```

也就是说：**我们的 3120×2080 buffer 其实从来没被 WS 画过**（断言发生在合成之前），
用户看到的"正常画面"是占位那个 1080p 的。

### 0.4 为什么撤掉占位是合理的下一步

- IOP 按 **framebuffer** 建 display pipe；两个 FB 里我们的那块没有 pipe（`0x2002`），
  占位那块也没有（`Unable to find display pipe … 0x…525`）。两个都半死不活，CA 只能二选一。
- 占位类是 `IONDRVFramebuffer` 子类（`kexts/XeGfxIntelFB/intelfb.cpp:156`），它在 S3 里
  **既不该拥有面板、也不该发布 FB**（core 的 M4a 已接管 PCI display class）。
- 它自带关闭开关：`-xeintelfboff`（`intelfb.cpp:276`，命中即 `return nullptr`）。

**本关先试运行时卸载**（零配置改动）；卸载被拒再谈 boot-arg（那是 A-36，要改 OC）。

## 3. 撤掉占位 framebuffer（本关唯一动作）

```bash
# 3.1 先看它是不是被持有（有 client 时卸载会被拒）
sudo /usr/bin/kmutil showloaded | grep XeGfxIntelFB
sudo kextunload -b org.watchthelight.XeGfxIntelFB 2>&1; echo "unload rc=$?"
sleep 3

# 3.2 立刻数一遍
for c in XeGfxIntelKMSFramebuffer XeGfxIntelFramebuffer; do
  printf "%-28s %s\n" "$c" "$(ioreg -l -w0 2>/dev/null | grep -ac "class $c")"
done | tee $L/fb-s3-after.txt
```

判读：

| 结果 | 含义 | 下一步 |
| --- | --- | --- |
| `XeGfxIntelFramebuffer` = **0**、`XeGfxIntelKMSFramebuffer` = 1 | 卸载成功，只剩我们一块 | 进 §4 |
| `unload rc != 0`（busy / in use） | 被 WS 或 IONDRV 持有 | **停手**，直接进 §6 Plan B（要改 OC boot-arg，本关不做） |
| 卸载成功但我们的那块也变 0 | 两者有依赖 | **立即重启**，报告原文 |

> ⚠️ 卸载后**屏幕可能变黑或冻结**。这是预期内的（占位那块不再供图）；
> 只要 `XeGfxIntelKMSFramebuffer` 还在、`XeGfxFbRegistered=Yes`，就继续往下走。
> 若黑屏超过 60 秒且 §4 也没好转 → 按 §5 止损重启。

## 4. 判决：只剩一个 FB 时，IOP 能不能建 pipe

```bash
( sudo log stream --predicate 'process == "WindowServer" OR eventMessage CONTAINS "IOPresentment" OR eventMessage CONTAINS "M3d" OR eventMessage CONTAINS "NMXAccel"' > $L/stream-ws.log 2>&1 & )
sleep 2
sudo launchctl kickstart -k system/com.apple.WindowServer
sleep 25

echo "=== A) 失败链 ==="
grep -c "Unable to create IOAccelDisplayPipe" $L/stream-ws.log
grep -c "Interface creation error" $L/stream-ws.log

echo "=== B) 进去了没有 ==="
grep -E "newDisplayPipe|initFramebufferResource" $L/stream-ws.log | tail -6

echo "=== C) 还有几个 FB / 几个 regID ==="
grep -oE "Created FB [0-9]+ of [0-9]+" $L/stream-ws.log | tail -4
grep -oE "Unable to find display pipe for IOFB service / regID: 0x[0-9a-f]+ / 0x[0-9a-f]+" $L/stream-ws.log | sort -u | head -4
grep -c "System set to use IOP but no display pipes are present" $L/stream-ws.log

echo "=== D) 断言 / WS ==="
grep -c "transient surface .* not found" $L/stream-ws.log
ps -o etime=,pid= -p "$(pgrep -x WindowServer)"
```

判读：

| 现象 | 结论 |
| --- | --- |
| `Created FB 1 of 1` + `Unable to create IOAccelDisplayPipe` = 0 + `newDisplayPipe` ≥1 | **打通**，进 §5 判据 |
| `Created FB 1 of 1` 但失败链不变 | FB 不是原因，回到 IOP 能力/接口层（那要读 IOGraphicsFamily 二进制） |
| `Created FB x of 2` 还在 | 卸载没真正生效（只是 kext 页面卸载、对象还在），停手报告 |
| WS 活过 60 s | **Gate 4 第 3 条成立** |

## 6. Plan B（本关不做，只记录，留给 A-36）

若 `kextunload` 被拒，唯一干净的办法是让占位 kext **开机就不起来**：

```
intelfb.cpp:276   if (PE_parse_boot_argn("-xeintelfboff", &off, sizeof off)) { XIFBLOG("off by boot-arg"); return nullptr; }
```

但 `boot-args` 由 OpenCore 的 `NVRAM → Add/Delete` 每次开机覆写（今天已核实），
所以要在 **内置 ESP 的 `config.plist`** 里加 `-xeintelfboff`，并在 `phase=%02` 时才有意义
（phase=0 时还需要它供屏）。这件事有 EFI 风险，单独一关做。

## 7. 停机

1. 黑屏/冻结 >60 s 且 §4 无进展 → 立即：

```bash

sudo log show --last 5m --predicate 'process == "WindowServer" OR eventMessage CONTAINS "XEGFX"' > $L/log-final.txt 2>/dev/null
sudo nvram xegfx-disp-phase=%00 xegfx-disp-trial=%00 xegfx-disp-expose=%00 xegfx-disp-fail=%01
sudo rm -f /var/db/xegfx/armed
sudo shutdown -r now
```

2. WS 出现第 2 个实例 → 同 §7.1（别等 watchdog）。
3. 门 1/2/3 任一不过 → 清门 + 重启，贴原文。

## 8. 铁律

1. **S3 只走 bootarm**（`bootarm=%01` + `phase=%02` + `load core`），**绝不**写 `debug.xegfx_stage`。
2. **`kmutil load core` 必须等 `fbgeom.out` 末行为「完成」**（A-34 踩过，本次开机耗时 2 min 26 s）。
3. `armed` 后 120 s 内不重启；WS 第 2 实例立即停。
4. 一次一个变量：本关只做"撤掉占位 FB"。**不要**同时改 plist、不要重编、不要动 AGDC。
5. `IOCFPlugInTypes` 与 `IOAccelDisplayPipeCapabilities` **保留**（A-33/A-34 的成果，不回退）。
