### 3.1 `accelfb3.txt`（本关核心）

```
=== 门 3：scanout-backed pipe ===

2026-11-01 08:53:27.574136+0800  kernel: (XeGfxAccel) NMXAccel:   level 3: registering any published head that has no pipe yet
2026-11-01 08:53:27.574159+0800  kernel: (XeGfxAccel) NMXAccel: sysctl debug.xegfxaccelfb=3: scanout-backed display pipe ENABLED, re-delivering the mode change
2026-11-01 08:53:27.574161+0800  kernel: (XeGfxAccel) NMXAccel: sysctl debug.xegfxaccelfb=3: scanout-backed display pipe ENABLED, re-delivering the mode change
```

配套回显（写入与读回）：

```
$ sudo sysctl -w debug.xegfxaccelfb=3
debug.xegfxaccelfb: 1 -> 1            ← 读回恒 1（读的是 gNvAccelArmed），已知现象
read-back: 1
```

写入前 `grep -c` 该串在 `/Library/Extensions/XeGfxAccel.kext/Contents/MacOS/XeGfxAccel` 里 = **2**（两个分支各一处），
说明在线 kext 就是带 `how>=3` 分支的那份源码（`kexts/NVRM/accel/nvrm-accel.cpp:764-784`）。

**为何走 `re-delivering` 分支**：源码里 `registerFramebufferLocked(1)` 返回 false 时打印这句并补一发 `deliverModeChange()`，
返回 true 时打印的是另一句（`the registration just delivered the mode change -- not delivering it twice`）。
实测落在 **false 分支**——即"注册没顺带把模式变更递出去，所以这里补递一次"。
这与 head 已经被 `IOFBDependentIndex=0` 占用、无需新注册一致。

## 4. `bufferFlipCount` 仍 0：displayID ↔ FB id 对照（按 §8.4，只记录不提改法）

`Invalid display` 的 displayID **自始至终是同一个**，与 A-41 报告的 `0x23d05e40` **完全一致**：

```
2026-11-01 08:55:01.665  WindowServer: (SkyLight) [com.apple.SkyLight:default] Invalid display 0x23d05e40
…（截至 09:00 共 116 条，全部是 0x23d05e40，无一例外）
```

ioreg 侧：

```
$ ioreg -l -w0 -c XeGfxIntelFramebuffer | grep -E "IOFBDependentID|IOFBDependentIndex"
    "IOFBDependentIndex" = 0
    "IOFBDependentID" = 6360568414703976449        → 0x5845474600000001
```

对照结果：

| 项 | 值 |
| --- | --- |
| SkyLight 报的 displayID | `0x23d05e40`（= 601,390,656） |
| ioreg 里 FB 的 `IOFBDependentID` | `0x5845474600000001`（= 6,360,568,414,703,976,449，ASCII `"XEGF"` + `00000001`） |
| `ioreg -l -w0 \| grep -i 23d05e40` / `601390656` | **0 命中**——这个 displayID 在 IORegistry 全树里**没有任何对应对象** |
| `ioreg -c IODisplayConnect` 对象数 | **0** |
| `IOFramebufferOnline` 键 | **不存在**（FB 只有 `IOFramebufferOpenGLIndex=0`） |
| `system_profiler SPDisplaysDataType` | 有 GPU 段（Xe-LPG+ 0x7d51，Metal 3），**无 `Displays:` 子段** |
| `screencapture -x` | `could not create image from display` |

即：**该 display 记录在 SkyLight/CoreDisplay 侧存在，在 IORegistry 侧不存在**（FB 的 dependent ID 是驱动自造的 `"XEGF"` GUID，与它无关）；
同时系统层面**没有任何一个 display 处于 online**。

## 6. 一处执行事故（已纠正，影响结论的都要在此声明）

第一阶段按提示词 §3 用 `( sudo log stream … & )` 起的日志流，**在 macOS 上根本没起来**——
我为了"防 SIGHUP"加了 `setsid`，而 **macOS 没有 `setsid`**，于是 `stream.log` 里只有一行
`sudo: setsid: command not found`。那一轮据此读出的 `Invalid display = 0` 是**假数**。

改用 `sudo nohup log stream … &` 后流正常（5 分钟 117 行），并用 `log show --start 08:52:00` 回溯补算了全部计数——
本报告 §2 判据 6 与 §4 的 **116 次**是 `log show` 的实数，**不是**那个假 0。其余判据不受影响（它们都不依赖该日志流）。

另外提醒：这台机器的 `ioreg -c XeGfxIntelFramebuffer` 匹配到的是 `IOFramebuffer` 基类，属性列表里**没有** `IOFramebufferOnline` 这类键，
所以"是否 online"只能用 `IODisplayConnect` 对象数与 `system_profiler` 判断（两者都指向"无在线 display"）。
