## 缺陷 P-0a（已修）

`PS_HSCALE/PS_VSCALE` 从 `0x4EC5/0x4276`（1920/3120、1080/2080）算成 `0x8000/0x8000`（1:1），

## 三条会改后续 gate 假设的实测事实

1. **平面几何寄存器是双缓冲，必须由一次 `SURF` 更新锁存。**
   按提示词"先 `reg surf` 后 `regset`"的顺序，几何永远不生效：回读全对、`SURFLIVE` 正常、
   `PIPESTAT=0`，但屏幕只有左上角 1920×1080 一块。补一次 SURF 更新后立刻全屏。

2. **几何一旦暂存，macOS 自己的 flip 会拿它去锁存 1080p 缓冲** → 满屏错位（本轮真实撞到一次）。
   → "让 macOS 画进原生缓冲"时，几何必须与 macOS 的模式切换同步，不能先摆几何等它翻页。
3. **`PS_HSCALE/VSCALE` 可当只读判据**：`0x8000` = 1:1，非 `0x8000` = 仍在缩放。
   以后不用拍照就能判"是否 1:1"。时序/DDI/水位全健康：`HTOTAL 0x0D470C2F`、`VTOTAL 0x089F081F`、
   `PIPEASTAT=0`、`PLANE_BUF_CFG=0x07FF0000`（DDB 给满）。

### 三个硬读数（我认可）

| 读数 | 值 | 意义 |
| --- | --- | --- |
| `regs-diff` | **0 字节** | 显示寄存器一个没动：`SURF/SURFLIVE 0xfe600000`、`0x70240 水位 0x80008035`、`0x7027c DDB 0x07ff0000`、`PS_CTRL 0x200` 全同 |

结论：**不是寄存器被改，是 GGTT 页表被改写**；而且"flip 栈缺失"解释不了本次现象（flip 计数器为 0，画面已花）。

### 我查到的根因（源码级，`xg_kext.cpp:501-508`）

```c
int err = xg_i915_reserve_bootfb(gBootSurf, xg_boot_fb_size);     // 0xFE600000 + 25958400
IOLog("XeGfx: boot surface GGTT 0x%x + %llu reserved: %d\n", ...); // err = -28
if (err == -28 && gBootSurf < 0xfee00000u) rc = -28;
```

**保留失败（-28 ENOSPC）→ i915 的 GGTT 分配器根本不知道这 26 MB 被占用** →
加速器一分配就往里放 → 覆盖帧缓冲的 PTE → 扫描读到别处内存 → 局部画面被写花。

算术上完全自洽：`0xFE600000 + 25,958,400 = 0xFFEC1800`，**跨过 `GUC_GGTT_TOP = 0xFEE00000`**，
insert 撞上 GuC 保留区必然 ENOSPC；而注释里"at or above GUC_GGTT_TOP keeps it free"的前提

### 四、彩噪的成因（写进交接）

`open()` 被拒后，preflight 已经把 scanout 指到我们自己的 buffer，而没人往里画

### 五、`XeGfxAccelPresent` 的发布时机（决定 A-30 的顺序）

```c

// :787  head 4 被 pipe 起来时再发布一次（"head 4 piped"）
```

1. 干净态加载 accel **不会**出现 `XeGfxAccelPresent`（那时是 `XeGfxIntelFramebuffer`，不是 `XeGfxFramebuffer`）
   → 门槛只能是 `class NMXAccel` 有实例，不能拿 Present 当门槛。
2. accel 是监听新 framebuffer 的，S3 的 KMS framebuffer 出现时它会补上 —— **A-27 就是 accel 先在场、S3 后起**。

## A-30 设计（相对 20:09 那版的改动）

- **把 accel 加载提到进 S3 之前**：这样 `Code=28` 之类的失败发生在干净态，屏幕正常、零风险；
  若按原流程在 S3 里加载失败，就会直接复现 A-29 的彩噪。
- 门槛改为：门1 `results` 全 1 + `nmxgpu-claimed`；门2 `class NMXAccel ≥1`；
  门3 S3 后 `XeGfxAccelPresent ≥1`；门4 AGDC `state=1`。
- 判据表 16 条，第 11 条要求 IOP 的 `agdc` 与 `accel` 两个句柄**都**非 0。

而 `getInformationForDisplayMode()` 的 S3 守卫是：

```c
if ((!fFbModeReady && !(fM3d && fM3dChecks == XEGFX_M3D_CHECKS_ALL)) || fMeasuredModeCount == 0 ||
    mode != fMeasuredModes[0].modeId)
        return kIOReturnUnsupported;
```

`fFbModeReady` **只在 `enableController()` 里置位**（A-32 已证：它和 `FbReady` 都是 `open()` 之后才发布）。
于是形成死循环：

```
CoreDisplay 要模式信息 → 我们要求 fFbModeReady → 它要 open() 之后才有
        ↑                                              ↓
        └──── CoreDisplay 正是拿不到模式信息才不建显示、不 open ────┘
```

而模式表 `fMeasuredModes[]` 是 `start()` 里从 VBT/实测时序建的（日志 `mode: 0 id 1: 3120x2080 …`
出现在 open 之前很久）——**读它根本不需要 open**。

### 四、两条旁证（本关记录，不作结论）

- `newUserClient(type 4/5/6) 全部返回 0x0`（A-34 是 type 0 → `0xe00002c9`）→ 客户端层已通，
  失败在 pipe 自身初始化。
- 我核过 SDK 的 `IOFramebuffer.h`：`getFramebufferInfo` **不存在**于该头，`connectFlags` /
  `getConnectionCount` 都是带默认实现的可选方法 → 不是"少实现一个方法"那类问题。

## A-36：解开死循环

只改 `XeGfxDisplay.cpp` 里**两处相同守卫**（`getPixelInformation` 约 438 行、`getInformationForDisplayMode` 约 480 行）：

```c
/* 旧 */
if ((!fFbModeReady && !(fM3d && fM3dChecks == XEGFX_M3D_CHECKS_ALL)) || fMeasuredModeCount == 0 ||
    mode != fMeasuredModes[0].modeId) return kIOReturnUnsupported;
/* 新：读操作不再依赖 open；mode 0（CoreDisplay 的"当前/默认"探测）映射到实测模式 */
if (fMeasuredModeCount == 0 || (mode != fMeasuredModes[0].modeId && mode != 0))
    return kIOReturnUnsupported;
```

不改 `open()` / `enableController()` / `setDisplayMode()`（写仍要求真就绪）。
重编 `tools/build-xegfxdisplay.sh` → 重签 → KC → 重启 → **bootarm 路径**（等 fbgeom「完成」）
→ **先验"模式信息失败计数"是否为 0，再决定要不要起 WS**（避免又进 10 秒循环）。

**本关不撤占位 FB**（A-35 已证撤了会全黑无兜底），只让"代码改动"成为唯一变量。

## 二、瓶颈 1：scanout 拷贝（已定位到具体代码）

`performTransaction()` 尾部是**逐 4 字节、两边 `volatile`** 的循环：

```c
for (unsigned y = 0; y < h; y++) {
    const volatile unsigned int *sp = src + y * spr;
    volatile unsigned int *dp = d + y * dpr;
    for (unsigned x = 0; x < words; x++) dp[x] = sp[x];
}
```

3120×2080 ⇒ **650 万次**存取；编译器无法向量化；目标又是写合并内存，4 字节窄写让 WC 缓冲几乎失效。
26 MB / 12 ms = **2.2 GB/s**。

**上游同处逐字相同**（`xe` 分支 `nvrm-accel.cpp:1219-1226`）——不是我们落后，是上游自己也吃这个代价。

## 三、瓶颈 2：WindowServer 侧 ~18 ms/帧

着色器翻译已缓存（空闲可证），所以这 18 ms 不是翻译。
待查方向：每帧管线/描述符重建、`NVMTLCommandBuffer` 提交路径、CA 的 display link 节奏。

## 四、A-45：先修拷贝

# 附：A-46 验收 + A-47 设计（2026-11-01 15:40）

## 一、A-46 判定：bootArm 六步跑通，零拷贝卡在一个等号


**唯一未通过的判据**（`:2477`）：

```c
if (qr == kIOReturnSuccess && q.kva && q.pitch == P && …)
                            ↑ 12480        ↑ 12544
```

| 条件 | 实测 |
| --- | --- |
| `gIopXeDefer` / `gIopXeFlip` | 1 / 1 |
| `s` 非空、`head == 4`、`nvXePlaneWriteAllowed` | 全部通过 |
| `W/H/P`、`P*H < 64MB`、`P & 3 == 0` | 3120/2080/12544，通过 |

| **`q.pitch == P`** | **12480 ≠ 12544** ← 唯一差异项 |

另记：**旧 flip 路径结构性不可用** —— `nvAccelIopFlip()` 里 `if (!fb->metaCast("NVRMNVDAFramebuffer")) return false;`，
我们的 `XeGfxIntelFramebuffer` 永远返回 false，所以 `iop_flip` 在这块屏上不可能增长；
只有新的 `iop_xe_flips` 一条路。

## 二、★ 为什么上游没这个问题

上游面板 2560 宽 ⇒ 2560×4 = **10240 = 256×40**，CA 的 256 字节对齐结果等于 scanout 行距，
`q.pitch == P` 天然成立，flip 从不需要碰 stride。

我们的 3120 宽 ⇒ 3120×4 = **12480**，12480/256 = 48.75 ⇒ CA 补到 **12544** ⇒ 差 64 字节。
**这是"3120 宽"特有的结构性问题，上游代码没有覆盖。**

## 三、A-47：让 flip 同时写 stride（一处）

### 3.1 依据（三条已核实）

1. **单位**：stride 寄存器 = 行字节/64。我们自己的 `11-native/xenative.cpp` 就是这么写的
   （`fReg[PLANE_STRIDE_1_A/4] = NAT_ROW / 64`，且有 `fStrideBefore` 还原），
   `NMIntelFB` 读法互证：`fRowBytes = stride * 64`。
2. **偏移**：`PLANE_STRIDE(0) = 0x70188`、`PLANE_SURF(0) = 0x7019C`（同一寄存器块）。
3. **面板接受任意 stride**：A-10/A-11 用 XeNative 改过 stride 显示 1080p，画面正常。

⇒ 12480/64 = **195**（当前），12544/64 = **196**（目标）。

### 3.2 改动边界

- **只改 `nvAccelXeFlipArm`（:1707）** —— 我们这条 IONDRV 路径的唯一终点（defer worker 走它）。
- **不动** `nvAccelXePresent`（:2065-2145，KMS 适配器的 present 路径，`phase=%00` 下不在场）。
- arm 之前写 stride；失败路径（`!latched`）**先还原 stride 再还原 surf**，避免"新行距 + 旧缓冲"的瞬间组合。
- `pitch % 64 != 0` 或 `pitch/64 > 0x7FF` 时**不写 stride**，行为与改动前一致。

### 3.3 期望

`iop_xe_flips` / `defer_queued` 开始增长，`copy_sum_us` 停止增长（去掉 4.5 ms/帧 + 每帧 26MB×2 内存流量）。
帧率提升有限（WS 侧 23 ms 才是上限），但能省电、降温、减少内存带宽。

**风险**：stride 写错 → 面板斜切。可回滚（装回备份 kext + KC + 重启），且重启后 FB 会重新编程模式。

# 附：A-47 验收（2026-11-01 18:20）——我的改动是死代码；零拷贝在 3120 宽上必须偏离上游

## 一、判定：判据 6/7/9 不通过，原因是**我的设计错误**

A-47 把 stride 写进了 `nvAccelXeFlipArm`，但 `iop_xe_arm_last_us = 0` —— **arm 一次都没被进入**，

根因是**位置鸡生蛋**：

```c

                                            ↓ 只有通过才入队 → 才 arm

```

写 stride 在 arm 内部，**在数学上不可能改变进入 arm 的条件**。这是我的疏漏，责任在我。

## 二、为什么"绕过"也不行（这次查到底了）

`q.pitch` 不是现读 `PLANE_STRIDE_1_A`：

```

   ↳ 我们的 XeGfxIntelFB 没实现 → 走"描述启动光圈"的兜底 → 报固件模式的 12480
```

所以即使把 stride 寄存器改成 196，`q.pitch` 仍然是 12480。**`q.pitch` 是缓存/兜底值，不是活值。**

要让等式成立，只有三条路，**全部偏离上游**：
1. 放宽那道闸门（允许 `P != q.pitch` 且 `P%64==0`，同时写 stride）
2. 让 FB 上报合成器的行距
3. 模式设置时直接分配 256 对齐的 scanout（3120 → 12544）

# 附：A-48 实验记录（2026-11-01 18:49）—— 结果"花屏"，但**测试本身未被验证**，判定无效

## 一、做了什么

用已装的 `xenative-ctl`（零代码）做 A/B：

```bash
xenative-ctl fill 1                          # 按 12480 行距填图案（左红右蓝）
xenative-ctl regset 3 1 0x081f0c2f 2 195 0 0xfd000000   # A 组：195 / 2080 行（对照）
xenative-ctl regset 3 1 0x08140c2f 2 196 0 0xfd000000   # B 组：196 / 2069 行（实验）
```

寄存器读回都正确（`0xc3`=195、`0xc4`=196；SIZE 也一致）。

## 二、结果：**B 组花屏**

用户目视：屏幕变成花屏（不是预期的"阶梯斜切"）。

## 三、为什么判定"实验无效"而不是"引擎拒绝 196"

1. **对照组的观察没拿到** —— A 组只保持了 10 秒，用户当时没描述；
   如果 A 组（195）也是花屏，那说明 `fill` 根本没把图案写进缓冲，花屏与 stride 无关。
2. **`fill` 的输出无法证明写成功** —— `filled 1 phys_base 0x71800000 flushes 2` 里的 `1` 是
   `wb` 参数（ctl 打印 `out[0]`），**不是写入计数**。
3. **`status` 的寄存器是缓存快照** —— `FRMCOUNT` 三次读数完全相同（1749304），
   说明它读的是 kext 里的 `fReg` 数组，不是实时值，**不能用它判锁存**。

⇒ 结论：**既不能证明"引擎采纳了 196"，也不能证明"拒绝了 196"**。这条测试需要在
"先验证图案确实写进去了（读回像素）"之后重做，否则每次都会得到同一个不可解释的花屏。

## 四、一个必须记住的坑

`xenative-ctl restore` 把 `SURF` 放回的是 **`SURF_before = 0xfe600000`**，
那是 **A-10 之前**的老缓冲；而当前真正在用的扫描地址是 **`0xfd000000`**。
⇒ **restore 之后必须补一次 `regset … 0 0xfd000000`**，否则面板指向错误缓冲。

# 上游深挖（2026-11-01 20:30）：K9 延迟 flip 的完整前置条件 + 两个静默丢帧分支

## 一、找到了权威文档：ArrowWhatever `docs/k9-deferred-flip.md`

它写的机制，正是我们缺的那一段：

1. **core 侧空闲探测**：`xg_i915_idle()` 经 `callPlatformFunction("xgFlipQuery")` 暴露，
   返回 1 空闲 / 0 忙 / -ENODEV。
   → **我们 core 里有**（`gpu/xegfx/shim/src/xnu/xg_kext.cpp:192`），这一环是通的。
2. **加速器 defer worker**：帧映射进 GGTT 槽后**不立即**写 `PLANE_SURF`，worker 轮询空闲后才 arm。
   参数：`iop_xe_defer` / `iop_xe_report_busy` / `iop_xe_wait_idle` / `iop_xe_idle_ms`。
   → 我们 bootArm 已全部置好。
3. **插件 no-wait 提交**（patch 0007 + 哨兵 `touch /private/tmp/xemtl-ws-nowait`）：
   "让（重新启动后的）WindowServer 里的插件走 no-wait 提交分支"。
   → **我们没有**：哨兵文件不存在，而且我们这份插件里**根本没有 `nowait` 字样**（那是 patch 0007）。

他们的实测：同步等待 ~15fps → 延迟 flip **~60fps**（2560×1600）。
他们踩过的坑：只上 no-wait 不上内核侧排序 → 28.4fps 但撕裂/光标回退/候选框异常。
→ 说明**两件事必须一起上**，这也解释了我们单开 defer 为什么没效果。

## 二、A-49 冻屏的两个候选原因（都在 `nvAccelXeFlipDeferQueue` 里，都会静默丢帧）

```c
if (gXePresentActive != 0)      overflow = true;   // ① 适配器正在写平面
else if (queue full)            overflow = true;   // ② 队列满
...
if (overflow) { gCntXeDeferDropped++; signalTransactionInterrupt(pipe); return; }  // 队列根本没进
```
另有第三条：`if (!gXeFlipLock || !gXeFlipCall) { gCntXeDeferDropped++; return; }`。

三条**都只加 `defer_dropped`**，而 A-49 的报告**没有读这个计数器**。
⇒ 换句话说，我们至今**不知道**那帧是被丢弃，还是被别的分支挡掉。

**排除了一个假设**：`gXePresentActive` 不会泄漏——present 路径里 2079 置 1 的前提是 `!deferBusy`，
而 2079~2181 之间唯一的 `return` 正是 `deferBusy` 分支，它发生**在置 1 之前**。清 0 在 `do{}while(0)` 之后无条件执行。

## 三、结论与下一步的正确做法

单靠"放宽闸门"必然冻屏——因为 defer 分支一旦接受帧就 `return kIOReturnSuccess`，
而队列丢弃时**没有回退到拷贝**。这是设计上的空档，不是我们配置错。

要安全地做，必须两件事一起：

1. **让 `nvAccelXeFlipDeferQueue` 返回成功/失败，`performTransaction` 在失败时落回拷贝路径** ——
   这样最坏情况退化成今天的行为，不可能冻屏；
2. **装 dead-man 看门狗**（`iop_ok` 30 s 不前进自动重启），保证即使全挂也能自愈。

有了这两条，才能安全地读出 `defer_dropped` / `defer_queued`，定位到底是哪一条分支在丢帧。

# ★★ 找到了 120fps 的真正杠杆（2026-11-01 20:45）——不是 flip，是 WS 每帧的等待

## 一、链条怎么被发现的

从 ArrowWhatever 的 `docs/k9-deferred-flip.md` 读到 K9 的三段结构，顺藤摸到我们插件里**已经有**这条机制：

```objc
// NVMTLObjects.m:5159
- (BOOL)commitAndWaitUntilSubmitted {
    static int ws = -1;
    if (ws < 0) ws = (getprogname() && !strcmp(getprogname(), "WindowServer")) ? 1 : 0;
    [self commit];
    // nvmtl_ws_kernel_waits: the swap waits for this composite in NVAccel instead
    if (ws && !nvmtl_ws_kernel_waits()) [self waitUntilCompleted]; else [self waitUntilScheduled];
    return self.status != MTICommandBufferStatusError;
}
```

# ★★★ A-53 成功：零拷贝 flip 真的跑起来了（2026-11-01 23:13）

## 一、做法（不改上游判据，只把前提补齐）

1. **`NV_XE_FLIP_MAX_PAGES` 4224 → 8192**

4. 自启脚本的成功判据补上 flip：零拷贝时 `iop_ok` 恒为 0 是**正常**，现在也认 `iop_xe_flips`。

# A-54（2026-11-02 上午）：映射缓存成功，no-wait 失败 —— 零拷贝在 3120 宽上判定不可行，已全部回滚

## 一、映射缓存：**成功，且是真改进**

问题：`nvAccelXeFlipArm` 每帧重走 6370 页 + 重写 6370 个 PTE + 刷 GPU TLB ≈ 20 ms。

# A-60/A-61 结论（2026-11-02 18:55）：把 backing 改小的路走到底了——**CoreDisplay 不接受**

## 一、这一轮真正推进到的地方

| 步骤 | 结果 |
| --- | --- |
| 找到模式尺寸的真正来源 | `IOFBConfig` 的 `"DM"` 字：`<300c0000 …>` = hact 0x0c30 = **3120** |

## 二、但 CoreDisplay 拒绝了这个模式，而且不报错

## 三、判定

**macOS 对内屏没有"小 backing + 面板放大"这条路。** 它的 scaled mode 是反的（timing 变小、面板放大），

⇒ **120fps 在这块屏 + 这套栈上不可达。** 4 倍像素这条杠杆被 CoreDisplay 的设计挡住，不是寄存器问题。

# A-68（20:10）：双缓冲实验——机制跑通了，但**撕裂更严重**，已回滚

## 做了什么

```

SURF = SURFLIVE = 0x80000000        ← 面板确实在扫后台缓冲

```

那正是 K9b/K7 那条路，我们测过它在本面板上更慢（14 vs 22）。

# A-69（20:18）：★ 非临时存储把 26MB 拷贝从 8.3ms 压到 3.0ms（2.5 倍）

## 改了什么

`performTransaction` 里的整帧拷贝：普通 `memcpy` → **`__builtin_nontemporal_store`（movnti）+ sfence**。
目标是指针从不回读的 write-combined 显存窗口，非临时写入不做 read-for-ownership、不污染缓存；
movnti 只用整型寄存器，在 kext 里安全。对齐检查失败时自动退回 memcpy。

## 实测（同一台机器、同一面板）

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 拷贝 last | 8282 us | **2994 us** |
| 拷贝 平均 | 8300–9500 us | **3913 us** |
| 拷贝 max | 33361 us | 26329 us |
| 事务 last | 9365–9824 us | **3849 us** |
| 带宽 | ~3.1 GB/s | **~6.7 GB/s** |

⇒ 每帧省约 **4.4 ms**，而且**撕裂窗口缩短一半以上**（写入 8.3ms → 3.9ms，越界概率大降）。

## 为什么之前没想到

一直在追"谁在等谁"，没量拷贝本身的带宽。26 MB / 8.3 ms = 3.1 GB/s，对 WC 内存的普通 memcpy
就是这个水平——换成 non-temporal 立刻翻倍。**这是今天唯一一个无风险、可量化、且同时改善帧率与观感的改动。**
