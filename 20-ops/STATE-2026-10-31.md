**时序本来就是原生的**，面板此刻就在按 3120×2080 扫。`PIPESRC` 是**缩放器输入尺寸**、`PS_WIN_SZ` 是输出尺寸。

## 判定：A-18a 达到目的（定性完成），且**推翻了报告与计划双方的原因判断**

### 三个硬读数（我认可）

| 读数 | 值 | 意义 |
| --- | --- | --- |
| `regs-diff` | **0 字节** | 显示寄存器一个没动：`SURF/SURFLIVE 0xfe600000`、`0x70240 水位 0x80008035`、`0x7027c DDB 0x07ff0000`、`PS_CTRL 0x200` 全同 |
| `live_run_pages` | **6656 → 1701** | 帧缓冲那 26MB 的连续映射被**从中间截断**（只剩 6.65MB） |
| `present_entries` | **3518 → 4789 (+1271)** | 表里新增 1271 条映射 ≈ 加速器提交时分配的缓冲 |
| `vmmap \| grep -c nvmtl` | **18** | **Gate 4 第 2 条（历史分水岭）已满足** |
| `mtlprobe` | **16/16** | 应用侧 Metal 真的算对了 |

结论：**不是寄存器被改，是 GGTT 页表被改写**；而且"flip 栈缺失"解释不了本次现象（flip 计数器为 0，画面已花）。

### 我查到的根因（源码级，`xg_kext.cpp:501-508`）

```c
int err = xg_i915_reserve_bootfb(gBootSurf, xg_boot_fb_size);     // 0xFE600000 + 25958400
IOLog("XeGfx: boot surface GGTT 0x%x + %llu reserved: %d\n", ...); // err = -28
if (err == -28 && gBootSurf < 0xfee00000u) rc = -28;
```

**保留失败（-28 ENOSPC）→ i915 的 GGTT 分配器根本不知道这 26 MB 被占用** →
加速器一分配就往里放 → 覆盖帧缓冲的 PTE → 扫描读到别处内存 → 局部画面被写花。

算术上完全自洽：`0xFE600000 + 25,958,400 = 0xFFEC1800`，**跨过 `GUC_GGTT_TOP = 0xFEE00000`**，
insert 撞上 GuC 保留区必然 ENOSPC；而注释里"at or above GUC_GGTT_TOP keeps it free"的前提
（整段都在 GuC 之上）不成立。

### 四、彩噪的成因（写进交接）

### 五、`XeGfxAccelPresent` 的发布时机（决定 A-30 的顺序）

```c

2. accel 是监听新 framebuffer 的，S3 的 KMS framebuffer 出现时它会补上 —— **A-27 就是 accel 先在场、S3 后起**。

## A-30 设计（相对 20:09 那版的改动）

- **把 accel 加载提到进 S3 之前**：这样 `Code=28` 之类的失败发生在干净态，屏幕正常、零风险；
  若按原流程在 S3 里加载失败，就会直接复现 A-29 的彩噪。
- 门槛改为：门1 `results` 全 1 + `nmxgpu-claimed`；门2 `class NMXAccel ≥1`；

IOFBSetDisplayModeAndDepth: Setting mode 0x0 with depth 0x0 on displayID: 0x0 fbRegID: 0x10000083f
IOFBSetDisplayModeAndDepth: Failed to obtain mode info from IOFBGetDisplayModeInformation()
```

而 `getInformationForDisplayMode()` 的 S3 守卫是：

```c
if ((!fFbModeReady && !(fM3d && fM3dChecks == XEGFX_M3D_CHECKS_ALL)) || fMeasuredModeCount == 0 ||
    mode != fMeasuredModes[0].modeId)
        return kIOReturnUnsupported;
```

`fFbModeReady` **只在 `enableController()` 里置位**（A-32 已证：它和 `FbReady` 都是 `open()` 之后才发布）。
于是形成死循环：

```
CoreDisplay 要模式信息 → 我们要求 fFbModeReady → 它要 open() 之后才有
        ↑                                              ↓
        └──── CoreDisplay 正是拿不到模式信息才不建显示、不 open ────┘
```

而模式表 `fMeasuredModes[]` 是 `start()` 里从 VBT/实测时序建的（日志 `mode: 0 id 1: 3120x2080 …`
出现在 open 之前很久）——**读它根本不需要 open**。

### 四、两条旁证（本关记录，不作结论）

- `newUserClient(type 4/5/6) 全部返回 0x0`（A-34 是 type 0 → `0xe00002c9`）→ 客户端层已通，
  失败在 pipe 自身初始化。
- 我核过 SDK 的 `IOFramebuffer.h`：`getFramebufferInfo` **不存在**于该头，`connectFlags` /
  `getConnectionCount` 都是带默认实现的可选方法 → 不是"少实现一个方法"那类问题。

## A-36：解开死循环

只改 `XeGfxDisplay.cpp` 里**两处相同守卫**（`getPixelInformation` 约 438 行、`getInformationForDisplayMode` 约 480 行）：

```c
/* 旧 */
if ((!fFbModeReady && !(fM3d && fM3dChecks == XEGFX_M3D_CHECKS_ALL)) || fMeasuredModeCount == 0 ||
    mode != fMeasuredModes[0].modeId) return kIOReturnUnsupported;
/* 新：读操作不再依赖 open；mode 0（CoreDisplay 的"当前/默认"探测）映射到实测模式 */
if (fMeasuredModeCount == 0 || (mode != fMeasuredModes[0].modeId && mode != 0))
    return kIOReturnUnsupported;
```

不改 `open()` / `enableController()` / `setDisplayMode()`（写仍要求真就绪）。
重编 `tools/build-xegfxdisplay.sh` → 重签 → KC → 重启 → **bootarm 路径**（等 fbgeom「完成」）
→ **先验"模式信息失败计数"是否为 0，再决定要不要起 WS**（避免又进 10 秒循环）。

**本关不撤占位 FB**（A-35 已证撤了会全黑无兜底），只让"代码改动"成为唯一变量。
