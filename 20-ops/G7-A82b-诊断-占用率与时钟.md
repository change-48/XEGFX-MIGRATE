# Gate 7 · A-82b 诊断提示词：占用率与时钟 —— 「不发热」到底说明什么

> 起因：使用者观察「Windows 下这个位置会发热，现在根本不热」。
> 已知数字完全吻合：WS 主线程 busy 26.2ms/帧 = **单核 68%**（全机 ~5%）、GPU 合成 13–15ms/帧
> @26fps = **GPU 占用 ~35%**。结论方向：不是算力不够，是**流水线串行 + 等待**——38.5ms 里有 12ms 纯等待。
>
> 本关目标（45 分钟，**先测量后动手**）：回答三个问题，每个都要数字：
> 1. **GPU 频率是多少？**（利用率低 → SLPC 压低频率 → 合成慢 → 帧率低 → 利用率仍低，自我锁死？）
> 2. **帧时间是不是被 vblank 量化卡住？**（38.5ms ≈ 4.6 个 8.33ms）
> 3. **那 12ms 等待/空转具体在等什么？**
>
> 必读：`G7-A82报告.md`（busy 三分类、`xa82load`、`parse_all.py`）、`G7-A77报告.md` §1。

---

## 1. 铁律

使用者在场；**本关零行为改动**（只读 + 用户态测量）；需要 accel 重编译时，只加只读寄存器/计数，
构建坑五条照 A-82；每轮测量用 `xa82load 25 1100 760 16 -b`（无人值守，替代人工拖动）。

## 2. 测量（按序，每项 5 分钟）

### 2.1 GPU 频率与占用（三个来源，能拿到哪个用哪个）

```bash
# ① macOS 自带（Intel iGPU 可能不支持，明确记"不支持"也是结论）
sudo powermetrics --samplers gpu_power -i 1000 -n 3
# ② 他们的 core 里有 debug.xegfx_gt_act（我们的树没有）——从他们的 0020/0022 补丁里 grep
grep -n "xegfx_gt" ~/src/ArrowWhatever/patches/*.patch | head
# ③ 若 ① ② 都没有：从 accel 里加一个只读 sysctl，读 GT 频率寄存器
#    地址从 i915 源码取（~/src/xe-src/drm-kmod：grep -rn "RPSTAT\|rps" drivers/gpu/drm/i915/gt/intel_gt_pm_debugfs.c）
```

**记录**：拖 `xa82load` 时与空闲时的 GPU 频率（MHz）、GPU busy 百分比。

### 2.2 帧时间是否被 vblank 量化

```bash
# iop_tl 已有逐帧时间戳；算相邻两帧 enter 的间隔分布
sudo sysctl -n debug.xegfxaccel_iop_tl > ~/xegfx-log/A-82b/tl.txt
# 统计：间隔值落在 8.33ms 的整数倍附近的占比（4×8.33=33.3 / 5×8.33=41.7 / 6×8.33=50）
```

**判读**：若绝大多数帧间隔紧贴 33.3 或 41.7 → **被 vblank 量化**（每帧占 4–5 个刷新周期），
那么减少任一环节 1ms 都可能整档跳（33.3→25→16.7）；若分布连续 → 不是量化问题，是纯 CPU 时间。

### 2.3 那 12ms 在等什么（复用已归档样本 + 补一个新样本）

```bash
# 用 sample 抓 12 秒，parse_all.py 三分类
sudo sample WindowServer 12 -file ~/xegfx-log/A-82b/sample.txt
python3 ~/xegfx-log/A-82/tools/parse_all.py ~/xegfx-log/A-82b/sample.txt
# 关键：idle 部分（runloop/mach_msg）细分到调用者——是等 displaylink？等 surface 空闲？等定时器？
```

## 3. 两个实验（各 10 分钟，都是"加负载看反应"）

### 实验 1 · GPU 提频测试（回答"是不是低频锁死"）

```bash
# 背景跑两个额外的 xa82load（不同窗口位置），同时测正主的 fps 与 mark 段
~/xegfx-log/A-82/tools/xa82load 30 800 600 8 &   # 背景 1
~/xegfx-log/A-82/tools/xa82load 30 700 500 8 &   # 背景 2
~/xegfx-log/A-74/fps-probe2.sh 25                 # 正主
```

**判读**：
- 若 **fps 不降反升、或 mark 段变短** → GPU 原来在低频晃，被背景负载拉上去了 ⇒ **提频是最大一笔**；
- 若 fps 明显下降、mark 段变长 → GPU 已是有效工作点，不是时钟问题。

### 实验 2 · CPU 加热测试（回答"CPU 还有多少余量"）

> **核数已核实（17:26 实测）**：`hw.ncpu=16`、`physicalcpu=16`、`logicalcpu=16`，
> **`perflevel0.physicalcpu=16`、没有 perflevel1/2** —— 255H 硬件是 6P+8E+2LPE，
> 但 **macOS 把它报成一个性能等级的 16 个同质核**，XNU 调度器不区分大小核。
> 所以加热测试要**打满 16 核**（不是 8），并且顺手查 WS 主线程实际在哪个核上跑。

```bash
N=$(sysctl -n hw.ncpu)                 # 16
for i in $(seq 1 $((N-1))); do yes > /dev/null & done   # 留 1 核给 WS，满其余 15 核
~/xegfx-log/A-74/fps-probe2.sh 25
killall yes
```

**顺带探测（重要）**：WS 主线程跑在哪些核上——若落在高编号核（LPE/小核），26.2ms busy 就是被小核放大的：

```bash
PID=$(pgrep -x WindowServer)
sudo dtrace -n "profile-997 /pid==$PID/ { @cpu[cpu] = count(); }" -c "sleep 10" 2>&1 | head -30
# dtrace 被 SIP 拦就改用：sudo powermetrics --samplers cpu_power -i 1000 -n 5（看核活跃分布）
```

**判读**：fps 掉多少 = CPU 余量。掉 <10% ⇒ CPU 不是瓶颈（印证"单线程串行"判断）；
若 dtrace 显示 WS 集中在少数核、且这些核是低编号/高编号一端 → 记下核号，A-83 里可用线程绑核验证。

## 4. 若确认低频，尝试提频（有条件才做，单独一步）

按 XeGfx 的机制（README：`debug.xegfx_env` 设置下一阶段的 LKPI tunables，例
`compat.linuxkpi.i915_enable_guc=3`），可尝试的候选（**一个一个试，每次记 fps**）：

```
compat.linuxkpi.i915_enable_rc6=0      # 不让 GPU 进低功耗态（最可能有效）
compat.linuxkpi.i915_enable_fbc=0/1
compat.linuxkpi.i915_enable_psr=0
```

先 `sysctl -w debug.xegfx_env="…"` 设置 → 重启 → 测 fps 与频率。**不设 EFI boot-args**（可回滚）。
若某项让画面异常，立即清掉重启。
