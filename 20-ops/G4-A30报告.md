## 3. `-19` 到底是什么（代码级）

```c
/* xg_kext.cpp:1156 */
rc = xg_display_check();
if (rc == 1 && !xg_drm_attached())
        rc = -19;   /* the init routines ran but no drm driver bound the GPU */
```

```c
/* xg_pci.c:3243 */
int xg_drm_attached(void) {
        TAILQ_FOREACH(d, &xg_pci_devices, devlink)
                if (d->state == DS_ATTACHED && d->driver != NULL &&
                    (strcmp(d->driver->name, "drmn") == 0 || strncmp(..., "i915", 4) == 0 ||
                     strncmp(..., "xe", 2) == 0))
                        return (1);
        return (0);
}
```

**矛盾就在这里**：同一次 stage 4，报错前 100 ms 的 newbus dump 是 `drmn0 state 30 driver drmn`
（30 = `DS_ATTACHED`，名字 "drmn" 命中 `strcmp`），而 `xg_drm_attached()` 仍返回 0。

- 不是源码/二进制不同步：`XeGfx.kext/Contents/MacOS/XeGfx` 建于 18:46，`xg_kext.cpp` 改于 18:29，
  `xg_pci.c` 更早（10-29 04:20），加载的就是当前这棵树。
- 不是时序竞争：boot 线程在 drm attach（31.173）之后 1.8 s 再跑一次 stage 4，仍然 `-19`。
- `xg_display_check()` 返回 1 而非 `-70/-71`：104 ms 与它内部的 `IOSleep(100)` 吻合，说明走的是
  正常分支（`skipped-pipe-a-off` 或帧计数在动），**面板这一层当时是好的**。
- 代码注释里早有先例：`xg_pci.c:3240` 写着 "N-225 was a false -19"。

**结论：门 1 卡在 `xg_drm_attached()` 的判定上，与加速器、AGDC、present 全都没有关系。**
要定位得给这个函数加一个诊断（把 `xg_pci_devices` 里每个条目的 state/driver 打出来），
但那是代码改动，**按本关"零代码改动"的纪律，没有做**。

## 5. 彩噪：处置与时序，以及一个不能下的结论

处置（20:56，§7 停机条件 1，全程未等 watchdog）：

```bash
sudo sysctl -n debug.xegfx_stage > $L/stage.txt
sudo log show --last 6m --predicate 'eventMessage CONTAINS "XEGFX" OR process == "WindowServer"' > $L/log-final.txt
sudo nvram xegfx-disp-phase=%00 xegfx-disp-trial=%00 xegfx-disp-expose=%00 xegfx-disp-fail=%01
sudo rm -f /var/db/xegfx/armed
sudo shutdown -r now
```

时序（全部有原文，但**因果未证**）：

1. display kext 在 31.096 被 IOKit 按需加载 —— 它在 31.097 就 `provider has no fb-index` 退出，
   `return false`，**没注册 IOFramebuffer、没写显示寄存器**（`XeGfxDisplay.cpp:2717`）→ 不是它。
2. i915 在 **1.8 s 内跑了两次** `sysinit_set`（31.173、32.961），`Initialized i915 1.6.0` 打出一次，
   GT/GuC 初始化（`mtl_guc_70.bin`、SLPC、RC）在 31.091–31.166。**这是本次唯一的异常**（A-29 只跑一次）。
3. 彩噪在 20:56:06 被用户看到，即最后一次 stage 4 之后约 2.5 分钟。

**能说的**：本次与 A-29 的差别只有"stage 4 被并发跑了两遍 / i915 双次 init"；
**不能说的**：彩噪就是双次 init 造成的 —— 这需要用单路径复跑一次才能证伪，本关不做（见 §7）。

面板在 20:55:31.09 那一刻是好的（`xg_display_check` 没返回 `-70/-71`，且 104 ms ≈ `IOSleep(100)`）。

## 7. A-31 的开口（不改代码，按证据排序）

1. **清掉 `xegfx-disp-bootarm`，只留一条入口**：`sudo nvram -d xegfx-disp-bootarm`，然后只用
   提示词 §2.2 的手工 `sysctl debug.xegfx_stage=7`。这样 stages 只跑一遍，与 A-29 通过时的
   "单次 `ran 58 sysinit_set entries`" 对齐。
2. **给 `xg_drm_attached()` 加一行诊断**（下一次允许改代码时）：把 `xg_pci_devices` 中每条
   的 `name/state/driver_name` 打进 `IOLog`。当前证据只能证明"dump 说 attached、函数说没有"，
   不能说出为什么 —— 这是必须补的一块，否则门 1 永远过不去，后面 §2.3 的加速器也永远测不到。
3. **彩噪归因实验**：单路径复跑一次阶段 1..4（不 arm、不写 nvram 门），看是否仍出现彩噪。
   若不出现，则本次彩噪 = 双次 i915 init；若出现，说明 core 的 stage 3/4 本身会扰动面板，
   那才是 A-29 一直没查到的更上游原因。

**本报告不提任何"改法结论"**，上面三条都是"下一次怎么把证据补齐"。
