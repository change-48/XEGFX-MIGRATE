## 2. A-19c-1：固化（成功，无副作用）

新增三段（`latch` 之前）：

```bash
MAP_OUT=$("$CTL" mapfast 0xFD000 6656 0x800000 2>&1)
case "$MAP_OUT" in
    *"bad 0"*) log "mapfast ok（bad 0）" ;;
    *) log "mapfast FAILED（bad != 0 或未出结果），保留原 SURF 不动"
       "$CTL" latch >> "$LOG" 2>&1 ; exit 0 ;;   # 仍按旧入口锁存，屏幕不至于没几何
esac
"$CTL" reg surf 0xFD000000
"$CTL" latch
```

**与提示词的一处有意识偏差**：`bad != 0` 时我没有直接 `exit`，而是先按**旧入口** `latch` 再退出。
理由是此时 `regset` 已把几何写成 3120，若直接退出会留下"几何已改但未锁存"的半态；先 latch 才是真正的"保持现状"。

两次开机实测：

```
[2026-10-31 16:00:06] 完成   ← 第一次（重启后 ~32 s）
[2026-10-31 16:11:57] 完成   ← 第二次（重启后 ~90 s，system_profiler 起得慢）
SURF 0xfd000000 / SURFLIVE 0xfd000000 / STRIDE 195 / SIZE 0x081f0c2f / PIPESRC 0x0c2f081f
dump 0xfe8000 = 0x00800003 ; dump 0xff4ff8 = 0x021ff003
```

**关键额外事实**：`kmutil load` 加速器之后 `SURF` 仍是 `0xfd000000`，**accel 没有把它改回去**。
→ 搬迁与加速器加载顺序无关，固化是稳的。

> ⚠️ 提示词 §2.3 与验收锚点 3 的 `dump 0x800000 2` **地址是错的**：PTE 索引 `i` 在 BAR0 的 `0x800000 + i*8`，
> `idx 0xFD000` 的偏移是 `0x800000 + 0x7E8000 = 0xFE8000`。按提示词跑 `dump 0x800000` 读到的是 `0xdc1f765b / 0xf4fba612`（idx 0 的垃圾），**会被误判成 PTE 被抢**。A-19a 报告 §3.2 里写的是对的。

### 3.2 为什么 A-19a 的 375 与本轮 133 差这么多

不是矛盾，是**开机时长问题**：A-19a 那次测于开机数十分钟、桌面上开着窗口/动效的状态；本轮测于开机 3 分钟、桌面全静止。
**这说明 `powermetrics` 单点读数在不同会话状态下能差 2–3 倍**——所以 §3.4 的"B < 250 ms/s"这个绝对阈值本身不可靠，只有同机会话内的 A/B 差值有意义。本轮 A=133.6 已经低于 250，若只看绝对阈值会把软件合成误判成"已硬件化"。

```
B3 sample(pid 2597)：命中 304 行   （CA::OGL::SW::Poly 458 次、::scanline 59、::Blend 48）
```

**WindowServer 崩溃报告（决定性证据）**：


→ **WindowServer 用的是 `CompositorSW`（软件合成器），NVMTL 只是被映射进来；一旦真走到用它的路径就 SIGABRT。**
重启后 WS 会因为 `throttleTimeout` 再拉起来（runs=4），所以是"崩一次、活下来、继续软件合成"。

### 3.4 我自己踩的一个坑（必须记下来，主 agent 复核时别再踩）

第一次 `vmmap "$(pgrep -x WindowServer)" | grep -ci nvmtl` 得到 **0**，我据此判断"WindowServer 没挂 NVMTL"。
**这是错的**：`vmmap` 不带 `sudo` 对 root 进程会静默失败（stderr 被我 `2>/dev/null` 吃掉），返回空 → grep 计数 0。
加 `sudo` 后同一进程立刻是 **21**（`lsof -p <ws> | grep -c nvmtl` = 5 也印证）。

> 顺带说明 A-19a 的 `18` 是**同一个测法的正确结果**，其证据文件 `A-19a/vmmap.txt` 只有一行 `18`、没有原始输出，无法复查——建议以后 vmmap 一律落原始输出。

## 6. 给主 agent 的三条判断

1. **搬迁固化这条可以结案**：C1-1/2/3 两次开机通过，accel 加载后 SURF 不回退。A-19a 的"零重编解决花屏"是真的。
2. **Gate 4 第 3 条不成立，而且原因不是"读数误读"，是结构性的**：WindowServer 的合成器是 `CompositorSW`，
   `MetalPluginName → NVMTLDriver` 只让 `system_profiler` 报出 `Metal: Supported`，**没有让 WindowServer 走 Metal 合成**；
   强行让它用（重启 WS 让它重新枚举）会 **SIGABRT 崩一次**，崩完仍然是软件合成、CPU 更高。
3. **下一步不该再调 CPU 阈值**，应该查"为什么 `CompositorSW` 选了软件路径"：
   最可能的两个方向——(a) `NMXAccel` 没有和驱动显示器的 `IOFramebuffer`（`IGPUConsoleRange`）关联，WS 拿不到"显示加速器"；
   (b) NVMTL 的 device 缺 WS 合成必需的 feature（崩溃线程在 `CompositeLayersToDestination`）。
   在查清之前，任何"A≈B 所以没成功/成功了"的判读都会继续打转。
