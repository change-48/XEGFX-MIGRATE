## 4. 这一关真正学到了什么

1. **`-19` 只是并发症状，不是判定逻辑有 bug。** 同机同树，两次 boot 只差"是否手工写 `debug.xegfx_stage`"：
   A-30 双跑 → `-19`；A-31 单跑 → stage 4 `rc=1 in 231 ms`。`xg_drm_attached()` 不需要打补丁。
2. **A-29 的 `open()` 拒绝已经被越过。** `present-failed`（`kIOReturnNotReady`）不再出现，
   `head 4` 确实开始扫描我们的 buffer，`adapter register writes = 0`（没碰硬件寄存器）。
3. **新的阻塞点上移到了 SkyLight/IOKit 初始化。** 三处可疑信号同时出现，且都与"呈现"无关：
   - `transient surface … not found`（QuartzCore OGL 上下文丢面）13 次；
   - WS 每次都重新走一遍 `NVMTL`（Vulkan-on-Metal）着色器特化，10 s 内 4 次 pipeline，
     说明 **WS 拿到的是 NVMTL 而不是我们的 `NMXAccel`** —— 而 display 侧日志明确写了
     `accel service NMXAccel found (XeGfxAccelPresent=true)`。两者口径不一致，这是下一关最该先分清的一条；
   - 主线程停在 `kernel + 317728` 的同步调用上（符 `IOKitWaitQuiet` 语义）。

## 6. 下一关（A-32）该先查什么（按证据强度排序）

1. **WS 到底用了哪个加速器**：对比 `NMXAccel` 的 `IOAccelerator` 发布属性与 WS 侧 `MTLDevice` 选择日志。
   若 WS 走 NVMTL，则 `first present accepted` 只是"面交上去了"，合成仍走软/图元层，`transient surface`
   与 hang 都可能由此而来。**这是零代码可查的**（ioreg + `MTL_DEBUG`/`NVMTL` 日志）。
2. **`kernel + 317728` 符号化**：在 panic/spin 对应的 kernel 上 `atos`/`nm` 定位，确认是哪一个
   `IOConnectCallMethod`（`IOKitWaitQuiet` 本身还是我们的 user client）。
3. **`transient surface not found` 的时序对齐**：13 次是否都发生在一次 flip 之后（`head 4` 换面），
   即我们的 `swapComplete`/`setGamma` 是否把面归还错了。
4. 复活窗口：`S3 watchdog armed for 120 s` 与 `open() RELEASED` 都在 21:03:33 完成，
   说明 120 s 预算没有超；下一次可保持同样顺序，**只是别让 WS 反复重启**（一旦发现第 2 个 WS 实例就停机取证，
   不要等到 watchdog panic）。
