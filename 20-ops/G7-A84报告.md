## 2. P3 · GPU 频率读数：第一次看见利用率 ✅

### 2.1 做法（照 i915 原文，不猜地址）

```c
// BAR0 已映射 16 MB（ioreg: IODeviceMemory length=16777216），0xc60 远在 0x71000 窗口之内，不需要扩映射。
#define NV_MMIO_MTL_MIRROR_TARGET_WP1 0xc60u   // intel_gt_regs.h:25  MTL_MIRROR_TARGET_WP1
#define NV_MTL_CAGF_MASK              0x1ffu   // intel_gt_regs.h:26  MTL_CAGF_MASK = GENMASK(8,0)
cagf = gDispMmio[0xc60/4] & 0x1ff;             // intel_rps.c:2114（IP 12.70+ 走 MTL 分支）
mhz  = (cagf * 50 + 1) / 3;                    // intel_gpu_freq: DIV_ROUND_CLOSEST(val*50, GEN9_FREQ_SCALER=3)
```

- **不需要 forcewake**：`intel_rps.c` 的 `__read_cagf()` 注释原文 —— *"For Gen12+ reading freq from HW does not need a forcewake and registers will return 0 freq when GT is in RC6"*。这是本关能安全落地的前提（A-82b §2.1 当时判断"要扩 BAR0 + forcewake，为一个已知答案的次要指标重启不划算"，实际两点都不成立）。
- 平台核对：`ioreg` `model = "Intel Arrow Lake Xe-LPG+"`，i915 用 `mtl_info`（`i915_pci.c:870 INTEL_ARL_IDS(..., &mtl_info)`）→ 走 `IP_VER >= 12.70` 的 MTL 分支，寄存器是 `0xc60`，**不是** `GEN12_RPSTAT1(0x1381b4)`。
- sysctl：`debug.xegfxaccel_gt_mhz`（`SYSCTL_PROC` + `CTLTYPE_INT`，**按需读**，因为"空闲"根本没有帧可采样）。附三个计数：`gt_mhz_last` / `gt_mhz_max` / `gt_reads` / `gt_sleep`。

### 2.2 频率表（40 个样本/格，0.5 s 一次）

| 配置 | 非零中位 | max | 样本为 0 的比例 | 判读 |
| --- | --- | --- | --- | --- |
| 空闲（无负载） | — | — | **100%**（连读 6 次全 0） | GT 在 RC6 睡着，读数有效 |
| flip=1 拖动 1100×760 玻璃 | **1625 MHz** | **2150 MHz** | 20/40 | GPU 真的在干活 |
| flip=0 拖动（同负载） | **800 MHz**（全部非零样本都是 800） | 800 | 23/40 | 只有 RPn 地板，活全在 CPU 拷贝上 |

> **这就是"利用率"的直接证据**：同一条拖动负载，拷贝路径让 GPU 停在 800 MHz、CPU 搬 26 MB；
> 翻转路径把 GPU 拉到 1.6–2.15 GHz。**GPU 从"没事干"变成"在干活"，且帧率同时 +11%。**

`gt_mhz_max=2150` 说明这块 255H 的 GT 上限约 2.15 GHz（额定 RP0 档），拖动时能打到顶 —— GPU 侧确实没余量问题。

## 3. P2 · E2 提前信号：判据取证 → 结构性不可用 ❌

### 3.1 先说清楚 0024 的真实判据（不是"8 帧集合 ≥3"）

提示词 §3.2 写的是「最近 N 帧的 sid 集合大小 ≥3」，但 **0024 原文**（`ref/0024-…patch` 第 250–262 行）是另一回事：

> *"the early signal is used only after **NV_XE_EARLY_RUN (32) frames in a row** came in on a surface that was neither the front nor the one before it, and a frame that arrives on the surface that was the front during an early-signalled arm counts a **hazard** and ends the run."*
> *"**Off by default: WindowServer alternates two surfaces here, so the early signal hardly ever applied and the frames it did apply to counted hazards** (§32.7/§32.11)."*

即：①要**连续 32 帧**都在"既不是 front、也不是前一个 front"的面上；②一旦某帧落在上一轮早通知时正在扫的面上，记 hazard 并终止；③**他们自己在本栈试过，默认关，结论是"几乎从不生效，生效的那几帧还都是 hazard"**。

### 3.2 本关做法：只加判据统计，不动帧路径

在 `nvAccelXeFlipDeferRun()` 里加 8 行计数（`iop_xe_early_frames / _third / _run_max / _ready`），行为零改动。为什么不直接实现：判据若不成立，改 `isTransactionComplete` 的记账就是纯风险（记错一次 = WS 卡死看门狗，A-79 修的就是这个）。

### 3.3 判据实测（本关最硬的一组数）

| 场景 | 帧数 | 落在"第三块面"上 | `run_max` | `ready`（达到 32 连） |
| --- | --- | --- | --- | --- |
| 稳态拖动 1100×760 玻璃 | 728 | **322（44%）** | 49（见下注） | **0** |
| 开机 / 桌面启动阶段 | 118 | 106（90%） | **49** | **18** |
| 自开机累计（19:14） | 8278 | 1941（23%） | 49 | 38 |

> `run_max=49` 是**开机那一段**（WS 启动时短暂用三缓冲）留下的历史最大值，不是拖动段的；拖动段 `ready` 增量为 **0**。

**`iop_tl` 的 sid 序列（拖动段，199 帧）**：

```
sid 去重 = 3  -> {4: 89, 6: 81, 23: 29}
序列: 6x1 4x1 6x1 4x1 6x1 4x1 ... 23x1 4x1 6x1 4x1 ... 6x1 23x1 4x1 ...
8 帧滑窗 sid 去重数分布 = {2: 37, 3: 155}      ← 78% 的窗口里确实同时有 3 块面
```

读法：**池子里有 3 块面（4/6/23），WS 也确实会用第三块，但每次只插一帧就回到 4/6 交替** ——
所以"连续 32 帧第三面"在稳态下永远达不到，`ready=0`。

### 3.4 就算能用，也跨不过那一拍

| 项 | 数值 | 说明 |
| --- | --- | --- |
| `arm->latch` p50 / p90 | **4.53 ms / 8.21 ms** | 这是 E2 唯一能省掉的那段（早通知后 WS 不必等翻页） |
| 当前帧间隔 p50 | 25.20 ms（3 拍 = 25.00 ms） | 93% 紧贴 vblank 整数倍 |
| 省掉 latch 后 | 25.20 − 4.53 ≈ **20.7 ms** | 仍 > 2 拍（16.68 ms）→ **被量化吸回 25 ms，fps 不变** |
| 到 60 fps 还差 | **8.5 ms** | latch 只占其中一半 |

**⇒ E2 的结论：在本栈稳态拖动下结构性不可用（判据永不满足），而且即使强开也不足以跨档。** 这同时解释了 0024 为什么默认关。

> 若要继续追 60 fps，靶子不在 latch，而在 `performTransaction` 之外那 21 ms（A-82b §3.3）：NVMTL 的三把锁 +
> `CA::Render::Fence::resolve_batches`。这属于 A-83 换血/插件侧，不是本关的筹码。

## 4. P4 · 两个便宜候选：都没做，理由

1. **`idle_ms=15`** — 没有靶子：`wait_idle=0` 时整条 idle 等待被跳过（`nvAccelXeFlipArm` 里 `if (waitIdle)` 不成立），`wait_idle=1` 时走的是 surface mark（`markonly_flips=5047`，`mark_timeouts` 只有 4），`idle_ms` 只在"GT 整体空闲轮询"那一档才用得上。**没有负载落在这一档，调它不会有任何变化。**
2. **`report_busy=0`** — 风险高且无收益：`isTransactionComplete` 恒真 = WS 永不等翻页，等于把 §5 那个残影放大成常态撕裂。**不做。**

## 5. 画面判据

### 5.1 残影（使用者目视，本关唯一未收口的瑕疵）

使用者报告：**"窗口移动有残影，但是再次窗口移动到那个位置就没有残影了"** —— 拖到新位置时该位置残留上一帧的内容，再拖一次就正确。

处置与取证：
- **不是翻转失败**：`flip_fail=0 / latch_timeouts=0 / parked=0 / retries=0 / defer_copied=0`，8278 帧 100% 走 GGTT 翻转，没有一帧回退拷贝。
- **与 marks 通道有关**：`surface_marks_dump` 里 `last_mark_age_ns` 多次读到 **5 s 级**（mark 通道间歇性停摆），
  此时 arm 会从"等本帧的 mark"回落到"等整个 GT 空闲"，**就失去了"这块面确实装着本帧内容"的证据** —— 与残影形态吻合。
- **归因对照（决定性）**：切到 `flip=0 defer=0`（拷贝路径，A-74 时代的老行为）跑**同一款 45 s 拖动**，
  使用者目视：**拷贝路径下也有同样的残影**。
  ⇒ **残影与本关的 flip 转正无关**，是合成/marks 通道的旧症（`surface_gpu_timeouts=134`、`last_mark_age_ns` 秒级），
  拷贝路径同样要吃这套握手。本关不引入、也不修复它；留给 A-85（靶子：marks 通道为什么间歇停摆）。

### 5.2 休眠唤醒：**整机休眠在本栈根本不可触发**（不是 A-84 引入）

两次尝试都失败，原因在电源策略与一个 display preventer 上，与翻转无关：

| 尝试 | 结果 | 证据 |
| --- | --- | --- |
| `sudo pmset sleepnow`（19:11:03） | 只走 darkwake，**没有 Sleep/Wake 转换** | `pmset -g log` 只有 `darkwakelinger`；`Sleep/Wakes since boot … :0` |
| **合盖**（使用者实测 19:16） | 同样**没有睡眠** | AppleACPILid tickle 有记录（盖子事件到了）；`Sleep/Wakes since boot: 0`；`System sleep preventers: .Display_boot`、`Idle sleep preventers: IODisplayWrangler`、`pmset -g` 里 `sleep 0 / displaysleep 0` |

> 也就是说这台机器现在**关盖也不睡**（`sleep 0` + `.Display_boot` 常驻 preventer）。这是既有状态，不是本关改出来的
> ——本关只动了 accel 的 bootArm 默认值与 bringup 的两行判定。**"合盖唤醒一次仍自愈"这一门无法在此状态下执行**，
> 报告里明确标为未测，改用下一节的显示器关/开做代偿。

## 8. 给下一关（A-85）的三句话

1. **P1 已落袋**：flip=1/defer=1 是开机默认，8278 帧零失败、零回退，`iop_ok` 恒 0 是正常现象（别用 iop_ok 判定死活，看 `iop_xe_flips`）。
2. **P3 已可用**：`sudo sysctl -n debug.xegfxaccel_gt_mhz` 就是 GPU 实时频率（0 = GT 在 RC6），从此每档都能报"利用率"。
