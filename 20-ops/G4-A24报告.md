## 2. 关键发现（比"插件装回去"更重要）

### 2.1 `XeGfx` core 与 `XeGfxAccel` **不随开机自动加载**

重启后 17:33 首查：`kmutil showloaded` 只有 `XeGfxIntelFB` / `NMIntelFB` / `XeNative`，
**core 与 accel 都不在**；`ioreg -c IOAccelerator` 为空；GPUWrangler 日志 `accel 0x000000000`；
`iconservicesagent` 报 `No accelerated OpenGL renderer available`。

那一刻 `mtlprobe` 就是 **count = 0**——但此时插件文件已经装好并签好了。
**所以 A-23a 的 `vmmap = 0` 是"没有加速器"，而不是"插件缺位"；本关如果只做装插件+重启，仍然会是 0。**

本次是靠手动三步才把服务拉起来：

```
sudo kmutil load -b org.watchthelight.XeGfx          # core，rc=0
sudo kmutil load -b org.watchthelight.XeGfxAccel     # accel，先"will match"但无实例
sudo sysctl -w debug.xegfx_stage=7                   # core 在 IOPCIDevice 上打 nmxgpu-claimed=Yes
                                                     # → accel 的 IOPropertyMatch 才满足 → NMXAccel 实例出现
```

`NMXAccel` 实例属性与提示词一致：
`MetalPluginName = ../../../Library/GPUBundles/NVMTLDriver`、`MetalPluginClassName = NVMTLDevice`。

accel 自己的日志也写明这是**单次开机**语义：
`debug.xegfxaccelfb now reads 1 -- armed-only Metal clients may have a device THIS BOOT ONLY`。

> **推论**：`vmmap nvmtl > 0` 目前**不可跨重启复现**。要么加一条 LaunchDaemon 做 core+accel 的加载与 stage 推进，
> 要么接受"每次开机手工三步"。这件事必须在 Gate 4 收尾前定掉，否则下一次开机又会回到 `vmmap = 0`。

### 2.2 插件层本身是健康的，且 WindowServer 会在运行时懒加载

- `mtlprobe`（自有进程、与 WS 无关）在 accel 起来后立刻 **count=1 / 16/16**，说明 bundle、`nvmtl/*`、
  平台位、`MetalPluginName` 路径全链路正确。
- WS **没有重启**（PID 204 从头到尾不变）。它在 17:36:48 运行时把插件装了进来：
  ```
  WindowServer: (NVMTLDriver) NVMTL: vk: UP in this Metal process —
                "Intel(R) Graphics (ARL)" api 1.4.363, queue family 0
  WindowServer: (NVMTLDriver) NVMTL: maxBufferLength -> 4095 MB ...
  ```
  也就是说 **"先起 WS 再起 accel"是可接受的**，不需要为此重启 WS。

### 2.3 `codesign -v` 报 "sealed resource" 不是本关引入的

`codesign -v /Library/GPUBundles/NVMTLDriver.bundle` → `a sealed resource is missing or invalid`。
但**备份原件（rollback-backup-20261031-162412）报一模一样的错**，且恢复出的二进制与备份
md5 完全一致（`1cc351bd934e3a4de83083ae873ac7ac`）。`CodeDirectory … Sealed Resources version=2 rules=13 files=0`。
→ 这是这个 ad-hoc 签名产物的固有状态，不是拷贝/权限损坏，也不影响 dlopen（实测 16/16 已证）。

### 2.4 顺手补上的东西

`metal-fix.sh` 本次除了回填已知的两个平台位，还**首次**给 7 个曾漏掉的库补了 `CS_PLATFORM_BINARY`：
`libSPIRV-Tools{,-diff,-link,-lint,-opt,-reduce,-shared}.dylib` 由 `flags=0x2` → `0x4000002`。
不补的话，SPIR-V 编译路径在 WS 里会因为"非平台二进制"被 dyld 拒。
