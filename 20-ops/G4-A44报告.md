## 4. 四次"提示词被现场推翻"的地方（这是本关真正的收获）

提示词给的是模板，下面四条是实测**与模板不一致**、已在脚本里改掉并留注释的：

| # | 提示词的写法 | 实测 | 证据 / 处理 |
| --- | --- | --- | --- |
| 1 | `console user ≠ root` 就算登录了 | **登录窗口期 `/dev/console` 属主是 `_windowserver`**，不是 root → v1/v2 在登录窗口就把 stage7 推了（A-25b 的雷区） | 09:22:02 `console user=_windowserver after 9s` → 已改为 `uid ≥ 500` 且排除 `_windowserver/_mbsetupuser/loginwindow`，并额外等 `launchctl print gui/<uid>` 存在 |
| 2 | `kmutil showloaded \| grep org.watchthelight.XeGfx` 判 core 是否加载 | **该前缀同时匹配 `XeGfxIntelFB` / `XeGfxAGDC` / `XeGfxDisplay`**（这三个开机自加载）→ 误判"core already loaded"，`debug.xegfx_stage` 实际不存在 | 09:22:28 假 `core already loaded` + 09:22 `sysctl: unknown oid 'debug.xegfx_stage'` → 改为精确匹配 `org\.watchthelight\.XeGfx (`，并以 `debug.xegfx_stage` 出现为成功判据 |
| 3 | §2 "重复 `accelfb=3`/`iop=1` 是幂等的，不会坏" | **不幂等**：第二次写 `accelfb=3` 会再走一次 `re-delivering the mode change`，`iop_ok` 当场停摆 **1–2 分钟**（然后自行恢复） | 09:12:09 二次写入 → `iop_ok` 4007 冻到 09:14 前后才恢复；09:15 再复现一次。另外 `sysctl -w debug.xegfxaccel_iop=0` 直接 `Operation not permitted`（一次性闩锁）→ 已加守卫：`iop==1` 就跳过 6/7 两步 |
| 4 | §0.1 "`pipe ENABLED` 之后**不需要**重启 WS" | **冷启动必须重启一次 WS**。开机时 WS 早于 pipe 存在，握着的是过期的 display 注册，`iop_ok` **120 秒纹丝不动为 0**；`launchctl kickstart -k system/com.apple.WindowServer` 之后 `0 → 169` 秒涨 | 09:26:54 `iop_ok 0 -> 0`（120 s）→ 手动 kickstart 后 `1→9→167`；A-43 当时"不用重启"是因为那台 WS 早已在开闸后重启过 |

补充一条执行事故（**未造成损坏**）：v3 里我把日志函数写成 `LOG=/usr/bin/log`，把日志追加到了那个二进制上。
实测 `/usr/bin/log` **仍是 809648 B、mtime 6月25日、可正常执行**——因为 SIP 签封卷只读，追加被 `Read-only file system` 拒绝。
v4 起改名为 `LOGF`，并全部用绝对路径 `/usr/bin/log`，避免与同名 shell 函数冲突。

## 5. 遗留风险（下一关要盯的）

1. **`09:33:20` 有一份 `WindowServer-2026-11-01-093320.ips`（bug_type 409 = stackshot/挂起）**：那是脚本 `kickstart` 出来的 WS（pid 1549）在重新注册时被看门狗收走的一次，随即 launchd 拉起 pid 1704，帧流才通。
   之后到 09:35 只有这 **1** 份，WS 稳定在跑。即"自动重启 WS"这一次里，**大约一半概率要先挂一次再被拉起**——不影响最终出画面，但会多花 ~30 秒。
2. `screencapture` 在 SSH 下依旧不可用（`could not create image from display`），判据只能靠目视。
3. 开机后第 1 分钟内，`system_profiler` 的 `Displays:` 子段是**间歇性缺失**的（09:26 与 09:34 两次读法不同），`ioreg -c IODisplayConnect` 稳定为 1。
