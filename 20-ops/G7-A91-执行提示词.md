# Gate 7 · A-91 执行提示词：App 拿不到 GPU（B0）——先判别是不是沙盒，再吃掉那 2 秒

> A-90 的 B 管把靶子换对了：**每次启动花 2.083 s 带起 ANV、枚举到 0 个物理设备、放弃 GPU 回落 CPU**。
> 也就是说除 WindowServer 外，**所有 App 都在 CPU 上渲染**。
>
> 本关两件事，按序：
> **P0（判别）**：0 个设备是**沙盒**造成的，还是 accel/libdrm 路径本身的问题？
> **P1（保底收益）**：不论结论如何，**先把那 2.08 s 吃掉**（每次启动都付，用户天天感受）。
>
> 必读：`G7-A90报告.md` §3.3（日志原文）、`G7-A89报告.md`（测量纪律）。

---

## 0. 已知（照抄，别重测）

```
2.083 s 花在：NVMTL initWithAcceleratorPort → dlopen(libvulkan_intel.dylib) → vkCreateInstance
              → vkEnumeratePhysicalDevices 返回 VK_SUCCESS(count 0) → 放弃
日志原文：vk: zero physical devices through this ICD — vkEnumeratePhysicalDevices -> VkResult 0, count 0
         NVK did not come up in this process - refusing to be the Metal device for Calculator
插件是支持 App 进程的：nvmtl_vk.c:251 专门处理"Chrome GPU 进程读不到 sysctl hw.memsize"的沙盒问题
但 nvmtl_vk.c:930 的日志预留了"sandboxed apps may have no device"这一情形
accel 的进程名过滤只有 marks 那几处（selector 1/2/5–8 限 WindowServer），**通用 DRM 路径没有进程过滤**
```

## 2. P0 · 判别：是不是沙盒（30–45 分钟）

### 2.1 造一个"最小 Vulkan 枚举器"

写 `work/a91/venum.c`（~60 行）：`dlopen("/Library/GPUBundles/nvmtl/libvulkan_intel.dylib")`
→ `vkCreateInstance` → `vkEnumeratePhysicalDevices` → 打印 `VkResult` 与 count，以及每步耗时。
编译：`xcrun clang -o venum venum.c -framework IOKit -framework CoreFoundation`（不链 Vulkan，
全用 dlsym）。**同时打印 `open("/dev/dri/renderD128")` 的 errno、`getprogname()`、uid/euid。**

### 2.2 三个场景对照（这是本关的核心实验）

| 场景 | 怎么跑 | 若成功说明 |
| --- | --- | --- |
| **A. 非沙盒 CLI** | 直接在 Terminal（或 SSH）里跑 `./venum` | 说明沙盒才是墙 |
| **B. 沙盒 App** | 把 `venum` 放进一个带 `com.apple.security.app-sandbox` 的最小 .app 且不申请 GPU entitlement，`open` 启动 | 复现 A-90 的 0 设备 |
| **C. 沙盒 App + GPU entitlement** | 同上但加 `com.apple.security.device.gpu`（若存在该键） | 说明"给 entitlement 就能用" |

另跑一次**对照**：`sudo ./venum`（root 非沙盒）——排除权限位问题。

### 2.3 判定表（先写死，避免事后拟合）

| A | B | 结论 | 下一步 |
| --- | --- | --- | --- |
| 成功 | 失败 | **沙盒**（Apple 的 App 改不了） | 放弃"让沙盒 App 用 GPU"；只做 P1，并写进 README |
| 成功 | 成功 | 沙盒不是主因；A-90 的 Calculator 另有原因（查 allow-list） | 进 P2（查插件 allow-list 与 ANV 路径） |
| 失败 | 失败 | accel/libdrm 路径本身不给非 WS 进程 | 进 P2（重点查自定义 libdrm 的节点匹配与 user client 权限） |

**门 P0**：三场景 ×（成功/失败 + errno + 耗时）表完成，明确落哪一格。

## 3. P1 · 吃掉那 2 秒（无论 P0 结论，必做）

### 3.1 做法（按风险从低到高，选一个）

| 序 | 做法 | 说明 |
| --- | --- | --- |
| **a** | **失败结果缓存**：插件在 ANV 枚举失败后，把「本机 + 本进程 cfg 无设备」写进 `~/Library/Caches/nvmtl/nogpu-<stamp>`（含驱动 sha + 系统版本作 stamp）；下次启动读到就直接跳过 ANV 带起（<10ms） | 最省事；风险：GPU 后来可用了要能失效（stamp 变化即失效） |
| b | **廉价预检**：带起 ANV 前先 `open("/dev/dri/renderD128")` 或探测 accel user client，失败就立刻放弃 | 更"正确"，但可能预检本身就要几百 ms |
| c | 缩短 ANV 的探测超时（若 2 s 来自固定超时） | 需要改 libvulkan_intel 侧，风险高 |

**本关做 a**（必要时叠 b）。

### 3.2 门 P1

| 判据 | 期望 |
| --- | --- |
| 首次启动 | 仍 ~2 s（不可避免） |
| 第二次起 | **≤3.0 s 总耗时**（A-90 基线 4.97/5.19 s → 至少 −2 s） |
| 日志 | 第二次起出现 `nvmtl: skipped ANV bring-up (cached: no device here)` 一行 |
| 失效 | 改 stamp（重装插件/升级系统）后能重新尝试一次 |
| 回归 | 热启动/冷启动各 3 次，文本编辑 + 计算器，中位对比 A-90 基线 |

## 4. P2 · 仅当 P0 判"非沙盒"时才做（时间盒 90 分钟）

重点三处（按嫌疑排序）：

1. **自定义 libdrm 的节点匹配**：`/Library/GPUBundles/nvmtl/libdrm.2.dylib` 里 `strings` 只有 `NMXAccel`
   一个线索；对照上游 README "devfs clone 节点问题 → libdrm 按 slot 匹配节点"，
   看它是否只在特定进程（WS）下才匹配到节点；
2. **accel 的 user client 打开策略**：`IOAccelXeGfxDRMClient::start/open` 是否只允许一个持有者
   （grep `start(` / `initWithTask` / 单例）；
3. **ANV 在非 WS 进程的 ioctl 路径**：`log show --predicate 'process == "Calculator"'` 里是否有
   `execbuffer`/`getparam` 的 EPERM/ENODEV。

**门 P2**：给出"哪一处挡住了 App"的一句话结论 + 改动点与风险评估（**本关不实现**，留给下一关）。
