## 3. 判据第一条：寄存器**完全没被动过**

`regs-diff.txt` 为 0 字节。逐项对照：

| 寄存器 | before | after | 含义 |
|---|---|---|---|
| `0x70180` PLANE_CTL | `0x84000008` | `0x84000008` | 平面格式/使能没变 |
| `0x7019c` SURF | `0xfe600000` | `0xfe600000` | **平面仍指着同一块帧缓冲** |
| `0x701ac` SURFLIVE | `0xfe600000` | `0xfe600000` | 硬件实际在扫的也是同一块 |
| `0x70240` PIPESRC/水位 | `0x80008035` | `0x80008035` | 水位没动 |
| `0x7027c` DDB | `0x07ff0000` | `0x07ff0000` | DDB 没动 |
| `0x68180` PS_CTRL | `0x00000200` | `0x00000200` | 面板时序没动 |

→ **按 §3.3 判据第 1 行：几何/平面没被动 = 内容被写花**。这一条把"accel 去编程 display pipe"整条分支**排除掉了**，
不需要再查 accel 的 display pipe 编程，也**不需要**为此换栈。

## 4. 比 dmesg 更硬的一条：GGTT 页表在 GPU 提交后被改写（本次的核心发现）

§3.3 判据第 3 条要的是"stolen 分配落在 `0x800000..0x1a00000`"。本 build 的 i915 在运行期**不打印** stolen 分配地址
（`dmesg` 与 `log show` 都只有 `boot surface ... reserved: -28`，没有任何 `Got Intel graphics stolen memory base 0x…`），
所以拿不到原始地址。但 `xenative-ctl scan` 直接读硬件页表，给出了**同一件事、更靠下、更难反驳的证据**：

```
            present_entries   live_run_pages   live_phys
加载前(scan 7000)      3518            6656       0x800000
提交后(scan 7000)      4789            1701       0x800000
```

- **`live_run_pages` 6656 → 1701**：从 live 页起那段"物理地址连续递增"的映射**被从中间截断了**，
  连续长度只剩 1701 页（6.65 MB），而原本是 6656 页（26.0 MB，正好覆盖 25958400 字节的帧缓冲）。
- **`present_entries` 3518 → 4789（+1271）**：表里**新增了 1271 条有效映射**——这正是加速器提交时分配缓冲、
  往 GGTT 里写新 PTE 的数量级。
- `live_phys` 仍是 `0x800000`，`live_run_pages` 重启后又回到 6656 ——**说明不是偶发读错，是可重复的改写**。

把三条并起来读：**加速器的分配落在"帧缓冲映射所用的那些 PTE 索引"上，把这些索引改写成了别处的物理页**。
硬件扫描输出时按 PTE 取数据，于是被改写的那一段（约 (6656-1701)/6656 ≈ 74% 的映射跨度）显示的是别处的内存
——表现就是"局部画面被写花"。**这与"上 1/3 横条"在量级上是吻合的**（具体哪一段对应屏幕哪一侧，取决于 PTE 索引
与扫描行的对应关系，本轮不做断言）。

> 注意：这不等于"我们那 6338 条残留 PTE 就是元凶"。残留 PTE 与帧缓冲映射**可能落在同一段被分配器视为空闲的索引区间**里，
> 两者都会导致同一个结果。要区分，需要下一轮把"分配到的 GGTT 索引/物理地址"打出来（见 §6 建议 2）。

## 6. 结论与建议

**一行结论：`A-18a 无效（条纹复现），进 A-18b` ——并且现有证据把矛头指向"加速器分配撞进帧缓冲的 PTE 索引"，而不是寄存器、不是 flip 语义缺失。**

依据 §3 与 §4，`bufferFlipCount=0` 的那个解释（"没有 flip 栈所以花屏"）**不足以解释本次现象**：
寄存器没动、flip 根本没参与，画面就已经被写花了。flip 栈是"能不能呈现/能不能零拷贝"的问题，
**而"地址被改写"是更前面的问题**。所以 A-18b 的顺序建议调整为：

1. **先加 `unmap`（写 0 清 `0x1000..0x28C1`）+ 一条分配地址日志**，再跑同一条观测链（load → stage 7 → mtlprobe → scan）。
   - 若 `live_run_pages` 不再从 6656 掉到 1701 → 元凶是残留 PTE，A-18b 只需这一步就够，不必整栈换。
   - 若仍掉 → 元凶是分配器起点（stolen 起点没跟着 26 MB 帧缓冲走），**修分配起点，而不是换栈**。
   - 关键：`unmap` 清残留前**先看 `scan` 的 live 索引是否落在 `0x1000..0x28C1` 内**；若重叠，清之前先备份表，
     免得一写 0 直接把扫描输出清黑（这本身就是一条判定"残留 PTE 与帧缓冲是否同一段"的零成本实验）。
2. **给 core/accel 加分配日志**：`XeGfxAccel` 里已经有现成字符串
   （`NVVidMemory::allocPhysical(%p): %llu bytes of REAL VRAM -- phys 0x%llx kva %p [BAR1 %llu]`、
   `... SCANOUT phys 0x%llx ... already backed`、`iop: zero-copy flip: %u GGTT slots x %llu bytes (first 0x%llx)`），
   只需确认这些 `IOLog` 在当前 build 里是否被编译进去/是否被日志级别过滤——本次 `dmesg` 一条都没有，
   而 `getStampMemory`/`createUserGPUTask` 有，说明**这几条恰好走了不打印的分支**。打出来就能一眼看到分配是否落在 `0x800000..0x2200000`。
3. 整栈换 0.0.44（§4）保留为第 3 步，只在 1、2 都排除后才做——现在直接换栈，很可能换了仍然花屏，
   还多引入一轮"6 处补丁重新定位"的风险。
