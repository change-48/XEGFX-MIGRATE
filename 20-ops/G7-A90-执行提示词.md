# Gate 7 · A-90 执行提示词：两个用户可感知的问题（开机直通加速 + 应用首次启动慢）

> 这两件事**独立于 60fps 追逐**，可以并行做，收益是"每天都能感觉到"的：
>
> **问题 A · 开机要重启一次 WS 才能加速**
> ```
> 20:45:51  stages ok（accel 已载入）
> 20:45:56  bootArm is driving
> 20:46:18  bootArm armed but no frames yet -- restarting WindowServer once   ← 22s 后
> 20:46:36  OK: frames are reaching the panel
> ```
> 根因（bringup 脚本注释自述）：**WindowServer 比 pipe 先启动**，握着过期的显示注册。
> 而脚本里**没有任何 display-change 通知**（`grep IOFBNotify\|IOFBEvent` = 0）。
> 目标：bootArm 之后**不重启 WS 也能出帧**（用户不用重新登录）。
>
> **问题 B · 应用首次启动慢**
> 着色器缓存**按进程名分目录**（实测：`…/C/WindowServer/nvmtl/spvcache` 1100 文件/292MB 是热的；
> `…/C/com.apple.iconservicesagent/nvmtl/spvcache` 193 文件是它自己的）。
> ⇒ **每个 App 第一次启动都要从零翻译自己的全部着色器**，A-86 实测单个新变体 **3.6–11.5 秒**。
> 目标：把这笔"首次代价"降下来，或让它不阻塞 UI。
>
> 必读：`G7-A84报告.md` §1.2（开机时间线）、`G7-A86报告.md` §3（翻译/缓存机制）、§6.3（冷缓存代价）。

## 2. 问题 A · 开机直通（先做，收益直接）

### 2.1 先确认机制（15 分钟）

1. 读 `xegfx-bringup.sh` 第 140–190 行，确认"22 秒后判定 no frames → kickstart"的判据与超时；
2. 抓一次开机全过程：`log show --last 3m --predicate 'eventMessage CONTAINS "XeGfx" OR CONTAINS "IOFB"'`
   与 `ioreg -l -w0 -c IOFramebuffer`（看 `IOFBModes`/`IOFBNeedsRefresh`/display 注册时机）；
3. 关键问题：**WS 是在 pipe published 之前还是之后完成 display 枚举的**？
   证据：WS 启动时间 vs `bootArm` 完成时间（都在 bringup 日志里）。

### 2.2 修法（按可行性排序，逐条试，每条都能回滚）

| 序 | 做法 | 原理 | 风险 |
| --- | --- | --- | --- |
| **A1** | bootArm 成功后，由 **FB** 发一次 display-change 通知（`IOFBNotifyDisplayChange`/`CoreDisplay` 通知；先 `nm` 确认符号可用，A-79 的 KC 符号验证法照用） | 让 WS/CoreDisplay 重新枚举显示，不必重启进程 | 低（只是通知） |
| **A2** | FB 在 bootArm 前后**重新提交一次 `IOFBConfig`/模式**（等价于一次"热插拔"） | 同上，走既有路径 | 中（可能引起闪烁） |
| **A3** | bringup 里把"22 秒等待"改成"**发现 no frames 时先发通知，仍无帧再 kickstart**" | 最小改动，A1 不行时的兜底 | 低 |
| A4 | 延后 WindowServer 启动（launchd 顺序/hold） | 最干净但动系统服务 | **高，不建议** |

**门 A**：连续 **3 次冷启动**，每次都满足：`frames are reaching the panel` 出现、
**且 bringup 日志里没有 `restarting WindowServer`**、用户登录后**不需要重新登录**、
拖动 p50 与现在同档（±1ms）。

### 2.3 如果 A1–A3 都不成

如实记录：**"WS 先于 pipe 启动"是 CoreDisplay 的枚举时序，本栈无解**，并把
"每次开机多花约 40 秒 + 一次重新登录"写进 README 的已知限制。**不要为了这个动系统服务。**

## 3. 问题 B · 应用首次启动慢（先量，再决定修不修）

### 3.1 量化（30 分钟，只测不改）

选 3 个没启动过的 App（或用 `rm -rf` 清掉它们各自的 `spvcache` 目录来模拟首次），
测「点图标 → 窗口出现」的耗时，并对照：

```bash
# 每个 App 的缓存目录（按进程名）
ls -1 /var/folders/zz/*/C/<AppName>/nvmtl/spvcache 2>/dev/null | wc -l
# 首次启动耗时（冷/热各 3 次，用 `time open -a` + 目视窗口出现）
```

| 场景 | 期望 |
| --- | --- |
| 冷（缓存清空） | 数秒（预期 3–10s） |
| 热（缓存已在） | <1s |

**同时确认归因**：`log stream --predicate 'process == "<App>"'` 里是否出现
`nvmtl_translate` / `emit_vulkan_spirv` 相关；或 `sample <App> 5` 看是否卡在翻译。

### 3.2 可能的修法（按性价比，**先评估再动手**）

| 序 | 做法 | 代价 | 预期 |
| --- | --- | --- | --- |
| B1 | **共享缓存池**：让所有进程共用一个 `spvcache`（现在按进程名分目录） | 改插件里缓存路径的 key（`nvmtl_spvcache_path_air` 附近） | 一个 App 编译过的公共 UIKit 着色器，其它 App 直接命中——**可能是最大一笔** |
| B2 | 翻译并行化/降优先级 | 改 `libnvmtl_translate` 侧 | 首次仍慢，但不卡 UI |
| B3 | 预热：开机后用脚本跑一遍常见 App 的着色器 | 脚本 | 开机后一段时间仍然会卡 |
| B4 | 不管 | — | 只在"首次"付代价，README 写明 |

**门 B**：① 冷/热耗时表（3 App × 3 次）；② 归因证据；③ **B1 是否可行的评估结论**
（若可行，给出改动点与风险，留给下一关单独做）。
