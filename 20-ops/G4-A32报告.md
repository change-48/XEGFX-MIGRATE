# Gate 4 · A-32 执行报告：WS 不是"卡在 GPU 等待"，是自渲染 10 s 后 SIGABRT

> 执行方式：Windows 侧 `ssh -i ~/.ssh/id_xegfx_remote change48@192.168.1.102`
> 执行时间：2026-10-31 21:20 – 21:36（三次重启：21:28 复位、21:31 设 bootarm、21:35 止损）
> 变更范围：**零代码改动、零重编、零 kext 安装**。只做了加载/卸载、nvram 门、取证。
> 证据：远端 `~/xegfx-log/A-32/`；本地 `20-ops/A-32/`

---

## 0. 一行结论

**WS 既没卡在 GPU 完成等待，也没卡在提交、IOKit。它每跑约 10 s 就 SIGABRT 自杀，死在
QuartzCore 的 surface 记账上**：

```
21:33:40.357  WindowServer[1174]: (QuartzCore) [com.apple.coreanimation:OGL]
              context(2) transient surface 0x7f95a3006a10 not found
21:33:40.371  launchd: [system/com.apple.WindowServer [1174]:] exited due to SIGABRT
              | sent by WindowServer[1174], ran for 10710ms
```

时间差 **14 ms**，7 个 WS 实例、7 次一模一样的落点。**A-31 的「WS 被内核同步调用扣住」被推翻**：
主线程全程停在 `server_loop → mach_msg`（空闲等消息），`vkWaitForFences` / `waitUntilCompleted`
在 5 份 sample 里出现 **0 次**。

## 1. 本关最重要的两个发现（比栈本身更重要）

### 1.1 `XeGfxDisplayNub` **只在 bootarm 路径才发布**，手工 `stage=7` 永远进不了 S3

提示词 §2.2 的单路径（`kmutil load core` → 手工 `sysctl stage=7` → `kmutil load display`）**走不通**，
我第一次完整跑完，门 3 三项全灭。实测对照：

| 顺序 | 现象 | nub 实例数 |
| --- | --- | --- |
| A：先 load core（bootarm 已删），后写 `phase=%02` | `results=0 1 1 1 1 1 1 1`、`nmxgpu-claimed=Yes`、`boot surface GGTT 0xfd000000 ... reserved: 0` | **0** |
| B：先写 `phase=%02`，再 load core | `results=0 1 1 1 -28 0 0 0`、`boot surface GGTT 0xfe600000 + 25958400 reserved: -28`、claim 未打 | **0** |
| C：`xegfx-disp-bootarm=%01` 在位时 load core | 日志 `boot-armed by NVRAM` → `boot stage 4 rc=1 in 280 ms` → `M4a core ready` | **1** ✅ |

display kext 的两个 personality 都是 `IOProviderClass = XeGfxDisplayNub`：

```
Dict {
        IOClass = XeGfxIntelKMSFramebuffer
        IOProviderClass = XeGfxDisplayNub
        IOClass = XeGfxFBClaim
        IOProviderClass = IOPCIDevice
        IOPCIMatch = 0x7d678086
        IONameMatch = display
```

**nub 不存在 → 不匹配 → 不 probe → 一行日志都没有**（这正是第一次失败时"加载 rc=0 但什么都没发生"的原因）。
`XeGfxDisplay/.kext` 里 `XeGfxDisplayNub` 只在 `Info.plist` 出现，**发布方是 `XeGfx.kext` 内核侧**，
且只在 bootarm 排程那条路上创建。

**结论：S3 必须走 bootarm 路径。** 铁律 2 的"二选一"应改写为"**bootarm 是唯一入口，手工 stage 只能用于
accel/claim 自检，不能用于 S3**"。

### 1.2 开机自启脚本从 17:56 起就已自我禁用，所以"开机进 S3"这条路现在是死的

```
/var/db/xegfx-boot/disabled 存在（17:56 创建）
/var/db/xegfx/boot.log 末尾 15 条全是 "self-disabled, skip"（17:57 → 21:31）
```

`org.xegfx.boot` 的 `xegfx-boot.sh` 逻辑是 `attempts > 3 → touch disabled`。
**这意味着：只要不手工 load core，bootarm 就永远不会被消费** —— 我这次 21:31 那次重启后
`boot-armed` 完全没出现，原因就在这里。要恢复自启需删 `disabled`，本关**没动**它。

```

1499  21:34:26 → 21:34:35  ran  9879 ms  SIGABRT

```

- **任何时刻都只有 1 个实例**（n 恒为 1），没有出现"第 2 实例"，所以 §3.1 的提前停机条件没触发；
  实际是"自杀→launchd 立刻重启"的循环。
- 每实例存活 **9.6–11.0 s**，远短于 60 s 采样窗口，也远短于 120 s watchdog。
  所以 **A-31 的"19 个实例全部 <60 s 被 watchdog 杀"这个描述不准确**：不是被 watchdog 杀，是它们自己 abort。
  A-31 那次最终 panic 是"WS 反复重启 120 s 内没有一次 checkin"的连带结果，不是"某个 WS 被扣住 120 s"。
- 本次 `armed` 在 21:33:11 建立，21:35 前就清掉并重启，**没有走到 120 s**，无新 panic。

## 6. 交给下一关的三条硬事实

1. **呈现链路已经完全通了**：`first present accepted` → `enableController READY` → `open() RELEASED (opens=1)`，
   `OpenCount=7`。**不要再查 present/open/AGDC。**
2. **卡点在 WS 自己的合成器选择**：`CDDisplay::render_update` 走的是 `CompositorSW`（软件合成），
   同一进程 `CA::OGL::SW::*` 满栈 —— 说明 **CA 没有把我们这条 framebuffer/accel 识别为可加速的显示目标**，
   于是退化成 CPU 合成，然后在 OGL 的 transient surface 记账上断言失败。
   这解释了 A-31 里"NVMTL 起来了但仍在软合成"的矛盾：**NVMTL 是给 App/CA 的 Metal 上下文用的，
   而显示更新那条路选的是 SW 合成器，两条路互不相干。**
3. **`vkWaitForFences` 方向可以关掉**（5 份 sample 全 0）。A-31 §6 的第 3 条（fence/中断完成路径）不必做了。
