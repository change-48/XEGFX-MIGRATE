## 1. 主 agent 复核后认为：先别急着换栈，有个自家遗留更可疑

A-12 / A-13 那几轮我们往 GGTT 写了 6338 条测试 PTE，**收尾只清了 `PTE[0x1000]` 一条**，
`0x1001 .. 0x28C1`（约 6336 条）**至今仍指向 `phys 0x01000000`**（A-16 报告末尾自己写着"无消费者"）。

但**现在有消费者了**：加速器一 attach，i915/accel 开始从 GGTT 里分配缓冲。那 6336 条残留 PTE
在驱动的分配器看来是"我们的"，在硬件看来是"有效的映射"。只要有一次分配/回收落到这段，
就会把扫描输出（`0xFE600000` 起）以外的物理页当成合法缓冲来读写 —— 表现正好是**局部画面被写花**。

**这不一定是真因，但它是我们自己留下的、最便宜就能排掉的一个变量。**

## 3. A-18a：复现一次并取证（唯一变量 = 无，纯观测）

**为什么不是"先修再测"**：A-16 已经证明条纹与 GPU 提交强相关，但我们还不知道
**是内存被写花，还是显示寄存器被改**。这两种原因的修法完全不同，猜错就是白烧两次开机。
所以这一轮**不改任何东西**，只在花屏发生的当下把证据抓齐，然后重启。

### 3.1 准备

```bash
mkdir -p ~/xegfx-log/A-18a
sudo /usr/local/bin/xenative-ctl status | tee ~/xegfx-log/A-18a/before.txt
system_profiler SPDisplaysDataType | grep -E "Resolution|Metal" | tee -a ~/xegfx-log/A-18a/before.txt
```

### 3.2 加载 → 推 stage → 跑一次探针 → **立刻抓这四样**

```bash
sudo kmutil load -b org.watchthelight.XeGfx
sudo sysctl -w debug.xegfx_wdog=60
sudo sysctl -w debug.xegfx_stage=7
sleep 25
sudo sysctl -b debug.xegfx_results | od -A n -t d4 | tee ~/xegfx-log/A-18a/results.txt

# 基线快照（花屏前）
sudo /usr/local/bin/xenative-ctl status > ~/xegfx-log/A-18a/regs-before.txt

~/xegfx-probes/mtlprobe 2>&1 | tee ~/xegfx-log/A-18a/mtl.txt
# ⚠️ 跑完立刻做下面三步，不要等
```

看屏幕出现条纹后，**按顺序、在重启之前**抓：

```bash
# A. 显示寄存器有没有被改（决定"内存写花"还是"寄存器被改"）
sudo /usr/local/bin/xenative-ctl status > ~/xegfx-log/A-18a/regs-after.txt
diff ~/xegfx-log/A-18a/regs-before.txt ~/xegfx-log/A-18a/regs-after.txt | tee ~/xegfx-log/A-18a/regs-diff.txt

# B. 关键只读寄存器：平面是否还指着同一块、水位/DDB 有没有被动
for o in 0x70180 0x7019c 0x701ac 0x70240 0x7027c 0x68180; do
  printf "%s: " $o; sudo /usr/local/bin/xenative-ctl dump $o 1 | tail -1
done | tee ~/xegfx-log/A-18a/planeregs.txt

# C. 内核日志：stolen / GGTT 分配、accel 提交、任何 IVB/underrun
sudo dmesg 2>/dev/null | tail -120 | tee ~/xegfx-log/A-18a/dmesg-tail.txt
sudo log show --last 5m --predicate 'eventMessage CONTAINS "XeGfx" OR eventMessage CONTAINS "NMXAccel" OR eventMessage CONTAINS "stolen" OR eventMessage CONTAINS "GGTT"' 2>/dev/null | tail -80 | tee ~/xegfx-log/A-18a/log.txt

# D. 这一条决定 Gate 4 的答案（花屏状态下也能测）
sudo vmmap "$(pgrep -x WindowServer)" 2>/dev/null | grep -ci nvmtl | tee ~/xegfx-log/A-18a/vmmap.txt
sudo powermetrics --samplers tasks -n 1 2>/dev/null | grep -A3 -i windowserver | tee ~/xegfx-log/A-18a/power.txt

sudo reboot
```

### 3.3 判据（这一轮就靠这四个读数定性）

| 读到的现象 | 说明 | 下一步 |
| --- | --- | --- |
| `regs-diff` **为空**、`0x7019c` 仍是 `0xfe600000` | 几何/平面没被动 → **内存被写花** | 倾向 A-18b（地址隔离/flip 栈） |
| `regs-diff` 非空，或 `0x70240/0x7027c`（水位/DDB）变了 | accel 动了显示寄存器 → **不是内存问题** | 另一条路：查 accel 的 display pipe 编程（不要换栈） |
| `dmesg` 里有 stolen 分配落在 `0x800000..0x1a00000` | **分配器把缓冲塞进了原生帧缓冲**（它会按 1080p 时代的 8.29 MB 去算"帧缓冲之后"） | 优先修分配起点，而不是换栈 |
| `vmmap > 0` | 插件确实进了 WS（A-16 的推断成立） | 与上面对应处理 |

> 第 3 条是主 agent 的重点怀疑：core 在 1080p 时代把 stolen 分配器起点定在"boot framebuffer 之后"，
> 而 A-14 把 framebuffer 从 8.29 MB 扩到了 **26 MB**。如果起点没跟着变，accel 的缓冲就会落进扫描输出的正中间 ——
> 这恰好能解释"上 1/3 一条横向带"。**在 `dmesg` 里找 stolen/GGTT 分配的起始地址来证实或否证。**

## 4. A-18b：换 matched flip 栈（仅当 A-18a 仍花屏）

**这是本关唯一已知能解决"呈现路径"的路径**，也是 1031 计划里写死的 fallback。

### 4.0 先明确"为什么是整栈换"

主 agent 已核实：
```
flip 树 core：~/src/NvGfx-5a19a73f36249efb99c44c3f9cb34603ef0c0eb8/gpu/xegfx/out/XeGfx.kext  → 版本 0.0.44（0001+0008）
当前 core：   /Library/Extensions/XeGfx.kext → 0.0.46 + 4 处补丁（**没有 0008**）
已装 accel：  0.1（21:50 生成，`shasum 3d1024…`，与 out-accel2..6 全都不同）
```
**accel 是 flip 时代的（0002+0009+0012），core 却不是（缺 0008）——这是一对不匹配的栈。**
A-16 的花屏完全符合"加速器按 flip 语义提交、core 不认"的表现。
所以 A-18b 不是"换个加速器"，而是**把 core 和 accel 换成同一代**。

### 4.1 0.0.44 需要重新定位补丁（不能用 0.0.46 的硬偏移）

0.0.44 装上去会停在 stage 5（历史记录）。需要按**特征字节**重新定位 6 处，**不许照抄 0.0.46 的偏移**：

| 目标 | 0.0.46 的原始字节（仅作参考） | 0.0.44 要做什么 |
| --- | --- | --- |
| 3× `pci_dev_put` → `kobject_release` | `e8 c1 9a f2 ff` 等 | 搜 `callq rel32` 且目标落在 `_linux_kobject_release`（用 `otool -tV` 看符号地址后算 rel32） |
| stage 循环 break | `0f 88 ae 04 00 00` | 搜 `testl %r13d,%r13d` 紧接 `js rel32` 的模式 |
| 2× `idr_preload` | `0x6edf0` call / `0x6ef36` jmp | 搜 `xg_sched_pin` / `xg_sched_unpin` 的调用点；**jmp 处尾字节必须是 `c3`** |

做法：`otool -tV <binary> > dis.txt`，在反汇编里按**符号名**定位（`_linux_kobject_release`、
`xg_sched_pin`、`xg_sched_unpin`），再回到文件偏移改字节 —— **不靠猜偏移**。
每改一处都要 `xxd` 前后对照，并 `codesign --force --sign -`。

> 如果 0.0.44 的补丁定位在 30 分钟内搞不定，**就停手报告**，不要用"大概位置"去试 ——
> `idr_preload` 尾部填错会直接启动 panic。

### 4.2 装栈 + 验证顺序

```bash
# 备份现有 0.0.46（含 6 处补丁）
sudo cp -p /Library/Extensions/XeGfx.kext/Contents/MacOS/XeGfx ~/xegfx-log/A-18b/XeGfx.046-6patch
# 装 0.0.44 core + 同代 accel，重建 AuxKC，逐条核对 id，arm，重启
```

**验证顺序（A-16 教训，务必照这个来）**：
1. 手动 `kmutil load -b` + 推 stage 7 → `results`
2. **先跑 `vkprobe2`**（不经 accel，验证 core 侧 GGTT 干净）→ 立刻看屏幕
3. 再跑一次 `mtlprobe` → 立刻看屏幕
4. 屏幕干净才继续 `vmmap` / `powermetrics`

## 5. 停机与回滚

| 现象 | 处置 |
| --- | --- |
| 花屏 | 立刻重启；不要继续跑 GPU |
