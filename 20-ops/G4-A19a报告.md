## 2. 这次实验证明了什么

1. **`0xFD000000 .. 0xFEA00000` 这一整段（6656 页）分配器不碰。**
   两次探针（每次都会触发 accel 分配显存）之后，新位置 9 个采样点（含首条、末条、以及紧贴顶部的 `0xFE9FF`）**逐条原值**，屏幕全程完整。

2. **旧窗口的 8 MB 确实被吃干净了。**
   搬迁时读 `PTE[0xFE600]` 已经不是 `0x800003`，而是 **`0x01e00003`**（phys `0x1e00000`）——
   也就是说 A-18b 里"断在 1783"只是当时的扫描窗口截断，实际分配器把 `0xFE600000` 起**整段**都重写了。

3. **根因链闭环。**
   reserve 整体 `-28 ENOSPC` → 一条没登记 → 分配器从 GuC 栅栏（`0xFEE00000`）往下吃满 8 MB → 帧缓冲 PTE 被覆盖 → 花屏；
   把 SURF 挪到它不去的 `0xFD000000`，行为同步消失。**寄存器语义、物理内存、macOS 侧全都没动，只换了 GGTT 入口。**

## 3. 三处必须反馈给主 agent 的现场事实（重要）

### 3.1 ★ `scan` 的 `live_run_pages` 在搬迁之后**不再是有效判据**

`xenative.cpp:611`：`UInt64 idx = fSurfBefore >> 12;`，而 `fSurfBefore` 只在 `init()`（第 374 行）赋一次值。
`reg surf <新值>` **不会**更新它。所以搬迁后 `scan 7000` 报的 `1024 / 0x1e00000` 读的是**旧锚点 `0xFE600`** 那格 PTE（已被分配器改写），**与 `0xFD000000` 上发生了什么毫无关系**。

→ 提示词 §3.3/§4 把 `live_run_pages` 当作 A-19a 的验收读数，**这条读法在搬迁后失效**。若照字面判读，会把"成功"误读成"被抢后变小"。

### 3.2 ★ 找到了替代的**只读**通道：`xenative-ctl dump`

GGTT 的 PTE 数组在 BAR0 偏移 `0x800000`，索引 `i` 的 PTE 在 `0x800000 + i*8`。`dump <off> [count]` 走 `SEL_REGREAD`，**纯读、不写、不 flush**，上限 `off < 0x1000000`、每次 ≤16 dword（= 8 条 PTE）。

已验证一致性：`dump 0xff3000 4` → `0x01e00003`，与 `scan` 报的 `live_phys 0x1e00000` 完全对上。

```bash
# 读新位置第 0 条 / 最后一条
sudo xenative-ctl dump 0xfe8000 2     # idx 0xFD000  → 0x00800003
sudo xenative-ctl dump 0xff4ff8 2     # idx 0xFE9FF  → 0x021ff003
```

**注意成本**：每次 `dump` 要 fork 一个 `xenative-ctl`、重开一次 IOService，实测 **≈0.7 s/次**。
832 次全量扫（8 条/次）≈10 分钟，不实用。**建议按需抽样（本次 9 点/轮，够用），或在 ctl 里加一个"整段校验"子命令**（下一轮的事）。

### 3.3 ★★ 危险操作教训：中断本地 SSH **不会**杀掉远端循环

我用 `TaskStop` 掐掉本地 `ssh` 后，Mac 上的 `zsh -c` 循环**照旧在跑**，每个循环反复 `sudo xenative-ctl`。
多次堆积后驱动的客户端名额被耗尽，之后**任何** `IOServiceOpen` 都要等 **15 秒**再返回 `kIOReturnError (0xe00002bc)`：

```
$ sudo xenative-ctl status
IOServiceOpen failed: 0xe00002bc        # 15.3s 后才失败
```

`kill -9` 掉那些 `xenative-ctl` 与 zsh 循环也**没能恢复**（名额在内核侧泄漏），**只有重启能清**。
→ 后续轮次：远端循环要么放脚本里并自带 `-timeout`，要么中断时**必须** `ssh ... pkill -9 -f <标记>` 收尾，不能只掐本地连接。
