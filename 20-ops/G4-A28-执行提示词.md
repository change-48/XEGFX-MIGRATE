# Gate 4 · A-28 执行提示词（让 open() 只在 aperture 真的能给出时才放行）

> 用法：把本文件全文作为一条消息发给执行会话。执行会话不需要任何前置上下文。
> **这是最后一个已知闸门，而且已经定位到两行代码的判断不一致。改动约 10 行 + 重编一个 kext。**

---

## 0. 断言原文与真因（已钉死，不用再猜）

崩溃不再是"不知道原因"了。ReportCrash 的 ASI 里就写着：

```
Assertion failed: (found != slist->end()), function push_surface, file ogl-context.cpp, line 1186
```

**`found != slist->end()`** 的意思是：CA 在自己的 surface 链表里**查不到它正要 push 的那个 surface**。
结合 A-27 的日志，原因很清楚：

```
open() RELEASED (opens=1) -- aperture 0x0/0 live                     ← 第一次 open：aperture 是空的
open() RELEASED (opens=2) -- aperture 0x2666d000/26091520 live        ← 之后才有了
aperture served phys 0x2666d000 len 26091520 (3120x2080 pitch 12544)
```

CA 第一次 open 时拿到**空 aperture**，据它建了 surface；等真正的 aperture 出现后，那个 surface 已经对不上，
后面 `push_surface` 就断言。**WS 每 8.7 秒崩一次、画面冻结/黑屏交替、最后 watchdogd panic —— 全部由此。**

### 源码级真因：`open()` 与 `getApertureRange()` 的判据不一致

```c
// XeGfxDisplay.cpp — open() 的第三道闸
else if (!m3dApertureReady())  why = "aperture-not-mapped";

// XeGfxDisplay.cpp — getApertureRange()
if (!fM3d || !fM3dReady || !m3dApertureReady() || fScanoutCount == 0)
    return nullptr;
```

`m3dApertureReady()` 为真，但 `fM3dReady` 或 `fScanoutCount` 还没就绪 → `getApertureRange()` 仍返回 nullptr。
**闸门放行了一个"其实还拿不到 aperture"的状态。**

---

## 1. 要做的改动（约 10 行，只改 `XeGfxFramebuffer::open()`）

原则：**不要靠"多等一会儿"赌时序，而是让 open() 用和 getApertureRange() 完全相同的方法去验证**——
问一次 `IODeviceMemory` 拿不拿得到；拿不到就**短暂等待重试**（把竞争变成等待），仍拿不到才 deny。

在 `open()` 现有 `why` 判定链里，把 `aperture-not-mapped` 那一档换成"实际探测 + 有限重试"：

```c
        else if (!m3dApertureReady())
            why = "aperture-not-mapped";
        else {
            /*
             * A-28: m3dApertureReady() can be true while getApertureRange() still
             * returns nullptr (it also needs fM3dReady and fScanoutCount != 0).
             * Releasing open() on that state hands CoreAnimation a null aperture,
             * it builds a surface from nothing, and the first push_surface then
             * asserts (found != slist->end(), ogl-context.cpp:1186).  Probe the
             * same path the client will use, and give the scanout a short window
             * to be served before deciding.
             */
            IODeviceMemory *ap = nullptr;
            for (int i = 0; i < 20; i++) {                  /* <= 2 s */
                ap = getApertureRange(kIOFBSystemAperture);
                if (ap != nullptr) { ap->release(); break; }
                (void)m3dEnsurePresented();                 /* 现有的助手，能推动 scanout 就绪 */
                IOSleep(100);
            }
            if (ap == nullptr)
                why = "aperture-not-served";                /* 明确区别于上面的 not-mapped */
        }
```

要点：
- **必须真的调用 `getApertureRange()` 并用返回值判断**，不要新写一个"看起来等价"的布尔判断 —— 这正是这一轮 bug 的来源。
- `getApertureRange` 返回的是新建的 `IODeviceMemory`，判完要 `release()`，别泄漏。
- **不要**因此把 open() 无限期拖住：上限 2 s，超时就 deny（deny 会走 S3 watchdog 的安全回滚路径）。
- 不要动 `getApertureRange()` 本身的逻辑（它是对的），也不要动 `m3dApertureReady()`。

### 顺手核对（同样重要，但先只记录不修改）

接管态下 `ioreg -c XeGfxIntelKMSFramebuffer` 里 `IOFBCurrentPixelClock` 出现过两个值
（`900788928` 与 `900045000`）。先记下来；若 A-28 之后 WS 仍崩、且断言变了，再来查这个。
**本轮不要改它**（一次一个变量）。

## 2. 铁律

- **只改 `open()` 这一处**；`static-panel` 时序源与 pitch=64B 对齐**都要保留**（A-27 的成果）。
- 装 kext 用 `kmutil create -z`；**绝不 `kickstart` `kernelmanagerd` / `syspolicyd`**。
- `launchctl kickstart -k system/com.apple.WindowServer` 是**允许**的（A-27 已证明这是让 S3 被看见的必要动作）。
- **core 不自动加载**：必须先 `kmutil load core` → 再 `kickstart WS`。这个顺序两次咬过人。
- **实验窗口纪律（A-27 的教训）**：S3 起来后 **60 秒内**必须判定"稳/不稳"；不稳立即
  `nvram xegfx-disp-phase=%00 / trial=%00 / fail=%01` + 重启，不要让 watchdogd 再 panic 一次
  （上次 panic 把 18:43 那次重编的日志吃成 0 字节）。
- 判"是否软件合成"必须**动画面**采样；且**WS 活不到 60 秒时任何 sample 计数都不算证据**。

## 验收锚点（主 agent 独立跑）

1. `grep -c "aperture-not-served" XeGfxDisplay.cpp` ≥ 1；`open()` 里**真的调用了 `getApertureRange`**。
2. 日志里第一次 `open() RELEASED` 的 aperture **不是 0x0/0**。
3. `ps -o etime= -p $(pgrep -x WindowServer)` > 60 秒，且期间无新 `.ips`。
4. `ioreg -c XeGfxIntelKMSFramebuffer | grep XeGfxFbOpened` = Yes。
5. `sudo sample $(pgrep -x WindowServer) 5` + `grep -c "CA::OGL::SW"` 与 1256 对比（**且注明 WS 存活时长**）。
6. 屏幕 3120×2080、零新 panic、`fbgeom.log` 正常。
