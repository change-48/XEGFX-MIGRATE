## 1. 方法：先修一个解析 bug，否则整张表都是错的

`~/xegfx-log/A-82/tools/parse_all.py` 用

```python
end = next(i for i, l in enumerate(lines) if l.strip() == "Total number in stack")
```

做截断，但 `sample` 实际写的是 **`Total number in stack (recursive counted multiple, when >=5):`** ——
等值判断**永远不成立**，`end` 落到文件末尾，于是**每个线程后面那段 "Total number in stack" 汇总块被当成调用树节点解析**
（它们顶格、也带计数），被算成新的"线程"和 self 样本。

后果：同一次采样，旧脚本给 `threads=16 / busy 20.7% / wait 24.3% / idle 55.0%`，
修好后主线程是 `busy 44.5% / wait 22.6% / idle 32.9%`。**A-77 §1 和 A-82b 的三分类数字都带这个偏差**
（量级上"busy 占多数"的定性结论没变，但具体 ms 值不可当基线）。

本关用修好的解析器（`D:\XEGFX-MIGRATE\work\a85\sparse.py` + `report_p1.py`），并在报告正文里注明每个数来自哪一段。

## 2. P1 · 20.7 ms 归因表

**样本**：flip=1 稳态拖动（xa82load 34 s 1100×760 α16 blur），拖动第 3 s 起 `sudo sample WindowServer 12`，
共 **4654 个采样点 / 16 线程**（每线程 4654 ⇒ 每个采样点覆盖全部线程，故 busy%/wait%/idle% 是**该线程的墙钟占比**，
折算一帧按 p50 = 25.15 ms）。

### 2.1 按线程（谁在花时间）

| # | 线程 | busy | wait | idle | 一句话 |
| --- | --- | --- | --- | --- | --- |
| 0 | `ws_main_thread` | **44.5%** | 22.6% | 32.9% | 帧主线程：干活 11.2 ms、等锁 5.7 ms、等 vblank 8.3 ms |
| 1 | `com.apple.coreanimation.render-server` | 4.9% | **44.5%** | 50.6% | 其中 **`CA::Render::Fence::resolve_batches` 占该线程 45%**（≈4.4 ms/帧，几乎全是 `__psynch_cvwait`） |
| 9 | 无名字（libdispatch workloop） | **99.5%** | 0.4% | 0.0% | **全程 100% 忙于 `create_pipeline_state → create_fragment_shader → nvmtl_translate`**（23.6 ms/帧） |
| 13/14/15 | 三条 `windowserver.root_queue` | ~0 | ~99% | ~0 | 信号量上空转，正常 |
| 2..12 | 其余 | <2% | — | — | 空闲 |

> 线程 9 的调用链（`sample` 原文，4370/4654 个采样点都在这条路上）：
> `_dispatch_workloop_worker_thread → invocation for block in CA::OGL::MetalContext::dispatch_async_pipeline
> → CA::OGL::MetalContext::create_pipeline_state → create_fragment_shader → load_shader_function
> → -[NVMTLLibrary newFunctionWithName:constantValues:error:] → nvmtl_translate_with_fc_cached → nvmtl_translate_fc
> → translate_one_as_written → emit_vulkan_spirv_inner …`
>
> **空闲 5 s 采样里 `create_fragment_shader` 计数 = 0**（`sample-idle.txt`）。⇒ 这条编译流**完全是拖动触发的**：
> 拖一次窗口，CA 每帧新建一个 fragment shader，NVMTL 每帧把 Metal IR 重新翻译成 SPIR-V，一整个核 12 s 不停。

### 2.2 主线程 25.15 ms 的三分类（对比 A-77 的旧表）

| 类别 | 本关（25.15 ms 帧） | A-77（38.5 ms 帧，口径已修正） | 结构变化 |
| --- | --- | --- | --- |
| busy | **11.22 ms（44.5%）** | 26.2 ms（68%） | 占比腰斩：A-84 的翻转 + GPU 提频把 CPU 搬砖拿掉了 |
| wait | **5.69 ms（22.6%）** | 6.3 ms（16%） | 绝对值没降，**占比升了**——它就是现在最大的可动项 |
| idle | **8.30 ms（32.9%）** | 5.9 ms（15%） | **恰好 = 1 个 vblank（8.33）** ⇒ 每帧白等一拍 |

**关键算式**：`busy + wait = 16.91 ms`，2 vblank = `16.67 ms`，**只超 0.24 ms**；
`idle = 8.30 ms` ≈ 1 拍。⇒ 现在这一帧的形态是"**工作刚好用完 2 拍还差一点点，于是被判给 3 拍**"。

### 2.3 wait 的归属（主线程，按调用者聚合）

| ms/帧 | 占比 | 等待点 | 调用者（真实链） |
| --- | --- | --- | --- |
| **1.06** | 4.2% | `__ulock_wait2` | `-[NVMTLCommandBuffer nvmtlSubmitWithEvents]` ⟵ `commit` ⟵ `commitAndWaitUntilSubmitted` |
| **1.02** | 4.1% | `__ulock_wait2` | `-[NVMTLCommandBuffer enqueue]` ⟵ `MetalContext::RenderCommandBuffer` |
| **0.97** | 3.9% | `__ulock_wait2` | `-[NVMTLCommandBuffer dealloc]` ⟵ `MetalContext::Flush` ⟵ `EndUpdate` |
| **0.83** | 3.3% | `__ulock_wait2` | `nvmtl_surface_in_for_cb` ⟵ `renderCommandEncoderWithDescriptor:` / `setFragmentTexture:` ⟵ `AccessComplete` |
| 0.76 | 3.0% | `__psynch_cvwait` | `CoreDisplay::DisplaySurface::AccessComplete()` |
| 0.75 | 3.0% | `__psynch_cvwait`+`__ulock_wait` | `MetalContext::Flush(bool,unsigned,unsigned,bool)` |
| 0.42 | 1.7% | `kevent_id` / `pthread_mutex` / 其它 | dispatch / std::mutex / nvlog |

**四笔加起来 3.87 ms/帧的同一种锁**：`@synchronized ([XeMTLCommandBuffer class])` ——
插件里那把**类级全局锁**（`NVMTLEventSync.m` 全文 20+ 处 `@synchronized`，其中提交/入队/析构/绑定面纹理
这四条热路径全在锁内）。这就是 A-82b §3.3 说的"NVMTL 三把锁"，实测**其实是同一把类锁在四个入口上的四次等待**，
每次 ~1 ms —— 与"持锁者一次临界区约 1 ms"完全吻合。

### 2.4 `CA::Render::Fence::resolve_batches`：4.4 ms/帧，但不在主线程

- 该符号**全部在 `coreanimation.render-server` 线程**（2104/4654 = 45% 墙钟），主线程 **0** 采样；
- 1900/2056 个采样点是 `__psynch_cvwait`，即"**围着 fence 等**"，不是算；
- 与线程 9 的 23.6 ms/帧翻译、以及"每帧 2.8 次串行 submit"是同一件事的三个观测面（fence 迟迟不 signal）。

**结论**：它是**症状**不是病灶；单独去"优化 resolve_batches"没有着手点（源码在 QuartzCore 里）。

### 2.5 每帧几次 submit、fence 几次（`/private/tmp/nvmtl-ws-prof.log`）

```
477 个 1 s 区间：submit 均值 111/s、waits 111/s（1:1，每次提交都等）
sub_p50 451 µs · done_p50 885 µs · tot_p50 1891 µs · 每秒被阻塞 189 ms
⇒ 每帧 111/40 ≈ 2.8 次 submit × 1.89 ms ≈ 5.3 ms 的"提交+等待"，几乎全在 nvmtl.execution 工作线程上
插件自报：commit: G-SUB submit-ahead ON, at most 16 parts in flight
         "G-SUB 1 parts submitted ahead, peak 1 in flight"   ← 上限 16，实际永远只有 1 转
```

**peak = 1** 是关键：ahead 通道形同虚设，GPU 队列深度实际为 1，于是 2.8 次提交严格串行，
每次都要等一个完整的 GPU 往返（885 µs）才能提下一笔。

### 2.6 两个梯度实验：每帧成本与"画什么/画多大"几乎无关

| 档 | 配置 | p50 | 相对基线 |
| --- | --- | --- | --- |
| 尺寸 | 1100×760 / 820×560 / 560×400 | **25.06 / 24.87 / 24.28** | 像素降到 1/4 只快 **0.78 ms（3%）** |
| 内容 | α16+模糊 / α1+模糊 / α16 无模糊 / α1 无模糊 | **25.06 / 25.30 / 25.14 / 25.23** | **全部在噪声内** |

⇒ **限速的是一帧的固定开销（提交链 + 每帧一次翻译），不是像素、不是 CA 的绘制量。**
这一条同时判死了"用减透明换 60fps"（提示词 §4 的第三个分支）——见 §4.3。

### 2.7 门 P1 判定

| 要求 | 结果 |
| --- | --- |
| 一张 20.7 ms 归因表 | ✅ §2.2/2.3/2.5 |
| 明确标出最大的一块（具体到符号/锁） | ✅ **每帧一次的 `nvmtl_translate`（23.6 ms/帧、独占一核）+ 类锁四次等待（3.87 ms/帧）+ 2.8 次串行 submit（5.3 ms/帧）**，三者同源：提交链没有流水 |

## 3. P2 · marks 判定：**不是停摆，是读数伪影**（A/B/C 三条都不成立）

### 3.1 先确认插件到底发不发 marks

| 检查 | 结果 |
| --- | --- |
| `sudo sysctl -n debug.xegfxaccel_surface_marks_dump` | `marks 149914 waits 14721 timeouts 316 max_wait_us 102231` + 逐 sid 的 `pending:` 列表 |
| 源码里有没有 | `~/src/a81-tree/plugin` 里 `nvmtl_ws_mark_pending/_ready`、`nvmtl_vk_surface_gpu_mark2` 全在（A-80 版**确实带这段**，A-84 §3.2 的怀疑不成立） |
| 拖动中的增量 | 15 s：`marks` **+4255**、`waits` **+604**、`timeouts` **+0** |

⇒ 可能 **A（没发 marks）排除**。

### 3.2 拖动中的 `last_mark_age_ns`（30 个样本，0.5 s 一次）

```
min 45 777 ns (0.05 ms) · p50 1.77 ms · p90 24.9 ms · max 27.4 ms
>100 ms 的样本：0 个     >1 s 的样本：0 个
```

同一份 dump 里的 `pending:` 一直是 `(none)` 或"落后 0–2 个序号"，没有卡死的挂起项。
⇒ **可能 B（ready 丢/hold 泄漏）在本场也不成立**：真丢 hold 会表现为 `timeouts` 持续增长 + pending 挂死，
这里 15 s 内 `timeouts` 一动不动。

### 3.3 那 A-84 §5.1 的"秒级"是什么

`last_mark_age_ns` 的语义是"**距上一次收到 mark 的时间**"，不是"某块面的 mark 等了多久"。
**没有新帧就没有新 mark**，于是空闲时它必然一路涨到秒级。本关实测：

```
空闲（无拖动）：surface_gpu_marks 不增长、pending: (none)、last_mark_age 自然变大
拖动中：        p50 1.77 ms
```

⇒ **真因是 D（读数语义）**：A-84 读到 5 s 的那几次，是**没有帧在跑的时候读的**。
`surface_gpu_timeouts` 从 134 涨到 316 也发生在**开机/登录阶段**（本关三次拖动 +0），与 A-81 §1 的结论一致
（"606 这个累计值不是拖动产生的"）。

### 3.4 剩下那笔真的异常：`behind by 1~2`

拖动中偶尔能看到

```
id 0x7 seq 50255 (newest 50256, behind by 1)
id 0x7 seq 50335 (newest 50335, behind by 0)
```

即 worker 偶尔要等本帧的 mark 落后 1–2 拍（`max_wait_us 102231` 那次 102 ms 的等待在启动期）。
**这是"快照与帧不同步"的形态，不是"通道死了"**，与残影的因果尚未建立。

### 3.5 门 P2 判定

| 判据 | 要求 | 实测 | 判定 |
| --- | --- | --- | --- |
| `last_mark_age_ns` 拖动中稳定 ms 级 | ms 级 | **p50 1.77 ms，无秒级** | ✅（本来就没有问题） |
| `surface_gpu_timeouts` 不增长 | +0 | 拖动 15 s **+0** | ✅ |
| 残影消失/减轻 | 目视 | **未取证**（本关未做目视对比，也未找到残影机制） | ❌ |
| 根因判定 A/B/C | 给结论 | **D：`last_mark_age` 是"距上次 mark"，空闲自然涨到秒级** | ✅（改写判据） |

> **给下一关的提醒**：残影不要再挂在 "marks 停摆" 上。可用的线索是 §3.4 的 `behind by 1~2`
> 与 A-84 的"拷贝路径同样有残影"——它更像是**合成内容与扫描出内容之间少了一道同步**，
> 该用"拖动时逐帧 dump `iop_tl` + `marks_dump` 的 sid/seq 序列"去对，而不是看 age。

## 7. 事故记录：`launchctl kickstart` 换 WS 环境时，显示器会从 WS 视图里消失

为了让 `reduceTransparency` 生效，本关对 WS 做了 3 次 `launchctl kickstart -k system/com.apple.WindowServer`。
第 2 次之后出现：

```
WindowServer: (SkyLight) Invalid display 0x23d05e40      （刷屏）
screencapture: could not create image from display
xa82load: screen 0x0                 ← NSScreen 报 0×0
```
期间的所有测量（p50 8.44 ms / 13 万 µs 之类）**全部作废**，已从报告里剔除。

恢复：`caffeinate -u` 一次后 `NSScreen` 报回 **1560×1040**，再测 p50 = 24.98 ms（= 基线）。
`flip_fail=0 / latch_timeouts=0 / plane_repairs=0 / asleep_frames=0`，**自愈链一次没动作**，
也没有新增 panic（最近两枚是 16:19 与 16:57，均在本关之前）。

**教训**：为了 A/B 一个环境变量去反复 kickstart WS 不划算——**要换插件环境，应该一次重启整机**（A-81 就是这么做的），
不要在同一次会话里连踢 WS。
