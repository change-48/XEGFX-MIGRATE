## 3. 装 kext 的两处计划外（都已解决，下次会重犯）

### 3.1 `kmutil install` 根本不收 XeGfxIntelFB —— 而 **作者的 `install.sh` 给出了正解**

`sudo kmutil install` 只打印 `kmutil rebuild done`，`kmutil inspect` 里没有 `XeGfxIntelFB`；
日志实证是审批门：

```
kernelmanagerd: library rebuild request failed: Extension with identifiers
  com.nullmoth.NMIntelFB,org.watchthelight.XeGfxIntelFB not approved to load.
```

按 A-20 的 `policy_fix.sh` 清了 `kext_load_history_v3` / `kext_policy` 并插入 `allowed=1 flags=0`
之后，`NMIntelFB` 回来了、`XeNative` 也进来了，**但 XeGfxIntelFB 依旧不收**。

**正解在作者自己的包里**（`~/src/xeintelfb-pkg/install.sh`）：它**完全不碰 kernelmanagerd**，
而是用 `kmutil create` 直接落 KC 文件：

```bash
sudo /usr/bin/kmutil create -n aux --volume-root / --allow-missing-kdk \
  -B /System/Library/KernelCollections/BootKernelExtensions.kc \
  -S /System/Library/KernelCollections/SystemKernelExtensions.kc \
  --repository /Library/Extensions -A /tmp/aux-a21.kc -z     # -z 跳过审批
sudo /usr/bin/kmutil inspect -a x86_64 -A /tmp/aux-a21.kc | grep XeGfxIntelFB
sudo mv -f /tmp/aux-a21.kc /Library/KernelCollections/AuxiliaryKernelExtensions.kc
```

一次成功，8 项全在。**以后任何 kext 进 AuxKC，优先走这条路，别再跟审批门较劲。**

## 5. 新闸门（A-22 的入口）：`0xe00002c7 framebuffer would not describe its scanout`

`debug.xegfxaccelfb=3`（打开 scanout-backed display pipe）之后：

```
NMXAccel: sysctl debug.xegfxaccelfb=3: scanout-backed display pipe ENABLED, re-delivering the mode change
NMXAccel: NVDisplayPipe::initFramebufferResource: framebuffer would not describe its scanout (0xe00002c7)
NMXAccel:   GATES after deliverModeChange: accel+0xc78 = 0x02 (enabled bit 0x2 SET)
NMXAccel:   GATES after deliverModeChange: pipe 0 active(+0x298) = 0, wsaaDefer(+0x282) = 0
```

`0xe00002c7` = `kIOReturnUnsupported`。**根因已定位（符号级证据）**：

| kext | `getPixelInformation` | `getCurrentDisplayMode` | `getAttribute` |
| --- | --- | --- | --- |
| `XeGfxIntelFramebuffer` | **未实现**（继承 `IONDRVFramebuffer`） | **未实现**（继承） | ✅ 自己实现 |
| `NMIntelFB` | ✅ 自己实现 | ✅ 自己实现 | — |

也就是说，`XeGfxIntelFramebuffer` 只是「换了类名的 IONDRV 皮」，scanout 描述全部转发给
`IONDRVFramebuffer` → 需要底层 NDRV 驱动应答；本机 `IGPU` 没有可用 NDRV 实例 →
`getPixelInformation` 返回 `kIOReturnUnsupported` → accel 拿不到 scanout 的 phys/size/pitch。

**→ A-22 的方向已经很清楚：让 `XeGfxIntelFramebuffer` 继承 IONDRV 类名的同时，
自己实现 `getPixelInformation` / `getCurrentDisplayMode`（把 `NMIntelFB` 里那套
adopt-固件模式的读数搬过来）。**这是一次「两条路合并」的改动，不是新的试错：
- 保住 A-21 的成果（类名 + `XeGfxL0Ready` → accel 认头）；
- 补上 A-20 的能力（自己描述 scanout → `0xe00002c7` 消失）。

需要的输入（都在仓库里）：`kexts/NMIntelFB/intelfb.cpp` 的 `getPixelInformation` /
`getCurrentDisplayMode` / `adoptFirmwareMode` 段，搬进 `kexts/XeGfxIntelFB/intelfb.cpp`。

## 9. 对 A-22 的三条建议

1. **不要再动探针分**。`IGPUConsoleRange 65000 > XeGfxIntelFB 20001 > NMIntelFB 5000` 这个序已经验证可用，改它只会引入新变量。
2. **A-22 只做一件事：给 `XeGfxIntelFramebuffer` 加 `getPixelInformation` / `getCurrentDisplayMode`**（从 `NMIntelFB` 搬）。
   判据是 `0xe00002c7` 消失 + `vmmap nvmtl > 0`，**不是** `Metal: Supported`。
3. **`fbgeom` 以后每次开机都该跑**（判据已修）。它的 `mapfast` 是 `results` stage4 唯一的保障，
   别让任何新 kext 的类名再把它误判成"跳过"。
